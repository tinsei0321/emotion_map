### 1.2 问题

|------|------|
| **用例与 bug 脱节** | `emc_test_cases.md` 是手动维护的静态列表，CB 诊断发现的 bug（如 MC→name 断裂、推理螺旋、假结论）未被注入 |

## 三、组件 1：Bug 采集 Skill（`.agents/skills/bug-collector/`）

### 3.1 功能定义

一个 ZCode/Claude Code 可调用的 skill，输入为用户描述的问题/bug，输出为标准化的用例条目。

### 3.2 Skill 工作流

```
用户描述 bug
    │
    ├─ Step 1：标准化语言处理
    │   原始："裁剪又失败了，字段MC找不到"
    │   标准化：→ TC-B06 · extract_feature · 字段名规范化断裂
    │          "用户上传面层（字段MC），LLM选extract_feature(where='MC/eq/西陵区')，
    │           resolve_boundary将MC→name重命名后_apply_attr_filter找不到MC字段"
    │
    ├─ Step 2：分类 + 标签
    │   类型：🐛 Bug / ⚠️ 降智 / 🚀 性能 / 🎨 UI
    │   来源：用户实测 / CB诊断 / 飞轮发现
    │   关联模块：数据识别 / 工具调用 / finalStep / FC诊断
    │   严重度：🔴 CRITICAL / 🟠 HIGH / 🟡 MEDIUM / 🟢 LOW
    │
    ├─ Step 3：生成飞轮用例
    │   问句 / 数据前提 / 预期行为 / 断言条件 / 已知失败模式
    │
    ├─ Step 4：写入用例 Log
    │   tests/buglog/YYYY-MM-DD-{slug}.md
    │
    └─ Step 5：更新飞轮用例目录
        tests/emc_test_cases.md（追加/更新对应条目）
```

### 3.3 SKILL.md 核心指令

```markdown
# Bug Collector Skill

## 触发条件
- 用户说"记录这个bug" / "加入飞轮" / "这个问题反复出现"
- CB 诊断报告产出后自动触发
- 飞轮测试发现新失败时自动触发

## 输入格式
用户提供：
- 问题描述（自然语言）
- 复现步骤（可选）
- 预期行为（可选）

## 输出
1. 标准化用例条目（Markdown）
2. 用例 Log 文件（`tests/buglog/`）
3. 飞轮用例目录更新（`tests/emc_test_cases.md`）

## 标准化规则
- 问句：保留用户原始中文，加注英文关键词
- 数据前提：明确列出需要的图层类型
- 预期行为：用「① ② ③」编号
- 已知失败模式：引用根因分析报告路径
```

### 5.2 UI 设计要求

| 元素 | 设计要点 |
|------|------|
| **色系** | 森绿主题（#2E8B57 通过 / #D97757 失败 / #4796E3 进行中） |
| **趋势图** | 简单折线图（Canvas 或 SVG·纯前端·无依赖） |
| **卡片布局** | 4 个 KPI 卡片 + 趋势图 + 热力图 + 清单，响应式排列 |
| **交互** | 点击条目展开详情（bug log 内容），支持筛选（按类型/模块/状态） |
| **刷新** | 手动刷新按钮 + 自动检测新报告（轮询 `reports/INDEX.md` 的 mtime） |
| **对比** | 选中两次报告 → 并排 diff（哪些用例从 PASS→FAIL，哪些从 FAIL→PASS） |

### 5.3 仪表盘数据源

```
仪表盘 UI
  ├─ 通过率 / 耗时 → 从最新 reports/*.json 读取
  ├─ 趋势图 → 遍历 reports/INDEX.md → 取最近 N 次
  ├─ Bug 统计 → 从 buglog/_index.md 读取
  ├─ 重复问题 → 从 buglog/_trend.md 读取
  └─ 未解决清单 → 从 buglog/open/*.md 读取
```

## 九、我的补充意见

### 意见 1：Bug Log 应该足够轻量，不要成为负担

建议每个 bug 条目控制在 20 行以内（模板中的核心字段）。详细的根因分析仍然放在 `docs/catch-ball/rootcause/`，buglog 只放摘要 + 指针。

### 意见 2：飞轮仪表盘不要过度工程化

第一版只需要 4 个 KPI 卡片 + 最近一次报告摘要 + 未解决清单。趋势图和热力图可以后续迭代。目标是让用户在 `?test=1` 打开后 3 秒内看懂飞轮状态。

### 意见 3：回归用例应自动生成

当 buglog 中某个 bug 标记为"已解决"后，自动提取其标准化用例 → 追加到 `regression.md`。这样确保修过的 bug 不会被飞轮遗漏。

### 意见 4：与 CB 流程的衔接

CB 诊断报告产出后 → skill 自动扫描报告中的失败案例 → 比对 buglog → 如果是新 bug 则自动创建条目，如果是已知 bug 则更新复现计数。
