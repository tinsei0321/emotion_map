## 零、执行摘要与我的总体意见

### 一句话

> **EMC 的架构方向是正确的（v2 FC + 契约 Schema），工具选择准确率 100%，但现实 LLM 延迟远超设计预算、数据识别存在系统性盲区、参数填充是多类问题的共同瓶颈。当前代码可用于演示，但需要一次专项"做对"修复来解决数据识别和参数填充的根因，以及探索减少 LLM 调用次数的路径来降低延迟。**

### 我的总体意见

EMC 经历了 v1→v2→v3→v3.1 的迭代，从三阶段管线到单次 FC 架构的转型是成功的。**工具选择准确率达到 100%**（飞轮测试 12 个执行案例全部选对），这说明"Smart Agent"部分的意图理解能力是达标的。

但三个系统性问题制约了可用性：

1. **"Dumb Tool"不够 Dumb**：数据识别（0LLM）有两个关键盲区——`pickVisiblePointLayer()` 不认识 `colorMode='polarity'` 的点层，`layerMeta.has_point` 看不到 group 容器里的点数据。这导致"数据已在 Layers 中但 EMC 说需要数据"的反复出现。

2. **"Smart Agent"的参数填充靠不住**：工具虽然选对了，但 LLM 经常不填或错填必填参数（center、layer_a/b、boundaries）。这是飞轮测试 60% 失败案例的根因。

3. **延迟是结构性而非偶然的**：设计预算 6-11s 建立在"LLM 调用 2-3s"的假设上，但现实是每次 LLM 调用 4-10s，最少 2 次调用 = 8-20s 基线。这不是代码 bug，是设计假设需要修正。

**我建议优先修复数据识别（Root Cause 1+2，改动小影响大），然后集中解决参数填充问题（系统提示增强+前端预填），最后考虑架构层面的延迟优化（探索 1-LLM-调用模式）。**

## 一、全链路耗时分析

### 1.1 实测数据 vs 设计预算

| 阶段 | 设计预算 | 实测（简单查询） | 实测（复杂查询） | 差距 |
|------|:---:|:---:|:---:|:---:|
| 接地上下文构建 | <100ms | ~50ms | ~50ms | ✅ 达标 |
| FC 诊断（1 次 LLM） | 2.7s | 3-6s | 3-6s | ⚠️ 2x |
| 编排器路由 | <10ms | <5ms | <5ms | ✅ 达标 |
| 工具执行 | 0.1-2s | 0.5-3s | 3-10s | ⚠️ |
| finalStep（1 次 LLM） | 3-5s | 4-10s | 4-10s | ⚠️ 2x |
| while-loop 轮次 | 0 轮 | 0 轮 | 3-6 轮 | 🔴 额外 20-78s |
| 质量防线 | <20ms | <5ms | <5ms | ✅ 达标 |
| **合计** | **6-11s** | **14-25s** | **60-93s** | 🔴 **2-8x** |

### 1.2 60s+ 的三大根因

#### 根因 1（🔴 主因）：While-loop ReAct 路径仍在跑

快速路径（`runTemplatePath`，0 额外 LLM 轮次）需要满足全部条件：
```
!ctx.resume && !diagnose.degraded 
&& diagnose.template 
&& SKILL_DEFS[template].category === 'single' 
&& _tplHitRateReady()
```

**`_tplHitRateReady()` 是最大风险点**：它要求 Flash 的 template 命中率 ≥60%（10 个样本后）。如果 Flash 有 40%+ 的 `template=unknown`，**所有查询都进入 while-loop**，每轮 5-13s，4-6 轮 = 20-78s。

飞轮测试中 60s+ 的三例（FC-04 83s、FC-05 60s、FC-19 93s）几乎确定走了 while-loop。

**验证方法**：检查 `localStorage` 中的 `ai_qa_template_stats_v1`。如果 `unknown` miss 率 >40%，就是这个原因。

#### 根因 2（🔴 结构性）：LLM API 延迟 2x 于设计预算

每次 LLM 调用（FC、finalStep、agentStep）实测 4-10s，设计预算 2-5s。最简路径（2 次 LLM 调用）的 LLM 时间基线 = 8-20s，已经超过整个设计总预算 6-11s。

**这不是代码 bug，是设计假设与现实的差距**。DeepSeek V4 Flash 的 API 响应速度达不到 2-3s 的预算。

#### 根因 3（🟡）：SSE 代理缓冲破坏流式体验

`serve.py:_proxy_api` 使用 `urllib.request.urlopen` + `resp.read()` 缓冲整个 SSE 响应再转发。**不增加总耗时**，但用户看不到渐进式 token 生成，感觉"卡住"直到全部返回。

### 1.3 全链路 timeout 值全景

| 位置 | 值 | 阶段 |
|------|:---:|------|
| `stages.js:298` | **20s** | FC 诊断 HTTP 超时 |
| `api.js:32` | **45s** | 所有 SSE 阶段的单次 LLM 超时 |
| `harness.js:730` | **75s** | 单次查询总预算（超时强制 answer） |
| `harness.js:10-11` | **4-6 轮** | while-loop 轮次上限 |
| `llm.py:58` | **60s** | httpx 底层 HTTP 超时 |
| `llm.py:28` | **3 次** | 每个 provider 重试次数 |
| `serve.py:204` | **120s** | 代理 HTTP 超时 |

**问题**：75s 总预算远远超过设计目标的 6-11s。即使 while-loop 跑到 6 轮 × 10s = 60s，也不会触发超时。应该降低到 ~30s。

## 二、数据识别深度分析

### 2.1 三级识别机制

| 层级 | 实现 | 覆盖字段数 | 何时调用 | 稳定性 |
|------|------|:---:|------|:---:|
| **0LLM（规则）** | `field_dictionary.py` `resolve_role()` | 33 角色 × ~190 variants | 每次 `getFieldCard()` 先调 | ✅ 确定性强 |
| **Flash（LLM 推断）** | `/aiqa/profile_fields` → Flash 模型 | 规则 miss 的字段 | `getFieldCard()` 规则 miss 后调 | ⚠️ 依赖 LLM 可用性 |
| **Pro** | **不参与字段识别** | — | — | — |

### 2.2 "数据已在 Layers 中但 EMC 说需要数据" — 两个根因

#### Root Cause 1（🔴）：`pickVisiblePointLayer()` 不认识 `colorMode='polarity'` 的点层

**位置**：`tools.js:651-670`

该函数只找三类点层：
```javascript
// 1. L2 组聚合（kind=group + children）
// 2. L2 独立点层（colorMode 以 'l2-' 开头）
// 3. L1 点层（colorMode='confidence'）
```

用户上传的点 GeoJSON 默认 `colorMode='polarity'`（`state.js:696`）。这不匹配任何条件 → `pickVisiblePointLayer()` 返回 null → **所有以 `resolvePointLayer()` 为回退的工具都失败** → 提示"需要数据"。

**受影响工具**：zonal_stats、rank、filter_attr、clip、hotspot、nearest、buffer（几乎所有需要点层的工具）。

**修复**：在 `pickVisiblePointLayer()` 中增加一条规则——接受 `colorMode === 'polarity'` 且 kind 为 point 的层。

#### Root Cause 2（🔴）：`layerMeta.has_point` 看不到 group 容器里的点数据

**位置**：`harness.js:750-753`

```javascript
ctx.layerMeta = {
    has_point: _ls.some(l => l.kind === 'point' && ...),  // ← 只检查 kind='point'
    has_polygon: _ls.some(l => l.kind === 'polygon' && ...),
};
```

L2 数据结构：**group 容器**（kind=`'group'`）内嵌 3 个子层（l2-positive/negative/neutral，kind=`'point'`）。`has_point` 检查顶层的 `kind`，group 的 kind 是 `'group'` 不是 `'point'` → `has_point = false`。

这导致 `select_candidates` 的 `_filter_by_context` 过滤掉所有需要点数据的工具（density、hotspot、rank、...）→ 0LLM 候选选择器返回空 → 接地上下文显示无可用工具 → LLM 说"需要数据"。

**修复**：`has_point` 应递归检查 group 子层——如果任何层的 kind 或任何 group 的子层 kind 是 `'point'`，则 `has_point = true`。

### 2.3 字段词典覆盖分析

| 类别 | 覆盖 | 缺口 |
|------|:---:|------|
| 情绪分析字段 | ✅ 完整 | polarity、score、emotion_type、domain、element、topic、issue_label… |
| 空间字段 | ✅ 完整 | lon/lat/lng、geometry、boundary_name/id、land_use_class |
| 治理字段 | ⚠️ 部分 | 有 hotspot、spatial_* 但缺 "投诉量"、"案件数"、"处置率" |
| 规划字段 | ❌ 几乎无 | 缺 "建筑面积"、"容积率"、"建筑密度"、"绿地率"、"用地面积" |
| 人口统计字段 | ❌ 几乎无 | 缺 "人口"、"户数"、"人均面积" |
| 时间字段 | ⚠️ 部分 | 有 timestamp/time_label 但缺 "年份"、"季度"、"月份" |

**总体评价**：词典对"城市情绪"核心领域覆盖良好（~190 variants），但对规划/人口等相邻领域覆盖不足。这些字段会落入 Flash 推断（不稳定），或完全丢失（`role=null`）。

### 2.4 字段识别稳定性风险

1. **LLM 不可用时降级静默**：`getFieldCard()` 的 catch 块（`tools.js:134`）在 Flash 不可用时给字段标 `role: null`，不报错。接地上下文仍然展示字段，但缺少语义角色（`?`），LLM 可能误判字段用途。

2. **`LLM_ROLE_CONFIDENCE_FLOOR = 0.3` 过于保守**：低于 0.3 的推断直接丢弃。Flash 对中文缩略词的推断置信度偏低，可能导致有效字段被丢弃。

3. **无跨文件字段一致性检查**：同一字段名在不同图层中可能被赋予不同 role，无冲突检测。

## 三、工具调用准确性分析

### 3.1 飞轮测试 20 案例拆解

| 指标 | 数值 |
|------|:---:|
| 总通过率 | **75%（15/20）** |
| 工具选择准确率 | **100%（12/12 执行案例）** |
| 参数填充准确率 | **~70%** |
| 输出质量通过率 | **~90%** |

### 3.2 5 个失败案例的根因分类

| 案例 | 模板 | 失败原因 | 类别 |
|------|------|------|------|
| FC-05 区域对比 | compare | LLM 填 `boundary`（单数）+ 1 个值，compare_regions 需要 `boundaries`（复数数组 ≥2） | **参数填充** |
| FC-08 缓冲分析 | buffer | LLM 未填必填参数 `center` → `_missingSlotAsk` 触发 → 无输出 | **参数填充** |
| FC-09 叠置分析 | overlay | LLM 未填必填参数 `layer_a`/`layer_b` → `_missingSlotAsk` 触发 | **参数填充** |
| FC-12 无点数据时拒绝 | density | density 被选中且执行（46s），但预期应拒绝。`layerMeta.has_point` 可能为 true（测试环境有数据） | **数据门禁** |
| FC-16 禁英文术语 | density | 工具正确执行，但 finalStep 输出含英文术语 | **输出质量** |

### 3.3 关键发现

**发现 1：工具选择准确率 100%**。这是 v2 FC 架构最大的成功——LLM 在 12/12 个案例中都选对了工具。问题不在"选什么"，在"怎么填参数"。

**发现 2：参数填充是 #1 失败模式（60% 失败案例）**。LLM 经常不填或错填必填参数。根本原因：
- FC system prompt 的"参数填写指引"覆盖不全
- 必填参数（center、layer_a/b、boundaries）在 contracts 中标记为 required，但 LLM 仍会忽略
- `validate_tool_call()` 只能修正错误值，不能凭空创造缺失的必填数据

**发现 3：契约命名不一致**。`compare_regions` 使用 `boundaries`（复数），其他边界工具使用 `boundary`（单数）。别名系统做了映射但隐藏了复数/≥2 的约束。

**发现 4：FC 路径完全绕过 `select_candidates` 的数据感知过滤**。FC 的 LLM 看到全部 13 个工具（7.4KB schema），不受 0LLM 候选过滤限制。这是有意设计（全注入 > 预过滤），但意味着 LLM 可能在无数据的情况下选择需要数据的工具。

### 3.4 触发词路由（v1 回退路径）

v1 回退路径（`select_template` → 触发词匹配）存在已知问题：
- `'热点'` 同时匹配 density 和 hotspot（列表顺序导致永远路由到 density）
- v1 路径未使用 `candidate_selector` 的扩展触发词（`_B_TRACK_TRIGGER_EXT`）
- 在飞轮测试中，**v1 回退路径未被使用**（FC 路径全部成功）
