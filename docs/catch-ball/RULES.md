## 一、评估原则

### 1.1 第三方中立
- 评估方不为项目方的任何决策背书或辩护
- 不预设结论，一切判断基于扫描证据
- 对项目的优势和问题同等重视，不偏袒

### 1.2 证据驱动
- 每个判断必须附带文件路径引用（尽可能到行号）
- 评分必须有可追溯的具体发现支撑
- 不依赖项目方的自我评价——独立核实
- **trace 取证（CB-12·步骤 0·B3 教训固化）**：
  - 根因分析/失败审查**第一动作 = 拉 trace.log 计数**（`py tools/trace_query.py --stats`）——数 `MOD_AIQA.F_002`（agentStep·while-loop 铁证）/ `F_003`（finalStep）/ `F_005`（FC）·**勿用 `F_001`**（LLM 公共出口·不区分 agentStep/finalStep）
  - 各组跑测试**带 session**（`EMOTION_TRACE_SESSION=<组>-<批次>`）·报告附 `trace_query --stats --session <批号>` 证据
  - 推断只作假设·trace 数据先行·定案须有 trace 计数支撑
  - 用法见 [`docs/trace-log-guide.md`](../trace-log-guide.md)

### 1.3 建设性批评
- 发现问题必须附带可操作的改进建议
- 建议按严重程度和影响面分级
- 讨论点聚焦架构级话题，避免陷入细节争论

### 1.4 双模型闭环（多评估方）
```
SCAN（Codex / glm组 独立评价）→ CB Journal（claude组 反评价 + 行动）
    → 下一轮 SCAN（对比验证改进效果）→ 持续迭代
```
- 每轮 SCAN 首章必须回顾上一轮建议的执行情况
- 对比验证是闭环的核心价值——衡量建议是否落地产生了实际改善
- **多评估方（2026-08-01 起）**：第三方评估可选 Codex（GPT-5）或 glm组（ZCode + GLM 5.2）·独立产出 SCAN·claude组 反评价
- **glm组 定位**：ZCode + GLM 5.2 以**第三方评估者**身份加入（非开发主）·评估、SCAN、讨论、反评价审核·与 Codex 互补视角

## 二、评估方法

### 2.1 七轴评分体系

> v2（2026-07-22）：六轴 → 七轴，新增「演示表现力」（10%）对齐项目"演示逻辑链"北极星（CLAUDE.md 最高优先级），防纯工程标尺盲视 UI/UX 债。原六轴权重各让 1-2% 凑足 100%。

| 轴 | 权重 | 评估内容 |
|----|------|---------|
| **架构设计** | 18% | 分层清晰度、模块边界、接口契约、扩展性、技术选型合理性 |
| **代码质量** | 22% | 可读性、DRY 原则、错误处理、追踪覆盖率、安全实践 |
| **测试覆盖** | 13% | 单元测试数量与质量、E2E 覆盖、边界条件测试、CI 集成 |
| **Harness 工程** | 18% | Agent 体系完善度、Hook/Command 有效性、SOP 风险分级、自动化门禁 |
| **文档完整度** | 9% | PRD/Spec/ADR/开发日志的同步度、准确性、可发现性 |
| **调用效率** | 10% | Agent spawn 次数合理性、Token 消耗、上下文加载效率 |
| **演示表现力** | 10% | 对齐"演示逻辑链"北极星：张力图面（对称拉伸/色带/空间自相关/密度对比）→ 引导点击 → 交互分析（点击→归因）→ 宏观诊断信号（定位关注区+主题倾向+排序优先级）；视野-数据-结论同步性（Overview 互动指挥台）；设计语言一致性（软折叠基调/theme var/自适应位置）。**UI/UX 与视觉表现力 = 与架构/代码同等的承重维度**，勿当"装饰"。 |

> 综合分 = 各轴得分 × 权重 之和（四舍五入到一位小数）

### 2.2 三级扫描深度

| 级别 | 阅读范围 | 适用对象 |
|------|---------|---------|
| **L1（全量阅读）** | 逐行阅读全部代码/配置 | 核心配置（AGENTS.md, CLAUDE.md）、所有 Agent 定义、所有 Hook 脚本、tracker.py、config.py、ai_qa/llm.py、frontend/serve.py |
| **L2（关键函数+结构）** | 阅读函数签名、关键逻辑、文件结构 | 所有 Core 模块、所有 API 路由、AI QA 核心文件、Frontend 主要 JS 模块 |
| **L3（概览+头部）** | 阅读文件头部 docstring、类/函数清单、文件大小 | SCRIPT 分析脚本、测试文件、文档文件、Scrapy 爬虫 |

### 2.3 九维评估子维度

1. **Vibe Coding 策略**：AI 辅助开发体系（Agent 协作、SOP、铁律）的合理性与有效性
2. **Harness 框架**：Hook/Command/自动化门禁的设计质量与覆盖度
3. **Agent 体系**：角色定义质量、协作协议、可发现性
4. **Skills 体系**：技能库的精选质量、落地率、触发规则
5. **架构设计**：分层合理性、模块边界、技术债
6. **代码质量**：逐模块评级（A/B/C）+ 跨模块共性问题
7. **推进情况**：各子系统完成度估算 + 最新进展
8. **调用消耗**：Agent spawn 频次、Token 消耗分析
9. **演示表现力**：UI/UX 与视觉表现力——对齐演示逻辑链三环（表现力/有用性/交互）+ 视野-数据-结论同步性；软折叠基调、theme var、自适应位置的落地度（对应 §2.1 第七轴「演示表现力」）

## 三、Catch-Ball 环节定义

### 3.1 环节流程图

```
CB-N 轮开始
    │
    ├── ① SCAN（第三方）
    │   ├── 回顾 CB-(N-1) 建议执行情况
    │   ├── 全面扫描项目当前状态
    │   ├── 六轴评分 + 趋势对比
    │   ├── 提出分级优化建议
    │   └── 输出 scan/{NN}-{model}.md
    │
    ├── ② Journal（项目方反评价）
    │   ├── 逐条评估 SCAN 建议（agree / disagree / partial）
    │   ├── 附证据和论据
    │   ├── 列出执行行动
    │   └── 追加 cb-journal.md 对应轮次章节
    │
    ├── ③ Retired（退役留痕）
    │   ├── CB 驱动的文件退役记录
    │   ├── 退役原因 + 零引用核验
    │   └── 追加 retired.md
    │
    └── ④ 下一轮 SCAN → 回到 ①
```

### 3.2 反评价标尺（项目方使用，第三方审核参考）

| 标签 | 含义 | 要求 |
|------|------|------|
| **agree** | 完全接受，证据充分 | 已执行或列入计划 |
| **disagree** | 拒绝 | 必须附带反驳证据（用错标尺 / 事实错误 / 撞承重红线） |
| **partial** | 方向对，细节偏 | 说明哪些部分采纳、哪些调整 |

### 3.3 承重红线（不可协商）

> **权威源 = [KNOWLEDGE.md](KNOWLEDGE.md) §1 承重红线清单**（单一权威，含来源标注，CB-03 建议1）。以下为摘要，详见 KNOWLEDGE §1。

以下项目方声明的红线，SCAN 建议不得触碰：
- 决策追踪系统编号连续性（铁律 10）
- diagnose prompt 永不动（保 Flash eval）
- 四态出口契约（success/gap/partial/answered）
- L0 走购买途径策略（不把 sim 数据当风险）

## 四、文档编号规范

> **CB 统一入口**：`docs/catch-ball/_cb-index.md` — 所有环境启动时先读此文件。

### 4.1 SCAN 文档
```
docs/catch-ball/scan/CB{NN}-{topic}_{env}-{model}_{YYYY-MM-DD}.md
```
- 所有 SCAN 类评估报告统一放入 `docs/catch-ball/scan/` 子文件夹
- 命名格式：`CB{NN}-{主题}_{环境}-{模型}_{日期}.md`
- 示例：`CB09-v1.0实测诊断_ZCode-DeepSeek_2026-07-28.md`
- `{NN}` 为两位 CB 轮次号
- `{topic}` 为简短中文主题描述
- `{env}` 为评估环境（ZCode / VSCode）
- `{model}` 为评估模型（DeepSeek / GLM / K3 / Gemini 等）
- **glm组 命名**：`CB{NN}-{topic}_glm组_{YYYY-MM-DD}.md`（如 `CB11-主通道验证_glm组_2026-08-02.md`）·评估方标注 `ZCode + GLM 5.2`
- CPD 专轨评估放入 `docs/catch-ball/scan/cpd/`

### 4.2 根因分析文档
```
docs/catch-ball/rootcause/{YYYY-MM-DD}-{slug}.md
```

### 4.3 综合审计文档
```
docs/catch-ball/audit/{YYYY-MM-DD}-{slug}.md
```

### 4.4 Catch-Ball Journal
```
docs/catch-ball/cb-journal.md
```
- 单文件，按轮**倒序**（最新在顶）
- 内部章节命名：`## CB-01`、`## CB-02` …

### 4.5 退役台账
```

```

```
docs/catch-ball/_handoff/HOME.md
```

## 五、CB 权限约束

### 5.1 可执行操作
| 操作 | 范围 | 说明 |
|------|------|------|
| ✅ 新建文件 | 仅限 `docs/catch-ball/` | RULES.md, SCAN 文档, cb-journal.md, retired.md |

### 5.1.1 评估意见落文件义务（2026-08-13 起·强制）
- **每次讨论/评估的意见必须落盘为 .md 文件**（`docs/catch-ball/discuss/` 或 `docs/catch-ball/scan/`），**禁止只回聊天文字**——不落文件 = 无法交流（claude组 靠读盘获取评估意见）
- 命名：`CB{NN}-{主题}_评估_{组名}-{YYYY-MM-DD}.md`（讨论类）·`CB{NN}-{主题}_scan_{env}-{model}_{YYYY-MM-DD}.md`（SCAN 类）
- 落文件 ≠ git 操作：评估方只写磁盘文件，commit 仍由 claude组 唯一执行

### 5.1.2 Excel 制作分工（2026-08-13 起·用户定）
- **PPT 表格 Excel 任务一律由 Codex 组负责**（claude组 三版对比后用户选定 Codex 版为正式版）
- 落盘位置（权限例外·仅此一文件）：`DATA/analysis/图数表出图_PPT表格汇总.xlsx`——**每个 sheet 对应一个 page**（sheet 名 = pageN）·page 下各表纵向排列、表间空 2 行
- 排版要求：简单、专业——表头加粗 + 细边框 + 列宽自适应 + 同值列合并单元格；**禁止颜色填充**
- 范围：只做 PPT 要用到的数据表（图数据源/文件索引等工作用表不做）
- claude组 职责：page md 完成后通知 Codex 补对应 sheet；Codex 落盘后 claude组 验收并 commit

## 六、工作要点

1. **优先使用 Explore Agent**：大规模扫描使用 Explore Agent 并行刺探，主线程负责汇总和报告编写
2. **引用格式**：文件引用使用 `` `path:line` `` 格式（如 `core/tracker.py:142`）
3. **评分一致性**：同一轴在不同轮次间保持评分标尺一致，变化必须有明确理由
4. **趋势判断**：↑（改善 ≥0.5 分）、→（持平 ±0.4 分内）、↓（退步 ≥0.5 分）
5. **建议可验证**：每条建议尽可能提供验证方法（如"运行 `pytest tests/ -q` 确认全绿"）
6. **报告语言**：中文为主，代码/路径/技术术语保留英文
