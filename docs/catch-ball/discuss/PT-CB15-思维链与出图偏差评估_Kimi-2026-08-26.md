## 一 白话摘要（零术语）

**一句话：你的新司机（Codex）是个通用老司机，车（EMC 的数据和工具）没问题，但没人给他做入职培训——他不知道咱们单位的办事流程，所以每办一件事都先翻一遍员工手册，还要按自己在外企养成的习惯（先查资料再动手）来，自然又慢又绕。**

用办事大厅打比方：

- **你以为的流程**（也是 dsh 老公务员的流程）：窗口问清意图 → 拿起对应的表格（工具）→ 填参数 → 盖章出图。三步，60 秒。
- **新司机的实际流程**：先问「你们单位有哪些表格」→ 翻员工手册确认办事口径 → 顺手多做了一个你没要的统计（区级总数，用来验算）→ 发现社区名单里没有「哪个社区属于西陵区」这一栏，只好挨个看门牌号猜归属 → 再翻出图规范手册 → 习惯性地想跑个命令行脚本，被保安拦下（只读沙箱）→ 最后才盖章。**八到九步，226 秒**。
- **为什么会这样**：dsh 老公务员是咱们自己培训出来的，办事流程背在脑子里；Codex 是外面请来的通用人才，能力很强，但**我们只给了他 18 件工具的说明书，没有给他「办事方法论」**。他脑子里装的是原厂（OpenAI）的通用工作习惯——先侦察环境、读文档、验证、再行动。这不是 bug，是「缺入职培训」。
- **图为什么画错**：你要求「西陵区 Top3」，但出图工具本身没有「只画前 3 名」「只画西陵区」这样的开关——画什么完全取决于上游传给他什么数据。他排了前 20 名就整个传过去了，「3」这个数字全凭他自觉，而他恰好没自觉。这是**契约缺口**，dsh 时代靠老公的自觉背下来了，新司机没有这份自觉。
- **EMC 到底行不行**：行。数据对（4416 条总数与各社区数交叉吻合）、工具对、最终文字答案对。病在「通用大脑」与「专用资产」之间的适配层，不在资产本身。这病有药方，且主药方（入职培训文件）成本很低——详见第五节。

## 二 直接回答：EMC 的 Harness 是不是 Codex 原版？契约加在了哪一层？

### 2.1 结论

**EMC 当前的 codex 引擎 = Codex 原版 app-server 的 agent loop（harness）零改动**。你的理解「EMC 在 Codex 的 Harness 上加了定制契约」**对一半**：契约加了，但加在了「供给侧」（工具/知识/渲染规则），**没有加在「思考侧」（harness 的系统提示与编排策略）**。

### 2.2 证据链

| 层 | 现状 | 证据 |
|---|---|---|
| 编排权 | **完全在 Codex 引擎侧**。EMC 壳（前端适配器+桥）是翻译层，不做任何编排 | `frontend/js/ai_qa/brain-adapter-codex.js:7`「编排权：引擎层（Codex agent loop）——本适配器是翻译层非编排层」 |
| 系统提示 | **原版通用编码 agent 提示**。桥在 initialize 握手时只传 clientInfo（名称/版本），无 instructions 字段，无任何 EMC 定制提示 | `core/codex_bridge.py:327-328` |
| 领域知识注入 | **刻意为零**。cwd 用仓外隔离目录 `_codex_cwd`，明确「防本仓 AGENTS.md（9-Agent 协作规范）注入 Codex 上下文」 | `core/codex_bridge.py:53-56`、`6` |
| Codex 能看到的 EMC | 只有三样：①18 件 MCP 工具的 description ②RAG 知识库（要它自己想起去查）③每次对话的用户输入 | `core/codex_bridge.py:143-148`（config 内 emc MCP 注册） |
| 行为约束 | sandbox=read-only + approvalPolicy=never（本能的 shell 探索被制度封堵） | `core/codex_bridge.py:331、358` |
| 推理档位 | model_reasoning_effort=high（转正批锁定·每轮工具调用前做长推理） | `core/codex_bridge.py:140` |

### 2.3 harness 是怎么「影响思维」的（机制讲解）

Harness（agent loop）对 LLM 思考的影响来自三个输入：

1. **系统提示（人格与方法论）**——告诉模型「你是谁、按什么套路办事」。Codex 原版的提示是通用编程助手套路：**探索环境 → 读文档 → 形成计划 → 执行 → 验证**。这就是你看到的「先查清单→再查口径文档→再看渲染契约」的来源——对通用 agent 这是严谨，对你的「意图→工具→出图」预期这是绕路。
2. **工具清单及 description（能力边界）**——模型选工具的唯一依据是每件工具的说明文字。我们的 description 写得像「参考手册」（参数+限制+纪律），没写「什么任务按什么顺序连用」——dsh 时代这些顺序知识内置在 dsh 自己的提示里。
3. **运行约束（沙箱/审批）**——read-only 沙箱把 Codex 的本能路径（跑命令行脚本做数据裁剪）封死，它撞上「命令行不可用」后才绕回工具路径，白耗一轮。

**dsh 与 codex 在架构位置上其实同构**——都是「引擎层编排 + EMC 工具插座」（brain-adapter-dsh.js:9 同样写「编排权：引擎层（dsh 自主 agent loop）」）。差别不在架构，在 **dsh 的 loop 是我们长期定制深耕的**（领域知识、任务方法论、口径默契全内置在它的提示与配置里），而 Codex 的 loop 是原厂通用的，领域注入目前为零。你以为的「dsh 走 toolbox 选工具路径」其实是 dsh 把这套路径内化成了自己的本能。

## 四 出图偏差（Top20 而非西陵 Top3）根因

三重叠加，逐层归因：

1. **契约缺口（根因·结构性）**：render_spec 参数面没有 top_n / filter / 行政区范围（mcp_server_emc.py:1732-1736）——画什么=上游传什么。「用户字面约束（Top3/西陵区/橙色）→出图参数」的传导**没有任何结构化保障，全靠 LLM 自觉**。这就是你说的「老问题」的统一根因：dsh 时代靠 dsh 的自觉（内置契约），Codex 没有这份自觉。正确路径其实存在（zonal_stats top_n=3 + layer_output=True → render_dataset_id 直传·mcp_server_emc.py:768），但 Codex 走了 top_n=20 全量出图。
2. **口径纪律未遵守**：zonal_stats description 明写「12345 社区级默认边界=base_community_area（193）；130/174 亦可合法时属口径分叉——**先请示再跑**」（mcp_server_emc.py:770）。Codex 用了 130 层且未请示——「请示」是交互动作，approvalPolicy=never + 通用 agent 的自主倾向让它直接干了。**纪律写在了工具手册里，但没写进它的脑子（系统提示）**。
3. **行政区过滤无表达**：「西陵区范围内」在工具面没有参数出口（zonal_stats/rank 的 boundary 都是整层引用），Codex 只能用 POI 猜归属——既慢又不可靠，且最终图的范围（130 混合层 Top20）直接暴露了「裁剪」这一步没有真正发生。

## 六 诚实评估：「EMC 到底行不行」

1. **资产层：行。** 本题数据全对（区级 4416=三社区 3088+其余·占比 69.9% 自洽）、工具链全通（18 件实测全确认）、文字答案正确（三社区与数值交叉吻合）。病灶不在资产。
2. **链路层：通而未顺。** spike 证明了「能开」（四问全通），本次暴露的是「开得不顺」——通用 harness 与专用资产之间的**领域适配层缺失**。这是 Codex 上岗两天的状态，dsh 的「顺手」是多个迭代深耕出来的，横向比不公平；纵向看，S1（playbook 注入）正是把 dsh 那份默契显性化、资产化的动作——做完后这份默契将**不再绑定任何一个引擎**，这本身就是对 PT-CB7 双机复刻痛点的根治。
3. **风险诚实面**：若 S1-S4 做完后 codex 链路在同任务对拍（S5）中仍系统性劣于 dsh，则说明「通用 harness+外部适配」的路径成本高于「定制 harness」，届时应回炉重估路线——建议以 S5 对拍数据作为终裁依据，而不是现在的体感。
4. **我的立场**：支持按 S1→S2/S3→S4→S5 顺序推进。S1 成本极低（一份文档）杠杆最大，建议立即做；S5 对拍是路线存废的判据，必须做。
