## 二、前端降级链路取证

### 2.1 链路（本机实证成立）

```
挂起（无数据返回）
  → api.js:34-36 45s abort（phase=answer）
  → fetch/reader.read() reject（浏览器规范·本机 43s 实测证明确实 reject——route 桩下 abort 后 catch 命中）

  → onFinalDone → 43s 收尾（实测）
```

### 2.2 用户「无降级」的两个合理解释（按概率）

1. **用户标签页运行旧 JS（最简·最高概率）**：ES module 在页面加载时一次性拉取·此后**常驻页面内存**——serve 重启/文件更新不会刷新已打开页面。三次修复（CB-22g/22h/22i 前）全在服务端文件侧——若用户 tab 从未 Ctrl+F5，三次修复全部落空 = 「没有任何变化」的完美解释。本机实测 serve 返回的 JS 与磁盘仅差 `?v=mtime` 参数（cache-bust 正常）——**刷新即新 JS·不刷新则永远是旧 JS**。
2. **后端 zombie 线程排队**：用户 18:09 请求挂死后（deadline 洞见 2.3）线程不释放——Starlette threadpool 被逐步占满后，**新请求（含 45s 降级后的重试）排队等待** → 用户看到「转圈更久」。当前 uvicorn 线程数 74（18:08 启动·仅 1 个用户会话）已偏高。

### 2.3 新发现：deadline 洞（MOD_LLM.D_004 不触发）

- 代码：llm.py:367-371
  ```
  for chunk in cli.chat(messages, **chat_kwargs):
      if time.monotonic() > _total_deadline:
          raise LLMError('LLM 流式总超时...')   # ← 检查在循环体内
      started = True
      yield chunk
  ```
  **检查只覆盖「两 chunk 之间」**——若首个 chunk 永不到达（阻塞在 httpx read·office 网络半开），循环体不执行→deadline 永不触发。
- 实证：运行中 uvicorn（pyc 已确认含 `_total_deadline`/`D_004` 代码）对用户 18:09:19 的请求**已挂 15+ 分钟·全日志 MOD_LLM.D_004 仅 4 次（CB-22h 单测产生·非真实会话）**；且 httpx 分段 read 超时（60s）也未触发——与 CB-22h 判断一致（网络半开/慢 trickle 可绕过 per-read 超时）。
- 后果：后端线程永久占用 → threadpool 累积 → 后续请求排队；前端 45s 降级虽能收尾 UI·但后端资源持续泄漏。

## 三、逐焦点

### 焦点 1：为什么 Playwright 通过但用户仍卡 — **代码侧通过已复现·差异在用户客户端 + 后端资源**

- 本机复现：正常 15s / 挂起 43s 降级（见一）——与 claude 一致。
- 差异解释（按概率）：① **用户 tab 未刷新**（旧 JS 常驻内存·三次修复全落空的最简解释）② 后端 zombie 线程排队（deadline 洞·新 JS 用户也可能被拖慢）③ 网络间歇（本机当前健康·触发条件真实存在但非「无降级」的充分解释——新 JS 下 45s 必降级）。

### 焦点 2：真实网络挂起时前端降级链路 — **链路正确·edge case 仅剩「旧 JS」**

- 45s abort → reject → catch → 降级：本机 route 桩实测 43s 走通（见 2.1）——浏览器规范行为与后端「是否返回」无关（abort 强制 reject 当前 read）。
- 真实场景与桩测差异：桩测请求未达后端；真实场景后端线程挂死。但**前端降级不依赖后端**（abort 是浏览器侧强制）——只要页面跑的是含 catch 的新 JS·45s 必降级。
- edge case = 旧 JS（无 `_composeKnowledgeDegraded` catch）→ 异常冒泡 panel → `[请求失败]` 或 UI 不收尾。

### 焦点 3：首问 vs 追问 — **trace 五次全首问·用户「追问」描述与 trace 不符**

- sess-19092/21952/17256 全部是 `rag_search → finalStep → LLM`（**quick-rag 路径·无 F_019**）——首问 finalStep 就挂·未到追问。
- 用户说「追问」但 trace 是首问——两种可能：用户把「首问就失败」口头概括为「追问不工作」；或用户此前首问成功过·本次会话首问才挂（trace 只覆盖失败会话）。**generate_point_layer/FC 路径无证据（用户没到那一步）**——本轮不修该路径。
- 建议：复现时让用户用「宜昌有哪些城市更新项目？」（精确命中 quick-rag·复现 18:09 路径）并记录首问/追问各自结果。

### 焦点 4：浏览器 JS 缓存 — **serve 侧正常·嫌疑在「打开的标签页」**

- 本机实测：serve 返回 harness.js = 磁盘 JS + `?v=mtime`（逐字节 diff 仅差 `import ... stages.js?v=1786351160`）·Cache-Control=no-store, no-cache——**刷新即新 JS**。
- 但 ES module **页面加载时一次性拉取·常驻内存**——serve 重启不刷新已开页面；`--open=both` 自动开的新 tab 才是新 JS。
- 结论：用户若一直用旧 tab（或 serve 自动开的 tab 被覆盖），三次修复永远不生效。**请用户强刷（Ctrl+Shift+R）或完全关闭重开标签页后复测。**

### 焦点 5：DeepSeek 流式挂起根治 — **D_004 有洞·须覆盖首 chunk 等待**

- 现有 deadline（llm.py:348-369）只检查循环体内（两 chunk 间）——首 chunk 等待未覆盖（见 2.3 实证）。
- 修复：deadline 检查移到**每次 `next()` 之前**仍不够（`next()` 阻塞时无法检查）——需要**线程级总超时**：
  - 方案 A（推荐·uvicorn 异步环境优雅）：LLM 调用改 `httpx.AsyncClient` + `asyncio.wait_for`（总 deadline 硬切）——改动较大（chat/chat_with_tools 同步生成器→异步）。
  - 方案 B（过渡·改动小）：`concurrent.futures.ThreadPoolExecutor` 跑生成器迭代·`future.result(timeout=ttl)` 超时抛 LLMError（线程弃置·请求可完成 + SSE error + 前端降级；泄漏 1 线程/挂起·可接受）。
  - 两者都补 D_004 触发点（已有 trace_error）+ 单测（fake provider 永不 yield → ≤ttl 抛错）。
- 前端 abort 降级渲染：本机 43s 实证正常——无需改。
