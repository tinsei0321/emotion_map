## 一、逐焦点回应

### 焦点 1：embedding 选型 — **disagree 前提（方案 A 概念混淆 + 阻塞未破禁选型）**

**方案**：A 火山 multimodal / B 智谱 / C 本地·推荐先验证 A/B + C 兜底。

**glm组 判断：disagree 前提——① 方案 A 概念混淆 ② 阻塞未破·"选型"为时过早。**

**① 方案 A 概念混淆（关键技术纠正）**：
- 方案称"火山 multimodal embedding·可向量化多模态（图表/GIS）"。
- glm组 核实 volcengine-vision skill（SKILL.md:28-42）：**火山 multimodal embedding 是图片→2048 维向量**（图文匹配/以图搜图）·**非文本 embedding**。
- RAG 需要的是**文本→向量**（笔记/段落/事实卡向量化）——**方案 A 混淆了"多模态 embedding（图片）"与"文本 embedding"**。
- 即方案 A 对 RAG 文本向量化**不可用**（除非火山另有文本 embedding endpoint·需验证）。

**② 阻塞未破·"选型"为时过早**：
- .env 无 embedding key（智谱未配/火山 ARK_EMBED 未配）·方案 A/B/C 全"需验证"。
- 在验证前"选型"= 纸上谈兵——正确做法是**先跑通一个 embedding（任何可用方案）·再谈选型**。

**glm组 建议（Phase 0 验证顺序·对齐 MCP 智谱优先策略）**：

| 验证顺序 | 方案 | 验证内容 | 预期 |
|---|---|---|---|
| **0.1** | **智谱 embedding-3**（文本） | 配 ZHIPUAI_API_KEY + 调 embedding-3 endpoint | 智谱优先·最可能可用 |
| **0.2** | **本地 BGE/sentence-transformers**（文本） | pip install + 跑中文模型（如 bge-small-zh） | 离线兜底·Python 3.14 wheel 需实测 |
| 0.3 | 火山 Ark 文本 embedding（非 multimodal） | 查火山有无文本 embedding endpoint | 若有可备选 |

**禁方案 A 原型**（multimodal 是图片·非文本）——除非 RAG 要向量化**图纸 JPG**（那是另一回事·后置）。

### 焦点 2：向量库 — **partial（chroma 合理·但 Python 3.14 兼容性须先验证）**

**方案**：chroma（本地持久化·可维护）。

**glm组 判断：partial——chroma 方向对·但 Python 3.14 wheel 兼容性是未验证风险（CB-14 已指）。**

**CB-14 风险重现**：
- CB-14（:62）"Python 3.14.5·chromadb/faiss wheel 兼容性存疑（Py3.14 太新·2025 末发布）"。
- CB-22c 方案未提及此风险·默认 chroma 可用——**需 Phase 0 实测**。

**glm组 建议（向量库 Phase 0 验证）**：
```bash
# Phase 0 必跑（embedding 验证时同步）
pip install chromadb  # Py3.14 wheel 是否存在？
# 若失败 → 降级 sqlite-vss（轻量·SQLITE 原生扩展）
# 若都失败 → 内存 + JSON 持久化（小规模 L0 数百文件够用）
```

**chroma vs sqlite-vss 选型（Phase 0 通过后）**：
| 维度 | chroma | sqlite-vss |
|---|---|---|
| 依赖 | 独立（含 sqlite） | sqlite 扩展 |
| Python 3.14 wheel | **存疑**（需实测） | 较可能（sqlite 原生） |
| 规模 | 中大 | 中小（L0 数百文件够） |
| 可维护 | 增量 API 好 | SQL 操作 |

**glm组 倾向**：**sqlite-vss**（Python 3.14 兼容性更稳 + L0 数百文件规模够 + sqlite 原生轻量）——但须 Phase 0 实测 chroma wheel 先（若可用则 chroma 优先·API 更友好）。

### 焦点 3：向量化颗粒度 — **agree（分层合理·补"字段级"建议）**

**方案**：L0 笔记 + L1.5 事实卡 + 案例 → 向量·L1 industry_kb 不向量（已注入）。

**glm组 判断：agree——分层合理·L1 不向量正确（已注入 prompt·防冗余）。**

**分层核实**：
- L0 笔记（docs/urban-renewal-plan/）→ 段落级向量 ✅
- L1.5 事实卡（CB-22b PROJECTS/INDICATORS）→ 条目级向量 ✅
- outlet_kb 案例（case_library）→ point 向量 ✅
- L1 industry_kb → 不向量（已 industry_kb_text 注入）✅ 正确

**glm组 补充建议（颗粒度分层 + 字段级）**：

| 颗粒度 | 对象 | 用途 | 示例 |
|---|---|---|---|
| **文档级** | L0 整篇笔记 | 宏观主题检索 | "南湖公园概念方案" |
| **段落级** | L0 笔记分节 | 细节检索 | "南湖停车缺口 1072" |
| **条目级** | L1.5 事实卡 | 精确数据检索 | "葛洲坝 12 个项目" |
| **字段级**（glm 补） | 事实卡 detail 字段 | 数值精确匹配 | "51.33 亿" |

- 字段级：事实卡 detail 是结构化数值（"55 个·51.33 亿"）——精确查询走 CB-22b query_knowledge_base（确定性 WHERE）·**不走 RAG**（RAG 是模糊语义·数值精确用确定性）。
- 即：**RAG 只管语义模糊的段落/案例·事实卡数值走确定性**——对齐 B 路径分工。

### 焦点 4：rag_search vs query_knowledge_base 边界 — **agree（互补·与 glm CB-22b/B 路径一致）**

**方案**：简单查询（city+topic）走 query_knowledge_base·复杂语义走 rag_search。

**glm组 判断：agree——与 glm CB-22b 分级查询建议一致·边界清晰。**

**边界矩阵（glm 确认 + 细化）**：

| 维度 | query_knowledge_base（CB-22b·确定性） | rag_search（CB-22c·向量） |
|---|---|---|
| 查询类型 | city+topic+keyword 精确 | 自然语言语义模糊 |
| 数据源 | L1.5 事实卡（结构化） | L0 笔记 + 案例全文（段落向量） |
| 返回 | Top-N 条目（id/name/detail/source） | Top-K 片段（文本 + 来源） |
| 示例问 | "宜昌有哪些更新项目" | "哪些项目适合这个片区的更新需求" |
| 手段 | WHERE 过滤（确定性） | embedding 相似度（概率） |

**glm组 分工确认**：
- **B 路径 query_knowledge_base**：确定性·CB-22b 先行（不依赖 embedding）。
- **RAG rag_search**：向量·CB-22c 后置（依赖 embedding·Phase 0 阻塞）。
- **执行顺序**：CB-22b 先（不阻塞）·CB-22c 待 Phase 0（embedding 验证）通过。

**禁 rag_search 替代 query_knowledge_base**——数值精确查询用 RAG 是杀鸡用牛刀（+ 概率误命中 + 延迟）。glm CB-22b 已强调·此处重申。

### 焦点 5：后期维护（增量重向量化） — **partial（方案对·但未提"漂移守卫"与 CB-22b 联动）**

**方案**：更新知识库 → 增量重向量化（只重嵌变更文件）。

**glm组 判断：partial——增量方向对·但须与 CB-22b validate_kb_drift 联动 + 哈希指纹。**

**glm组 建议（增量重向量化 + 指纹）**：

```python
# 向量化时记录哈希指纹
{'id': 'URP-P01', 'source': '...', 'content': '...', 'embed_hash': 'sha256(content)'}
# 重向量化时
for doc in L0_docs:
    h = sha256(doc.content)
    if doc.embed_hash != h:  # 仅重嵌变更
        re_embed(doc)
```

**与 CB-22b validate_kb_drift 联动**：
- CB-22b 的 validate_kb_drift（source 指针校验）+ CB-22c 的 embed_hash（内容指纹）= **双重漂移守卫**。
- L0 更新时：validate_kb_drift 检 source 指针 + embed_hash 检内容变更 → 触发增量重向量化。
- **glm组 建议**：两个守卫合并到一个 CI（validate_kb_consistency.py）—— source + content + embed 三层校验。
