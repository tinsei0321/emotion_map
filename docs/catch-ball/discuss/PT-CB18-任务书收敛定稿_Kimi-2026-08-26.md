## 二、v1.0 变更明细（Qoder 可直接照此执行）

- **W1-1**：①`_board.yaml` 增决策区，结构=编号/事项/候选/状态，收敛者每批维护；②骨架首行=生成时间+HEAD 短哈希；③交接段八字段、里程碑级才写；④验收改 `check_state.py` 或 pytest 断言「重生成 diff=0 且分支/最近提交与 git 输出一致」（照抄 progress 契约门禁先例）。
- **W1-2**：①下沉白名单（沟通纪律/白话摘要硬条款/学习报告必回应/双环境同步，禁下沉留根）；②去重清单四列=原分布文件/删后唯一落点/哪些 harness 读该落点/grep 校验命令，清单随交付落盘；③验收并入判据 A-D（信息未丢 grep 零命中/四条纪律关键词校验/全新会话问答纪律+当前分支答对/重生成 diff=0+门禁全绿）；④工时 0.5→0.75~1 天。
- **W1-3**：验收改「覆盖率≥80% + 未配对裸编号清单落盘」（部分标题本身裸编号需回读文内首段）；工时 0.25→0.5 天。
- **W2-1**：下一批起严格试用（回应§小节追加同文件），本批不计样本。
- **W2-2 / W2-3**：判据分别改「成文+下批首批派发验证」「模板定稿后首次派发逐字段核对」。
- **W3**：顺序=W3-2→W3-5→余件；W3-5 加门禁信号不失真条；W3-3 上限按双阈值改写。
- **验证法**：主判据=②文档份数行数+④token 读数，「≥2 项改善 30%」只在硬数据上判。
- **文本**：全文「七字段」→八字段、「12 条建议」→11 条。
- **总工期**：2.75~3.25 天（W1-1 1~1.25 / W1-2 0.75~1 / W1-3 0.5 / W2 0.5）。

## 三、对 Zcode 的评估（任务书 v0.2 质量）

**定性：方向正确、细节未校的草案——骨架一次成型，但自家纪律在自家文件上打了折。**

- [OK] 亮点：①流转链与边界/红线章节齐备，「防过度精简红线」有自觉；②知乎文章映射表逐条可核，吸收方式标注（升级/新增/校准）是规范动作；③六个裁决点配白话表，拍板界面友好；④风险章自带「改造者悖论」，预判了 Qoder 的角色冲突。
- [WARN] 扣分：①**数据源核查缺位**——「待拍板项」无现成结构化源未自查，属任务书级硬伤，靠执行方审计才兜底；②**数字口径失准两处**（八字段写七字段、11 条写 12 条）——瘦身批自身数字失准，恰是本批要治的病，讽刺且不该；③**六处虚验收**——任务书要求别人「验收可判真伪」，自身六条验收靠人眼或本批窗口内不可判；④工时偏乐观约 20%。
- 一句话：派发质量在平均线以上，但「验收可判真伪」这条规矩以后派发前需自查一遍——本批六个虚验收全在执行方手里才暴露。
