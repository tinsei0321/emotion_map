## 一、焦点 5 定案：3D 热力形式 —— **选 a（MapLibre setTerrain + RGB DEM）**

### 1.1 三方案判定与选择

| 方案 | 连续曲面真实性 | 编码/实现成本 | 与现有栈冲突风险 | 演示张力 | glm组 判定 |
|---|---|---|---|---|---|
| **a. setTerrain + RGB DEM** | ✅ 真曲面（MapLibre 三角网）| M（后端 DEM 编码 + 前端 terrain 接线）| **中**（全局地形 draping，见 1.3）| ✅ 最强（exaggeration 可调）| **选** |
| b. deck.gl TerrainLayer | ✅ 真曲面 | M（deck.gl 依赖 + 混栈）| **高**（已踩坑）| ✅ 强 | ❌ 不选 |
| c. fill-extrusion 改造 | ⚠️ 阶梯近似（非真曲面）| S | 低 | ⚠️ 改善有限 | ❌ 不选 |
| d. THREE/customLayer | ✅ 真曲面 | L | 高（自研）| ✅ | ❌（不在候选）|

### 1.2 选 a 的理由（逐点论证）

**① 连续曲面真实性 = a/b 同级，c 是伪曲面。**

claude组 5.2 的"千层饼"根因诊断我**独立确认成立**。实查渲染代码：

```
// map.js:636（当前 terrain 3D 渲染）
'fill-extrusion-height': ['interpolate', ['linear'], ['get', heightField], 0, 0, 1, maxHeight]
```

`heightField` = `_level`（terrain，`map.js:617`）。关键在 MapLibre `fill-extrusion` 的语义：**表达式按 feature 的属性取值，每个 feature 只有一个恒定高度**。等值线环（`spatial_analysis.py:959-969` contourpy 逐 level 提环）的每个 Polygon 的 `_level` 是该环的归一化级（`spatial_analysis.py:948-951` Lmin/Lmax 归一），是**常量**。所以 interpolate 的 `[0,0]` 与 `[1,maxHeight]` 两 stop 之间，对单个 feature 而言只取一个点——**feature 内部无高度梯度**。7 层 levels（`spatial_analysis.py:944` quantile 0.25~0.97）= 7 级固定高度的梯田。这就是用户看到的"看不出起伏地势感"的**技术根因，实锤**。

c 方案（fill-extrusion 改造）用更细的网格片代替等值线环，本质是把"7 级梯田"变成"N 级梯田"——只要还是 fill-extrusion，就逃不开"逐 feature 固定高度"。要做到视觉连续，网格片要极细（≤ cell_m 60m 的栅格级），此时 feature 数爆炸（一个主城 KDE 栅格 `nx×ny` 轻松上千片），fill-extrusion 渲染性能急剧下降，且**仍是阶梯近似**。所以 c 是"用性能换只是稍微好一点的阶梯"，不解决根本问题。

只有 a/b 的三角网地形才是数学意义上的连续曲面。

**② b（deck.gl）已被本仓实测证伪——这是 claude组 没有充分强调的硬证据。**

实查 `map.js:791-794`：
```
// ── deck.gl grid 渲染已弃用（回 MapLibre fill-extrusion：addPolygonPaint grid 分支）──
// 放弃原因：deck.gl GridLayer extruded（方柱）在 MapLibre+MapboxOverlay 不渲染；
//           ColumnLayer 效果不及 kepler 理想 → 用户决定回自创 fill-extrusion
```

这是**已发生过的踩坑**：deck.gl 的 3D 几何层（extruded）在 MapLibre + MapboxOverlay 混栈下不渲染。TerrainLayer 虽是不同层类型，但**同属 deck.gl 3D 渲染栈**，在未实测验证前，"TerrainLayer 能渲染"只是假设，不是事实。claude组 5.3 表里 b 的风险标"中（memory 教训：GridLayer extruded broken）"——我觉得应该标**高**：有前车之鉴的混栈渲染问题，不应在没有 PoC 的情况下作为定案选项。这恰好是"今天定稿"时间约束下该砍掉的选项。

**③ a 的 RGB DEM 编码成本被 claude组 略微高估，但方向对。**

claude组 5.3 标 a 成本 = M（后端 DEM 编码 + 前端接线）。我实查后端，**编码所需的现成件齐全**：

- KDE 栅格 `Hs`（`spatial_analysis.py:938`，`np.clip(_convolve_separable(H, sigma_cell), 0.0, None)`）已经是**地理参照过的连续密度曲面**（坐标由 `xe/ye` 定位，EPSG:4546 米制，`spatial_analysis.py:933-935`）。
- Mapbox/MapLibre RGB DEM 编码 = `(r*65536 + g*256 + b)` 解码高程，编码侧只需 numpy 位运算 + `PIL.Image` 或 `matplotlib.image.imsave`（matplotlib 已在 requirements.txt:43）输出 PNG。**无需 rasterio/gdal**（requirements.txt 确认无此依赖，也不需要新增）。
- 编码逻辑 ≈ 20 行：`Hs` 归一化到 `[0, encoding_max]` → 拆 R/G/B 三通道 → `uint8` → PNG，附带 bounds（4326）给前端 `raster-dem` source 的 `tilesize`/`bounds`。

所以编码成本实为 **S（小）**，不是 M。真正的工作量在**前端接线 + 全局地形冲突处理**（见 1.3），那部分才是 M。

**④ MapLibre 版本满足。** `index.html:12` 用的是 `maplibre-gl@5.2.0`，setTerrain 自 v2 起官方支持，5.2 是最新主线，无版本障碍。

### 1.3 a 方案的真正风险：setTerrain 全局 draping（claude组 低估）

这是我要**重点补充**给 claude组 的：5.3 表把 a 的风险标"低"，理由是"MapLibre v2+ 官方支持"。但官方支持 ≠ 与本仓现有图层零冲突。`setTerrain` 的行为是**全局**的：

- 一旦 `map.setTerrain({source, exaggeration})` 生效，**地图底面变成 DEM 曲面**，所有 2D 图层（`fill`/`line`/`circle`/`symbol`）会被 **drape（投影贴附）** 到地形上。
- 本仓现有的 2D 图层：行政区面（fill）、路网/边界（line）、POI 点（circle）、标签（symbol）、**2D 热力图（`type:'heatmap'`，`map.js:678` addHeatmapPaint）**——这些在 setTerrain 开启后**视觉行为全部改变**（贴地形起伏，可能扭曲）。
- 更隐蔽的冲突：**grid 3D 方格柱（fill-extrusion）与 setTerrain 共存时的语义**。MapLibre fill-extrusion 在 setTerrain 开启时，其高度基准是"地形表面之上"还是"海平面"？这需要实测验证——若方格柱的地基被地形抬高，原本对齐的 grid 柱会漂浮或穿模。

**可操作的风险隔离方案（这是我给 a 的定案条件）**：

1. **setTerrain 不常驻**：只有当用户显式进入"3D 地形"模式（terrain 工具）才开启，退出时 `map.setTerrain(null)`。与现有 `setView3D(on)`（`map.js:318`）的 pitch 开关同生命周期。
2. **互斥显隐**：3D 地形模式开启时，**隐藏所有 fill-extrusion 图层**（grid 3D 柱等），避免 draping 冲突；"3D 地形"与"3D 网格柱"是**两种互斥的 3D 表达**，不共存。这符合演示逻辑链——张力图面用 KDE 地形（连续）或网格柱（离散）二选一，不同时上。
3. **exaggeration 参数化**：KDE 密度归一化后的高程差通常很小（0~1），必须乘 `exaggeration`（建议 5~20，演示可调滑块）才有"山势"。但这会导致底图地形也被夸张——若底图是天地图 raster（`map.js:16`），raster 瓦片被 drape 到夸张地形上会严重撕裂。**解法**：KDE 地形模式用**平面底图（无地形 DEM 的 default）+ KDE DEM 作为唯一 terrain source**，不要把天地图 raster 也 drape 上去（setTerrain 只接收一个 source，天地图 raster 不受影响——这是 setTerrain 的正确用法）。

> 一句话：a 的成本不在编码（S），在**全局 draping 的图层隔离设计**（M）。claude组 把风险标"低"是基于"官方支持"，但官方支持只保证 setTerrain 本身能跑，不保证与本仓 8+ 个现有图层共存无碍。这点必须在执行前 PoC。

### 1.4 2D 与 3D 是否共用同一 KDE 栅格（焦点 5 子问题 2）

claude组 问：2D radius（屏幕尺度）vs 3D bandwidth（地理尺度）是否统一到后端栅格一条链。

**我的建议：统一到后端 KDE 栅格（Hs）一条链，2D/3D 共用。**

理由：
- 第一轮我和 Codex 都指出 2D（MapLibre 原生 heatmap，`heatmap-tool.js:830-871`，GPU 屏幕空间核·radius 像素）与 3D（后端 KDE mesh·bandwidth 米）是**两套 KDE 近似**，同一份数据可能画出不一致的热度中心。这是"效果不对"的隐患。
- 既然焦点 5 要为 3D 引入后端 RGB DEM（基于 `Hs`），**顺手把 2D 也改成消费同一个 Hs 栅格**（前端用 `raster-dem` source + hillshade 或 raster 可视化，而非 MapLibre 原生 heatmap），就能彻底统一。2D = Hs 栅格的平面色带渲染，3D = Hs 栅格的 setTerrain 高程渲染，**同源、同尺度、同中心**。
- 代价：2D 热力图失去 MapLibre 原生 heatmap 的 GPU 平滑（radius 自适应缩放），但换来 2D/3D 一致性——对演示而言一致性更重要（用户切换 2D/3D 时热度中心不跳）。

**若时间紧（今天定稿）**：先不统一，2D 保留原生 heatmap（快），3D 先上 setTerrain DEM；统一作为 P2。但要在文档里**标注两者暂不一致**，避免被误认为对齐。

### 1.5 旧地形退役（焦点 5 子问题 3）

**建议：`create_terrain_mesh`（F_007）的等值线环渲染退役，但函数本身保留转换用途。**

- 退役的是**前端 fill-extrusion 等值线环渲染**（`map.js:631-641` 的 terrain 3D 分支），不是 `create_terrain_mesh` 函数。后者改成**只产出 RGB DEM PNG + bounds**（不再提环），供 setTerrain 消费。函数名可保留（track ID F_007 稳定），内部实现改。
- `generateTerrainForAI`（`heatmap-tool.js:879-921`）的契约（返回 `{layerId, fc}`）需扩成返回 DEM 元数据（PNG URL + bounds），或新增 `generateTerrain3DForAI`。
- retired.md 登记：fill-extrusion 等值线环渲染（`map.js:631-641` terrain 分支）→ 退役原因"千层饼非连续曲面"→ 替代 setTerrain DEM。

## 二、焦点 2 收敛复核：Gi\* 网格粒度与权重 —— **改投 claude组 收敛建议，附前置验证**

### 2.1 网格粒度：500m 起步（接受 claude组 / Codex）

**我第一轮建议 200-400m，本轮修正为 500m 起步**，理由：

1. claude组 2.4 收敛建议"500m 对齐宏观诊断信号 + 演示尺度"是对的。Gi\* 在本项目的定位是"显著聚集关注区"（宏观诊断信号环），不是"微观落点"。200-400m 的格太细，在宜昌主城点密度下会有大量 `point_count<3` 的空/稀格（Codex 第一轮修正 2 提的过滤条件），Gi\* 的邻接矩阵会稀疏，反而引入 claude组 想避免的"岛屿"问题。
2. 我第一轮的 200-400m 是基于"对齐 `create_square_grid` 默认 200"（`spatial_analysis.py:727`）和"density cell_size=600"（`tool_contracts.py:46`）的代码惯性，**不是基于演示尺度**。500m 对齐 claude组 的尺度表"区=500m"（`tool_contracts.py` 多处），与"宏观诊断信号"的结论颗粒度一致。这点 claude组 比我想得对。
3. **Codex 的 `point_count >= 3` 过滤是必要的**（第一轮 Codex 焦点 2 修正 2），我补一条：过滤后的空格**不参与 Gi\***（不入邻接矩阵），而非填 0 填充——填 0 会制造伪冷点。

### 2.2 权重：KNN k=8 保留 + 距离带作 P2（接受 claude组）

**我第一轮建议"距离带优先 + KNN fallback"，本轮修正为"KNN 保留为默认，距离带作 P2 实验项"**，理由：

1. claude组 2.4 的判断务实："先改输入粒度（P1）看效果，权重再议（P2）"。我同意——**单元语义缺失（单条评论 score）是比权重尺度漂移更上游的问题**。改了输入粒度（500m 格的 score_mean），单元语义先对了，此时 KNN 尺度漂移的影响会**自然减弱**（格已经是 500m 级的稳定单元，KNN k=8 的"邻居"是 8 个 500m 格，尺度漂移从"50m vs 2km"压缩到"4km vs 16km"，相对可接受）。
2. 我第一轮担心的"KNN 尺度漂移致跨区不可比"在**逐点**场景下严重，但在**500m 网格**场景下大幅缓解。所以权重的优先级确实应降到 P2。
3. **但保留一个前置验证要求**（见 2.3）。

### 2.3 前置验证（claude组 未提，我补）

claude组 2.4 说"先改输入粒度看效果"——但"看效果"需要可证伪的基准。我要求在 P1 执行**前**补一个 Codex 第一轮三、已提的 A/B 验证：

- **A/B 出图对比**：用真实 L2 宜昌数据，跑「逐点 Gi\*（现状）」vs「500m 网格 Gi\*（修正）」，对比显著格（hot/cold）的数量、空间形态、z 分数分布。
- **这是 P1 改动的判据**：若 500m 网格 Gi\* 的显著格与逐点版**空间分布一致**（只是边界更规整），说明根因不在单元（claude组 接受的"单元语义"修正被证伪），需回到权重；若**分布显著不同且更符合业务直觉**（显著聚集落在已知问题区），则单元修正成立。
- Codex 第一轮"给 claude组 的验证要求"第 1 条已提此 A/B，我**重申并升格为 P1 前置**（不是"建议"，是"必须"）。没有这个 A/B，"改了输入粒度看效果"是主观判断，不可证伪。
