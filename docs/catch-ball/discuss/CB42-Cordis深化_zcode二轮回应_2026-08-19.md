## 二、深度解读：七概念 × EMC 现状对照

| Cordis 概念 | EMC 现状对应物 | 差距判定 |
|---|---|---|
| Context（服务容器） | 无统一容器；模块级单例（`_CACHE`/`_FIELD_CACHE`）+ import 图 | 差距真实，但 Python 栈无需复刻——见暂缓⑤ |
| Plugin（能力携带者） | 无插件机制；功能=模块文件 | 同上，思想层面吸收 |
| Service（能力接缝） | **部分有**：`tool_contracts.py`=契约描述 + `geo_registry`=按 id 解析 + `/geo/catalog`=服务发现 | **三者分散**——见修正⑥，MCP v1 统一 |
| inject（依赖声明） | 无；import 顺序即初始化顺序（T2 中防循环依赖用函数内 import，正是无依赖声明机制的 workaround） | 思想吸收：模块间依赖显式化的方向正确 |
| Event（解耦通信） | `document` CustomEvent（前端）+ trace 日志（后端·记录非通信） | 后端事件总线缺——C 线会话事件流时一并考虑 |
| Effect（可逆副作用） | 朴素形态：缓存 clear 函数（T2 的 `clear_layer_usage_cache`）、测试 fixture 清理 | **机制文化差距**：无"卸载即回收"约定 |
| Fiber（生命周期） | 无对应；「FAILED 明确报错不静默」与 CB-39 诚实度纪律同构 | 原则已一致，确认 |

**第八节最值钱的三个洞察**（zcode 评价）：

1. **「每个副作用必须有补偿」（Effect/Saga 思想）**——EMC 的"诚实收尾"目前靠纪律（测试清理、缓存失效手动调），Cordis 把它做成了机制（注册即 effect、卸载自动回收）。启示落点：今后新增模块级缓存/后台资源时，**同文件必须带显式清理函数**（T2 已示范）。
2. **「观察者必须放行」（waterfall 短路纪律）**——对 EMC 守卫管线是硬规则：**拒绝型守卫**（T2 的 usage 拦截）= 有意短路；**观察型守卫**（未来的脱敏审计、口径标注）= 必须放行不得吞链。这条在守卫管线成形时要写成测试断言，不靠自觉。
3. **「顺序由依赖决定，不由文件顺序决定」（inject 声明）**——EMC 的 import 顺序耦合是真实痛点（函数内 import 是症状）。不引运行时，但设计上向"依赖显式声明"靠拢的方向正确。

## 三、四档裁决（第八节增量）

### 立即吸收（零排期成本）

- **A5「观察者必须放行」入守卫纪律**：写入守卫管线设计约定（本回应即载体；管线成形时固化为测试）。与 A1/A2 并列为本学习线第三条落地纪律。
- **A6「副作用必带补偿」入模块规范**：新模块级缓存/资源必须同文件带清理函数（T2 `clear_layer_usage_cache` 为首个示范，此后惯例）。

### 并入现有排期（不新开专项）

- **B5 Service 命名空间规划（`em.*` 前缀）**→ 并入 B3/B4 条（MCP v1 立项设计输入），记入 CB42 前轮回应的 MCP 条目。
- **B6 事件流投影式日志**（Session Events→deriveMessages 的"从事件投影"形态）→ 补充进 B2 条（C 线蒸馏素材规范）的具体设计语言。

### 暂缓（挂看板）

- **C3 Python 侧 effect/守卫链原型（ExitStack/装饰器近似）**：**不做独立原型**。理由：T2 守卫已按"管线首闸"形态落地（`_guard_usage_refs` 单一入口+明确挂点），第二个守卫出现前抽象管线是为未来写验证代码，违背「不增加无谓排期」。定形时机=第三个守卫落位时（三次法则）。
- **C4 后端事件总线**：等 C 线会话事件流真实需求，不预建。

### 反对与修正

- **D3 修正 8.6.1 的同构表述**：报告称 `tool_contracts.py` 与 Cordis「服务名扁平命名空间+声明合并」同构——**部分修正**：tool_contracts 是**静态契约描述**（数据：工具长什么样），不是**运行时按名查找的服务注册表**（行为：工具怎么取）。EMC 真正的 Service 对应物是 `geo_registry`（按 id 解析）+ `/geo/catalog`（服务发现）的合体。契约与服务发现目前分散两处——MCP v1 时应统一为一层（这正是第 11 问的答案基础）。
