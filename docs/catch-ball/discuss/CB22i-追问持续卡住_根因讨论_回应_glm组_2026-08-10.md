### 2.2 deadline 检查失效的代码根因（承重级发现）

**glm 核实**（ai_qa/llm.py:367-369）：

```python
for chunk in cli.chat(messages, **chat_kwargs):   # ← 生成器阻塞点
    if time.monotonic() > _total_deadline:        # ← 循环体内·不可达（上一行挂死）
        raise LLMError('LLM 流式总超时({:.0f}s)'.format(_ttl))
    started = True
    yield chunk
```

**Python 实测铁证**（glm 独立验证）：
```python
def blocking_gen():
    while True: time.sleep(100)   # 模拟 DeepSeek 挂住（永不 yield）

_deadline = time.monotonic() + 3.0
for chunk in blocking_gen():      # ← 永久阻塞
    if time.monotonic() > _deadline:  # ← 永远到不了
        break
# 实测：5 秒后进程仍挂·deadline 永不触发
```

**glm 结论**：`cli.chat()` 是同步生成器·`for chunk in` 等待 `__next__()` 时**整个 Python 线程阻塞**·循环体内的 deadline 检查（被动检查）**永远执行不到**。CB-22h 的 deadline 设计有致命缺陷——**它是「被动检查」不是「主动中断」**。

### 2.3 为什么 17:29 触发但 18:09 不触发

**glm 分析两种挂起模式**：

| 场景 | DeepSeek 行为 | httpx 行为 | deadline 检查 | 结果 |
|---|---|---|---|---|
| **17:29（触发 D_004）** | 发了首 chunk·后续挂·或 httpx read timeout 先抛 | `iter_lines()` 抛 ReadTimeout → `except LLMError` → retry 循环 :361-362 检查 deadline | :362 检查可达（进了 except 分支） | D_004 触发·降级 ✅ |
| **18:09（不触发）** | 首个 chunk 前挂死（连接建立·TCP keepalive·但无 SSE data） | `iter_lines()` 阻塞在等首行·**read timeout 计时未开始或被 keepalive 重置** | :368 检查不可达（没进循环体）·:362 检查不可达（没进 except） | **无 D_004·永久阻塞** ❌ |

**关键差异**：httpx 的 `resp.iter_lines()` 在「连接已建立但无数据」时·read timeout 是否计时**取决于 httpx 版本与 keepalive 行为**。DeepSeek 的 SSE 端点可能在连接建立后发 TCP keepalive（非应用层 data）·让 httpx 认为连接活着·read timeout 不触发·`iter_lines()` 永久阻塞。

### 2.4 serve 反代的同款挂死

**glm 核实**（serve.py:199-235 `_proxy_api`）：

```python
resp = urllib.request.urlopen(req, timeout=60)   # ← 同款 SSE 心跳陷阱
```

- urllib `urlopen(timeout=60)` 的 timeout 是「连接 + 单次 read」超时·**非总时长**。
- SSE 流式 `resp.read()` 分块转发时·若 uvicorn（后端）间歇发数据（或 keepalive）·urllib read 不超时·**反代线程也挂死**。
- serve 是 `SimpleHTTPRequestHandler` 单线程（或受限线程池）·一个反代线程挂死 → 后续 `/api/v1/chat` 请求排队 → **多个用户请求互相阻塞**。

### 2.5 前端降级在「fetch 等响应头」阶段的 edge case

**glm 核实**（api.js:42-47）：

```javascript
const r = await fetch(`${BASE}/chat`, { ..., signal: _ac.signal });  // ← 等响应头阶段
if (!r.ok) { ... throw }
const reader = r.body.getReader();   // ← 响应头到了才能拿 reader
```

- **桩测场景**：fetch 已 resolve（200 已返）·`await fetch` 完成·`reader = r.body.getReader()` 已拿到·reader.read() 阻塞 → abort 让 reader 抛 AbortError → catch 降级 ✅。
- **真实场景**：serve 反代挂在 `urlopen`（没返 200）·`await fetch` **未 resolve**（等响应头）→ 45s abort 触发 `_ac.abort()` → 浏览器应让 fetch reject with AbortError。
- **edge case（核心）**：浏览器规范上 abort 应让 pending fetch reject·**但 serve 的 SimpleHTTP 单线程阻塞在 `urlopen`·无法及时处理客户端 TCP FIN**（操作系统层 FIN 要等应用层 read 返回才能感知）→ fetch reject **可能延迟到 TCP keepalive 超时（~2-5 分钟）**·或浏览器在 certain 状态下等待。

**这就是用户看「读秒 5 分半」的最终机制**——前端 abort 信号发出·但服务端单线程阻塞·TCP 断连未被及时处理·fetch reject 延迟·降级渲染迟迟不触发。

## 三、逐焦点（6 条）

### 焦点 1：为什么 Playwright 通过但用户仍卡 —— **agree 矛盾·glm 给出根因（桩测与真实挂起点不同 + deadline 失效）**

- **agree**：矛盾成立——同机同 serve·Playwright 正常·用户挂起。
- **glm 根因**（双层）：
  1. **桩测模拟的挂起点 = fetch 已 resolve 后**（前端层·reader.read 阻塞）·abort 能 reject reader → 降级。
  2. **真实场景挂起点 = fetch 未 resolve**（serve 挂在 urlopen·200 未返）·`await fetch` 等响应头·abort 应 reject fetch·**但 serve 单线程阻塞·TCP FIN 处理延迟** → fetch reject 延迟/丢失。
- **加上 deadline 失效**（§2.2）：后端 uvicorn 永久阻塞·serve 反代也挂·前端 abort 的 TCP FIN 无法被 serve 及时处理。
- **结论**：**Playwright 桩测无法复现真实场景**——桩测用 `page.route` 在浏览器层拦截·绕过了 serve 反代 + uvicorn 的真实阻塞链路。要复现需在**后端层模拟 DeepSeek 挂死**（如 monkeypatch `cli.chat` 让它永不返回）。

### 焦点 2：真实网络挂起时前端降级链路 —— **agree edge case 存在·glm 定位到 serve 单线程 + fetch 等响应头**

- **agree**：前端 abort 后 reader.read() 的 edge case 存在。
- **glm 补充**（关键修正）：edge case 不在 reader.read()（那已被桩测证明有效）·而在 **`await fetch` 等响应头阶段**——serve 反代挂在 `urlopen`·200 未返·fetch pending·abort 的 TCP FIN 被 serve 单线程阻塞无法处理。
- **修复方向**：
  - **后端根治**（首选）：llm.py deadline 改主动中断（见焦点 5）·让 uvicorn 不永久阻塞·serve 反代能正常返回。
  - **serve 兜底**：serve `_proxy_api` 加总超时（`signal.alarm` 或 threading.Timer 强制中断 urlopen）·反代超时返 502 给前端·前端 `!r.ok` throw → 降级。
  - **前端兜底**：`await fetch` 外层加 `Promise.race` 超时·不只是 abort signal（abort 在 fetch pending 时依赖浏览器/服务端配合·race 强制超时更可靠）。

### 焦点 3：首问 vs 追问真实卡点 —— **agree trace 显示首问就挂·追问未到达**

- **agree**：trace 五次全首问（rag_search → finalStep）·全挂起·**未到追问**。
- **glm 核实**：sess-17256 18:09:19 是 `MOD_AIQA.F_015 rag_search → F_003 finalStep → F_002/F_001 LLM → 无 exit`——**首问知识问答的 finalStep 就挂了**·用户根本没到追问（generate_point_layer/FC）。
- **结论**：claude 判断「三次修复都针对首问 finalStep」正确·但**修复没兜住首问的「首 chunk 前挂死」场景**（deadline 失效）·所以用户仍卡。追问路径（generate_point_layer）的潜在卡点**本轮无法验证**（首问都没过）。

### 焦点 4：浏览器 JS 缓存 —— **disagree（排除·glm 核实 serve 返回新 JS）**

- **disagree**：glm 实测 serve 返回的 harness.js **含 `_composeKnowledgeDegraded` ×2 处**（curl `/frontend/js/ai_qa/harness.js`）·api.js 含 `phase === 'answer' ? 45000`·文件大小 176785（含 `?v=mtime` 注入）。

## 四、修复 plan 建议（glm）

### 4.1 P0 · deadline 改主动中断（承重·根治后端永久阻塞）

**方案 A（推荐）**：`LLMClient.chat` 的 stream 分支加 `threading.Timer` 强制 close。

```python
# ai_qa/llm.py chat 方法 stream 分支（:96 附近）
if stream:
    with httpx.Client(timeout=self.timeout) as client:
        with client.stream('POST', url, headers=headers, json=body) as resp:
            # CB-22i：总预算超时——Timer 到时强制 close resp·中断 iter_lines 阻塞
            import threading
            _total_timeout = 60.0   # 总预算（flash·pro 可参数化）
            def _force_close():
                try:
                    resp.close()   # 强制中断流·iter_lines 抛 StreamClosed
                except Exception:
                    pass
            _timer = threading.Timer(_total_timeout, _force_close)
            _timer.start()
            try:
                for line in resp.iter_lines():
                    ...  # 现有逻辑
            finally:
                _timer.cancel()   # 正常完成·取消 Timer
```

**效果**：Timer 到时调 `resp.close()`·httpx `iter_lines()` 抛 `httpx.StreamClosed` → 进 `except httpx.HTTPError`（:142）→ 抛 LLMError → `chat_with_fallback` retry/deadline 逻辑接管 → D_004 触发 → SSE error → 前端降级。

**红线核对**：不碰 diagnose prompt / orchestrate / D019 / @track() / 不造轮子（复用 httpx resp.close + threading.Timer 标准库）✅。

### 4.2 P0 · serve 反代加总超时（兜底·防 serve 单线程挂死）

```python
# frontend/serve.py _proxy_api（:212 附近）
try:
    resp = urllib.request.urlopen(req, timeout=60)
except ...

try:
    # CB-22i：反代总超时——Timer 到时强制 close resp·中断 read 阻塞

    _proxy_timer = threading.Timer(50.0, lambda: resp.close())   # 50s·比前端 45s abort 略宽

        # 现有 SSE 转发逻辑
        ...
    finally:
        _proxy_timer.cancel()
finally:

```

**效果**：反代 50s 超时 close resp·urllib read 抛错·反代返 502·前端 `!r.ok` throw → 降级。即使后端 uvicorn 挂死·serve 也不被拖死。
