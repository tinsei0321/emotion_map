## 〇、讨论演进脉络（今日核心认知的形成过程）

今日对 EMC 数据认知体系的理解，经历了**四阶段演进**——每一步都是用户对产品本质的追问澄清，最终收敛为两个核心定性：

### 阶段一：范围识别的边界问题（B3-verify-06 触发）

B3 飞轮出现 PRM-05/07 fail：EMC 在硬识别「小溪塔」「龙泉」等**法定功能区**（非行政区划），FC 把整层当 boundary、derive 想修但修不动。用户首次定性：**EMC 不需要"死磕"非行政区划的范围识别**——这些区域应让用户上传标准资料，EMC 自己识别不可信。**只有用户上传数据中的情绪地图专属语义（极性/4×5 归因）才由 EMC 识别。**

### 阶段二：「范围」= 矢量落图（不关键）vs「地点」认知（关键）

用户进一步区分：
- **「范围」的识别 = 地图上矢量数据的表达**（geojson/csv/shp 如何落图）——**不关键**，需要范围的分析都是用户指定/临时上传，EMC 自己判断的不可信
- **「地点」的认知 = 关键**——EMC 要对地点（POI/区域/片区）有**准确认知**，范围与 POI/关键地点的**包含/覆盖/相邻拓扑关系**必须明确

### 阶段三：逆地理编码的确认（能力盘点）

用户问：需要用到逆地理编码吗（不只是 POI 接入，还有更多详细准确地理信息）？目前架构有没有？能否调度 API？
→ **调查确认：逆地理编码已存在且高德 regeo 已接入**（返回地址/区/街道/乡镇），但**只服务 UI 弹窗，未接问答管线**——能力有了，断链了。

### 阶段四：归因↔地点联动 = 中微观标准出口（核心定性）

用户最终定性，定义 EMC 中微观情绪分析的标准出口：
> 中微观尺度的情绪分析，必须建立「归因」与「地点」的联动，这是 EMC 回答的标准"出口"之一。但不是对地点进行归因分析，而是**通过标准分析工具的结论（方格网/柱体、热力图热点/冷点等）与地点信息进行联动**。

**四阶段收敛**：范围（矢量落图）→ 不关键·用户为准；地点认知（位置/拓扑/联动）→ 关键；归因↔地点联动 → 中微观标准出口。EMC 的核心价值 = 让宏观分析结论落到具体地点。

## 一、用户意图与产品定位（总纲）

情绪地图（EMC）是"城市连续主观体检"——通过海量评论聚合，让规划者**定位关注区 + 生成假设 + 排序优先级**（宏观诊断信号）。今天用户对 EMC 的数据认知体系提出两个核心定性，重新定义了 EMC 的识别边界与标准出口：

1. **「范围」的理解与要求**：范围 = 地图上的矢量数据表达（不关键）；**「地点」认知 = 关键**（拓扑关系必须明确）。
2. **「归因」↔「地点」联动**：中微观尺度情绪分析的标准出口——标准分析工具结论（格子/热点）与地点信息联动，归因指向具体地点。

**核心命题**：EMC 要"用数据替代直觉、用地图承载叙事"，关键不在"识别范围"，而在**让宏观分析结论落到具体地点**——"这片区域为什么消极"→"滨江公园绿化做的好 / xx小区电梯老旧 / xxxx路经常堵车 / xxxx停车太难了"。

## 二、定性一：「范围」的理解与要求

### 2.1 范围 = 矢量数据表达（不关键）

EMC 对「范围」的识别，指的是**地图上的矢量数据表达**——geojson/csv/shp 等格式的数据如何落到地图上（几何 + 坐标 + 渲染）。这部分**不关键**：需要用到范围的分析（zonal/compare/clip/buffer），通常都是**用户指定范围或临时上传范围**，EMC 自己判断的范围是不可信、不可用的。

### 2.2 范围三来源（可增补注册机制）

「范围」参数必须锚定**明确来源**，不做自由语义猜测。来源机制是**可扩展注册表**（当前三个初始种子，非封闭枚举）：

| # | 来源 | 说明 |
|---|---|---|
| ① | **用户绘制** | 地图手绘 polygon |
| ② | **临时上传范围** | a) 不需要剪裁 b) 需要剪裁 |
| ③ | **数据库固化范围** | 开发者固化/向量化标准范围（中心城区、行政区划等·可涉及剪裁）|
| ④ | 未来可增补 | 来源机制 = 注册表，可追加 |

### 2.3 EMC 不主动识别范围（诚实 request_upload）

- 问句范围名 → 依次锚定到已注册来源（**确定性匹配**）→ 得到精确要素/范围
- 锚定成功 → 执行（必要时剪裁）
- **锚定失败（不在任何来源）→ 诚实 request_upload（让用户绘制/上传）·不硬识别**
- EMC **不做**自由语义猜测（不靠内部预置知识猜"小溪塔在哪"）——识别不可信

### 2.4 范围 ↔ 位置的拓扑关系（关键）

EMC 对「地点」要有认知，**而且要准确**——范围与 POI/关键地点的**包含、覆盖、相邻等拓扑关系**必须明确。这是关键。包含两部分：

1. **底层地点/POI/区域/片区的位置信息认知** + 问答时能否"触发联动"（与区域/地点/POI 等相关词汇形成联想/联动）
2. **EMC 能否获取/判断/输出「范围」与「位置信息」的拓扑关系**（包含/覆盖/相邻）

## 三、定性二：「归因」↔「地点」联动（EMC 标准出口）

### 3.1 中微观情绪分析的标准出口

中微观尺度的情绪分析，必须建立「归因」与「地点」的联动——这是 **EMC 回答的标准"出口"之一**。

### 3.2 不是对地点做归因分析，而是分析结论 ↔ 地点联动

**关键澄清**：不是对地点（POI）做归因分析（POI 不是分析主体），而是**通过标准分析工具的结论与地点信息进行联动**——方格网/柱体（聚合）、热力图热点/冷点（空间聚类）等标准分析产物，联动到它们涉及的地点信息。

### 3.3 应用场景（用户举例·下钻链）

> 得到 L2 数据的 400m 网格空间聚合分析结果 → 筛选典型网格/柱体（积极/消极/中性比较聚集，或某类"归因"比较多的网格）→ EMC 准确且全面判断这些网格涉及的**地点信息** → 产出结论性"归因"："滨江公园绿化做的好 / xx小区电梯老旧 / xxxx路经常堵车 / xxxx停车太难了" → **归因指向具体地点**。

**下钻链**：`标准分析结论（网格/热点）→ 地点信息（POI/区域/片区）→ 结论性归因（指向具体地点）`。

## 四、现状评估（调研结论）

### 4.1 已有的（基础能力较完整）

| 能力 | 现状 | 位置 |
|---|---|---|
| **范围三来源（部分落地）** | 固化库行政区划白名单 `FIXED_ADMIN_DISTRICTS` + deriveAvailable 确定性匹配 + 锚定失败→request_upload | `frontend/js/ai_qa/tools.js` |
| **网格级归因** | 网格聚合产出 domain_top/element_top/issue_label/place_name（代表地名） | `core/spatial_analysis.py:561-607` |
| **POI 引擎** | 1270 高德 + 157 种子 + 7 地标·rapidfuzz+pypinyin 分档匹配·11 叙事区 zone 映射 | `core/place_layer.py` |
| **逆地理编码** | 本地 place_layer.reverse + **高德 regeo**（formatted_address/district/township/street）+ lru_cache | `core/geocode.py:262`、`api/routes.py:438` |
| **L1/L2 点数据带地点标注** | area_seed/spatial_hotspot/location_mentioned（模拟期写入·如"夷陵广场周边停车太难"） | `SCRIPT/sim_performance_data.py` |

### 4.2 缺失的（断链点）

| 环节 | 缺失 | 影响 |
|---|---|---|
| **POI 进问答管线** | `frontend/js/ai_qa/` 零 place_layer/逆地理引用·agent 无地点查询工具·LLM 不可见不可调 | 问"万达在哪"→ LLM 凭训练记忆自猜坐标（有编造风险）|
| **格↔POI 空间查询** | 网格聚合只聚情绪点不碰 POI·无 spatial join(格×POI)·place_name 是单一代表名非 POI 清单 | 网格→地点枚举不可达 |
| **评论↔POI 运行时关联** | 仅模拟期打标签·无最近 POI 反查·无 text 地点抽取 | 无法输出"滨江公园"相关评论集 |
| **地点级归因聚合** | 归因是网格级·落不到具体 POI | "滨江公园绿化好"不可达 |
| **批量逆地理** | 当前仅单点反查（弹窗）·无网格批量·高德 QPS/日配额需节流 | 网格→地点需批量逆地理 |
| **范围↔位置拓扑** | 仅 sjoin within + overlay·无相邻/邻接/覆盖枚举 | "西陵区含哪些 POI""伍家岗与谁相邻"答不出 |

### 4.3 关键洞察

- **基础能力你有**（POI 引擎 + 逆地理编码 + 网格归因），缺的是**"接入问答管线 + 批量查询 + 评论↔POI 关联"的中间层**——不是从零建，是打通。
- **孤岛数据**：`DATA/POI/yichang_pois.geojson`（3220 条含 address/district）无运行时消费方；ingest 产出文件缺失。
- **已知 bug**：`amap_poi_centralcity_wgs84.json` 缺失（中心城区外围 POI 空）·EMC buffer 中文 POI 名失败（"奥体中心"无法解析·AI 路径无 searchPlaces 兜底）。

## 五、实施方向与讨论焦点（供两组收敛）

### 方向一：地点认知接入问答管线（治"LLM 不可见地点"）
- 给 agent 加「地点查询」工具（复用 `place_layer.forward` → 中文地名→坐标/区域/类别）→ LLM 可查"万达在哪""奥体中心"
- `buildContext` 注入 POI/地点词表（轻量·按需）
- 修复 buffer 中文 POI 名失败（AI 路径加 searchPlaces 兜底·现状"奥体中心"无法解析）

### 方向二：逆地理编码批量接入（治"格子→地点"）
- 给 agent 加「坐标→地点」工具（复用 `reverse_geocode` → 地址/区/街道/最近 POI）
- 网格/热点 → 质心/代表点批量逆地理 → 格子涉及地点清单
- 高德 QPS/日配额节流（批量上限 + 本地 place_layer 优先 + `lru_cache`）

### 方向三：归因↔地点联动工具（下钻链核心·用户场景）
- **格↔POI 空间查询**：网格聚合时 sjoin 格×POI → 输出格子覆盖 POI 清单（名称/类别/位置）
- **评论↔POI 关联**：评论按最近 POI 反查 / text 地点抽取 → "滨江公园"相关评论集
- **归因→地点落点**：格的归因（domain_top/element_top/issue_label）+ 涉及地点 → 结论性归因"该格停车难归因指向夷陵广场周边"

### 讨论焦点（需两组深入收敛）

1. **架构分层**：地点认知/归因↔地点联动放**后端**（core/spatial_analysis + geocode·空间查询/批量逆地理）还是**前端**（ai_qa tools·联动工具）？还是后端提供空间查询、前端提供联动工具的**分层**方案？——用户场景是"分析结论→地点"的**空间联动**，天然需后端空间能力 + 前端交互。

2. **触发范式**：归因↔地点联动是**标准分析产物的默认输出**（格子自带地点清单·分析即得）还是**按需工具**（选中格子→查地点）？——需对齐 EMC 交互范式（悬停试探/点击锁定·Overview 指挥台）。用户场景"筛选典型格子→判断涉及地点"暗示**格子选中后的联动呈现**。

3. **数据接入**：
   - `DATA/POI/yichang_pois.geojson`（3220 条含 address/district）孤岛数据是否接入运行时（补 ingest 缺失文件）？
   - `amap_poi_centralcity_wgs84.json` 缺失（中心城区外围 POI 空）怎么补？
   - 评论↔POI 关联用**最近 POI 反查**（坐标就近）还是 **text 地点抽取**（评论文本提地名）？——L1/L2 点已带 area_seed/spatial_hotspot 标注（模拟期写入），是否复用？

4. **配额/性能**：高德 regeo 批量调用 QPS/日配额策略？本地 `place_layer` 优先 + `lru_cache`(256) + 前端缓存(200) + 批量上限？网格大量格子逆地理会打满吗？

5. **承重红线**：`place_layer`/`geocode` 是承重组件（搜索栏/弹窗依赖），接入问答须守红线（改前先扩 eval）。方案是否触碰 `diagnose prompt`/`harness orchestrate`/`ChatRequest schema`？

6. **拓扑关系扩展**：用户强调"范围与 POI/关键地点的包含/覆盖/相邻拓扑关系必须明确"——现状仅 sjoin within + overlay。是否需补**相邻/邻接/覆盖枚举**能力（"西陵区含哪些 POI""伍家岗与谁相邻"）？

### 方案设计约束（用户意图锚点）
- **不是对地点做归因分析**——POI 不是分析主体，是分析结论的**落点**（网格/热点的归因 → 指向涉及地点）
- **范围识别不关键**——EMC 不猜范围，锚定用户提供的来源，失败则诚实 request_upload
- **地点认知是关键**——准确的位置 + 拓扑关系 + 问答触发联动
- **下钻链**：标准分析结论（网格/热点）→ 地点信息（POI/区域）→ 结论性归因（指向具体地点）

## 二、关键发现（glm 独有·已核实）

**glm 致命发现（Codex 遗漏）**：`spatial_analysis.py:585-597` 的 `place_name` 只依赖点数据**自带**的 `spatial_hotspot`/`area_seed` 标注字段（sim 期写入）·**不碰 POI** → 真实采集数据若无这两字段，`place_name` 恒空 → **下钻链第一步就断**。已核实属实。

**修正方向**：P0 须先改 `place_name` 为「sjoin POI 清单优先·fallback spatial_hotspot·再 area_seed」（双源融合保兼容）。

## 三、实施优先级（两组共识·严格分阶勿同时铺开）

| 优先级 | 内容 |
|---|---|
| **P0** | 下钻链最小闭环：格↔POI sjoin（聚合输出 poi_names）+ 修正 place_name 双源融合 + `/grid/pois` 端点（选中格子按需）+ 3220 接入 |
