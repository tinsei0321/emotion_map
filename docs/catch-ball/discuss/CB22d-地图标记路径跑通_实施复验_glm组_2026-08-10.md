#### 3.2 agentStep 30s 超时 + 流式 token — **agree + ★ glm 自我修正**

**★ glm 上轮误判修正**：glm 在根因讨论轮说「agentStep 的 streamChat 无单轮超时·deadline 够不着」。**本轮核实发现此判断有误**：
- `streamChat`（[api.js:34](frontend/js/ai_qa/api.js#L34)）**早有** per-phase 超时：`agent_step=30000`（30s）·`answer=45000`（45s）·`setTimeout(() => _ac.abort(), _timeout)`。
- 该超时是 commit `4322504`（Hotfix R2）引入·**早于 sess-19156 挂起和 ace4f8f**。
- 即：**挂起发生时 agentStep 30s 超时已存在**。

**真实挂起机制重判**（glm 修正）：trace 显示 7 分钟挂起·而 agentStep 有 30s 超时——说明挂起源**不在 agentStep**·而在 **finalStep（answer phase·45s 超时）**。Codex 判断「finalStep 单调用挂起」更准确。可能机制：finalStep 的 45s 超时 abort 后·异常处理/降级路径有缺陷致 UI 卡死（Codex「超时异常 UI 卡死」）。

**但无论旧机制细节如何**：B1 新路径（零 LLM）**从根本上不进 finalStep** → 挂起源被绕开 → 根治有效。agentStep 30s 超时作为通用防护（治「reasoning 不收敛」）仍然有价值·且**流式 token 输出确认存在**（api.js:72-73 逐 token onToken/onReason·用户能看到在思考·不静默挂）。

**glm 结论**：B1 是挂起的真正根治（绕开 finalStep）·agentStep 30s 超时是通用防护（已存在·非本轮加）。**P0-2 命门达成**。

#### 3.3 是否还有「停半途」场景未覆盖？— **低风险·1 处观察**
