## 〇、一页通俗版摘要（先看这里）

### 背景：这份审计说了什么

Qoder（知识库架构师）检查了情绪地图的「知识库」（RAG——就是 AI 回答问题前先去查资料的那座小图书馆）。他的结论用大白话讲：

- **图书馆的保管制度很好**（书不会丢、不会坏、断电也不怕——原子写/校验/离线纪律），这 8.5 分；
- **但找书的方式很老**（只有一个「按意思找」的检索台，没有「按书名/编号/地名找」的卡片目录——专业上叫缺 BM25 混合检索、缺重排序），这 4.5 分；
- **而且书太少，还有 80 多本书锁在管理员的抽屉（Python 代码）里没上架**，最权威的 12 张「口径卡」（就是规定"哪个数字才算数"的那沓卡片）也没放进图书馆。

他建议花 6~8 个工作日分五步修：先定考核标准（P0）→ 加卡片目录（P1）→ 请复核员（P2）→ 把抽屉里的书上架（P3）→ 改善借阅体验（P4）。

### 我的研判（一句话）

**报告骨架可信、方向正确，我核实后支持大半；但有三处要修——一处顺序要对调、几处数字错了，还有一个「复核员」建议要先缓一缓。**

用图书馆接着打比方，我的裁决是：

1. **考核标准马上定**（P0 吸收）——不先定标准，后面所有装修都说不清有没有变好。而且我实测发现现有考卷已经悄悄从满分掉到 90 分了，没人发现——因为这张考卷根本不在自动门禁里。这证明报告说「评估要先行」不但对，还挺急。
2. **卡片目录（关键词检索）和上架新书并行做**（P1 并入排期）——两件事互不挡路，一个解决「找不准」，一个解决「没有货」。
3. **「复核员」（重排序模型）先缓**（P2 暂缓·不是否决）——理由来自我们自己的实测记录（台账 R43，大脑实测）：通用助手宁可自己翻文件也不走我们的插座，原因判明是**书不够**，不是**找得慢**。先花力气请复核员、书架却半空，是装修顺序颠倒。等书上够了，如果考卷显示还是找不准，再请（触发条件写死，不是无限期搁置）。
4. **上书时最权威的口径卡先上**（吸收+拆两步）——12 张口径卡和 57 张图层说明书卡不必等「搬家工程」完工就能先进索引，半天见效，直接解决「答得出但引不到权威源」的痛点。

### 代价与推荐

| 选项 | 代价 | 我的推荐 |
|---|---|---|
| 全按报告 P0→P4 顺序 | 重排序先于内容上架；2GB 模型下载+每次检索多 1~2 秒；主矛盾（书不够）后解 | 不推荐原顺序 |

### 1.3 研判新增实测证据（报告没有·本轮贡献）

这些是研判轮独立跑出来的，**直接支撑或修正报告的建议排序**：

1. **当前基线实跑（office 机·2026-08-21）**：正确召回 **9/10 = 90%**、越维 2/2 通过、案例不引数据 2/2 通过、黄金集整体通过。基线不是满分——P0「先立基线」不是纸上需求。
2. **唯一未命中题暴露两个活问题**：「葛洲坝片区体检有什么问题」（期望命中含「葛洲坝」或「体检」的来源）Top-5 全被更新域事实卡占据（URP-C01/URP-M01 等）——①「体检」「葛洲坝」这类精确关键词正是纯向量检索的弱项（BM25 缺位的活证据·报告 E1 痛点实证）；② Top-5 全是 fact 类型疑似 **fact ×1.2 加权把体检笔记挤出了榜单**——报告 3.4 说「类型权重应作可观测参数」，这就是权重需要调的第一个数据点。
3. **门禁排除链**：`pytest.ini norecursedirs = tests/browser` → 黄金集回归测试在 442+2 门禁里**不跑** → 断言过时（10/10 vs 实际 9/10）无人发现。三个环节叠加，恰好证明 P0 的必要性和「评估进门禁」的落点（不只是写测试，是**接进门禁+断言动态化+无索引环境可跳过**）。
4. **重排序与「笨中间」内核的合规判断**（用户必读清单点名要判）：`docs/copilot-architecture.md` 铁律 1 的原文是「Tool 不**内嵌 LLM 推理**、单一职责、纯函数式、参数契约」。交叉编码重排序模型（bge-reranker 类）是**固定权重打分函数**（输入问题+候选段 → 输出分数），不生成、不决策、不进推理循环——与已在检索层里跑的 BGE embedding 模型**同类同性质**。管线仍是确定性机械接线（召回→融合→精排→取 Top-K）。**结论：重排序不违反「聪明两端+笨中间」内核**——真正的成本不在架构合规，在 2GB 模型下载、CPU 每次 1~2 秒延迟、预热扩展这三件工程事上。

### 2.2 重点裁决展开

**P0 为什么是吸收且加急**：本轮实跑显示基线 9/10、门禁排除链三环叠加（测试存在→被 norecursedirs 排除→断言过时手跑即红）。P0 的正确落点因此比报告多三件事：① 把黄金集回归接进标准门禁（新建 `tests/test_rag_gate.py`·非 browser 目录·自动被收集）；② 断言动态化（从 gold set 算期望值·不再硬编码「10/10」）；③ `skipif` 索引/模型缺失（索引 gitignore 每环境必建——跨机可移植·debug-memory R19「跨机复刻先取装成机器实录」教训）。扩容目标 60 条合理，但**新增条目须过术语纪律**（来源可溯/禁自创分类——CB-22 用户实测沉淀的素材纪律同样约束考题）。

**P2 暂缓的完整理由与触发条件**：暂缓≠否决。架构合规已判定无冲突（1.3-4），缓的是**时机**——
- R43 证据链：宿主绕插座直读文件=覆盖缺货信号·非排序失准信号（报告自己也把 E3 列为「战略级信号」·但其路线图 P2 重排仍排在 P3 内容前——**报告内部此处自相轻微不顺**，本裁决修正之）；
- 现有 364 条上黄金集召回 90%（>80% 软目标）·排序尚非最痛失败模式；语料入到 600+ 后候选更拥挤·精排边际收益才放大——**先内容后链路同时符合规模驱动逻辑**；
- 2GB 模型下载（HF 镜像一次性）+ CPU 20 对 1~2s + 预热扩展（T17 机制复用）三件成本在演示期都真实。
- **重启触发条件（写死·可证伪）**：内容批（C 线）+ P1 BM25 落地后，黄金集分类型指标（精确名词类/MRR）仍低于扩容后基线目标（如 Recall@5 <95% 或精确名词类未全对）→ 重启 P2；届时优先用 `sentence_transformers.CrossEncoder` 复用既有依赖（**不新增 FlagEmbedding 包**）。

**P3 拆两步的理由**：报告 5.4.3 迁移策略（导出器先行→双轨→生成镜像）本身吸收——有 G8a「单一源→派生镜像」先例背书。但把它与「内容入库」绑成一批会让**最急的内容（口径卡）等最慢的工程（目录体系）**。拆法：
- 第一步（快·随内容批）：口径卡 12 张（含 X-01 作废卡带 `status: retired` 标记·默认过滤显式问及可召回）+ 图层说明书卡 57 层 manifest 投影 + 政策卡 11 张**直入现有索引**——`rag_index.py` 加两个 loader 的事，三入口零改动，立刻解 E2（引不到权威源）/部分解 E3（库变厚）；
- 第二步（工程批）：`knowledge/` 目录+frontmatter 规范+Python 卡片导出迁移+`industry_kb` 收编（收编须保 `kb_facts` 插座行为兼容——铁律 11 契约三处同步义务触发）。

**X4 暂缓补充**：现行「越维降级」运行时呈现已有弱版本（`dim_counts` 维度分布随结果透传·前端 finalStep 有维度声明）。X4 的增量是对**问句侧**推断维度——用 `_infer_dim` 同款启发式跑在 10~20 字的问句上，误判率会显著高于长文本（关键词覆盖更稀疏），一旦误判会产生「明明答得了却声明不可得」的**反向伤害**（诚实降级机制的误报比漏报更伤可信度）。等 P4 的 frontmatter 声明式元数据落地、维度标签可靠后，问句侧推断的地基才存在。
