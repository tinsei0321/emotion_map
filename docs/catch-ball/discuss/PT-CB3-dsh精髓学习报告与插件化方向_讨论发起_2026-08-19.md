## 一、dsh（DeepSeek Harness）是什么

### 1.1 一句话定位

dsh 是 DeepSeek 开源的通用 AI 智能体运行框架，口号是：

> **Everything is a Plugin（一切皆插件）**

它没有不可替换的“特权核心”。模型适配器、工具注册表、会话日志、甚至 Agent 主循环本身，都是可替换插件。

### 1.2 底层框架：Cordis 插件树

dsh 建立在 Cordis 插件框架之上。插件向共享上下文贡献：

- services（服务）
- typed events（类型化事件）
- reversible effects（可撤销副作用）

所有注册都是副作用，插件卸载时自动撤销。

**白话比喻**：房子墙壁全是标准化卡扣，家具插上就用，拔掉就走，不破坏结构。

### 1.3 组装方式：Profile → Bundle → Patch

- **Profile**：具名配置档，如 `web`、`headless`
- **Bundle**：可分发的插件组合包，如 `dsh-base`、`dsh-web-app`
- **Patch**：配置覆盖层，可局部修改或插入插件

查看实际配置树：

```bash
dsh --profile web --dump-config
```

**白话比喻**：同一套家具拼成书房版/客厅版/工地版；配置清单全透明。

### 1.4 轮次与步骤：Turn / Step

- **Step** = 一次模型请求 + 它调用的工具
- **Turn** = 从接收输入到“不再欠任何工作”关闭的责任窗口

流程：

```text
turn/start
  → 接收输入
  → agent/pre-step（可改写或拒绝）
  → 组装 prompt + 工具 schema
  → 调用 LLM
  → assistant/message
  → 工具调用 → tool/call → 工具流水线 → tool/result
  → step/end
  → 需要则下一 step
  → agent/turn-stopping
turn/end
```

**白话比喻**：Turn 是“责任窗口”，中途拒绝/失败也记账，不假装没发生。

### 1.5 会话日志：模型可见即已记录

核心不变量：

> 抵达模型请求的一切，都必须能从会话日志重建。

实现：

- 会话日志是 append-only 事件流
- 模型历史由 `deriveMessages()` 从日志投影
- fork、恢复、transcript、遥测都从事件流派生

**白话比喻**：AI 的“黑匣子”，以后可以回放它到底看到了什么。

### 1.6 工具执行流水线：五道闸

```text
tools/pre-execute（权限/沙箱/钩子）
  → 单调守卫（deny / abstain）
  → ctx.approval（一次性审批，缺人应答=拒绝）
  → tools/execute（超时/重试/指标）
  → fs/write-intent（文件系统写门）
  → tools/post-execute（accept / block / replace / add-context）
  → 结果规范化
  → finalizeContent（内容不变式）
  → tools/result（冻结权威结果）
```

**白话比喻**：工具调用像过机场安检：查证件 → 保安否决 → 放行条 → 执行监理 → 出门验货。

其中 `post-execute` 四态：

| 状态 | 含义 |
|---|---|
| accept | 放行 |
| block | 拦截 |
| replace | 替换成更安全版本 |
| add-context | 补充上下文/警告 |

### 1.7 能力接缝：Seam

一个能力拆成三角色：

1. Service Definition（接口定义）
2. Provider（提供方/实现）
3. Consumer（消费方，通常是面向模型的工具）

换 Provider 不换 Consumer，整体能力可迁移。

**白话比喻**：插座 + 电器 + 用户；换供电方，全屋电器照用。

### 1.8 事件三域

| 域 | 作用 | 例子 |
|---|---|---|
| Session Events | 持久事实 | `turn/start`、`tool/result` |
| Agent Events | 实时控制 | `agent/pre-step`、`agent/turn-stopping` |
| Capability Events | 附加策略/适配器 | `fs/*`、`tools/*`、`telemetry/*` |

### 1.9 上下文压力管理：Compaction

- 派生请求前检查压力
- 先工具结果剪枝，再摘要
- 失败步骤后、轮次结束前恢复

### 1.10 防御性模式七条

1. 正交结果独立上报
2. 公共约定两侧规范化
3. 异步状态 ≠ 同步状态
4. dispose 必须完全停稳
5. 分发器隔离回调异常
6. 绝不把环境变量/可预测路径暴露给不可信输出
7. 链接形态路径用 unlink 删除

## 二、dsh 核心精髓与横向对比

### 2.1 核心精髓

1. **无特权内核**：所有能力可替换、可插拔
2. **能力接缝**：接口/实现/消费分离
3. **模型可见即已记录**：决策可回放、可审计
4. **工具五道闸**：安全靠流水线强制，不靠模型自觉
5. **轮次/步骤生命周期**：责任窗口清晰
6. **Profile 分层组装**：同一系统拼不同环境
7. **防御模式**：把真实踩坑固化成工程纪律

**一句话总结**：

> dsh 的精髓不是让 AI 更聪明，而是让 AI 在可替换、可审计、可防御的框架里运行。

### 2.2 对比表

| 维度 | dsh | Claude Code | Codex | ZCode（GLM 系定制助手） |
|---|---|---|---|---|
| 开源/自托管 | MIT 开源，可自托管 | 闭源，主要官方托管 | 闭源，主要官方托管 | 取决于产品，通常是定制工作流 |
| 模型绑定 | DeepSeek 原生，也可接其他 | 深度绑定 Claude | 深度绑定 OpenAI | 通常绑定 GLM 系 |
| 插件哲学 | 最激进，一切皆插件 | Skills/Hooks/MCP，核心不开放替换 | MCP/工具，不如 dsh 激进 | 支持自定义，但通常不是无特权内核 |
| 界面形态 | CLI + 浏览器原生 Web GUI | 终端/IDE 为主 | 终端/IDE/云端为主 | 终端/IDE 或定制界面 |
| 稳定性 | 开发者预览，破坏性变更活跃 | 相对成熟 | 相对成熟 | 取决于定制程度 |
| MCP 支持 | 原生一阶 MCP 客户端 | 支持 | 支持 | 通常支持 |
| 适合谁 | 会改插件的开发者 | 追求稳定产品化的团队 | 追求稳定产品化的团队 | 深度绑定特定工作流/模型 |

### 2.3 各自优劣势

**dsh 优势**：

- 开放、可自托管、可深度定制
- 唯一在“浏览器原生 Web GUI + MIT + 自托管”上较完整的
- 原生 MCP，一份 MCP Server 可被多宿主消费
- 可审计设计强

**dsh 劣势**：

- 开发者预览，周级 breaking change
- 插件长期维护成本高（TS 全栈 + API 陪跑）
- 开放式 Agent Loop 易出现推理螺旋/死循环
- 无原生 GIS 工具面

**Claude Code / Codex 优势**：

- 产品化程度高，模型和工具配合成熟
- 生态丰富，开箱即用

**Claude Code / Codex 劣势**：

- 闭源，深度定制受限
- 核心循环不可替换
- 不适合直接当面向规划师/住建局的产品壳

**ZCode 优势**：

- 与当前工作流、GLM 模型深度绑定
- 定制成本相对可控

**ZCode 劣势**：

- 生态和社区可能不如 dsh/Claude Code/Codex 大
- 如果也走“自研路由智能”，同样会陷入个人开发者 vs 巨头商品化竞赛

### 2.4 对情绪地图的关键结论

> 正确做法不是把 dsh 搬进平台，而是把平台能力做成“标准插座”，让 dsh、Claude Code、Codex、ZCode 都来消费。

## 三、如何把 dsh 的 Harness 精髓嵌入情绪地图平台

### 第 0 步：纠正认知

“嵌入 dsh 精髓” ≠ “把 dsh 代码嵌进平台”。

正确理解：

> 移植 dsh 的机制思想，同时把平台能力做成标准协议。

### 第 1 步：盘点资产，建立“能力目录”

平台真正值钱的资产：

- 治理好的城市数据（边界、POI、12345、情绪图层、聚合结果）
- 行业知识库（规划/更新/运营/治理）
- GIS 分析能力（缓冲区、聚合、排名、热点）
- 地图渲染资产（样式、色带、图例、交互逻辑）
- 出口卡片（能填进城市体检/更新报告的表单）

为每个资产登记造册：

```text
dataset_id: yichang_admin_community
名称: 宜昌社区边界
类型: 面图层
坐标系: EPSG:4326
字段: name, code, area
样例: 3行
口径: 174 社区，去村口径
安全: 只读，可公开
```

### 第 2 步：把每个能力写成 Dumb Tool 契约

参考 `ai_qa/tool_contracts.py`，定义：

```json
{
  "name": "zonal_stats",
  "description": "按边界聚合统计某个点/面图层的数量或情绪值",
  "inputSchema": {
    "type": "object",
    "properties": {
      "dataset_id": {"type": "string", "enum": ["poi", "emotion_l2"]},
      "boundary_id": {"type": "string"},
      "top_n": {"type": "integer", "default": 20}
    },
    "required": ["dataset_id", "boundary_id"]
  },
  "outputSchema": {
    "type": "object",
    "properties": {
      "rows": {"type": "array"},
      "caliber": {"type": "string"}
    }
  },
  "limits": {"timeout_ms": 60000, "max_rows": 100},
  "security": {"read_only": true, "pii_filter": true}
}
```

核心原则：Tool 越 Dumb 越好，只做一件事，参数明确，输出制式化，不内嵌 LLM 推理。

### 第 3 步：实现一个 MCP Server（推荐 Python FastMCP）

仓库已有 FastMCP 先例：`.claude/mcp_servers/vision_bridge_server.py`。

建议暴露 7 个工具：

| 工具 | 作用 |
|---|---|
| `list_data` | 列出数据集，返回 schema/CRS/样例/口径 |
| `rag_query` | 知识库检索，默认带 LLM 综合 |
| `kb_facts` | 返回确定性行业知识事实 |
| `outlet_card` | 生成出口卡片，对接城市体检/更新表单 |
| `zonal_stats` | 按边界做空间聚合统计 |
| `buffer` | 缓冲区分析 |
| `rank` | 排名/排序 |

关键注意点：

1. `list_data` 要“开卷定参”：返回 schema、CRS、样例、口径。
2. `rag_query` 要带 `synthesize: true`：平台侧 LLM 综合后输出，不返回裸 chunk。
3. 每个工具输出带 `caliber` 字段：宏观聚合 / 确定性组装 / 仅供参考。

### 第 4 步：把 dsh 接入 MCP Server

dsh 原生支持 MCP：

- 在 dsh profile 配置 mcp-client 插件行
- 工具命名自动变成 `mcp__emotion_map__zonal_stats`
- dsh 零代码即可消费

注意：

- dsh MCP 工具是 profile 级全局生效，不是按会话隔离
- MCP Server 必须做到：只读、dataset_id 白名单、脱敏在 server 侧完成
- 不要依赖宿主审批作为唯一防线

### 第 5 步：把“守卫流水线”移植到平台

把现有“结论白名单/降级/口径标注”升级成 post-execute 守卫管线：

```text
工具执行完成
  → 守卫1：数据脱敏检查（block 含 PII 的结果）
  → 守卫2：口径标注（replace/add-context，补“宏观聚合，非精确诊断”）
  → 守卫3：结论白名单（block 无数据支撑的结论）
  → 最终结果
```

### 第 6 步：建立“可重放日志”

至少记录：

- 用户问题
- 意图卡
- 工具调用
- 工具结果
- 最终答案
- 审查结果

以后可回放“AI 到底看到了什么数据，才给出这个结论”。

### 第 7 步：渲染资产契约化

定义 `render_spec`：

```json
{
  "type": "geojson",
  "data": {},
  "style": {
    "color_ramp": ["#8B0000", "#FF9000", "#00A050"],
    "stretch": "symmetrical",
    "opacity": 0.8,
    "legend": "积极/中性/消极"
  }
}
```

这样地图资产不再被锁死在一个前端里。

### 第 8 步：保留 Smart Agent + Dumb Tool 内核

平台内部仍可保留轻量对话入口：

```text
用户提问
  → LLM 意图理解（Smart）
  → 确定性编排器（Orchestrator）
  → 调用 Dumb Tools
  → LLM 结果表达 + Review 审查（Smart）
```

但不再投入大量精力自研“路由智能”，优势放在数据、口径、知识、出口卡片、地图资产。

### 3.1 实施路径总结表

| 阶段 | 做什么 | 产出 |
|---|---|---|
| 1 | 资产盘点 | 数据清单、能力目录 |
| 2 | 契约化 | Tool Contracts、Dataset Registry |
| 3 | MCP Server | 7 个只读工具 |
| 4 | 接入 dsh | dsh profile 配置，零代码消费 |
| 5 | 守卫管线 | post-execute 四态、脱敏、口径标注 |
| 6 | 可重放日志 | 会话事件流、eval 重放 |
| 7 | 渲染契约 | render_spec JSON |
| 8 | 自有轻量入口 | Smart Agent + Dumb Tool 保留 |

## 四、聚焦“让 dsh 精准理解我的诉求，帮我制作出功能匹配的插件”——工作重点

### 4.1 建立“插件需求卡”模板

每次让 dsh 生成插件前，先填卡：

```text
插件名称：宜昌社区情绪聚合工具
业务背景：规划师想按社区查看情绪极性分布
输入：
  - dataset_id: emotion_l2
  - boundary_id: admin_community
  - top_n: 20
输出：
  - rows: [{community_name, polarity_index, count}]
  - caliber: "宏观聚合，供排序参考"
数据源：
  - DATA/analysis/emotion_l2.geojson
限制：
  - 只读
  - 60 秒内返回
  - 不做微观归因
验收标准：
  - 输入合法时返回结构化 JSON
  - 输入非法 dataset_id 时返回明确错误
  - 输出不含 PII
```

### 4.2 先建设“能力目录/契约单一源”

让 dsh 生成插件前，先让它知道平台有哪些标准零件：

- 数据集注册表
- 工具契约
- 安全规则

dsh 生成插件时应从契约派生，而不是自己发明。

### 4.3 把“开卷定参”做进工具

`list_data` 必须返回：

- dataset_id
- 行数
- schema（列名+类型）
- crs
- 样例 3 行
- 口径链接

这样 dsh 生成的插件能基于真实数据工作。

### 4.4 让 dsh 生成“小工具”，不要生成“大插件”

- ✅ 好拆分：`list_data`、`zonal_stats`、`buffer`、`rank`
- ❌ 坏拆分：一个“全能城市规划分析插件”

小工具容易测试、组合、替换，不容易产生黑盒逻辑。

### 4.5 建立“生成后自动验收”

```text
1. schema 校验
2. 数据校验：真实样例跑通
3. 安全校验：不输出 PII、不访问白名单外路径
4. 性能校验：60 秒内返回
5. 回归测试：不破坏已有功能
```

### 4.6 沉淀“失败案例”为规则

当 dsh 生成不符合预期时，记录：

```text
失败案例：dsh 生成的 zonal_stats 插件没有返回 caliber 字段
根因：需求卡里没写清楚 caliber 要求
改进：在插件需求卡模板中增加“口径标注”必填项
```

### 4.7 分清“生成插件”和“生成架构”

- 适合 vibe coding：Dumb Tool、小脚本、UI 小部件、测试用例
- 不适合 vibe coding：核心架构、路由策略、数据治理逻辑

工作重点：

- 用户/主手定“接缝”：接口、契约、安全边界
- dsh 填“实现”：在接缝内生成插件代码
- 然后验收和沉淀

## 八、深化学习：Cordis 框架系统讲解（2026-08-19 追加）

> 本节承接上文——上文讲"dsh 有什么"，本节讲"dsh 底下的 Cordis 是什么、为什么这么设计、论文依据在哪、对我们意味着什么"。按用户"行动轨迹线性、一脉相承"原则，作为本报告第八节追加，不单列文档。

### 8.1 为什么专门学 Cordis

dsh 的口号是"一切皆插件"，但"插件化"不是 dsh 发明的，它站在一个底层框架上实现：

> **Cordis —— dsh 的插件心脏。** dsh 以 vendor（内置源码副本）方式引入 Cordis（包名 `@deepseek-ai/cordis`），所有"可插拔""可撤销""事件流水线"能力都是 Cordis 提供的。

**Cordis 是什么**：一个"可逆插件系统"的小型运行时——应用的所有能力（服务、事件、资源）都挂载到共享上下文上，任何挂载都可以"干净地拔掉"，拔掉时自动回收它产生的全部副作用。

**历史源流**：Cordis 出自开源聊天机器人框架 Koishi（作者 shigma），最初是 Koishi 的插件内核，后独立成框架。Koishi 文档有篇《可逆的插件系统》——"插件的加载和卸载必须对称"，这是 Cordis 的灵魂。dsh 以 vendor 方式内置并加了自己的 Loader/HMR/Include，Cordis 从"机器人框架内核"变成"Agent 平台底座"。

**白话比喻**：Cordis 像一间"标准化卡扣房"：墙壁（Context）上全是标准卡扣（注册点），家具（插件）插上就用、拔掉就走；拔的时候家具自带的插头（effect 的 disposer）自动断电清场，不在墙上留洞、留线、留垃圾。

### 8.2 七个核心概念（逐个讲透）

**概念 1：Context（上下文）= 服务的容器**

- 白话：房间本身。公共电源箱（服务），谁要用电对着墙上的插座喊名字，不自己拉电线到发电厂。
- 机制：服务占据稳定 `ctx.<key>`（如 `ctx.tools`、`ctx.llm`）；消费方按 key 查找，不 import 实现类——"能力接缝"的基石。
- 源码印证：Context 是 Proxy（`new Proxy(this, ReflectService.handler)`），属性读取动态走服务解析器；`extend()/isolate()/intercept()` 三种派生都不修改父级。

**概念 2：Plugin（插件）= 能力的携带者**

- 白话：家具。台灯（函数）、组合柜（对象）、自带插座的大电器（Service 类）。
- 机制：三种形态——函数插件（最常见）、对象插件（`{name, apply}`）、类插件（`extends Service`，要公开服务时用）。插件只描述贡献，由配置决定组合，无框架启动代码。

**概念 3：Service（服务）= 能力接缝的"接口"**

- 白话：标准插座规格 + 插座本身。换供电方不换电器——"能力接缝"的实体。
- 机制：`class GreeterService extends Service { constructor(ctx) { super(ctx, 'greeter') } }`；TS 声明合并（`declare module`）加类型，纯编译时；注册即 effect（卸载自动移除）；服务名全局扁平命名空间，自有服务建议加前缀。

**概念 4：inject（依赖声明）= 顺序由依赖决定，不由文件顺序决定**

- 白话：点外卖写"要米饭"，不用管厨房先后——写清单（inject），不写流程（时序）。
- 机制：`export const inject = ['greeter']` 声明硬依赖；插件保持 PENDING 直到服务就绪；**运行期间服务消失则依赖插件随之卸载，恢复后再加载**（防引用不可用服务）；可选依赖用 `ctx.get()` 探测。
- 坑：PENDING 的 fiber 不保持事件循环活跃，组合里没有运行项时进程会静默退出——"为什么没输出"的常见答案。

**概念 5：Event（事件）= 无需知道"谁在听"的通信**

- 白话：广播（emit）+ 传话游戏（waterfall，每人可改写、可中途截住）。
- 机制：`ctx.on()` 即 effect（监听器随插件卸载自动移除，绝不手动 removeListener）；五种分发模式：

| 模式 | 是否 await | 语义 | 类比 |
|---|---|---|---|
| `emit` | 否 | 同步广播，不等待不收集 | 广场喊话 |
| `parallel` | 是 | 所有监听器并发运行，一起等待 | 同时派多个快递员 |
| `serial` | 是 | 按序运行，第一个非空返回值胜出 | 依次敲门，有人应就停 |
| `bail` | 否 | serial 的同步版 | 同上 |
| `waterfall` | 否 | 环绕中间件 `(...args, next)`，可改写返回值、可短路 | 传话游戏 |

- **waterfall 语义（dsh 常设规则）**：调用 `next()` 执行下游；不调用直接返回 = 有意短路（否决）。**只观察/标注的监听器必须调用 next()**——日志监听器忘调会悄无声息吞掉下游默认行为。
- dsh 用 waterfall 处理协作决策：`agent/request`（替换模型调用配置）、`approval/request`（策略代替用户作答）。

**概念 6：Effect（可逆副作用）= 整个框架的灵魂**

- 白话："用完必还"的承诺。借了定时器承诺还，接了连接承诺断；卸载时按**登记顺序逆序**全部兑现（dispose），热重载也不例外。
- 机制：`ctx.effect(executor)`——executor 加载期间运行注册资源，返回的 disposer 卸载期间运行；支持同步/异步/generator effect。
- 内置注册 API 本身已是 effect：`ctx.on()`、`ctx.plugin()`、服务注册、`ctx.tools.register()`——**很少需要手写 `ctx.effect()`**，只用于包装 Cordis 不管理的资源（定时器、连接、watcher）。
- 顺序纪律：disposer 逆序启动，但多个**异步** disposer **并发**运行（源码 `_unload()`: `Promise.all(this._disposables.clear().map(...))`）；拆除必须按序时放同一个 disposer 里依次 await。disposer 一次性（effectInertia WeakMap 防重入）。

**概念 7：Fiber（运行句柄）= 插件的"运行时身份证"**

- 白话：家具上的"插电状态指示灯"。
- 机制（五态状态机）：

```
PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                 ↘ FAILED
```

- PENDING=已声明但服务不可用；LOADING/ACTIVE=apply 运行中/完成；FAILED=apply 或配置校验抛异常（明确报错不静默跳过）；UNLOADING/DISPOSED=拆除中/完成。
- `ctx.plugin(child)` 返回 fiber；`fiber.dispose()` **递归卸载所有子插件**，等全部清理（含异步 disposer）完成才结束。

### 8.3 组合与运行时（Loader / 配置 / HMR）

- **cordis.yml = 应用说明书**：配置项 = `{ id, name, config, disabled }`；`id` 提供稳定标识区分"修改"与"先删后加"；`disabled: true` 卸载不删配置项；**组**可嵌套子列表作为单元加载/卸载，`isolate` 为组提供服务独立实例；`!!js` 表达式支持 config/disabled 运行时求值（按环境门控一行）。
- **Schema 校验（Schemastery）**：导出 `Config`（TS 接口 + 运行时 schema 同名），apply 前校验；错误配置绝不启动，`ValidationError` 给出精确路径（`$.targets expected array but got not-an-array (at targets)`）。
- **HMR 热模块替换**：卸载回卷 effect + 加载遵循依赖 → 先卸后载替换运行中插件；编辑 cordis.yml 本身也触发（按 id 只动变化部分）；**不带 id 的配置项每次读取获新 id，文件任何编辑都会"先删后加"重新挂载**。

|---|---|---|

> Parnas 告诉我们"把每个设计决策藏在一个模块后面"；微内核告诉我们"核心只留最小必要，其余全部外挂"；Saga/可逆计算告诉我们"每个副作用都必须有补偿"；Fowler 告诉我们"消费接口、不消费实现"。Cordis 是把这四句话工程化成一个 25KB 级运行时。

### 8.5 dsh 如何在 Cordis 之上构建（把概念串起来）

| dsh 现象 | Cordis 机制 |
|---|---|
| 插件树：`cordis.yml` 装配 | Loader + 配置项列表（profile/bundle/patch 三层都是配置覆盖层） |
| 工具注册表 `ctx.tools` | Service + 注册即 effect（卸载自动注销工具） |
| 工具流水线五道闸（pre-execute → 单调守卫 → 审批 → execute → fs 写门 → post-execute → finalize → result） | 一系列 `tools/*` 事件用 waterfall/serial 串联；post-execute 四态（accept/block/replace/add-context）= waterfall 监听器决策结果 |
| 会话日志"模型可见即已记录" | 事件流（Session Events 持久事实）+ append-only 日志，模型历史从事件流投影（`deriveMessages()`） |
| 事件三域（Session/Agent/Capability） | 事件系统分层约定：持久事实 / 实时控制 / 附加策略适配器 |
| 热重载、插件即改即生效 | HMR 插件（卸载回卷 effect → 新代码加载） |
| 审批缺人应答 = 拒绝 | `approval/request` waterfall：策略监听器可代替用户作答 |
| 上下文压力管理（先剪枝工具结果再摘要） | 监听 `pre-step`/`step/end` 事件的策略插件 |

**dsh 对 Cordis 的纪律性要求**（来自 cordis 插件开发 Skill，对开发组同样有参考价值）：

1. **先查真实接口再写代码**——用 inspect 类工具读运行时注册表，禁止从示例/记忆推断 API。
2. **每个注册必须能撤销**：`ctx.on`/`ctx.effect`/注册表 disposer；**禁止在模块顶层（apply 外）创建进程级/页面级副作用**。
3. **waterfall 监听器必须调用 `next()`**，除非有意短路。
4. **可选能力用 `ctx.get()` 探测**，硬依赖才 `inject`，不滥用。
5. **内部活数据不外泄**：不 JSON.stringify 服务实例/事件载荷，只取所需叶子字段。
6. **版本语义**：Plugin（稳定身份）/Package（不可变代码版本）/Run（每次激活实例）三层分离，失败修复 = 定义新 Package 而非覆盖旧版本。

### 8.6 对情绪地图开发组的启示（对照上文第三、四部分）

1. **能力接缝 = Service + 契约单一源**：学习报告第 2、3 步的"Tool Contracts + MCP 7 工具"本质是 Service 模式（按名查找、实现可替换）。情绪地图已有 `ai_qa/tool_contracts.py` 契约单一权威源，与 Cordis"服务名扁平命名空间 + 声明合并类型"同构。启示：MCP 工具面 v1 若立项，服务命名空间应预先规划（如 `em.*` 前缀），避免与通用名冲突。
2. **守卫流水线 = waterfall 事件链（机制而非自觉）**：学习报告第 5 步"post-execute 守卫管线（脱敏→口径→白名单）"在 Cordis 里就是一条 waterfall 链，每个守卫是一个监听器，`block` = 不调用 next 直接返回（短路）。关键纪律迁移：**观察型守卫（日志/审计）必须放行**，绝不吞掉下游。审批语义迁移：缺人应答 = 拒绝（对应 `approval/request`）。
3. **可重放日志 = 事件流**：学习报告第 6 步对应 Cordis"Session Events 持久事实 + 从事件流投影"。启示：EMC 对话审计可按事件流设计——每个环节发事件、事件落盘、答案从事件投影，比记一条 JSON 日志更可回放、可派生（eval/回放/统计同源）。
4. **插件需求卡 = 插件契约**：学习报告第 4.1 节"插件需求卡"在 Cordis 语境里就是插件元数据契约：`inject`（依赖哪些服务）、`Config` schema（输入校验）、`output`（制式输出）。启示：dsh 生成插件时若能先读到"数据集注册表 + 工具契约 + 安全规则"，就能像 Cordis 插件一样"声明依赖、由运行时保证就绪"。
5. **风险提示**：① Cordis 是 TS 生态，情绪地图是 Python 栈——**借鉴机制思想（Service/事件/effect/守卫链），不引运行时**；② 可逆副作用有学习成本（disposer 逆序+异步并发+单次调用），Python 侧可用 `contextlib.ExitStack` 近似封装；③ waterfall 短路是双刃剑——若 EMC 守卫管线采用，必须把"观察者必须放行"写成硬规则+测试。

## 九、更新结论与讨论发起（2026-08-19 追加）

### 9.1 结论更新

1. **Cordis = 可逆插件系统**：Context 装服务、Plugin 带能力、Service 做接缝、inject 管依赖、Event 解耦通信、Effect 保证可撤销、Fiber 管生命周期——七个概念合成一个"无特权内核"。
2. **有明确的学术谱系**：Parnas 信息隐藏（模块化）、微内核（最小核心）、Fowler DI（接口消费）、Saga/可逆计算（补偿）、责任链（守卫链）——不是新发明，是经典思想的现代工程化。
3. **对情绪地图的价值**：上文第三、四部分提出的"能力接缝/守卫管线/可重放日志/插件需求卡"四个借鉴点在 Cordis 里都有成熟对应物，可直接映射为设计语言；但**只借思想、不引运行时**（Python 栈）。
