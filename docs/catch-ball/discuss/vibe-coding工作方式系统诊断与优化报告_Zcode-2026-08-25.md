# Vibe Coding 工作方式系统诊断与优化报告（Zcode · 2026-08-25）

> **性质**：受用户直接委托的元评估——对「本人 + 多 AI 协作」的 vibe coding 工作方式进行系统性诊断（降 token 消耗 + 优化工作体系两大目标）。纯讨论件，零实现零 git。证据全部来自本仓实测（文件清点、git 历史、CB 档案抽样），非印象流。
> **写法约定**：面向非技术背景读者；术语首次出现附白话解释；内部编号首次出现附业务名称；收益数字凡属估算均标注口径。

---

## 白话摘要

把你的项目比作一家工厂：**程序代码约 12 万行，而给各路 AI 互相传阅的「会议纪要」（流程文档）已有约 11.5 万行、855 份——纪要快比产品本身还厚了**。每来一个 AI 帮手，它开工前都要先读完一大摞纪要（规矩手册 + 进度索引 + 交接卡 + 记忆卡），光「读纪要」估计就占每次开工成本的三到五成；而且纪要有 9 个版本互相打架——主入口那份停在 4 天前，还写着已经作废的旧工作副本名字。帮手读错纪要就会干错活，干错就要返工，返工最烧钱。另外，**一个话题平均要写 5 份以上文件**（草稿、回应、再回应、收敛、定稿），其中不少是 AI 之间的礼貌性互评。

诊断结论一句话：**你的方向和底子是对的（自动测试把关、任务书先行、踩坑规则库，这三样是专业团队水准），但「制衡过度、记忆多头、文档只增不减」让 token 大量烧在仪式而不是产出上**。按本报告 11 条建议改造，估算总开销可降三到五成：开工读纪要的成本减半以上、AI 互评文书减半、过期信息导致的返工基本消除。先做前两条（单一状态源 + 规矩手册瘦身），两周内即可见效，且零代码风险。

## 一、现状诊断

### 1.1 先说做对的（这些是资产，改造时必须保留）

你的工作方式已经远超「随便聊着让 AI 写代码」的原始 vibe coding，以下是实测确认的亮点：

| 做法 | 业界对应 | 实测证据 |
|---|---|---|
| 测试门禁全绿才收工 | 持续集成（CI：每次改动自动跑全套检查） | 门禁 613 件测试每批必跑、基线递进有记录 |
| 任务书先行、验收标准写在做之前 | 规格驱动开发（spec-driven） | 交互三机制定稿（编号 PT-CB16-D1）含验收口径与依赖表，随后 C2 实施批一次跑通 |
| 踩坑规则库 | 复盘制度（post-mortem 蒸馏为规则） | debug-memory 30 条规则（如 R2「空值静默丢数据」），有真实拦截案例 |
| 进度表由数据文件自动生成 | 单一事实源 + 生成式文档（不手写易过期的汇总） | docs/progress.md 由 _board.yaml 经脚本确定性生成 |
| 接口锁 / 契约冻结 | 契约优先（contract-first） | rag_query 变更走「新键并存过渡」的版本化路径 |

**问题不在方向，在剂量**：下面这些坑，多数是把好东西用过量的结果。

### 1.2 坑与误区清单（按烧钱严重度排序，每条附实测证据与后果）

#### 坑 1【最重】开工阅读税：每次会话开场 2~4 万 token 花在「读规矩读状态」

- **现象**：规矩手册（AGENTS.md）309 行 / 2.4 万字节，每次会话开场被**全量自动注入**；其中 9 个 Agent 花名册、模块编号全表等内容，按你们自己的结论（CB-02 讨论 1）「不描述实际运行方式、实际由主线程直接干」，却仍占正文篇幅。此外还叠加多条「启动必读」义务：CB 索引（1.2 万字节）、「涉及某线必读 736 行权威报告」「排查前必读规则库」等。
- **术语**：token 是 AI 的计费单位，约 1 个汉字 ≈ 1 个 token；上下文窗口是 AI 一次对话能装下的全部内容，像桌面大小，放满了旧纸就放不下新活。
- **后果**：干活的指令往往只有一句话，却要先付 2~4 万 token 的「入场费」。以汉字估算，这相当于每次开工先让 AI 读完一部 3 万字的中篇小说梗概。按每天 5~10 个会话算，仅入场费一项每月可达数百万 token。

#### 坑 2【最重】状态记忆 9 头并存、互相矛盾，且已实际造成误判返工

- **现象**：同一份「项目当前状态」分散在至少 9 个载体：CB 索引、CB 台账（cb-journal.md，2523 行）、workspace 记忆（MEMORY.md）、每日记忆、会话交接卡（session-handoff.md）、家/办公室交接卡（HOME/OFFICE）、目标状态表（goal-status.md）、进度表、看板数据（_board.yaml）。
- **实测证据（过期实锤）**：CB 索引自称「启动必读入口」，最后更新停在 08-21，其「当前分支」仍写已合并删除的旧分支名；而 workspace 记忆 08-24 已改为新分支名。两者矛盾 4 天无人修。另有当日实录：Kimi 曾据当前代码「差点误判 Qoder 报告失实」，靠 git 历史考古（git log -S）才还原「报告在先、修复在后」。
- **后果**：每个新会话要先花 token 调和矛盾信息；调和失败 = 基于错误事实干活 = 返工。返工是最贵的 token 消耗，因为它把「写、跑、验」全部重来一遍。

#### 坑 3【重】一事多档：一个话题 5+ 份文件，阅读量按乘法增长

- **现象**：标准流程产出：讨论稿 → 回应 → 二轮回应 → 收敛 → 定稿 → 派发 prompt → 通俗版，同一话题最多 7 份文件。历史极端案例：CB-22 一个话题 20+ 份文件。实测单日（08-25）落盘约 10 份讨论文档。讨论目录累计 643 份 / 7.9 万行。
- **后果**：收敛者要通读全部前文才能拍板——阅读成本 = 份数 × 单份长度，按乘法涨；「白话版 + 专业版」双写让同一内容写 2~4 遍；档案总量膨胀后，谁也读不完，反而更依赖口口相传（进一步加重坑 2）。

#### 坑 4【中】跨 AI 评审链不分风险等级，回应义务摊给全组

- **现象**：评估（SCAN）→ 反评价 → 收敛 → 审计 → 复验全套链条；「学习报告必讨论必落盘、无回应不收敛」把回应义务摊给所有组，不论该报告与自己是否相关。
- **后果**：大量 token 花在 AI 互评的礼节性文书上（「全部同意 + 复述一遍」类回应占比不低）。真正改变结论的高价值评审（如 Qoder 在交互三机制讨论中挑出的「零件装在旧引擎上」断层）被淹没在同权重的低价值回应里——**评审没有分级，等于把稀缺的 token 均摊给了不值得的件**。

#### 坑 5【中】内部编号考古：自家铁律「禁裸用内部编号」被自家体系系统性违反

- **现象**：规矩手册明文「禁裸用内部编号（如 G10、B1、P3）」，但 CB 索引的「最新讨论」栏、commit 信息、文档标题本身就是 PT-CB8/PT-CB16/C2-1/G4/B013/R17 的连续裸编号串。用户本人 08-25 反馈「看不懂」后新增了「裁决点白话义务」——症状已出现，但只给裁决点打了补丁，没有治理根源。
- **后果**：每个新会话（以及用户本人）都要做「编号考古」——顺着编号去读 2~3 份文档才能知道在说什么；每新增一条「必须附白话」的补丁规则，又进一步加重坑 1 的入场费。

#### 坑 6【中】马拉松会话 + 上下文摘要衰减，越到后段错误率越高

- **现象**：单日实录（08-25）：复核他组根因报告 → 评价第三方报告 → 自做根因分析 → 改版 v1.1 → 执行九件修复 → 写汇总报告 → 审计收尾 → 写下批计划 → 实施两件 → 收敛定稿 → 再实施一批——11 件大事压在连续会话里。
- **实测证据**：当日出现「验证脚本字段名假设错误，第三次全字段扫描才翻案」——这正是长会话后段细节丢失、模型凭摘要而非原文干活的典型症状（且你们自己的规则库 R8「验证忌与实现同构」踩中同类根因）。
- **后果**：长会话后期一次误判 = 三轮返工；而返工发生在会话最深处时，纠错还要再读一遍全部上下文。

#### 坑 7【中长期最贵】规则只增不减，单调膨胀

- **现象**：规矩手册 v2.0→v2.5，每条用户令都固化成全局永久条款（白话摘要硬条款、派发 prompt 义务、当轮回应义务、双环境差异适配五条……）；规则库 30 条且「排查前必读」。**没有任何一条规则被降级或退休过**；规则之间已出现打架（禁裸编号 vs 全系统裸编号运行）。
- **后果**：入场费持续上涨（复利式）；AI 每次都要在脑内调和冲突规则——调和本身也耗 token 且可能调错。今天坑 1 的 2~4 万，半年后就是 4~8 万。

#### 坑 8【轻】同一内容最多写四遍

- **现象**：专业版正文 + 白话摘要 + 派发 prompt + 通俗收工报告，四个载体大量重叠。
- **后果**：写作 token 翻倍以上；四份载体日后还会分别过期、分别需要维护（回到坑 2）。

#### 坑 9【轻】门禁计数「613+1」中的「+1」语义不明

- **现象**：多批 commit 均记录「门禁 600+1 / 602+1 / 607+1 / 613+1 零失败」。若「+1」是长期已知失败/跳过的用例，它每天都要被所有读记录的人重新解读一次。
- **后果**：小，但属于「每次都付一点」的慢性损耗，且侵蚀门禁信号的纯净度（全绿才有威慑力）。

### 1.3 后果链总览（钱烧在哪）

```
入场费（每次会话读规矩+状态）        ← 坑1/2/5/7   估 25%~40% 总消耗
评审文书（AI 互评 + 一事多档读写）    ← 坑3/4/8     估 20%~30% 总消耗
返工（过期信息误判 + 长会话衰减）     ← 坑2/6       估 10%~20% 总消耗（单次最贵）
有效产出（写码/测试/真评审）          ←             上述压缩后自然提升
```

> 口径说明：以上比例为基于文本量（本报告 1.2 节实测数字）与典型 token 换算的**估算**，非计量实测。建议落地时按第五章的验证法实测校准。

## 二、根因分析

三个层面，按影响权重排序。**结论先行：提示词不是主要问题；一半以上是机制问题。**

### 2.1 机制层（约 50%，最深，决定另外两层的表现）

| 根因 | 表现 | 对应坑 |
|---|---|---|
| **无单一状态源**：状态手写在 9 处，而手写必然过期 | 索引停在 4 天前、分支名矛盾 | 坑 2 |
| **知识按「档案」组织而非按「查询」组织**：115k 行历史只能通读，不能检索 | 每次用历史都要全文重读 | 坑 1/3 |
| **规则无预算、无退休机制**：只进不出 | 手册单调膨胀、规则打架 | 坑 7 |
| **无上下文成本意识**：没有「这次会话该带多少背景」的纪律 | 全量注入 + 全量必读 + 马拉松会话 | 坑 1/6 |

### 2.2 流程层（约 35%）

| 根因 | 表现 | 对应坑 |
|---|---|---|
| **制衡不分级**：为「大团队互不信任」设计的重型评审链，套在「一人主控 + AI 执行」的实际结构上 | 任何件都可能走五段评审；回应义务全摊 | 坑 4 |
| **档案即沟通**：AI 之间靠「写文件给对方读」交流，而不是共享一个文件原地追加 | 一事 5+ 档 | 坑 3 |
| **双写文化**：为可读性把内容写多遍，而非写一遍+分层呈现 | 四载体重叠 | 坑 8 |

### 2.3 提示词层（约 15%，次要）

| 根因 | 表现 | 对应坑 |
|---|---|---|
| **文档即上下文的派发方式**：把 700 行整报告塞给另一个 AI 从头读，而非「路径 + 三行背景 + 任务动词」 | 派发 prompt 越写越长 | 坑 3 |
| **为合规而写的段落**：AI 生成的文档里有大量「复述对方观点以示已读」的段落（评审礼节） | 回应文档虚胖 | 坑 4 |

**需要说破的一点**：用户本人的单句指令（「用户令」类）质量并不差——短、决断、带时间戳，这恰是高级用法。**真正的问题不在「你怎么跟 AI 说话」，而在「你为 AI 搭的记忆与制衡系统长什么样」**。所以优化重心不在教用户写提示词，而在改造系统。

## 三、优化建议（11 条，按落地优先级排序）

> 每条含：做法 / 为什么有效 / 预期收益（标注估算口径）。收益百分比为对「该条所涉环节」的估计，非全局。

### 建议 1 · 单一状态源：把「项目当前状态」变成机器生成（两周内第一件）

- **做法**：扩展现有的看板数据（_board.yaml）+ 生成脚本（gen_progress.py）——你们已经用这套生成进度表了，只需扩为生成一份 **STATE.md（≤60 行）**，固定五栏：当前分支 / 在途批次（每批一行） / 待用户拍板项 / 门禁基线 / 最近 5 条提交。CB 索引中手写的「当前状态」表整体退役，索引退化为纯历史导览。**规则：状态类信息只准住在 STATE.md，任何手写状态字段到期即删。**
- **为什么**：生成式文档不会过期（每次从数据重新算）；9 处手写状态合并为 1 处机器状态。
- **收益**：开场对齐成本省 50%~70%（估算：以 CB 索引 12KB + 记忆卡 + 交接卡的读取量对照 60 行）；分支矛盾类误判返工基本归零（可验证：矛盾字段数 9 处 → 0）。

### 建议 2 · 规矩手册瘦身到 ≤150 行：把「参考书」从「口袋守则」里搬出去（两周内第二件）

- **做法**：AGENTS.md 只保留四类内容：沟通纪律、编码铁律、当前有效流程指针、状态指针。移出（各存为独立参考文件、按需链接）：9-Agent 花名册（你们自己已判定不描述实际）、模块编号全表、知识源全表、SOP 分级详表、历史沿革注记。手册顶部写明「参考库清单 + 何时读哪个」。
- **为什么**：业界共识（含 Anthropic 对 CLAUDE.md 的官方建议）：常驻指令文件应短，细节按需加载（渐进式披露，progressive disclosure——像抽屉柜，常用的放手边，不常用的进抽屉）。
- **收益**：每次会话注入省 8k~12k token（估算：309 行 → 150 行，含移出的 9-Agent 表与编号表）；且规则少了，AI 遵守率反而升（指令越短越被当真）。

### 建议 3 · 一事一档、原地收敛：一个话题一个文件

- **做法**：讨论稿落盘后，各组的回应以「§回应（组名·日期）」小节**追加进同一文件**；收敛人就地把正文改写为定稿（文件头留 3 行变更记录：谁、何时、改了什么）。不再新开「回应 / 二轮 / 收敛 / 定稿」分件。派发 prompt 若必要，作为该文件末尾一节，不再单独立档。
- **为什么**：收敛者读一份文件即得全史；档案数不随轮次爆炸；git diff 天然留痕，无需靠分文件存证。
- **收益**：单话题文档数 5+ → 1（可验证）；收敛者阅读量降约 60%（估算）；新会话考古成本同步下降。

### 建议 4 · 评审分级：三个风险档，只有最高档走全套制衡

- **做法**：任务书落盘时同步标档：
  - **高档**（核心数据管道 / 接口变更 / 口径变更）→ 保留完整链条：独立评审 + 收敛 + 审计复验；
  - **中档**（一般功能 / 多文件改动）→ 一轮独立复核（另一组只读代码与测试结果，不写全套文书，产出限 20 行意见）；
  - **低档**（文档 / 样式 / 单点修复）→ 只跑门禁，零跨组文书。
  同时把「学习报告当轮全组必回」改为「**月度批量回应**」（每月一次集中回应上月全部学习报告）。
- **为什么**：制衡的价值密度随风险递减；把 token 集中给高档件（如 Qoder 挑出引擎断层那种评审，一次就值回全部成本）。
- **收益**：跨 AI 评论文书量估降 40%~60%；高档件的评审资源（注意力）不减反增。

### 建议 5 · 派发 prompt 定长模板：背景三行、材料给路径不给正文

- **做法**：所有跨组派发用统一模板（可做成脚本脚手架）：
  ```
  背景：≤3 行（只写对方不知道的）
  材料：1~2 个文件路径（共享 git 仓库内，禁止粘贴正文）
  任务：动词开头，一句话
  验收：≤5 条，可判真伪
  输出：落盘路径 + 篇幅上限（如 ≤80 行）
  ```
- **为什么**：材料在同仓，对方自己会读；贴正文 = 同一内容双份 token。验收条目前置 = 一次命中率的最大杠杆（你们 C2 批已实证：定稿带验收，一次跑通）。
- **收益**：澄清与返工轮次估降 30%+；派发件本身瘦身 50%+。

### 建议 6 · 编号带名 + 机器生成术语表

- **做法**：①文档与 commit 标题强制「业务名（编号）」格式；②写个小脚本从全部文档标题抽取「编号 → 业务名」对照表，生成 GLOSSARY.md（≤100 行），随 STATE.md 一起生成；新会话遇到裸编号先查表，不考古。
- **收益**：编号考古成本趋零；用户可读性直接改善（「看不懂」反馈的根治，替代逐条打白话补丁）。

### 建议 7 · 会话切分纪律：一会话一族事

- **做法**：写进规矩手册三条：①一个会话只做同一族的 3~4 件事；②跨主题（如「修 bug」跳「定规范」）必须开新会话；③新会话开场只读 STATE.md + 本次任务书，不读历史档案（要历史走建议 8 的查询）。赶进度的冲动用「批内串行、批间新会话」消化。
- **为什么**：上下文摘要衰减是长会话返工的根因（1.2 节坑 6 实证）；切小会话让每次都在「桌面上只有相关文件」的状态下干活。
- **收益**：马拉松后段误判类返工估省 10%~20%（按 08-25「第三次才翻案」类事件频率估算）。

### 建议 8 · 用自家 RAG 吃自家档案：历史从「负债」变「资产」

- **做法**：你们已有完整 RAG 工具链（索引构建脚本 + 375 chunk 语料经验）。把讨论归档目录（discuss/archive，约数万行）纳入同一索引；各 AI 会话需要历史结论时**查询**（如「历史上谁裁过 130 vs 193 口径」），不再通读索引和台账。
- **为什么**：115k 行档案的正确打开方式是查询而非阅读；这套能力你们已经建好了，只是没喂自己的料。
- **收益**：单次历史检索从万级 token 降为千级（估算，按典型 RAG 检索 top-5 chunk 对照通读台账节选）。

### 建议 9 · 规则预算与除草：规矩手册设上限，定期降级死规则

- **做法**：①手册硬上限 200 行（含留白）；新规则入册必须同时挤掉或合并等量旧规则——写不出「替换谁」就不得入册，改为落参考文件；②每 10 批做一次「除草」：引用次数为零的规则降级到参考文件存档；③规则库（debug-memory）保留但改读取方式：不「排查前全读」，改为「按症状关键词索引读相关 2~3 条」（R 编号 + 一句症状即可索引）。
- **收益**：入场费停止复利上涨（这条的收益是「省未来的钱」，最容易忽略也最值钱）。

### 建议 10 · 白话摘要定长模板：3~5 句，一段写完

- **做法**：白话摘要固定三句式——「比喻一句 + 关键数字一句 + 建议一句」，上限 150 字；专业正文唯一。裁决点白话表（选 A 会怎样 / 选 B 会怎样 / 我建议哪个）**保留**——那是用户真实需要的决策界面。通俗收工报告与白话摘要合并为一个载体，不再两份。
- **收益**：双写减半（坑 8）；用户阅读提速；AI 写作模板化后更稳定。

### 建议 11 · 门禁「+1」显式化（顺手件）

- **做法**：若「+1」为长期已知失败/跳过用例，在测试代码中显式标记（业界标准做法是 xfail 并注原因一行）；commit 记录从此只写「门禁 N 件全绿」。若另有含义（如跳过），在 STATE.md 固定一行解释。
- **收益**：小；但让「全绿」恢复一票否决的威慑力，每次读门禁记录省一次解读。

## 四、改进后的工作架构

### 4.1 上下文金字塔（四层，每层有明确的进入方式与体量上限）

```
第1层 常驻层   AGENTS.md 精简版（≤150行）        每次会话自动注入
              只有：沟通纪律 + 编码铁律 + 指针
第2层 状态层   STATE.md（≤60行·机器生成）         每次会话开场必读（唯一状态源）
              分支 / 在途批次 / 待拍板项 / 门禁基线 / 最近提交
第3层 参考层   规范细则 / 编号术语表 / 规则库分条    按需链接读取（不常驻）
第4层 档案层   CB 历史全档（11.5万行）            只查不读（RAG 检索 / 按文件精读）
```

对比现状的变化：第 1 层从 309 行减半并删掉已失效内容；第 2 层从 9 处手写合并为 1 处生成；第 4 层从「必读索引 + 台账」改为「查询」。

### 4.2 单批次工作流（改进后）

```
① 任务书（≤40行：背景/目标/验收/边界/依赖/风险档位）
      ↓ 风险档位在此确定 → 决定 ④ 走哪级评审
② 实施（单会话单族事；门禁全绿是硬条件）
      ↓
③ 落盘（一事一档：执行记录追加进任务书同文件）
      ↓
④ 评审（按档：高档全套制衡 / 中档20行复核意见 / 低档零文书）
      ↓
⑤ 收敛（高档件就地收敛 + 裁决点白话表；用户拍板）
      ↓
⑥ 收尾（STATE.md 自动再生成；有新踩坑才蒸馏规则；commit 用「业务名（编号）」标题）
```

### 4.3 角色与义务（简化后）

| 角色 | 何时在场 | 义务变化 |
|---|---|---|
| 用户 | 拍板裁决点 + 验收 | 不变（拍板件由 STATE.md「待拍板」栏统一呈现，不再散落各文档） |
| 主开发（当批一主） | 每批 | 任务书 + 实施 + 执行记录，一事一档 |
| 评审组 | 仅高档/中档 | 意见限 20 行追加进同文件；不再写独立回应文书 |
| 学习线 | 月度批量 | 集中回应，不再当轮全摊 |

### 4.4 与现有资产的衔接（不推翻、只接驳）

- 看板数据 + 生成脚本 → 升格为 STATE.md 生成器（建议 1）；
- 讨论归档目录 + RAG 工具链 → 自家档案检索（建议 8）；
- 规则库 R1~R30 → 原文不动，只改读取方式为索引式（建议 9）；
- 测试门禁、任务书模板、接口锁 → 原样保留，是这套体系的承重墙。
