#### micro 需求位置升级（:329-340）— partial

| 条件 | 处理 | 判定 |
|------|------|:---:|
| source=`poi_sjoin` | value 不动·source 补注精确 | ✅ |
| 有 poi_names | value 升级为首个 POI | ✅ 方向正确 |

**发现 W-A（建议级·glm 未报）— source 文案自相矛盾**：`build_outlet_schema.py:334-339`

```python
_first_poi = str(_pois).split('、')[0].strip()
_loc['value'] = _first_poi if _first_poi else _loc.get('value', '')
_loc['source'] = 'place_name（POI 落点·poi_names 首个·精确）' + (f'｜面域代表名兜底 {_loc.get("value", "")}' if _loc.get('value') else '')
```

`_loc['value']` 已被赋值为 `_first_poi` 后才构造 source → 「面域代表名兜底」显示的是**升级后的 POI 名**而非原面域名。正常升级路径下卡片 source 变成「POI 落点·poi_names 首个·精确｜面域代表名兜底 滨江公园」——同一字段既标"精确 POI 落点"又标"面域代表名兜底"，文案自相矛盾，违背 P3-4"诚实标注"初衷。**修法（约 1 行）**：先缓存原值 `_orig = _loc.get('value', '')`，source 用 `_orig`；或直接删掉兜底段（value 已是 POI 名时无需再标面域兜底）。现有测试（`test_p3_4_micro_polygon_upgrade_to_poi`）只断言 `'POI 落点' in source`，未覆盖此矛盾。

**发现 W-B（建议级·glm 事实错误更正）— poi_names「首个」无排序依据**：glm 回应称"poi_names 首个 = 最近/最高频 POI"。代码核实：`core/spatial_analysis.py:685-694` `_names` 按 `_recs`（sjoin 输出序）顺序去重追加，`_top = _names[:5]`——**无距离/频次排序**。唯一按距离排序的是 grid 模式 place_name（`:697-702` `min(_recs, key=geometry.distance)`），与 poi_names 列表无关。因此 micro 升级选中的"首个 POI"取决于 POI 数据源顺序，不一定是最有代表性/最近的 POI。风险：需求位置升级到真实但次优的 POI（如面域内数据序第 1 的"公共厕所"而非标志性建筑）。**建议**：① polygon 模式下升级选择改为有依据排序（如与面域质心距离最近 / poi_count 最高），或 ② source 措辞从「精确」降为「精确到 POI 名（列表序首个）」避免暗示代表性。非阻断（value 仍是格内真实 POI·非编造·优于边界名）。
