## 一、用户三点质疑（保留原意）

**质疑 1（核心分歧·与我上轮相反）**：
> "恰恰相反。如果非要给 EMC 加思考能力，也只能是基于现有规则的最粗问题类型判断（宏观/微观/分析/纯问答）。**具体怎么分析、决定用哪些工具、出什么颗粒度的答案，都要交给更聪明灵活的 MCP 宿主**，再回到 EMC 的标准化接口执行，最终形成 EMC 制式化的分析图与回答范式。如果按 zcode 说的'EMC 用确定性规则决定工具与路由'，又陷入无尽思维 loop 和分叉——个人开发者无力承担。**EMC 就不应该有任何思考能力，它只是'需求契约'的壳子，本质是一大堆契约的集合体**。"

**质疑 2（契约形态）**：
> "契约分类型：意图理解类、方法论类、工具调用类、回答范式类等——把我之前在 EMC'出口'中指定的范式、规则**契约化**，发挥宿主灵活性，针对契约形成结果。"

**质疑 3（拆解方向）**：
> "将现有的意图理解 Agent、结果范式 Agent 等全部拆解成'契约'。"

## 二、zcode 回应

### 2.1 总立场：接受修正——用户方案比 zcode 上轮收敛更正确

zcode 上轮 N2 写的是"LLM 只做转译，范式路由留在 EMC 确定性执行"。用户指出这正是**保留了路由智能**——而路由（怎么分析/用哪些工具组合/什么颗粒度）是开放决策空间，是 ai_qa 历史 bug 的温床（diagnose→select_template→ReAct 链上的衔接分类器、排序 fallback 链等都是 planner 复杂度的实证），个人开发者确实养不起。

**三个承认**：
1. **MCP 生态哲学本就如此**：宿主（dsh/Claude Code/Codex）的核心能力就是"读工具描述→规划调用组合"。server 的职责是提供描述性契约（tools/prompts/resources），不是内置 planner。zcode 上轮的"确定性路由保留"实为再造内部 planner，与 MCP 哲学相悖；
2. **成本论证成立**：守卫（有限、封闭、可枚举的校验规则）个人开发者养得起；路由（开放决策分叉）养不起。**该保留的是验证，不是决策**；
3. **范式知识的正确形态是"说明书"不是"执行体"**：paradigm.py 的领域知识（尺度→工具→颗粒度对应）不丢，但形态从"代码里执行的路由逻辑"转为"方法论契约里的推荐路径"——供宿主参考执行 + 供出口验证引用。

### 2.2 技术性补充（在同意用户方向上画三条边界，供 dsh 评价）

- **B1 "零思考"的精确定义**：零**开放决策**（无思维 loop/分叉），保留**有限校验**（封闭规则集：参数 schema 校验、用途守卫、口径标签检查）。守卫不是思考——它是契约的机器执行体。"壳子"= 契约集合 + Dumb 工具集 + 守卫验证器，三者都无决策分叉。
- **B2 制式化输出器保留**：最终"分析图/回答范式"的**模板填充与组装**（出口卡三段式等确定性拼装）留在 EMC——填充模板不是思考，是制式化（这正是"EMC 制式化"的价值所在：宿主灵活分析，出口统一制式）。
- **B3 质量下限护栏**：路由全外置后，输出质量下限依赖宿主 planner 水平。护栏两层：方法论契约写"推荐路径"（弱约束·引导）+ 出口验证（强约束·不合规打回）。若两层仍不够，是否需要"最粗分流器"（如 知识问答 vs 空间分析的基础设施级指示牌）——**开放问题，请 dsh 评价**。

### 2.3 契约四分类的对照（用户质疑 2 → zcode 映射）

| 用户分类 | EMC 现状对应 | 形态 |
|---|---|---|
| 工具调用类 | `tool_contracts.py`（已有·单一权威源） | 保持 |
| 意图理解类 | 意图卡 schema（上轮新增设想） | 描述"好的意图理解长什么样"·供宿主参考+验证 |
| 方法论类 | `paradigm.py` 知识**转译**（路由执行逻辑退役） | 新形态：推荐路径说明书 |
| 回答范式类 | 出口卡三段式/结论结构（CB-18 已有雏形） | 契约化+制式化输出器执行 |

### 2.4 拆解方向（用户质疑 3）

现有 Agent → 契约的拆解映射：意图 Agent → 意图理解类契约（外置）；结果范式 Agent → 回答范式类契约 + 确定性模板组装（B2 保留）；中间 ReAct 循环 → 宿主天然自带（不再自研）。**过渡次序沿用上轮 N3 四步**（冻结→建成→切换→拆旧），拆解目标从"退役"改为"转译成契约"。
