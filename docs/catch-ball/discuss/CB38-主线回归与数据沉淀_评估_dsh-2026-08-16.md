### F2 RAG 数据层级设计

- **分库 vs 单库：单库 + domain 标签（meta 字段），物理源目录可分域**。理由三条：① 跨域问题是常态（「西峡社区的更新项目有哪些」= 体检域问题 × 更新域项目），分库会把跨域问答切开；② 295 条 → 加体检域后 ~400-500 条，远未到分库的性能阈值；③ 现有 rag_search/构建流程单库跑通，分库动的是检索内核，收益低。domain 进 meta 后，检索按 domain 过滤即可达到分库效果。
- **四类型够用，不加第五类**：新增「口径」需求用 fact 的字段扩展（加 domain + 口径注字段），类型越少越好维护。
- **「宜昌市基础数据」域：要，作为第三域共享底座**（行政区划 22 街办/174 社区/1562 小区/26426 楼栋、坐标系 WGS84 口径、中转站路径与规则）——既不属体检也不属更新，是两个域的共同语境。
- 域结构定案建议：**域1 城市体检（找问题：77项/安全/民生 + 12345 主观）· 域2 城市更新（规建营：现有 urban_renewal_knowledge + 项目库口径）· 域3 宜昌基础（共享底座）**。
- 提醒：现有 outlet_kb `urban_renewal_knowledge` fact 与新口径的归属可能有重叠（更新知识库若含体检内容），加标签时逐条核对，不做批量想当然。

### F3 大文件边界

- **同意：geojson/xlsx 一律不进 RAG，只进口径/结论/摘要**。补一条承重级理由：RAG 定位 = 本地化聚焦的专业知识蒸馏（CB-22 用户定），空间明细是图层体系（geo_registry/manifest）的职责；把空间数据塞进 RAG 会把「专业知识蒸馏」变成「数据仓库镜像」，且 BGE 512 维对坐标/表格数值的语义检索能力弱，检索质量必然掉。
- **分工契约建议写进文档**：RAG = 知识与口径（答「是什么/为什么/口径多少」）· 图层体系 = 空间与明细（答「在哪/有多少」）· EMC 按问题类型路由——这是 CB-22「分类→范式映射」的自然延伸。
- **桥接产物必须写**：每个图层一张「图层卡片」（名称/几何/字段/点数/口径/更新时点），进 RAG fact——它是 RAG 和图层体系的唯一桥，没有它，问答只会答口径、永远不知道去哪取数。

### F4 口径漂移防线

- 同意需要防线，落地四件：
  1. **入库前全量口径复核 pass**：Codex 出「数字→最新口径→来源文件」对账清单，程序化核验（复用 `_tmp_audit_cb35_page7.py` 审计方法论）。
  2. **素材头部「现行口径」标记规范**：fact/note 头部固定字段（现行口径值/适用时点/口径链/来源文件+行号）。
  3. **作废数字纪律**：「5,615」「87.9%」「港务 1,153 件」等作废值**不入素材正文**，只进一条「作废数字清单」concept——检索到旧数字时能命中作废声明而非沉默（CB-22 版本口径张冠李戴的防复发机制）。
  4. **索引重建纪律**：蒸馏后 `--build` 重建 + `--stats` 核对条目数与 domain 分布；两机各建各的（家/办公室都要跑）。
- **我补的一条源纪律（最重要）**：**蒸馏源只认 DATA/analysis 最终产物，禁从 docs/catch-ball/discuss/ 讨论稿取数**——讨论稿里全是过程态数字（zcode CB-32 的 26 双高表、港务 1,153 都是旧口径），拿去蒸馏必系统性错。
