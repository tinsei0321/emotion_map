# 一、独立现状评估

## 1.0 一句话总判断

> **这个项目方向正确、骨架健康、治理密度罕见地高；当前最大的风险不在架构，而在「体验层契约缺位」与「治理成本随文档熵同步膨胀」——前者让用户测得不舒服，后者让团队跑得不轻松。**

十轮（CB1→CB10）从「契约派生」走到「全局收口」，主线清晰、每轮有裁决有证据有教训入库，门禁 442+2 全绿。就两周产出的工程成熟度而言，这是我见过治理最厚的同规模项目之一。但治理厚不等于方向免检——以下分「认同 / 质疑 / 隐患」三层给出我的诚实评估。

## 1.2 专项评估①：零思考壳子架构成立吗？

**结论：作为工程纪律成立，作为字面定义不成立——建议更名或补一条「受管默认值」契约类，否则会在语义默认值上反复翻车。**

成立的部分（判据按 CB3 自己的操作性定义）：
- 十件插座工具（list_data/rag_query/kb_facts/outlet_card/zonal_stats/buffer/rank/render_spec/render_file/emc_status）抽查均为查表/枚举/schema 校验的闭包逻辑，无 LLM 调用、无模糊匹配——壳内确实没有「不可枚举决策」。
- 守卫（usage 拒绝/scheme 词表校验/60 要素硬顶/top_n≤20）全是纯规则，且拒绝时给结构化指引（符合 D-a 纪律）。

不成立/需要补丁的部分：
1. **语义默认值就是隐性思考**。CB7 的「zonal 默认按极性指数排序而非件数」导致「最密集」问题答错——这个默认排序不是用户选的、不是宿主选的，是壳子替大家做的决策。同理：`rank(by='worst')` 的默认方向、choropleth 默认 `value_field=polarity_index`、countStops 默认反转。这些默认值每一个都是「不可枚举决策空间」被悄悄折叠成了常量。**壳子不是零思考，是把思考藏进了默认值。**
2. **方法论双写 = 思考转移到提示工程**。CB3 定稿已承认「工具描述是 planner 必读」，即真正的决策面在提示词与人设文本里。这不是缺陷，但意味着「零思考」的真实含义应精确化为：**决策权外置给宿主 + 壳内只留受管默认值与闭包校验**。
3. **修补建议**（进讨论批）：新增一类「受管默认值登记」——凡影响结论语义的默认值（排序字段/top_n/默认色带/默认方向）必须登记出处与理由，并在工具输出中回显（如 zonal_stats 输出带 `sorted_by` 字段）。成本极低（每工具加一行字段），收益是「默认值漂移」也可审计。

## 1.3 专项评估②：契约化过度还是不足？

**结论：工具/数据/渲染/口径四类契约化适度且有效；但「会话与交互」维度契约化不足——用户测试暴露的五个问题，四个半都落在没有契约覆盖的交互层。**

证据链：
- 问题 2（选择机制）、问题 4（追问机制）、问题 5（规模分级）——三件全是交互行为，目前靠人设文本和 dsh 原生工具（ask_user_question）自觉，无 schema、无出口校验。主手自己的排档意见也承认是「半成品接线补完」。
- 问题 3（色板「没修好」）——根因 R7.3 是工程问题，但「修复生效口径靠口头传达」暴露**没有版本可见性契约**（页面不知道自己跑的是哪版代码）。
- 结果呈现契约（render-contract §七）是「行为义务」文本——「凡工具可成图必出图」「图文并茂双交付」——这些是可机器校验的（工具调用序列里有没有 render_spec），但目前靠人设自觉。**这与零思考精神自相矛盾：壳内对数据敢做硬守卫，对交互却只敢做软倡议。**

不过度的判断：render-contract 十节 + C2-9/C2-10 两张登记表，量级合理。但注意 §1.4-P4 的「机制空转」风险。

## 1.4 专项评估③：入口体验离「让用户舒服地测试」还有多远？

**结论：机制层约 70%，体验层约 40%。差的三块：进度不可见、分支不可选、结论不可追（追问断链）。**

已具备的（实测证据）：
- 入口 v2（C1·Codex 已交付）：点击→注入固定文本→模型用 emc_status 轮询报进度→并行探测 8080→down 态静默拉起→ready 开系统浏览器→90s 超时恢复。这是「模型当向导」的正确形态。
- 快分析档标准任务 29.73s（<2 分钟线），/emc-ready 就绪门+快通道。
- 出图一步到位（render_file 第 9 插座·T18），「显示到地图」不再误入 Range。

缺的（用户五连问题即证据）：
1. **进度只有文本流，没有结构**。用户多步任务时看不到「进行到哪一步/还剩几步/卡在哪」——文本进度被刷走就没了。
2. **选择点不受控**。该问的时候不问（规模判断错了就一路狂奔），不该问的时候乱问（无频率上限契约）。
3. **追问断链**。followup_cue（CB-22f）建了没接线，第二轮追问等于重新理解。
4. **版本不可见**。修没修好用户无法自查（要懂 netstat+build stamp 三态核对，这对非开发用户是不可能任务）。

# 二、目标架构与体验蓝图

## 2.1 我对 U1-U24 拍板的理解（归并为五条第一性原理）

1. **资产权威归 EMC，思考权归宿主**（零思考壳子/契约四类/权威工具登记/不绕插座）；
2. **体验要可控**：规模属性（意图控思维量）+ 选择机制 + 追问机制——用户要在关键分叉点有方向盘；
3. **过程要可见**：进度可视化 + 全程记录 + 业界先例对照；
4. **工程要可续**：双环境+差异适配 + 先定稿再执行 + 一条线（控制线）；
5. **治理要进化**：CB 优化 + 学习必落盘 + Kimi 可推倒——机制本身也接受审判。

与核心思想 v1.1 的关系：**零推翻，一处增补**——把「意图层」从 v1.1 的隐含层（散落在双模档位+人设+意图卡草案里）提为显式层，因为用户五问题证明它是体验的承重墙。

## 2.3 推倒 or 不推倒：我的裁决

**不推倒。理由（非沉没成本逻辑）：**

1. 方向经过十轮真刀真枪的证伪收敛——插座考试 -67%、快分析 29.73s、用户实测 S6 通过，这些是**行为证据**，不是文档自嗨；
2. 暴露的问题（P-1~P-12）全部属于「补强」而非「方向错误」——没有任何一条指向「应该回到内部路由」或「应该放弃契约化」；
3. 推倒的真实代价：442 条门禁、57 层 manifest、12 张 K 卡、十件插座、渲染契约、R19 教训库全部重估，工期不可控，且新方案大概率在第三周重新发明这些轮子。

**但允许自己大幅修改实施计划的编排**（见 §三）：现有「A 收口 → B RAG → C 环境」的串行控制线，把体验问题（用户最痛的）排到了讨论批 D1「与 B 并行」——实际上体验实施件要等 RAG 大工程之后。我建议**插队一个小而快的「体验契约批」**，理由与代价见 §3.5。

## 2.4 蓝图落地的四个体验锚点（「让用户舒服地测试」的操作定义）

| 锚点 | 舒服的标准 | 现状差距 |

# 四、CB 机制优化方案

## 4.0 现行流程诊断（SCAN→Journal→四档裁决→审计→回收）

| 环节 | 现状 | 诊断 |
|---|---|---|
| SCAN | 七轴评分+三级扫描深度，全量阅读 | **过重**：两周项目每轮全量 SCAN 成本极高；且 PT 时代 SCAN 已演化为「事件驱动评估」（收口批/执行包评估），七轴全量评分名存实亡 |
| Journal/裁决 | 四档（吸收/并入排期/暂缓/反对）落盘回应 | **缺闭环追踪**：裁决「吸收」后进哪个批次靠人工记忆，无落点登记 |
| 审计 | 批末审计，CB10 才首用 | **缺位十年**（P-6）：且审计任务书批末才签发，审计组无法提前备检 |
| 回收 | 主手人工读记录+自由心证 | **无标准**（P-5）：抽检深度不可比，C1 出现「回收后二次收编」尾巴 |
| 状态管理 | todo.md（1008 行）+台账 R57+控制线+交接卡四处手工同步 | **多点手工维护=漂移温床**（emc_status 白名单漂移就是同类病） |

## 4.1 优化六改（按见效排序）

**改1 · 回收标准化**（§3.6 全套：回收四步+抽检清单模板+SLA）。——解决 P-5，零成本，立即生效。

**改2 · 审计前置**：审计任务书随批次任务书同步签发（不是批末补发）；审计组在批内即可抽查执行记录草稿——把「批末突击审」变「随批伴随审」。解决 P-6 的深层原因（审计不是不想做，是进场的门开在终点）。

**改3 · 用户复测点前移进任务书**：每个体验相关任务的验收标准里必写「用户复测点」（操作步骤+预期表现+通过判据），主手回收时先自查复测点再交付用户。解决 P-11（用户不再裸撞坑），代价=任务书多三行。

**改4 · SCAN 改双档制**：
- 轻档（默认）：批次销号时的 delta SCAN——只评本批改动+门禁趋势+机制使用率（见改5），半小时内完成；
- 重档（触发制）：阶段切换（A→B→C→稳定）或用户点名时做七轴全量。
解决「SCAN 过重」，同时保留阶段门的严肃性。

**改5 · 机制空转检测**（解决 P-4）：每批销号时加一项「机制健康检查」——C2-9/C2-10 登记表、待开发工具清单、followup_cue、本设计书新增的受管默认值登记——凡「建成 ≥2 批仍零使用」的机制，必须裁决：激活（找真实场景跑一笔）/改造/退役。**机制不进使用统计=机制不存在。**

**改6 · CB 生命周期脚本**（`tools/cb_lifecycle.py`·P2）：批次创建（任务书/执行记录/审计包骨架生成+编号校验）→ 状态扫描（各任务执行记录状态字段汇总一屏）→ 销号（门禁快照+台账行+进度面板 yml 更新一处完成）。解决「四处手工同步」——状态单源化（yml 为权威，md 为派生视图，与 §五同构）。**此件与契约单源化同一哲学：能派生的不手写。**

## 4.2 不建议改的

- 四档裁决不扩档（够用了，扩档=决策模糊化）；
- 文档必落盘纪律不动（聊天不留痕=不存在，这是多组异步协作的命脉）；
- 白名单制不动（越界成本已经被证明值得）。

### 派生视图②：入口插件状态卡（A+-6 落地后）

dsh 会话内多步任务的实时进度（步骤清单+当前步+卡顿时长），数据源与 yml 无关（会话内状态机），但**阶段级进度链接到 dashboard**——用户在测试时问「项目现在到哪了」，模型经插座可答（rag_query 入库 dashboard 或 emc_status 扩展返回阶段摘要·接口锁兼容=新增字段）。

### 维护纪律（进 DoD）

- yml 由主手在每批销号时更新（=销号单的一个字段，不是额外工作）；
- dashboard.md 由脚本派生，手改即被下次生成覆盖（与 contract_mirror 同哲学）；
- yml schema 由 render_status.py 校验（阶段状态枚举/milestone id 连续/awaiting_user 非空检查）——校验进 pytest 门禁，**进度视图自己也是契约，享受与 stages.js 同款的派生守卫**。

### 为什么是这个形态（而非看板工具/网页）

1. 项目一切治理载体都是「仓内 md + git 同步」，进度视图不应引入第二个系统（TAPD/Notion 类工具=双环境同步新断点）；
2. yml 单源+md 派生复用了 CB1 已验证的「派生+守卫」模式，团队零学习成本；
3. 新人 onboarding 成本从「4+4 份必读」降为「dashboard 一页 + 按需深读」（顺带解决 P-8 的一半）。

# 六、Kimi 的独立意见

> 以下各条独立于上文设计书，是我作为新加入者的个人判断。用户欢迎批评，我不客气。

**意见 1 · 这个项目最被低估的风险是「治理通胀」。** 十轮下来，每轮都在加机制：登记表、守卫、审计、交接卡、控制线、规则七、差异适配……每一条单看都对，合起来的维护成本正在指数化。证据：todo.md 1008 行、台账 R57、必读清单 4+4 份、一个收口批的挂账顺修能拆出 6+1+10+4 件。我不是建议砍治理——我是建议**给治理本身设预算**：每新增一条机制，必须回答「它替代/废止了什么」，净增机制数应趋近于零（改5 的机制空转检测就是它的执行件）。否则第三年这个项目的主要工作将是维护治理文档。

**意见 2 · 主手单点是协作上最大的技术债，且没人还。** zcode 承担判裁/规格/回收/清账/讨论主持/进度维护——十轮全景表里每一轮的关键决策都是同一个人。这不是不信任 zcode，恰恰相反：正因为他干得对，所有人（包括用户）都默认让他继续干。但执行手换了三轮（Codex→Qoder→Codex），主手从未轮换，连「主手不可用时怎么办」都没有一行字写过。建议最低成本的对冲：每批次的「任务书规格」与「回收抽检」强制留档到模板化程度（本设计书 §3.4/§3.6 已在推这个方向），让任何一个副组长级执行手能按文档代理主手 24 小时。

**意见 3 · 用户在替团队做集成测试，这是不对的分工。** 五个测试问题（色板没修好/契约弱/选择/追问/规模）全是用户在真实使用中撞出来的。R7 三形态连踩三次，每次的「验收口径」都在打补丁（重启/强刷/build stamp），但这些补丁都是给用户布置作业。A+-5（版本徽章）+ 改3（复测点前移）+ D-1（E2E 自动化）三件套落地前，用户的每次复测都在消耗他对这套系统的信任本金。我认为这比 RAG 召回率 5.9/10 更紧急——所以我把 A+ 批插队在 B 之前。

**意见 4 · 「零思考壳子」这个名字在害这个项目。** 概念本身是对的（§1.2 已论证），但名字引导了一种错误的心智模型：仿佛壳子里真的什么都没有，于是语义默认值（排序/方向/top_n）就被当作「配置」而非「决策」对待，CB7 排序事故就是这么来的。改名为「决策外置壳」并在契约体系里正式收养「受管默认值」这一类，比任何补丁都根治。——这条我预期会有争议，欢迎主手四档裁决时驳回，但请驳回时回答一个问题：zonal 默认按极性排序这件事，按现行四类契约应该登记在哪一类里？如果答不上来，这个类就缺了。

**意见 5 · 对 dsh 的依赖没有退出策略。** rc.7/rc.8 差异已经咬过一次（R14 三约束），入口插件 API（IConversation/host.openPath）是宿主私有 API，随宿主版本漂移无测试。核心思想 v1.1 说了「稳定阶段 EMC 壳吸收」，但没说「如果 dsh 明天改了 API 或停更，测试阶段怎么活」。最低成本对冲：M2 manifest 里加「宿主 API 依赖清单」（插件用到的每个 dsh API 一行）+ M3 体检加一项 API 存在性探测。半天成本，买的是「宿主翻脸」的预警能力。

**意见 6 · 我反对把 RAG 重建当作「唯一在途大工程」而独占叙事中心。** RAG 重要，但用户测试五连问里没有一个字提知识库答得不好——用户此刻的痛点在交互可控性。PT-CB9 v1.1 写得很好，我不动它；我只要求 A+ 批与它并行且不被它的收口阻塞（B-4 收口等 A+ 字段兼容性这条我已写进依赖链）。如果主手裁决 D1 不提前、A+ 不插队，我请求至少把 A+-5（版本徽章）单独摘出来立即做——它是所有件里成本最低、用户感知最强的。

**意见 7 · 一句表扬，免得以上六条显得我只看得见问题：** 这个项目的「证据文化」是真的。插座考试用轮次计数说话、审计用 diff 说话、教训用复现路径说话、连用户的拍板都编了号（U1-U24）。两周做到这个密度，说明团队值得被更锋利的批评对待——以上六条就是我的敬意。
