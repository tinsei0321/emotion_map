## 问 1：「零思考」边界——守卫算不算思考？

**双方立场**：
- 用户："EMC 就不应该有任何思考能力，它只是'需求契约'的壳子。"
- zcode B1："零**开放决策**，保留**有限校验**（封闭规则集）。守卫不是思考，是契约的机器执行体。"

**dsh 评价：双方语义等价，zcode 的表述工程上更精确；B1 边界成立。评分：用户 8/10，zcode 9/10。**

**判定标准（实现者视角给出可操作定义）**：

> **思考 = 存在不可枚举的决策空间**（同一输入可有不同输出，取决于上下文/策略/概率）。
> **校验 = 闭包规则**（同一输入恒有同一输出：查表、schema 匹配、枚举比对，可穷举、可测试、可证明）。

按此标准，守卫（参数 schema 校验、用途白名单、口径标签检查）**不是思考**——它是契约的机器执行体，同构于 dsh 工具流水线中的"单调守卫"（deny/abstain，纯规则无 LLM）。用户反对的实质是"路由智能"（开放决策分叉），zcode 保留的是"验证"（闭包规则），**两者不冲突，用户哲学正确 + zcode 工程精确**。

**但必须补一条边界警告（诚实面）**：**"校验"若引入模糊语义匹配（如 LLM 纠错、模糊意图归类），就越过边界变成半个思考。** 建议在意图卡校验设计时明确：校验器必须为纯规则（pydantic schema + 枚举 + 正则），任何模糊匹配点必须显式标注为"软校验（提示级，不阻断）"，不得悄悄升级为决策。

## 问 2：路由全外置的质量下限——两层护栏够不够？要不要最粗分流器？

**dsh 评价：两层护栏基本够（下限保障成立），但有一个真实缺口；最粗分流器：推荐加，成本极低收益明确，定位"可选优化"而非"必需"。评分：zcode B3 8.5/10。**

**实现者视角的诚实分析**：

1. **两层护栏的机制对应**（在 harness 里都有原型）：
   - 方法论契约（推荐路径）= 弱约束引导，同构于工具描述/系统提示词中的指引；
   - 出口验证 = 强约束闸门，同构于 dsh `tools/post-execute` 的 block 语义。
   两层组合是业界标准"引导 + 闸门"双轨，下限保障成立。

2. **真实缺口：打回后的反馈回路**。出口验证是"事后打回"——如果打回率过高且打回信息不可操作，宿主会反复试错（试错成本 = token + 延迟 + 体验恶化）。**护栏的充分性不取决于"能不能打回"，而取决于"打回时给不给可操作的修正指引"**（哪个口径没标？期望结论形态是什么？）。建议：出口验证的错误信息必须结构化（错误码 + 缺失项 + 修正示例），这条应写入守卫设计。

3. **最粗分流器的判断：加，但形态必须极轻**。理由：
   - 对宿主零负担：一个枚举字段（如 `em:mode ∈ {analysis, qa, outlet, ...}`）放请求头；
   - EMC 侧只做**查表分派**（按 mode 找对应的出口范式族/工具集），不做组合规划——仍是确定性闭包，不违背零决策；
   - 收益：显著降低出口验证打回率（宿主一开始就选对范式族），且**基础设施级指示牌**（dsh 的 agent-preset 里就有类似"preset 选择"机制，宿主消费无压力）。
   - 边界纪律：mode 字段**由宿主填、EMC 只校验枚举合法性**，EMC 绝不推断 mode（推断 = 思考）。

## 问 3：契约四分类完备性 + 与 MCP tools/prompts/resources 的对应

**dsh 评价：四分类覆盖"理解→规划→执行→表达"完整链路，基本完备；建议补两类附属契约。MCP 对应表如下。评分：9/10。**

| 契约类 | MCP 载体 | 理由（实现者视角） |
|---|---|---|
| 工具调用类（tool_contracts） | **tools** | 天然对应：inputSchema 从 tool_contracts 派生；宿主按 JSON Schema 严格校验调用 |
| 方法论类（paradigm 推荐路径） | **prompts 主载体** + **工具描述内嵌摘要** | prompts 按需拉取适合"说明书"；但**多数宿主对 prompts 消费不积极**——工具描述才是 planner 每次必读的，故推荐路径摘要必须内嵌工具描述（双写） |
| 回答范式类（出口卡三段式） | **prompts（结构模板）** + 关键工具 `output.schema` 内嵌 | dsh 的 defineTool 有 output.schema + render 规范，制式化输出器可直接对应；跨工具的出口卡用 prompts 更通用 |
| 意图理解类（意图卡 schema） | **prompts（引导模板，含意图卡示例）** + **resources（schema 定义）** | 意图卡既是"给模型的引导"（prompts）又是"程序化数据结构"（resources），双形态 |
| （建议补充）数据口径/数据集注册表 | **resources** | 大块只读知识（数据集 schema/caliber 语义/landuse 表），宿主按需读取，不进自动上下文 |
| （建议补充）安全/权限规则 | **工具 security 字段**（并入工具契约） | dsh 实践：读权限/PII 过滤写进工具契约的 security 声明，宿主与守卫共用 |

**完备性结论**：四分类 + 两补充即完整。特别提醒：**"方法论推荐路径双写"是 dsh 实测经验**——纯 prompts 载体有"宿主不拉取就失效"的风险，工具描述内嵌摘要是性价比最高的引导杠杆。

## 问 4：拆解次序（冻结→契约转译→外置验证→切换拆旧）的过渡风险

**dsh 评价：次序正确（与 dsh 自身演进同构），低风险；但有两个风险点必须补护栏。评分：8.5/10。**

1. **转译失真（最高风险）**：paradigm.py 的知识转译成契约时，**文档未写、代码隐含的边界条件**会丢。对策：转译期做**行为对拍**——取现有链路典型问答做回归集，验证"契约转译后新链路"与旧链路输出口径一致（口径级一致，非字面一致）。
2. **切换判据缺失**（zcode 已标注待 Codex）：建议可操作判据——①工具面全通；②意图契约 schema 冻结；③外置实连 30 个典型问题、出口验证打回率 < 20%；④静态演示场景双轨均出图。
3. **双轨维护成本**：冻结 ≠ 不维护。建议明确冻结期预算（只修 CRIT），并设**回滚开关**（feature flag）：外置链路验证不达标可一键回退旧链路——切换不是单行道。

## 问 5（harness 实现者视角）：宿主消费四类契约的最佳载体形态

**dsh 评价（此题是 dsh 的主场，给出实现者实测结论）：**

1. **工具调用类 → MCP tools**（无争议，inputSchema 派生自 tool_contracts）。
2. **方法论类 → 双写**：详细版 = prompts；摘要版 = 内嵌工具描述。**原因（实测）**：宿主 planner 的规划完全基于"当前可见的工具描述"，prompts 需要宿主主动拉取（list_prompts/get_prompt），消费率低。想让宿主"看见"，就写进工具描述；想让人"细读"，就放 prompts。**只写 prompts 是最常见的失败形态。**
3. **回答范式类 → prompts（输出结构模板）** + 关键工具 output.schema 内嵌；制式化组装（B2 保留的模板填充）在 EMC 侧执行，宿主只提供"内容素材"，不提供"版面"。
4. **意图理解类 → prompts（引导模板含示例）**，schema 本体放 resources 供程序化读取/校验。
5. **数据/口径 → resources**（按需读取；不进自动上下文，控 token）。
6. **安全边界 → 工具 security 字段**，server 侧强制（脱敏/白名单在 EMC 侧完成，不依赖宿主自觉——dsh 的硬规则）。

**一句话**：**tools 管执行、prompts 管引导、resources 管知识、工具描述是最大的引导杠杆**——四类契约按此落位，宿主零学习成本即可消费。

## 结论（供 zcode 终收敛 v2）

1. **B1 边界成立**：零开放决策 + 有限闭包校验；校验不得引入模糊语义匹配（显式标注软/硬）。
2. **两层护栏 + 最粗分流器（推荐）**：mode 枚举字段由宿主填、EMC 只验不推；出口验证必须带结构化修正指引。
3. **契约落位**：四类 + 两补充，按问 3/问 5 对照表落地；方法论契约必须双写（prompts + 工具描述摘要）。
4. **过渡**：次序确认；补行为对拍（转译期）+ 回滚开关（切换期）+ 可操作切换判据。
5. **对用户质疑的总表态**：用户"零思考壳子论"哲学上正确，与 zcode B1-B3 工程化表述互补；EMC 终态定义成立，可以进入实施设计。
