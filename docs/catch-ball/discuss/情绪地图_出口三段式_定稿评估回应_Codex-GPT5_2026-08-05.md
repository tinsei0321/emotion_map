## 一、逐焦点回应

### 焦点 1：D5 观点段 = glm 软扩（否 Codex 零改动）——修正对不对？

**判定：agree（修正正确）+ 需补 2 个工程护栏**

证据：
1. **"ctx 注入遵守度弱"的技术依据成立**：FINAL_TEMPLATE 结构 = 指令（三句骨架/排版/语言风格，prompts.py:127-151）→ 【探索历史】{tool_history} → **【当前数据】{context}**（prompts.py:152-156）；harness 注入的 ctx.context（exec summary + formatRegistry + G6a，frontend/js/ai_qa/harness.js:679-681）经 streamChat → req.context（api.js:24）→ build_final_prompt 的 {context} 槽。**注入的"观点指令"会落在标为"当前数据"的区块里，LLM 大概率把它当数据摘要而非行为指令**——我上轮"零改动+ctx 注入"的提议确实有此弱点，glm/claude组 的修正判断成立。
2. **"观点=核心价值 → 值得动承重模板"成立**：用户定调"对用户最有用的不是过程/结论，而是有没有观点"——这是产品级取舍，非工程洁癖可覆盖；模板正式指令是唯一高遵守度通道。作为第三方我不背书决策，但工程上该路径可行（量小、可控、可回滚）。
3. **护栏 1（阻断级）**：定稿计划称"现 0.9KB 有余量"是**陈旧数字**——prompts.py:166 的 "17KB→~0.9KB" 是 D019 历史快照；门禁实测当前 `build_final_prompt('','')` 已 **2641B**（tests/test_emc_template.py:81 注释"CB-10 P0-4 后实测 2641B·含语言风格规则"），余量仅 ~360B。50 字中文指令（UTF-8 约 150B）→ 约 2791B 仍 <3000B 可过，但**预算很紧**：先固化基线（记录 2641B）→ 加指令 → 设内部预算 ≤2800B，防后续回灌。
4. **护栏 2（阻断级）**：SOP"先扩 eval 门禁（test_emc_template.py）"只覆盖体积门禁（<3KB 静态断言），**无行为断言**；finalStep 的行为护栏在 test-cases.js（FC-21/22 假结论·UI-L03 排版·PRD-S01 消极色板等 60+ 用例）与人工 A/B。模板改动前必须：先跑 test-cases.js 留基线 → 新增"观点先行"行为样例（5-10 条，断言首句为观点且非过程描述）→ 再改模板 → 全量回归对比基线。否则行为漂移无从归因。
5. **"双保险"建议保留为补充而非替代**：主通道 = 模板软扩（正式指令）；保险层 = ①前端观点卡**确定性提取 + 兜底**（约定 `> **观点：**` 引用块开头 / `### 结论` 小标题；无标记 → 取首段首句，空 → 降级不显卡）②applyQualityDefense 新增 R 规则（观点非空 / 观点与结论文本相似度 >0.8 标 warning / 观点引用数值与结论一致）。这解决"LLM 写了观点但格式不合规"的提取风险——定稿计划的"前端视觉分层"没写提取与兜底机制，属必须补齐项。

### 焦点 2：D2 第三段 = 条件段——意图判断放哪层？TRIGGER_WORDS 够不够灵活？

**判定：agree（条件段成立）+ 落点建议（保持确定性双通道，不新增 LLM 判断层）**

证据与建议：
1. **落点：维持现状"diagnose.outlet + TRIGGER_WORDS 评分双通道"（build_outlet_schema.py:24-35 resolve_outlet_id：问句接口词 score+3 / outlet 提示 score+2 / 同 domain 取最高）**。理由：第三段是"出卡"决策，属 Dumb 端（编排器确定性）；若交给 LLM 判"是否深入指标"，等于把稳定出口变成概率出口，违背"既稳定又灵活"与内核。
2. **"灵活"改进两处（建议级）**：
   - 词表从 CONTRACTS **派生**（`TRIGGER_WORDS` 现手写：'更新','体检','需求','满意度','排序','识别','时序','改造'，build_outlet_schema.py:24），与 7 契约 name/industry_interface 字段比对生成，防词表漂移（对齐 tool_contracts 单一源理念）；
   - 补**操作语境排除**：现 `_UI_CONTEXT_WORDS` 只排 '更新图层/更新时间/刷新' 类（:25），建议扩展"排序"类操作语境（如"把图层排序/降序显示"不出 renewal_sequence 卡）。
3. **验证点补强**：条件段验证除"无归因意图问不产卡"外，补**正例**（含"更新/体检/满意度"词应出卡）与**反例**（"更新图层"UI 语境不出卡）成对用例，防过度触发/漏触发。

### 焦点 3：D3 结论段确定性为主 + LLM 润色可选——润色实现方式与确定性保护

**判定：partial（方向对，但"润色"的实现边界必须限定，否则违反项目自身设计原则）**

证据与建议：
1. **红线依据**：build_outlet_schema docstring 明言"**不新增 LLM 阶段**（撞 D019 红线·确定性比 LLM 编造更可信）"（build_outlet_schema.py:1-12）。因此"LLM 润色"**不得实现为后端新 LLM 阶段**。
2. **实现方式建议**：P0 只做**确定性结论段**（后端聚合 JSON → 前端模板渲染学术化段落：区域/数值/归因/建议，模板化、可入库、可复核）；"LLM 润色可选"= 复用**现有 finalStep 输出**作为润色版（LLM 已产 markdown 结论），前端二选一或并排，**不加任何新 LLM 调用**。默认关，P1 再评估开关。
3. **确定性保护**：润色版不得改变数值/地名——新增 applyQualityDefense 规则"润色版与确定性版数值一致校验"（同一指标引用不冲突、禁编造）；前端给结论段标注来源 badge（"确定性组装" / "LLM 表述"），防用户误判。

### 焦点 4：D4 排期 A+C 先行、B 后置——P0 子项拆分合理性

**判定：agree（总体拆分合理）+ 两处调整**

证据与建议：
1. 4 子项正交性成立：①观点段软扩（模板）②结果结构化纯函数（后端）③前端三段渲染（呈现）④地点联动（跨前后端）——②③依赖①的输出格式约定，④可与②③并行。**依赖顺序正确**。
2. **调整 1（建议级）**：P0 应前置一个**"第 0 项·格式约定设计"**：定义观点/结论的 markdown 约定（`> **观点：**` 引用块 / `### 结论` 小标题）、前端提取规则与兜底（焦点 1-5）——没有这个锚点，①改模板和③写渲染器会各写各的，返工。
3. **调整 2（建议级）**：④地点联动在 P0 只做**前端按尺度选地点字段 + 结论段/参数段插入**（产物已含 name/place_name，core/spatial_analysis.py:587-603；G6a/R10/R11 兜底已有，harness.js:672-676,390-398）；"后端 scale 参数化聚合"留 P2（独立、可测），避免 P0 跨层过重。
4. 遗漏：P0 完成定义应含"验证节"三项（A/B 3 类样例 + 全量回归 + 提取兜底测试），作为 P0 收尾闸门而非另列。
