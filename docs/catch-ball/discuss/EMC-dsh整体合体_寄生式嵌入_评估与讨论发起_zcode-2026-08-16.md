# EMC × dsh 整体合体（寄生式嵌入）· 评估与三组讨论发起

> 整理：zcode组（ZCode + GLM 5.3）· 2026-08-16 · 分支 `EMC_harness_dsh` · **零实施纯讨论**。
> 缘起：用户在「EMC harness 架构借鉴 dsh」专题（底稿同目录）基础上提出**更大胆设想**——将情绪地图**整个项目**（项目+数据+功能模块）作为扩展嵌入 dsh，让 EMC 模块**直接融合进 dsh 对话机制而不是作为一个模块**，直接运用 dsh 的高度开放性 + 人机交流 + 工作流 + 工具调用（通用工具+GIS 工具）的 harness。
> 本稿 = zcode 对该设想的独立评估（实事求是·不附和·该挑战底稿自己也挑战）+ dsh组/claude组/Codex组 三组联合讨论议程。
> 前置阅读：`EMC-harness架构借鉴dsh_专题底稿_zcode-2026-08-16.md`（dsh 四支柱研读 + EMC 现状对照 + G6-G9 借鉴清单）——本稿不重复其内容，只在其上叠加「整体合体」这个新变量。

## 〇 一句话结论

**方向性反对「整体寄生」（方案A），证据性支持「工具级寄生」（方案B）**。用户设想里真正有生命力的诉求不是「把情绪地图搬进 dsh」，而是「**通过开放 agent 对话直接使用情绪地图的能力**」——这个诉求的正确实现是**把情绪地图的稳定入口打包成任意 harness 可消费的工具面**（MCP server 优先，dsh plugin 为可选载体），EMC 产品本体零改动；而「整个项目寄生进 dsh」会在四条承重红线上全部失守、与 EMC 的非开发者地图产品形态根本错位、并把 CB-22 系列花了 10+ 轮硬化的行为全部置于开放 loop 的再退化风险之下——换来的收益（agent loop/session log/守卫管线）恰是 G6-G8 自建合计 2.5-4 天即可等价拿到、或用户已经拥有三份的东西（zcode/claude code/codex 本身就是通用 harness）。

## 一 用户设想还原与拆解

设想原文要点：① 整个项目（项目+数据+功能模块）作为**拓展**嵌入 dsh；② EMC 模块**融合进 dsh 对话机制**，「而不是作为一个模块」；③ 直接用 dsh 的开放性 + 人机交流 + 工作流 + 工具调用（通用+GIS）。

拆成两层不同性质的诉求：

| | 内容 | 本质 |
|---|---|---|
| **A 整体寄生**（设想字面） | 情绪地图运行时迁入 dsh：EMC 的对话机制（diagnose→tool→final 确定性管线）被 dsh 开放 agent loop 取代，19 契约工具/知识库/RAG/范式映射改写为 dsh plugin，项目+数据住在 dsh 架构里 | **架构迁移**：换掉 EMC 的 harness 本体 |
| **B 能力融合**（设想的精神） | 在开放 agent 对话（工作流+通用工具+GIS 工具）里**直接调用**情绪地图的能力（分析管线/空间分析/RAG/知识库/出图），人机交流体验与 dsh 原生一致 | **能力暴露**：给通用 harness 开工具面 |

**A 与 B 常被混为一谈，但技术后果完全不同。** A 是推倒 EMC 内核换运行时；B 是 EMC 体外开侧门。下文分别评估。

## 二 方案A（整体寄生）逐维评估

### 2.1 承重红线符合性 —— 四条全失守

| 承重红线 | 整体寄生下的命运 | 判定 |
|---|---|---|
| **diagnose prompt 永不动**（KNOWLEDGE·两度豁免均有 3 条件+回滚条款） | dsh 无「FC 单次意图理解」概念，诊断逻辑必须翻译进 dsh 的 system prompt / agent loop 组装——等于重写 | ❌ 失守 |
| **编排器确定性**（内核铁律 3·三态出口由代码裁定非模型自觉） | dsh 开放 loop = LLM 自主决定调多少工具/何时停，正是内核刻意不采用的模式 | ❌ 失守 |
| **契约单一源**（`ai_qa/tool_contracts.py`→SKILL_DEFS→prompts 派生链） | dsh 工具 schema 是另一套注册体系；要么双源漂移，要么重建一条「tool_contracts→dsh plugin schema」派生链（技术上可行——`contracts_to_tools_schema()` 已在 `tool_contracts.py:473`，但整条链重做） | ❌ 重建 |
| **三支柱缺一不可**（知识库完备度+分类→范式映射+LLM 综合·CB-22 定） | 知识问答路径/RAG 综合引用/范式路由要改写为 dsh plugin/context provider；CB-22「砍支柱出假结论」的教训（曾砍 LLM 支柱走确定性拼列表、被用户人工验证否定）在开放 loop 下重演风险更高 | ❌ 重写+再硬化 |

### 2.2 产品形态错位 —— 地图即产品，dsh 是终端

- EMC 的输出半条命是**图层生成 → MapLibre → 视野-数据-结论同步**（演示逻辑链最高纲领）。dsh 是开发者终端/CLI 形态，**没有地图 UI**。19 个契约工具中相当部分的价值就是「驱动地图出层」——寄生后这半条工具面无家可归，要么给 dsh 配一个浏览器 viewer 侧车（那其实是把 EMC 前端拆出来远程遥控，架构更碎），要么放弃地图输出（产品残废）。
- **用户错位**：dsh 的目标用户是「会改插件的开发者」（其文档自述）；EMC 的目标客户是**规划师/住建局非开发者**（CLAUDE.md 目标客户画像）。对非开发者，dsh 的审批门（allow/deny/ask）、开放 loop 的不可预测性、「需要人把关工具调用」的预设，全部不可用。「稳定压倒灵活」是 EMC 的产品决策不是技术妥协（底稿 §三）。

### 2.3 隐性成本最大项 —— CB-22 系列硬化行为的再硬化

这不是移植代码的成本，是**重付历史学费**的成本：

- **颗粒度**（CB-22 颗粒度系列多轮）：问题尺度→回答范式映射是代码路由（`paradigm.py` select_template），不是模型自觉——开放 loop 下回归「答成坐标/答非所问」。
- **诚实度**（B002/B004 假结论·CB-39 D1 白名单正在做终态）：四态出口契约 + 结论白名单是代码裁定——开放 loop 下 finalStep 类幻觉防线要全部换成 dsh 守卫再调一遍。
- **推理螺旋**（B001 多要素推理死循环 / B003 LLM 推理螺旋耗时异常·CB-09）：EMC 刻意不做开放 loop 的直接病因——寄生等于把病请回来当特性。
- **CB-08 实测**：FC 工具选型 100% 准确（12/12），瓶颈在参数填充——「不够聪明」不是 loop 的锅，换 loop 一个参数填充问题都解决不了。

### 2.4 供应链与工具链风险

- dsh 自述**开发者预览阶段、有破坏性变更**；Cordis 框架 + TypeScript monorepo + pnpm 全套工具链。项目现状：前端纯 JS 单页零构建 + Python 后端，**零 TS 基础设施**。把生产产品绑在 preview 阶段框架上，每次 dsh breaking change 都是一次全量适配——维护成本压在「用户一人 + agent 组合」上。
- 安全半径：开放 loop + 通用工具（bash/文件写）与政务数据（12345/体检）、城市数据同处一个运行时，误操作半径远大于 EMC 的 Dumb Tool 沙箱化设计（工具单一职责、无 shell、无文件写）。

### 2.5 收益盘点 —— 每一项都有更便宜的等价物

| 整体寄生的收益 | 等价物 | 成本对比 |
|---|---|---|
| 开放 agent loop（多步链/自由对话） | G9 CPD 复活借 delegated turn 语义（受控多步·plans 契约） | CPD 排期内解决 vs 重付 B001/B003 学费 |
| Session log 可重放 | G6 前端 turn 事件化（专题议题1） | 自建 1-2d vs 整体迁移数周 |
| 守卫管线 | G7 post-execute 管线（专题议题2） | 自建 0.5-1d（D1 落地后顺势） |
| 通用工具+工作流+人机交流 | **用户已拥有三份**：zcode / claude code / codex 即通用 harness，CB 流程即工作流层 | 0 成本 vs 再引入第四份 |

**量级估算（honest）**：工具层移植（20 契约→TS plugin + viewer 侧车）3-5d 起步；知识库/RAG/范式 plugin 化 2-4d；CB-22 系列行为再硬化 + eval 重建**不可估**（历史投入 10+ 轮 CB）；期间 CB-39 B/C 线、CB-40 G1-G5 全部停摆。保守合计 **2-4 周纯 agent 时间，换 preview 阶段框架的一张船票**。

### 2.6 方案A成立的唯一假想世界（steelman，仍不成立）

设竞赛演示结束、产品重心转向「用户自己 + agent 出 PPT/报告」的生产线（城市更新专项规划主线），地图前端权重下降——在这个世界里开放 agent 确实比地图 copilot 更贴工作形态。**但即使如此，工具级寄生（方案B）仍优于整体寄生**：用户的 harness 是 zcode/claude code/codex（已深度嵌入 CB 工作流），不是 dsh；模型选择与 harness 选择正交（EMC `llm.py` 有适配层，DeepSeek 模型任何 harness 都能接）。dsh 在这个世界里提供的增量 ≈ 0。

## 三 方案B（工具级寄生）：设想精神的方向性落法

### 3.1 方向

**EMC 不搬家；给全部通用 harness 开一扇工具侧门。** 把情绪地图的稳定入口暴露为标准工具协议（MCP 优先），任何开放 agent——zcode / claude code / codex / dsh（若接 MCP）——都能在对话里直接调用「情绪地图能力」，获得用户想要的「开放性 × 人机交流 × 工作流 × GIS 工具」体验，而 EMC 面向规划师的产品本体一字不动。

> 这是「寄生」的正确方向反转：**不是情绪地图寄生进某一个 harness（运行时级寄生），而是情绪地图的工具面寄生在所有 harness 上（协议级寄生）**。前者让领域产品降格为单一框架的人质；后者让领域能力升格为生态公共设施。

### 3.2 已有基础（实锤，非愿望）

- **契约层现成**：`tool_contracts.py:473` `contracts_to_tools_schema()` 已能从 TOOL_CONTRACTS（20 条·19 工具+1 concept）产出 JSON schema——MCP/dsh plugin 的工具定义输入**已经有了**，G8（派生全自动）做完后更是单一源直出。
- **分析入口统一**：AGENTS.md 铁律 4/5——`run_analysis_task()` 全入口共用，天然适合包成工具。
- **MCP 工程先例**：`.claude/mcp_servers/vision_bridge_server.py`（FastMCP）已在仓内跑过，模式可复制。
- **事实上已在用**：CB 出图主线上 Codex/各组 agent 天天通过 bash 调脚本消费情绪地图能力——方案B 只是把这个「野生侧门」标准化（带 schema/脱敏/审批），不是从零发明。

### 3.3 工具面候选清单（最小集，讨论用）

| 工具 | 入口 | 说明 |
|---|---|---|
| `run_analysis` | `run_analysis_task()` | L1-L4 管线（重操作·需审批） |
| `spatial_query` | `core/spatial_analysis.py` + `buffer_analysis.py` | 缓冲/聚合/对比（MVP 面） |
| `rag_query` | RAG 检索接口 | 检索素材+来源引用（只读） |
| `kb_facts` | `ai_qa/industry_kb/` + outlet_kb | 行业知识事实（只读） |
| `export_outlet_card` | `core/export.py` F_005 | 出口卡 CSV（脱敏铁律续用） |
| `list_data` | DATA/ 清单只读盘点 | agent 自发现可用数据 |

### 3.4 边界与红线

- **EMC 本体零改动**——四条承重红线原样保留；方案B 是体外器官，不碰内核。
- **脱敏铁律 7 续用**：工具输出禁个人身份信息。
- **写操作过审批**：run_analysis/export 类副作用工具由宿主 harness 的审批门把关（zcode/claude code/codex 均有）。
- **EMC 委托主 Toolbox 不自造 geo 端点红线不冲突**：该红线约束的是 EMC 内部 toolbox；方案B 暴露的是既有稳定入口，不新增 geo 端点实现。

### 3.5 量级

最小 spike（3-5 工具 MCP server + 一个 harness 实测）：**1-2d**，不阻塞 CB-39 B/C 线与 CB-40 G1-G5。

## 四 关键洞察（本稿最重要的一段）

**用户想要从 dsh 那里得到的东西——开放性、人机交流、工作流、通用+领域工具调用——就是「通用 agent harness」的定义，而用户已经每天指挥着三个这样的 harness（zcode/claude code/codex），CB 流程就是它们的工作流层。** 情绪地图真正独有的资产不是 harness（通用 harness 满地都是），而是**领域栈**：数据（12345/体检/POI）、GIS 管线、范式映射、行业知识库、出口卡片、地图叙事。

所以「EMC × dsh 合体」的真正杠杆点是：**让领域栈工具化、对外可寄生（协议级），而不是让项目寄生进某一个通用框架（运行时级）。** 前者一次实现处处可用（含 dsh 自己）；后者把领域产品绑死在一个 preview 框架上，还给 EMC 换上一个它病史里最忌讳的大脑。

## 六 三组联合讨论议程

**总纪律：零实施、零 git 写、意见落盘 discuss/、实事求是不附和（对 zcode 本稿结论该挑战就挑战）。**

- **议题1（方案A 裁决）**：zcode 六维反对（红线/形态/再硬化/供应链/工具链/收益覆盖）是否有漏洞？是否存在 zcode 未识别的方案A 合理场景？
- **议题2（方案B 载体）**：MCP server（一次实现多 harness 消费）vs dsh plugin（若 dsh 不支持 MCP 或用户指定 dsh 为宿主）vs 维持 bash 野生侧门——选型与理由。
- **议题3（工具面清单）**：§3.3 六工具的增删；契约 schema 直接复用 `contracts_to_tools_schema()` 的可行性；副作用工具的审批分级。
- **议题4（dsh 专项质证·dsh组 主答）**：dsh plugin 开发的真实成本与破坏性变更节奏；dsh 是否/如何消费 MCP；「领域产品作为 plugin 寄生」在 dsh 设计哲学（Everything is a Plugin）下的利弊内部视角。
- **议题5（红线与治理）**：方案B 下脱敏/审批/中转站数据纪律（sim 禁入、gdb 只读）如何映射到工具面约束。
- **议题6（排期）**：方案B spike（1-2d）是否入 CB-40 缺口清单；与 G1-G5 合并总优先级表（衔接专题议题5）。

**分组侧重**：dsh组=议题4 主答+议题1/2 质证（dsh 母框架技术事实方）；claude组=议题1 红线/产品形态独立裁决+议题5；Codex=议题2/3 实施成本与清单可行性+议题6 排期影响。
