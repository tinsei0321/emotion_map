## 议题 1 · A1 前注维护成本——**有条件支持**（条件=三条护栏，缺一降级为可选）

成本判断同意主手：<1k chunk × DeepSeek 离线一次性，API 成本可忽略。**真正成本不在钱，在漂移**：上游 md 改一段 → 前注明明可自动重生成，却因「重建索引才触发」被遗忘 → 前注与正文失配 → 检索吃到**错误语境**（比没有前注更糟）。EMC 的 39 份同源 md 是高频编辑资产，这不是假想风险。

三条护栏（并入泳道①任务书才支持）：
1. **前注进 build_id 派生物**：`content_hash` 覆盖「正文+前注」整体——正文变而前注未重生成时 build 不更新（强制一致性），R-1 成组原子（v1.1 补-A）扩为四件（vectors/meta/bm25/ctx_prefix 或并入 meta 但 hash 必须含）；
2. **重建命令一体化**：`rag_index.py --build` 内部串「生成前注（可选 API）→入库→索引」，禁拆两个手工步骤（双机重建纪律 §五.8 才可执行）；
3. **前注质量门禁 1 条刚性**：黄金集中抽 N 条验证前注含出处要素（文档名/小节/口径状态任二）——防 LLM 生成空话前注污染 BM25。

挑战业界判断一处：Anthropic -49% 是**英文大语料+通用检索**场景；EMC 中文小语料的预期收益应打折看待。建议 A1 并入后**在泳道②消融纪律里独立成层**（前缀/前注/BM25+RRF 各自分 commit）——若前注层增量 <2pp，收口时降级为「口径类 chunk 专用」而非全量。

## 议题 3（重点）· 本地重排 Windows 双环境——**替代方案：参数位照设，模型选 ONNX int8 cross-encoder，bge-reranker 原生权重仅备选**

### 3a · 现状事实（本机实测）

- `requirements.txt:70` 现有 `sentence-transformers>=2.0.0`（08-22 刚补装销项 N3）；`torch 2.13.0+cpu`（本机实测·**无 CUDA**）；现有 embedding `BAAI/bge-small-zh-v1.5`（`tools/rag_index.py:34`）CPU 冷启动 ~15s——这些是双环境的现实基线。

### 3b · bge-reranker 原生权重在 Windows 双机的坑（实现者预判）

| 坑 | 说明 | 严重度 |
|---|---|---|
| **PyTorch CPU 推理延迟** | cross-encoder 对 top20 候选逐对编码，CPU 单对 ~百 ms 级——20 对即秒级；3080/dsh 工具调用有 tool_timeout 压力 | 高 |
| **双机依赖膨胀** | bge-reranker 原生路线=transformers+torch 全家桶（torch 现仅因 sentence-transformers 间接在场）；office/home Python 版本差（全局规则五③）下锁版矩阵翻倍 | 高 |
| **模型分发** | HuggingFace 权重 ~1GB 级（base）——离线纪律（§五.6）要求双机手动同步模型缓存；无 GPU 时性价比进一步塌 | 中 |
| **双机行为漂移** | CPU 线程数/指令集差异 → 打分微差 → 黄金集名次抖动（X2 阈值已挂余弦不挂名次，v1.1 E-3 有先见） | 中 |

### 3c · 选型建议（替代方案）

1. **首选：ONNX Runtime int8 量化 cross-encoder**（如 BAAI/bge-reranker-base 的社区 ONNX int8 版，或 FlagEmbedding 官方 onnx 分支）——依赖只加 `onnxruntime`（几 MB·CPU 优化好·Windows 成熟），延迟较 PyTorch CPU 常降一个量级，模型文件缩到 ~100-300MB；
2. **次选：更小中文 cross-encoder**（若黄金集 A/B 显示精度够）；
3. **bge-reranker 原生权重 = 备选**：仅当 ONNX 路线在 A/B 中精度显著落后才启用，且必须走 P2 重启任务书四护栏（§六·零 LLM/纯打分/rerank=False 可关/模型版本入 build meta）；
4. **无论哪条**：A/B 实证前默认 `rerank=False`（主手立场一致）+ 模型文件走「来源 URL+版本+下载/校验命令」入 M 配方（全局规则五②·禁手工拷贝）。

一句话：**参数位是免费的，权重是有价的——别让 0.5d 的可选项拖进 1GB 级双机维护债**。

## 议题 5 · H2 事件载荷最小集——**支持最小集起步，建议补 2 字段留 1 口**

主手最小集（query 摘要/命中数/口径 refs）够起步。从壳阶段对话框渲染与 ACP 状态对象（`docs/acp-contract-v1.md` §三 toolcall 含 `caliber?`）反推，建议补：

## 议题 6（重点）· ctx_prefix 进 P0-6 契约——**支持，附 schema 细化与泳道影响评估**

### 6a · 字段设计（建议进 P0-6 半页契约）

```
chunk schema（P0-6 增补处）:
  ctx_prefix: str | None     # A1 前注（1-2 句·生成态）；None=未启用 A1（向后兼容泳道①先行）
  ctx_prefix_model: str|None # 生成模型名+版本（如 deepseek-v4-flash@2026-08-22）——溯源
  ctx_prefix_hash: str|None  # 前注内容 hash——与 content_hash 分离，build 校验「正文变→前注 hash 必重算」
```

设计理由：三字段分离让「前注过期」**可检测**（议题 1 护栏 1 的数据基础）；None 态保 P0 与泳道①可先行（前注是增强不是前置依赖——顺序不该倒挂）。

### 6b · 对泳道②③的影响

- **泳道②**：R-1 成组原子多一件校验（ctx_prefix_hash 与 build_id 绑定）；R-2 RRF 的 embed/BM25 输入拼 `ctx_prefix + content`（一处函数·消融层独立）；R-4 元数据过滤不受影响（prefix 是检索增强非过滤维度）。**不新增任务项，扩现有两任务验收即可**；
- **泳道③**：E-1 搬家时 chunk schema 整体迁移（三字段随行·loader 契约保证）；E-3 体验件不受影响；
- **接口锁（收口 G4）**：ctx_prefix 是**内部 schema 字段**，不进 rag_query 对外返回——G4 零破坏承诺不受触（前注价值在检索侧，不在展示侧）。

## 附：对业界判断的两点适配坑挑战（发起档案邀）

1. **A1/A3 的小语料收益存疑处**（已散见议题 1/3，此处集中）：EMC <1k chunk 且黄金集主痛点是「精确名词类」——这类问题的胜负手在**元数据路由（A2）与 BM25 精确匹配**，前注与重排都主要改善「叙述类」；若黄金集 60 条中口径/名词类占大头（P0-1 要求各≥8，实际比例待测），A1/A3 的整体指标增量可能被稀释。建议收口报告按**分类增量**呈现，防「整体 +2pp」掩盖「叙述类 +8pp/名词类 +0」的真实结构；
2. **「业界 2026 标配」的语境差**：混合+重排的标准画像基于万级以上语料与 GPU 服务；EMC 的等价优势在小语料侧——**全量暴力检索（现状 numpy）在 <1k 规模没有召回瓶颈**，重排的价值只剩排序质量。这正是 A3 默认 False + A/B 实证路线正确的根本原因，也是本组坚持把选型成本算进决策的原因。
