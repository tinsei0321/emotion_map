# EMC 聪明路径 · 入口端灵活性 · 讨论稿

> 整理：zcode组（ZCode + GLM 5.3）· 2026-08-17 · 分支 `EMC_harness_dsh` · **零实施纯讨论**。
> 缘起：用户在 EMC×dsh 合体讨论 R3 轮纠偏——前几轮（方案A/B、D1-D4）讨论的核心点与真痛点错位。真痛点 = **EMC 从自然语言到分析方法+工具调用+结果产出的路径不够"聪明"**：LLM 接入效果未充分发挥，靠提示词/字典驱动预制分析路径；稳定有了但灵活性被大大弱化；意图判断不够准/不够灵活 → 选不中正确方法+工具组合；困境持续很久，"拆东墙补西墙"修不完，没发挥出 agent 优势。
> 本稿 = 该痛点的机理分析 + 解法方向 + 议程建议，供用户拍板与（若开轮）三组讨论。前置：同目录底稿（G6-G9）、发起稿（方案A/B）、讨论过程台账 R0-R3。

---

## 〇 一句话结论

痛感真实且有机理：**开放问题空间 vs 封闭意图分类法 + 单发诊断不可恢复 + 参数闭卷填空 + eval 失真**四层叠加，使修补在数学上不收敛（拆东墙补西墙的结构性根源）。但解法不是换更聪明的架构（开放 loop 只把"路由错误"换成"过程漂移"），而是**把灵活性归还到入口端**——内核承诺的"Smart 入口"从未兑现足额（不能追问澄清/不能看数据定参/不能产多步计划）。四个机制（迭代诊断/参数接地/计划生成/eval 重放）全部长在内核允许的位置上，其中三个就是底稿 G6-G9+CB-08 方向——**用户这轮把"为什么做它们"说清楚了**。

## 一 真痛点的精确表述

用户原话要点：① 路径不够聪明，LLM 效果没发挥；② 靠提示词+字典驱动预制路径；③ 稳定换灵活的代价太大；④ 意图判断不准/不灵活 → 选不中正确方法+工具组合；⑤ 拆东墙补西墙无穷尽。

精化（据证据校准）：**不是"单次选型精度"问题——CB-08 实测覆盖内题型 FC 选型 12/12 全对。是四件结构性缺失的叠加体感**（见下节）。此精化重要：四件事各有各的药，混在一起看才会觉得"无解"。

## 二 四层机理（每一层都有代码/CB 证据）

| # | 机理 | 证据 | 后果 |
|---|---|---|---|
| 1 | **开放问题空间 vs 封闭意图分类法** | `ai_qa/paradigm.py` select_template 尺度→方法映射；`frontend/js/ai_qa/harness.js:57` 起轻量预判词表（geo 动词表/宜昌地名表/「宁落不误断」）；intent→template 路由表 | 有限字典索引无限空间：每个落在分类法外的题型都表现为路由错/颗粒度错 → 一轮 CB 补一条映射 → 长尾永在。**修补不收敛是这类架构的固有属性，不是 bug 密度高** |
| 2 | **单发诊断不可恢复** | diagnoseStep 一次 FC 调用定终身 → dumb 执行 → finalStep 表达；失败路径全走降级（`harness.js:185` 起 degraded 出口串：rag 超时退概念/diagnose 失败退 general），**宁可降级也不向用户澄清** | 诊断偏了整轮作废，且要用户看到错误结果才知道。真 agent 遇模糊会问，EMC 遇模糊会猜、猜错硬跑 |
| 3 | **参数闭卷填空** | CB-08：选型 12/12 全对、瓶颈全在参数填充（buffer.center / overlay.layer_a,b 填不出）——LLM 看不见数据资产清单（有什么图层/口径/范围），全靠提示词死知识 | 对的工具产出饥饿/错误参数结果 |
| 4 | **eval 失真** | CB-01 C6 老病：eval 手工构造空 context，不反映运行时真实组装 | 补丁过当轮用例、长尾回归、下轮再补——Whac-A-Mole 循环闭环 |

## 三 核心 reframe：灵活性归还入口端，不在中间开放

- 内核（Smart 两端/Dumb 中间/编排器确定性）没有错——B001/B003（推理死循环/螺旋）是**中间变聪明**的病，当年修向 dumb 中间是对的。
- 但检查"两端"会发现：**入口端只给了 LLM 一发子弹**——不能追问澄清、不能先看数据再定参、不能产出多步计划（CPD 空骨架·CB-10）；出口端 finalStep 也只管表达。
- 所以：**痛不在内核错，在内核承诺的"Smart 入口"未兑现足额**。归还灵活性的位置 = 入口端三个机制 + eval 地基（下表），全部与内核铁律兼容。

## 四 四个机制（落法·红线兼容性·量级粗估）

| 机制 | 落法 | 红线兼容性 | 量级（粗估·待三组细化） |
|---|---|---|---|
| **M1 迭代诊断**（低置信就问，不猜） | diagnose 前置澄清门：置信度低/关键槽缺失 → 出 1-2 轮澄清追问（对话内），用户答后重诊断。轮次上限+超时守卫 | **不動 diagnose prompt 本体**——澄清作为独立小步（前置 gate/置信度出口），非改写诊断指令。B001 防护=轮次硬上限 | 1-2d（交互+守卫+前端） |
| **M2 参数接地**（开卷考试） | 把数据/图层资产清单实时注入**工具 schema**（参数 enum/描述动态派生：图层名枚举、口径枚举、范围可选项），LLM 从真实选项里填参 | **红线兼容关键：走 schema 侧不走 prompt 侧**——契约参数定义动态化恰是 G8（契约派生全自动）的自然延伸；CB-08 方向 | 0.5-1d（与 G8 同源·资产清单管道与 G10 `list_data` 同源） |
| **M3 计划生成**（多步组合） | G9 CPD 复活：diagnose 产出多工具 plans（显式·可检视·可拦截）→ dumb 逐步执行 → 结果回填；借 dsh delegated turn 语义设计 plans 接口 | CB-10 约束：复活须同步恢复 plans 产出指令；中间仍 dumb（每步纯执行） | 2-3d（引擎+契约+eval） |
| **M4 eval 重放**（反 Whac-A-Mole 地基） | G6 session log：前端 turn 事件化（user/diagnose/tool/final 全记）→ eval 从日志重放真实上下文 → 补丁在真实分布上验证 | 无红线接触；底稿专题议题1 | 1-2d（底稿已有方案骨架） |

**推荐顺序：M4 → M2 → M1 → M3**（先让验证不再失真，再开卷，再允许问，最后多步——每一步建立在前一步的可验证性上）。

## 五 诚实校准（不附和）

1. **"彻底解决"不存在**：开放 loop 也做不到意图一次到位——它把"路由错误"换成"过程漂移"（B001 死循环=过程漂移极端形态），dsh 自己也靠 guards/审批兜底。能收敛的是把结构缺失逐个补成机制，不是换脑子。
2. **无需动架构骨架**：四机制全长在内核允许位置（入口/出口/eval 基建），底稿"不需推倒重来"判定仍成立。
3. **M1 有交互代价**：非开发者用户（规划师）对追问的容忍度有限——澄清轮次要克制（关键槽缺失才问，1-2 轮封顶），形态需设计（对话内 vs 参数面板预检确认）。
4. **M3 是最大件**：CPD 空骨架病史（CB-10「只说不做」曾致根治性手术），复活必须带 plans 契约+eval 同步，否则重蹈。

## 六 对当前讨论（D1-D4/G10）的影响

- 用户真痛在 EMC **体内**聪明度 → 方案A（换运行时）与方案B/G10（工作流侧门）都**不治此痛**（R2 诚实边界①升为主矛盾）。
- D1（否决A）结论更稳固；D2/D3/G10 仍成立但降权为"工作流侧门"，**不与聪明路径争资源**。
- 底稿 G6-G9 的定位变化：从"泛泛的借鉴候选"升格为"对症药方"——G6=M4、G8 含 M2、G9=M3，缺一个 M1（迭代诊断·新增项）。
