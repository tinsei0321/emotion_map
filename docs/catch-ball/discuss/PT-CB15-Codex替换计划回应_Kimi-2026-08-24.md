# PT-CB15 · Codex 替换 dsh 计划 · 回应（Kimi 组 · 产品/用户视角 · 2026-08-24）

## 白话摘要（零术语·按 AGENTS 3b）

这次要干的事，打个比方：EMC 是一位病人，以前请的「外聘医生」dsh 只接受写信问诊——您把问题寄过去，等一封完整回信（一次性给出·看不到思考过程·也没有上下文记忆，每封信都是新病人）。现在要换成 Codex 医生，他能视频通话——您在 EMC 自己的窗口里就能看着他逐字思考、一步步开检查单（调工具）、最后出报告，而且他记得您上次说过什么（多轮对话）。

**我的总体判断**：该换、时机也对——药方（计划书三步走）大体抓得准，我支持收敛后开工。但有两味药的剂量要调：①「每次出图前都要您点头批准」这条会毁掉视频通话的流畅感——出图不是动手术（不改数据），应该免检放行、只记账备查；②视频线路要装「断线警报器」——Codex 进程如果悄悄死掉，窗口不能干等，要在几秒钟内告诉您「线路断了」而不是让您猜。

另外两个体验预期先给您打底：换完后您看到的逐字流可能是「一小段一小段蹦」而不是「一个一个字蹦」（技术上有个 50 毫秒的打包缓冲·差别不大但能感觉到）；真正的大升级其实不是流式，是**记忆**——以后可以追问「那西陵区呢？」，他能接上，dsh 做不到这个。

---

## 〇 一句话结论

**计划成立、时机正确，支持收敛后开工；两处有条件——C4 审批分类错误（render_spec 是渲染副作用不是写面，审批弹窗会毁掉「看着 AI 出图」的流畅感，应免审批+审计日志），D4 需补断流看门狗（subprocess 静默死亡场景，api.js 已有同类坑的修复先例可循）。**

## 一 D1-D6 逐条表态

### D1（接入传输：stdio vs HTTP）——agree（HTTP·补一条硬证据）

主手倾向 HTTP，我支持，且手里有决定性证据：**RAG 嵌入模型是进程内单例缓存**（rag_index.py `_get_model`·local_files_only），而 `warmup()` 预热（CB-22 修复·消首检冷加载 18.6s）只在常驻进程里有效。stdio 模式每会话冷启动一个新 MCP server 进程 = **每次会话都要重新加载 92M 嵌入模型**（实测冷加载 18.6s·首次下载更久），用户在 EMC 窗口里每开一轮对话先干等 20 秒——体验死刑。HTTP 常驻 8600 已就绪、模型常驻内存、startup_timeout 问题不存在。**stdio 免端口依赖的优点在用户体验面前不值一提。**

### D2（app-server 客户端：subprocess vs SDK）——agree

SDK 0.0.0-dev 无语义化版本号，subprocess `codex exec --json` + 锁 commit schema 类型对冲是稳健工程判断，Qoder 已勘察源码确认可行。产品视角无补充——这个决策对用户不可见，选可维护性高的即可。

### D3（人设双层拆分）——agree（拆法有原则·我给判据·重点题）

**拆分判据一句话：按「违反成本」拆，不按内容主题拆。**

dsh 的定稿人设（PT-CB7 双写：agent.cordis.yml persona 行 + router-bootstrap-v1.mjs RL_PERSONA 常量）内容是两类东西的混合物，拆开时对号入座：

| 层 | 内容 | 判据 | Codex 落点 |
|---|---|---|---|
| **铁律层**（常驻） | 先 list_data 再操作 / A2 路由分工（精确→kb_facts·叙述→rag_query）/ 口径纪律（禁把格结论说成社区结论）/ 出口四态 / 禁裸输未标注数字 | **违反即事故**——哪一轮忘了都会产错答案，必须每轮在场 | AGENTS.md 常驻段 |
| **知识层**（触发） | 身份卡查询路径（「你是谁」→ kb_facts(keyword=EMC) 按 EMC-IDENTITY-01 答）/ 领域背景（城市更新项目概况类） | **查得到即可**——只有特定问题才需要，常驻反而稀释注意力 | 身份卡 skill 触发注入 |

这个判据与我在 PT-CB9 回应里的治理管线设计同构：**AGENTS.md 常驻段=宪法层**（改一次影响全部会话·变更须人审——对应我 D3 设计的「事实层人审必过」）；**身份卡 skill=知识层**（走 kb_facts 既有口径治理·R24 引句纪律已覆盖）。分层之后人设的治理也自然分层，不要两边都走同一变更通道。

**用户体验影响两条**：
1. **拆分本身用户无感**——只要铁律层完整常驻，答案行为不变；真正的风险是拆漏（某条铁律被归进 skill 没触发）→ **C3 工具验证里必须加一道「身份问」**（见 D6·这是拆分正确性的试金石）。
2. **附带红利**：Codex 的 AGENTS.md 是 Codex 通用机制，未来别的开发者 clone EMC 仓用 Codex 打开，自动获得 EMC 工作纪律——人设从「dsh 私有配置」（~/.dsh 仓外·双机复刻痛点）变成「仓内资产」，这正好治了 PT-CB7 时代人设双机同步的老毛病（当年 persona 在 ~/.dsh 仓外，换机要手工复刻）。**这是本次替换的一个隐性收益，值得写进 C12 验收报告。**

### D4（流式：延迟/粒度/丢包）——partial（50ms 缓冲可以，缺断流看门狗·重点题）

主手的批量转发（50ms 缓冲）+ seq 单调保证方向对，但**只覆盖了「正常流」的一半风险**。缺的是「异常流」：

- **断流看门狗（必须补）**：subprocess 承载的 JSONL 流有一个经典死法——**子进程静默死亡**（崩溃/被杀/管道破裂），没有 close 事件、没有 error 帧，前端永远等不到下一个 delta。EMC 在这个坑上流过血：api.js 的 fetch 总超时 Promise.race 就是为此而建（CB-22i P1「serve 反代挂死未返 200·用户读秒 5 分半」根因修复，api.js:42-51）。Codex 客户端必须带同款：**无事件 N 秒（建议 15-20s·对齐既有 per-phase 超时族）→ 主动发 error 事件 + 语义化降级文案**，不能让窗口干等。
- **50ms 缓冲的用户体感**（诚实预期）：缓冲后是「块状流」而非「逐字流」——每 50ms 一小段蹦出。对照 dsh 3080 的逐字丝滑，敏感的用户能觉出「一顿一顿」。这不影响接受度（信息完整性优先），但 **C12 验收报告应如实记录这个体感差异**，别到时候用户以为「Codex 比 dsh 卡」。
- seq 单调之外建议加 **seq 缺口检测**：JSONL 丢行（管道缓冲截断）时 seq 跳号 → 按 error 处理而非静默跳过——丢一段思考链用户看不出，丢一段正文就是事故。

### D5（四引擎并存）——agree（并存对·但切换入口要管住·重点题）

?engine=light|dsh|mock|codex 四态常驻、用户随时切——方向对（dsh 保底是逃生门·删不得）。用户操作复杂度评估：

1. **URL 参数对测试期用户（您自己+开发组）够用**，但它有一个隐蔽成本：**用户会忘了自己当前在哪个引擎**。建议复用 A-4 版本徽章的现成模式——左下角角标旁边加引擎标识（`v5c0b593 · codex`·一行 cssText 的事），让「当前引擎」永远可见。否则对拍阶段「这答案是哪个引擎产的」会成为日常困惑。
2. **心智模型给用户一句话就够**：「默认用最顺的（codex）·出问题切保底（dsh）·light 是快通道·mock 是测试用的」。四态不可怕，可怕的是没有默认叙事——这句话建议原样进 C12 的切换操作指引。
3. **退役另议我支持**——dsh 退役的判据不是「Codex 好用」，是「连续 N 周无人切回 dsh」·让使用数据说话，别提前埋逃生门。

### D6（对拍标准量化）——agree（补两道必测题）

口径标签一致率/出图一致率/抽 3 题人工核的方向对（claude 会细化）。产品视角补两道必测题：

1. **身份问**（「你是谁/你能做什么」）——D3 人设拆分正确性的直接验收：若身份卡 skill 没接上，这题当场穿帮；
2. **越界/缺口题**（问一个知识库没有的东西）——测出口四态一致性：Codex 会不会像 dsh 一样诚实说「未收录」，而不是更「聪明」地编一个。**Codex 模型能力更强，反而更容易越过诚实出口——这是对拍里最该警惕的系统性风险**（能力越强的引擎越要盯出口四态）。

## 二 纠错（一处表述不精确·非错误但影响理解）

计划书 §一白话摘要与 §2.1 表格：「dsh 只有写信问诊（一问一答·无流式）」「dsh ❌ headless 无流式」——**严格说 dsh 不是「没有流式能力」，是「headless 接入形态拿不到流式」**。dsh web 3080 驾驶舱本身有流式（私有协议），只是宪法禁依赖私有协议、headless 模式又是一问一答。这个区分影响对「为什么换」的准确理解：**换 Codex 的核心理由不是「dsh 产品不行」，是「dsh 不给我们的接入方式不行（私有协议+headless 无流）vs Codex 有官方 SDK 全量面」**——这与 Harness 选型讨论「能力代差真实存在·dsh 无官方 headless」的既有结论一脉。建议收敛时措辞校准，避免给未来留「dsh 不行」的误读档案（dsh 保底还要长期服役，档案别把它写死）。

另：§三 C4「写面（render_spec）单独收紧」——render_spec 分类有误（见 §三 C4 裁决），它不是写面。

## 三 实施建议（三条·并入现有件不新开）

1. **C4 审批重分类**（见裁决表）：render_spec 归「副作用面」免审批+审计日志，审批弹窗留给未来真写面（kb_inbox 知识写入·已有 ACP approval.req 接线注记等着它）——别把「看着 AI 出图」的流畅感祭给错误的谨慎。
2. **C7 加断流看门狗**（D4）：brain-adapter-codex.js 内建无事件超时→error 事件，模式照抄 api.js:34-51 的 per-phase 超时族（25s/30s/45s 分档可复用）。
3. **C12 验收报告固定三节**：①50ms 块状流体感如实记录（防「Codex 比 dsh 卡」误读）②人设入仓的隐性收益（PT-CB7 双机复刻痛点治愈）③引擎切换一句话叙事（D5-2）。
