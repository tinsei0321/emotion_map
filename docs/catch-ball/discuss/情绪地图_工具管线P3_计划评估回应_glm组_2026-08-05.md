## 一、逐焦点评估

### 焦点 1：P3-1 依赖图判定（DAG + 拓扑·纯函数）— **agree（判据够·但对齐 EMC 实际场景）**

**计划**：依赖判据 = ① `$n` 引用 / layerId 传入 ② 同源数据链 ③ 无依赖（不同数据源/维度）可并行·纯函数·不交 LLM。

**glm组 判断：agree·判据够·不交 LLM 对。**

**理由**：
1. **依赖判据三类够用**——`$n` 引用（显式·tools.js:202 `ref()` 解析）+ layerId 传入 params（显式）+ 同源链（隐式·如聚合→排序）覆盖了 EMC 当前所有工具协作模式。
2. **不交 LLM 判依赖对**——对齐"编排器确定性"铁律（AI·Copilot 内核）。LLM 判依赖不可控·代码判依赖可测。
3. **DAG + 拓扑排序是标准工程**——成熟算法·纯函数可单测。

**glm组 补充（判据边界）**：
- **buffer 依赖 center POI**（焦点 1 问）——若 center 是 search_place 返回的坐标（非前序图层 layerId）·则**非图层依赖**（是参数依赖·place_search 不产图层）·不阻止并行。但若 center 是前序 extract_feature 产的图层·则有依赖。**判据须区分"参数依赖"与"图层依赖"**。
- **merge 工具强制依赖**——merge 的 layer_a/layer_b 必然是前序图层·**merge 永远在最后一层**（无并行可能）。

**glm组 建议**：P3-1 依赖图**可独立做**（纯函数·零红线·~1 天）·即使不做并行·依赖图本身也有价值（可视化工具协作关系 + 为未来并行铺路）。

### 焦点 2：P3-2 并行执行（Promise.all 同层）— **disagree（阻断级·$n 机制 + 收益不足）**

**计划**：同层 `Promise.all` 并行·结果按原顺序合并·失败不阻塞·PARALLEL_ENABLED 开关。

**glm组 判断：disagree——两个阻断级问题 + 收益不足。**

**🔴 阻断 1：`$n` 引用机制依赖严格顺序·并行破坏索引确定性**

**证据（tools.js:181-207）**：
```javascript
const _stepResults = [];      // 按产出序单调 push
const _resultIdByStep = [];   // 与 _stepResults 平行
function ref(v) {
  const idx = parseInt(v.slice(1)) - 1;   // $1 → idx 0, $2 → idx 1
  const fc = _stepResults[idx];            // 按索引取
  ...
}
```
- `$n` 引用是**按产出顺序索引**——`$1` = 第一个产出的图层·`$2` = 第二个。
- **并行执行时·完成顺序不确定**——若 density_A 和 density_B 并行·A 先完成则 A=$1·B 先完成则 B=$1·**`ref('$1')` 指向不确定**。
- 计划称"结果合并按原 tcs 顺序写入 toolHistory"——但 `_stepResults` 的 push 时机是**工具执行时**（tools.js:369 `addResultLayer` 内）·非合并时。即**并行工具各自 push _stepResults·顺序由完成时序决定·非 tcs 顺序**。

**后果**：merge `$n` 引用（如 merge layer_a=$1 layer_b=$2）在并行场景下可能**合并错误的两个图层**——静默数据污染·不可接受。

**修复成本**：要让并行 + $n 共存·须重构 _stepResults 机制（改为按 tcs 预分配索引·非动态 push）——**这是编排器深度改造·非"一次一处"能控**。

**🔴 阻断 2：并行收益不足（glm 上轮已判·本轮强化）**

**证据（multi skill 实际触发场景）**：
- `_allToolCalls` 主要触发点 = 族 A 用地扩展（harness.js:632 `autoExpandOverlays`·如"居住+商业"→ 多个 overlay/merge）——**这些是有 `$n`/layerId 依赖的·不能并行**。
- CHAIN_REGISTRY 2 条链（extract_overlay / clip_density）——**都是串行依赖链**。
- 真正"无依赖独立并行"场景 = **多极性 density**（如同时跑 positive/negative/overall 三张热力图）——但 EMC 当前 FC 极少产这种多 tool_calls（用户通常问一种极性）。

**收益量化**：
- 现状 multi 触发频率：**低**（族 A 用地扩展是主要场景·且有依赖·非并行）。
- 真正可并行场景（多极性 density）：**极少**（FC 通常产单工具或串行依赖链）。
- 墙钟收益：**几乎无**（绝大多数 multi 场景有依赖·串行无变化）。

**glm组 判断**：并行执行在 EMC 当前规模下**收益 ≪ 成本**——
- 成本：$n 机制重构 + 并行 eval + 失败处理 + 顺序确定性（~3 天 + 高红线风险）
- 收益：极少数多极性 density 场景提速（用户感知 ~秒级·非核心痛点）

**开关设计**：PARALLEL_ENABLED 开关本身合理·但"默认开"不对——**应默认关**（并行是优化·非功能·默认关保稳·验证充分后再开）。

### 焦点 3：P3-3 编排器稳定性（先扩 eval·一次一处）— **partial（SOP 够·但并行对防线有副作用）**

**计划**：先扩 eval（依赖图单测 + 并行 E2E）再动·一次一处·PARALLEL_ENABLED 开关。

**glm组 判断：partial——SOP 够·但并行对现有防线有未识别副作用。**

**SOP 充分性**：
- "先扩 eval 再动·一次一处"——✅ 对齐承重红线 SOP。
- 依赖图纯函数单测——✅ 可做（零红线）。
- 并行 E2E——⚠️ **难做**（并行时序非确定性·E2E 难稳定复现·需 mock 时序或多次跑取并集）。

**并行对现有防线的副作用（计划未提）**：

| 防线 | 副作用 | 严重性 |
|---|---|---|
| **`_stepResults` / `$n` ref** | 并行 push 顺序不确定·`$n` 索引错（焦点 2 阻断 1）| 🔴 阻断 |
| **applyQualityDefense 对账** | L1 `_verifyClaims` 查"声称图层不在地图"——并行时图层产出时序乱·`getArtifacts()` 快照可能漏层 | 🟡 中 |
| **R 规则（R3 参数一致/R4 状态矛盾）** | 并行工具各自 obs·合并后 toolHistory 顺序与 obs 时序不一致·R3 对账可能误判 | 🟡 中 |
| **出口卡 _maybeBuildOutletCard** | 并行多工具产多图层·`getArtifacts()` 取 last——可能取到非主分析图层 | 🟡 中 |
| **`_lastToolRows` 缓存**（Wave 1）| 并行 rows 型工具各自 push·`_lastToolRows` 被最后一个完成者覆盖（竞态）| 🟡 中 |

**glm组 建议**：若做并行·须先**审计所有依赖执行顺序的状态**（_stepResults / _lastToolRows / getArtifacts / _consumedIds）·并行化前全部加"预分配索引 + 合并时统一提交"——**这是编排器深度改造·非"一次一处"能控**。

### 焦点 4：P3-4 地点联动（工具出口统一 place_name）— **agree（值得·低风险·但须守契约）**

**计划**：各工具返回结果统一带 `place_name`（若含空间落点）·供 EMC/出口消费。

**glm组 判断：agree·值得做·低风险·但须守工具契约。**

**理由**：
1. CB-15 已落地 place_name（聚合层 _attach_poi_attrs）·但**只在 zonal/grid 产物**——density/buffer/hotspot 等工具的返回结果**不带 place_name**。
2. P3-4 统一各工具带 place_name——让出口卡/结论段从**任何工具**都能取地点·对齐"地点=关键点"（用户）。
3. 低风险——工具返回值加字段（非改签名）·既有消费方不受影响（不读 place_name 的忽略）。

**会不会动工具契约？**
- TOOLS 返回值结构：现 `{observation, data: {layerId, rows, ...}}`——**加 `data.place_name` 是增量·非契约变更**。
- 但须守 **tool_contracts.py 契约三处同步**（CB-04 教训）——若 place_name 进契约 params/yields 描述·须三处同步。
- **glm组 建议**：place_name 是**返回值字段**（非 params）·不进 tool_contracts params schema·只进 yields 描述（可选）·**避免触发契约同步开销**。

**实现建议**：
- density/buffer/hotspot 等点/面工具：在 addResultLayer 时·从图层质心 reverse_geocode 取 place_name（复用 place_layer.reverse·已有）。
- 或：工具返回时统一调 `_attach_place_name(result)` 纯函数（从图层几何取质心→reverse）。

## 三、可否执行结论

### ⚠️ 有条件执行——P3-2（并行）砍掉或后置·P3-1+P3-4 可立即做

**glm组 核心立场（与上轮一致·强化）**：

1. **P3-2 并行执行——不建议做**：
   - 🔴 `$n` 引用机制阻断（_stepResults 顺序依赖·并行破坏索引）
   - 🔴 收益不足（multi 触发场景多有依赖·真正可并行极少）
   - 成本严重低估（3 天 → 5-9 天·含 $n 重构 + 状态审计）
   - **glm组 建议：砍掉 P3-2 或后置到 EMC 规模化（多用户/批处理）时再做**。

2. **P3-1 依赖图——可做（纯函数·零红线·~1 天）**：
   - 即使不做并行·依赖图本身有可视化/审计价值。
   - 为未来并行铺路（依赖图是并行的前提条件）。

3. **P3-4 地点联动——可做（低风险·~0.5-1 天）**：
   - 工具返回加 place_name 字段·对齐"地点=关键点"。
   - 守契约（不进 params schema·避免同步开销）。

4. **排期——后置到热点图专题之后**：
   - P3 动编排器·热点图也动工具/渲染——**避免撞车**。
   - 热点图是用户核心诉求·P3 是优化·优先级低。

**承重红线复核**：
- **四态出口**：P3-1（纯函数）/ P3-4（返回值加字段）不触碰。P3-2（若做）动 runAllToolCalls·**不碰四态裁定**（四态在 applyQualityDefense·非 runAllToolCalls）✅
- **finalStep D019**：P3 不涉及 prompts.py ✅
- **diagnose 永不动**：P3 不涉及 diagnose ✅
- **但 P3-2 动编排器（runAllToolCalls）= 核心稳定性**——即使不碰三红线·也是高风险区·须"先扩 eval 再动·一次一处"。

**glm组 最终建议**：
- **立即做**：P3-1 依赖图（~1 天）+ P3-4 地点联动（~0.5-1 天）= **~2 天·零红线**
- **后置/砍**：P3-2 并行执行（$n 阻断 + 收益不足 + 热点图冲突）
- **排期**：P3-1/P3-4 在热点图专题完成后做（避免 harness 撞车）
