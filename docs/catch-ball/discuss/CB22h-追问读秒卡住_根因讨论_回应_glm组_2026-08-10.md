### 1.3 为什么 trace 里 LLM 挂 5 分半无 exit（焦点 1 回应）

**glm 根因分析（代码 + 网络双视角）**：

trace 时间线：`17:13:45 flash finalStep LLM 开始 → 无 exit → 17:19:11 pro 重试（5 分半后）`。

- **非"连接挂着不返回"**：DeepSeek 流式若连接挂住不发数据·httpx read timeout=60s（llm.py:58·核实见 §二）应在 60s 后触发 ReadTimeout → 抛 LLMError → `chat_with_fallback` mid-stream raise（llm.py:357-358）→ 后端 SSE error 帧（router.py:108）→ 前端 onError。**但 trace 挂了 330s（5 分半）远超 60s**。
- **glm 推断**：DeepSeek 在流式连接建立后**间歇发送心跳/空 chunk/极慢 chunk**——每次有数据到达都**重置 httpx 的 read timeout 计时**·导致 60s read timeout 永远不触发。这是 SSE/HTTP-2 流式协议的常见陷阱——"慢速攻击"（slowloris 类）让连接名义上活着实则不产出有效内容。
- **铁证**：trace 的 `all providers exhausted: 401 + net + mid-stream failure`（17:11:20）——`mid-stream failure` = 流中途断（llm.py:357 D_003）·说明 DeepSeek 确实在流式过程中断·但中断时机不确定（有时首 chunk 前·有时首 chunk 后）。
- **5 分半无 exit 的真正机制**：`MAX_RETRIES=3`（llm.py:28）× 退避 `2**attempt` 秒（1+2+4=7s）× provider 链（DeepSeek→Ark→讯飞·多家）= retry 总耗时可达数十秒·**但不足以到 330s**。**5 分半更可能是前端 streamChat 的 45s abort 没真正生效**（见 §三焦点 3）·后端仍在 retry/挂·前端读秒不停。

## 二、代码根因独立取证

### 2.1 后端 LLM 超时——httpx timeout=60s 存在·但 stream 模式有心跳陷阱

**glm 核实**（ai_qa/llm.py）：

| 行 | 代码 | 核实 |
|---|---|---|
| :58 | `timeout: float = 60.0`（LLMClient 构造默认） | ✅ 有超时·非"无超时" |
| :62 | `self.timeout = timeout` | ✅ |
| :96 | `with httpx.Client(timeout=self.timeout) as client:` | ✅ 传给 httpx |
| :97 | `with client.stream('POST', url, ...) as resp:` | ⚠️ stream 模式 |
| :103 | `for line in resp.iter_lines():` | ⚠️ 逐行读 |

**httpx.Timeout(60.0) 语义**（glm Python 核实）：
```
connect=60.0  read=60.0  write=60.0  pool=60.0
```
- `read=60.0` = **每两次 chunk 之间最多等 60s**（非总时长）。
- **陷阱**：若 DeepSeek 间歇发心跳/空 chunk（每 < 60s 发一个）·read timeout 被反复重置·**理论上可无限挂**。
- trace 挂 330s（5 分半）远超 60s = **心跳重置 read timeout 的铁证**（或 httpx 在 stream 模式 timeout 不生效于 iter_lines·需进一步确认）。

**glm 结论**：claude 焦点 2「后端无服务端超时」**部分不成立**——httpx 有 timeout=60s·但**标量 timeout 在 stream 模式 + 心跳保活场景下失效**。修复不是"加 timeout"（已有了）·而是**改用总预算超时**（如 `httpx.Timeout(connect=15, read=60, write=60, pool=60)` 不够·须在 `chat_with_fallback` 外层加**总 deadline**·如 `time.monotonic() + 90s` 强制 break）。

### 2.2 承重发现：`_assembleKnowledgeQA` 调 finalStep 无 try/catch（知识问答路径裸抛）

**glm 核实**（harness.js + stages.js 交叉对比）：

**这是 CB-22f 引入的回归**——CB-22 三层架构加 `_assembleKnowledgeQA` 时·照着 quick-general 短路（:1127 裸 await）写的·没照 runTemplatePath（:850 有 catch）的健壮模式。**CB-22f 的知识问答路径是后加的·漏了降级兜底**。

### 2.3 前端 abort 降级链路——45s abort 生效但降级无出口

**glm 核实**（api.js:34-79 + stages.js:474-486）：

| 层 | 行 | 代码 | 核实 |
|---|---|---|---|
| 前端超时 | api.js:34 | `_timeout = opts.phase === 'answer' ? 45000 : ...` | ✅ answer phase 45s |
| abort 触发 | api.js:36 | `setTimeout(() => _ac.abort(...), _timeout)` | ✅ 45s 后 abort |
| fetch signal | api.js:46 | `signal: _ac.signal` | ✅ 传给 fetch |
| reader 中断 | api.js:57 | `await reader.read()` | ⚠️ abort 后应抛 AbortError |
| onError 回调 | stages.js:479 | `(err) => { throw new Error(err) }` | ⚠️ throw 在 Promise 里 |

**glm 分析**：
- 前端 45s abort **会触发**（api.js:36 setTimeout）·AbortController.abort() 会让 fetch 的 `reader.read()` 抛 AbortError。
- streamChat 的 `finally { clearTimeout(_timer) }`（api.js:77-79）清理 timer·但 **streamChat 本身没 try/catch 包 `await reader.read()`**——AbortError 会冒泡到 streamChat 的调用方（stages.js:477 finalStep 的 `await streamChat`）。
- finalStep 的 onError 回调（stages.js:479）`throw new Error(err)`——**但这是 streamChat 内部 reader 抛的 AbortError·不走 onError·而是直接 reject Promise**。
- 所以 finalStep 的 `await streamChat` reject → finalStep throw → **harness.js:214 裸 await 抛出** → 无降级。

**glm 结论**：前端 abort 生效（45s 触发）·但**降级无出口**——`_assembleKnowledgeQA` 没 catch·abort 后的异常无处可去·UI 读秒不停。**焦点 3「用户没看到降级结论」的根因 = `_assembleKnowledgeQA` 无 try/catch**（不是 abort 没触发）。

### 2.4 BGE 冷加载 15.9s——预热已存在但竞态

**glm 核实**：

| 文件 | 行 | 代码 | 核实 |
|---|---|---|---|
| api/main.py | :70-86 | `@app.on_event('startup') async def _startup_rag_warmup(): threading.Thread(target=_warmup, daemon=True).start()` | ✅ 预热存在 |
| tools/rag_index.py | :259-270 | `def warmup(): _get_model()` | ✅ 单例缓存 |
| tools/rag_index.py | :251-256 | `def _get_model(): if _model_cache is None: _model_cache = SentenceTransformer(MODEL_NAME)` | ✅ 首次加载 |

**预热竞态分析**：
- startup 用 **daemon thread** 异步预热（api/main.py:86）·非阻塞启动。
- 用户首问若在预热完成前到达 → `_get_model()` 在 rag_search 端点内**同步加载**（15.9s）·阻塞 uvicorn 事件循环。
- trace 17:13:29 rag_search enter → 17:13:45 exit（15.9s）= **预热竞态铁证**（daemon thread 未跑完·用户已问）。
- **15.9s 阻塞 uvicorn** → finalStep LLM 调用排队 → 加剧读秒感知（但非主因·主因是 §2.2 无降级）。

**glm 结论**：预热存在但竞态。修复方向：
- **方案 A（推荐）**：预热改**同步阻塞启动**（startup 时 `await _warmup()`·uvicorn 等 BGE 加载完再接请求）——启动慢 15s 但消除首问竞态。
- **方案 B**：rag_search 端点检测 `_model_cache is None` 时**返"模型加载中"友好提示**（非阻塞 15.9s）·前端显示"知识库加载中·请稍候"。
- glm 倾向 A（一次阻塞换稳定）·但需用户确认启动时间可接受（15s）。

## 六、glm 交叉挑战

### 挑战 claude（2 条）

**挑战 1：claude 焦点 2「后端 LLM 无服务端超时」——glm 核实 httpx timeout=60s 存在·为什么 claude 说"无超时"？**

**挑战 2：claude 根因链 R2「后端 uvicorn LLM 调用无服务端超时→单线程阻塞」——但前端 45s abort 应已让 streamChat reject·为什么用户看 5 分半？**
