## 白话摘要

把您测出的两个毛病翻了个底朝天，结论一句话：**不是 AI 变笨了，是"货架"上摆错了货**。

第一个毛病（口径说 130 个社区、还提"两个方面"）：您今天整理的数据和口径说明，存在两个仓库里，**AI 检索用的那个仓库（08-20 建的索引）根本没更新**，您更新的那个仓库（对话学习库）AI 又**不读**；加上旧口径的说明文字还挂在"权威清单"上没撤下来，AI 一问就捡到旧说法。更要命的是：**您上传的 193 个社区，货架上真的没有**——文件在硬盘里躺着，但登记表里查不到它，能查到的只有 130 和 174 两个旧范围。所以 AI 说"130 个社区"，不是它瞎编，是它翻遍货架只能找到 130。

第二个毛病（7 个社区画得歪歪扭扭、对不上）：因为 AI 在货架上找不到 193 那批真实边界，又没有任何工具能让它"按名字取出一块真实边界"，它只能凭记忆"凭手感画"——您看到的粗糙多边形就是这么来的。**真实边界数据完全在**（7 个社区在 193 文件里个个都能对上号，中位数 215 个顶点，而 AI 画的只有 5~20 个点），就是没有通道把它送到 AI 手里。修法也不难：把 193 登记上货架 + 给一个"按名字提取边界"的工具 + 让 AI 检索库吸收今天的整理，两个毛病一起好。

## 二、Bug1 根因链（四层·全部实测证据）

### R1-1 · RAG 检索索引未重建（直接根因）

- 索引 `DATA/RAG/rag_index/`（meta.jsonl + vectors.npy）mtime = **08-20 17:16**，364 条；今天（08-25）DATA 整理与口径完善**未触发重建**（`py tools/rag_index.py --build` 未执行或未生效）。
- 检索链路：`rag_query` → `tools/rag_index.search` → 索引；索引数据源 = `docs/urban-renewal-plan/*.md` + `ai_qa/outlet_kb/`（事实卡 + case_library）（rag_index.py:37/254/277）。
- **实证**：`rag_query('统计范围 130 社区')` 命中 08-20 索引内旧知识卡（URP-*）。

### R1-2 · 用户今天的「RAG 完善」落点不在检索链路

- 用户完善落点 = `DATA/RAG/ai_qa/episodes.jsonl`（mtime **08-25 14:17**·L3 学习库·`ai_qa/episode.py` 写入路径）。
- **episodes 不在 rag_query 检索链路**——索引数据源不含它。完善对象与检索对象是两个系统：**完善了，检索端读不到**。

### R1-3 · 旧口径素材仍在检索源 + 消费面不对称（新证据·比 claude 报告更深一层）

- `docs/urban-renewal-plan/00-宜昌专项/_口径注册表.md`：**130 行 55 标 current**（西陵+伍家岗）；「两个方面」行 15-17 仍在（08-13 定稿）；193 行 52 也标 current——**三口径并存、无「任务临时 vs 现行权威」标注**，且 130 值锚点引用旧路径 `DATA/boundaries/presets/manifest.json`（已迁移不存在）。
- **消费面实测（resolve_boundary）**——这是本次复核的新关键证据：

| preset id | 含义 | resolve_boundary 实测 |
|---|---|---|
| `checkup_cfg_community` | 174 社区（去村） | ✅ OK（174 features） |
| `checkup_cfg_community_xlwj` | **130 社区**（西陵+伍家岗） | ✅ OK（130 features） |
| `base_community_area` | **193 社区（含村）** | ❌ **FAIL：文件未落盘**（manifest file= `../../analysis/体检对象_社区_面.geojson`·迁移后旧路径不存在） |
| `subj_12345_safety/livelihood_community_point` | 12345 两类社区点层 | ❌ FAIL（file= `../../analysis/12345主观/…`·已退休） |

- **用户上传的 `DATA/AUTHORITY/boundaries_社区村_193.geojson`（08-25 11:43）未登记进 manifest**（grep 'boundaries_社区村' 零命中）。
- **结论**：模型（cdh）list_data 时社区边界只有 174/130 可见、193 不可见——**它说「130」不是随机引用，是货架上只有它**。这句是本次复核对 claude 报告的最大补充。

### R1-4 · 模型行为面（知识口径 vs 本次输入未区分）

- 模型把 RAG 知识口径直接当成本次任务口径，未声明「130=西陵+伍家岗历史口径·与你上传的 193 非同一对象」；「安全韧性/民生基础=12345 数据分类名」被表述成「你上传的两类社区层」——知识卡语境与本次任务语境混用。
- AGENTS.md/persona 无「用户上传数据优先于知识库口径」纪律 → 无约束。

### 关联放大项（环境）

- **manifest 内 file 引用与迁移后实际路径不符**：Codex 08-25 迁移已同步代码常量（`range_selector._PRESETS_DIR` 等），但 **manifest.json 内部的相对 file 字段**（`../../analysis/…` 一系）未同步——193/12345 点层等 preset 全部 resolve 失败。这是「迁移半程」的实锤，且影响面比 claude 报告所述（MANIFEST 常量路径）更大。

## 三、Bug2 根因链（三层·产物 spec 实证）

### R2-1 · 模型手绘内联 GeoJSON（直接根因）

- 最新 applied spec（`DATA/Export/exports/render_inbox/applied/1787638661446-8079.json`·用户实测产物）：`kind: choropleth`·**dataset_id 无·inline 7 feats**·`origin: {producer: dsh, source_tool: manual}`。
- 顶点统计：朝阳路 18 / 万达 6 / 港务 5 / 建设 MP(4+8) / 岳湾路 11 / 大学路 20 / 伍临路 7——**5~20 顶点/面**。
- **真实 193 社区面顶点：min 21 / 中位 215 / max 1512**——差 10~40 倍。且 7 个社区名在 193 中 **7/7 全部命中**（SQMC 字段）：**真实边界数据在位，只是模型拿不到**。
- 历史同模式：`1787634299060-2226.json`（20 feats·5~20 顶点）同源手绘——非偶发。
- 注：`producer: 'dsh'` 系 render_spec 默认值（mcp_server_emc.py:1454），无法凭该字段区分投递引擎；现场为 cdh（codex Harness·claude 报告已确认）。

### R2-2 · 工具面缺「从边界 preset 提取子集精确几何」能力（结构性根因）

- 18 件 MCP 工具中：zonal_stats/rank/compare_regions 返回聚合 rows（无几何）；`zonal_stats(layer_output=True)` 虽带 geojson，但 `_layer_output_geojson` **带 shapely simplify 简化（>100 顶点即简化）+ 200KB 体积硬顶**——即使走此通道也是失真几何，且语义是「top_n 聚合面」非「按名取子集」。
- **没有任何工具能把 boundary preset 按名称过滤子集并返回精确几何** → 模型想画「这 7 个社区的范围」时无工具可用 → 退化到 LLM 自画。

### R2-3 · 无出图几何纪律约束

- AGENTS.md/cdh 引导只规定「必出图」·未规定「几何必须来自工具提取」；无内联几何质量守卫（顶点下限/面积合理性校验）→ 手绘静默上线。
