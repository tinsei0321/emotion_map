## 一、逐焦点

### 焦点 1：方案选择 — **A+B 结合（A 主 + B 兜底）**

| 方案 | glm组 判定 | 理由 |
|------|:---:|------|
| **A（request_upload 短路）** | **✅ 主路径** | 根因在 harness derive 失败（:1602 else）——该处只打 console.info 不处理 boundary → 空对象传入 zonal。在 else 分支加 `strategy='request_upload'` → 复用 :1115 短路 → buildRequestUploadText 出诚实文案。**零新机制·复用现有四态出口** |
| **B（handler 兜底）** | **✅ 补充** | tools.js :1009 zonal handler 已有 boundary 校验（`if (!params.boundary)`）。补一条：boundary 是空对象/无 features → observation 返"边界无法解析·需上传标准资料"。**防御纵深——即使 A 漏了（如 deriveMissingParams 未触发），handler 层兜底** |
| C（不动） | ❌ | PRM-07 持续 fail + 用户被误导 |

**为什么 A+B 结合**：
- A 在 orchestrate 层拦截（deriveMissingParams 的 else 分支）——**最早拦截点**·boundary 空对象根本不传到工具
- B 在 handler 层兜底——**如果 A 因某种原因未触发**（如非 zonal 工具也收到空 boundary）·handler 层有防线
- 两层防御·与黑名单（boundary-resolve.js 单要素拒识）形成**三层覆盖**：
  ```
  层 1（boundary-resolve.js）：单要素 + 有 name + 命中黑名单 → throw
  层 2（harness deriveMissingParams）：boundary 可疑 + derive 失败 → request_upload 短路  ← 方案 A
  层 3（tools.js zonal handler）：boundary 空对象/无 features → observation 兜底  ← 方案 B
  ```

### 焦点 2：用户上传层权衡 — **不误伤（derive 成功 = 放行 / derive 失败 = 诚实 request_upload）**

**关键区分**：

| 场景 | deriveAvailable 结果 | 方案 A 行为 | 合理性 |
|------|:---:|------|:---:|
| 用户上传合法层（含"南山区"）→ deriveAvailable 匹配 | 非 null | **放行**（boundary 精确填充） | ✅ 用户上传层不受限 |
| 用户上传无 name 合法 GeoJSON → deriveAvailable 无匹配 | null | **request_upload** | ✅ 诚实——EMC 确实无法用该边界（无 name 无法定位要素） |

| LLM 直传"西陵区"→ deriveAvailable 匹配 | 非 null | **放行** | ✅ 正常路径 |
| LLM 直传"小溪塔"→ 白名单过滤 → deriveAvailable null | null | **request_upload** | ✅ 法定功能区不硬猜 |

**结论**：方案 A **不误伤用户上传层**——"用户上传但 EMC 无法 derive" = EMC 确实无法用该边界 = 诚实 request_upload 是正确行为（不是误伤·是如实告知）。

### 焦点 5：补充与异议

**根因链核实**：claude组 描述的根因链**准确**——`_boundarySuspect`（:1586-1590）识别空对象为可疑 → deriveAvailable 返回 null（小溪塔不在白名单）→ else 分支只打 console.info → p.boundary 保持空对象 → 传 zonal → 后端"无数据" → 误导。

**一个补充**：方案 A 的触发条件应**加 `_boundarySuspect(p.boundary)` 守卫**——只在 boundary 确实可疑（空/多要素/字符串）时才设 request_upload。如果 boundary 是合法单要素（deriveAvailable 偶发失败但 boundary 本身有效）·不应 request_upload（应让它执行）。

```javascript
// 建议的条件（不只是 derive 失败·还要 boundary 可疑）
if (_boundarySuspect(p.boundary)) {
    diagnose.data_plan.strategy = 'request_upload';
    // ...
}
```

**这样避免误伤**：如果 FC 直传了一个合法的单要素 GeoJSON（features.length=1·有 name·不在黑名单）但 deriveAvailable 因层加载竞态偶发返回 null → `_boundarySuspect` 返回 false（单要素 = 不可疑）→ 不设 request_upload → boundary 保留 → 正常执行。
