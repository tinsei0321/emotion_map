## 〇、问题摘要（claude 已核实）

### 现象
问「小溪塔范围内按面聚合情绪统计」→ 实测回答「**[object Object] 范围内未聚合到足够的情绪点数据**…换一个区域重试」——**误导用户**（听起来像「小溪塔真的没数据」·实际是 **EMC 无法解析边界·应诚实要求上传标准资料**）。

### 根因链（代码核实）
```
LLM 直传 boundary = 空对象/无 name GeoJSON（FC 偶发不填 boundary 名）
  ↓
harness.js _boundarySuspect（:1585-1590）识别「可疑」（f.length !== 1）
  → _needDerive = true → deriveAvailable('小溪塔') → 返回 null
  （小溪塔=法定功能区·不在 FIXED_ADMIN_DISTRICTS 白名单·derive 拦）
  ↓
:1602 else 分支（derive 失败）：只打 console.info 诊断·不处理 boundary
  → p.boundary 保持空对象 → 传 zonal
  ↓
zonal 后端「无数据」（该范围无点覆盖）→ LLM 弱化转述「数据不足」→ 误导用户
```

### 影响
- **用户理解被误导**（以为区域真无数据·而非 EMC 无法定位边界）
- **PRM-07 持续 fail**（verify 加严后诚实暴露）
- 黑名单（单要素拒识）已覆盖「单要素小溪塔」·但**空对象/无 name** 是盲区

---

## 一、修复方案（候选·待两组收敛）

### 方案 A（推荐·复用 request_upload 流程）
**boundary 可疑 + derive 失败 → 走 request_upload 短路**（对齐 CB-14「EMC 不硬猜」）：
- harness.js :1602 else 分支：derive 失败时·若 boundary 可疑（非精确单要素）→ 设 `diagnose.data_plan.strategy='request_upload'` + `needed=['标准边界资料（行政区划/更新单元 Shapefile/GeoJSON）']` → orchestrate :1115 短路 → `buildRequestUploadText`（说清需要什么/为何/格式）
- **效果**：替代「传空对象让 zonal 报无数据」·用户看到诚实「需上传标准边界资料·因为小溪塔为法定功能区·EMC 不预置」
- **复用**：`buildRequestUploadText`（harness.js:192）·`orchestrate` request_upload 短路（:1115-1118）·零新机制

### 方案 B（前端 handler 兜底）
- tools.js zonal handler：boundary 为空对象/无 name → observation 返「边界无法解析·请上传标准资料」（非「无数据」）
- **缺点**：observation 是工具结果·LLM 转述仍可能弱化（P2-3 暴露的转述问题）·不如 request_upload 短路直接
- **优点**：改动更小（仅 handler）

### 方案 C（不动·维持现状）
- 「无数据」虽误导·但用户可「换区域重试」（实测选项）·非阻塞
- **缺点**：PRM-07 持续 fail·用户理解持续被误导

### 关键权衡（两组评估重点）
1. **与「用户上传层不受限」**：用户上传的**无 name** GeoJSON（合法·未命名区域）→ 方案 A 会 request_upload（误伤）？如何区分「用户上传」vs「LLM 直传空对象」？
   - 可能：deriveAvailable 能 derive（用户上传的合法层）→ 放行；derive 失败（无匹配）→ request_upload（诚实）
   - 用户上传但 EMC 无法 derive → 也应 request_upload（EMC 确实无法用该边界·诚实）
2. **承重风险**：改 orchestrate 短路路径（:1115）·影响 request_upload 整体流程？还是仅新增一条触发路径（boundary 解析失败）？
3. **与黑名单协同**：单要素拒识（已有）+ 空对象 request_upload（新增）→ 全覆盖？
