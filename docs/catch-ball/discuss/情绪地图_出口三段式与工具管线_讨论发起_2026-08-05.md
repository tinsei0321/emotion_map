## 〇、执行摘要（结论先行）

**用户提出两个后续优化方向**：

**方向 A —— 分析结论「出口」重新整理成新三段式**（替换旧三段式）：

```
第一段  明确观点（LLM 核心价值）：基于用户提问/要求形成的"观点"（一句话/一段话）
第二段  4 要点：①分析方法(方法论/工具/流程) ②使用数据(类型/来源) ③分析结果(图/数/表) ④分析结论(基于图数表的描述性论述·专业学术)
第三段  行业接口对标对表 → 一键入库"参数"：城市体检/更新板块·「更新需求调研」场景具体指标（参考国内指标案例）
```

> **关键区分（用户强调）**：第一段「观点」≠ 第二段「分析结论」——观点 = 分析结果**转化**→ 针对用户提问的解答；分析结论 = 基于图/数/表的**描述性论述**（更专业、更学术）。

**方向 B —— 工具管线优化**：工具调用、工具间协作（线性/并行关系）、工具分析结论与地点信息联动。

**方向 C —— 所有工具出口联动空间/地点信息**（关键点）：宏观→行政区划/片区面域；中微观→用地类型/详细地点，以此类推。三段式**哪个环节插入地点描述由成果范式 agent（LLM）思考**。

**目标**：让生成内容（即"出口"）**既稳定又保持灵活性**。

## 一、用户意图整理（原文要点 → 专业术语化）

### 1.1 新三段式（用户原话 → 结构化）

| 段 | 用户要求 | 专业解读 |
|---|---|---|
| **第一段 · 明确观点** | "一句话（或一段话）简要说明对应'用户提问/要求···'的'明确观点'（一定要在用户提问或要求基础上形成这个'观点'，这是 LLM 介入的核心价值）" | **观点 = 面向提问的转化性回答**（insight/answer to the question）·LLM 的认知增值发生在"把分析结果转成对用户问题的直接回答" |
| **第二段 · 4 要点** | "①分析方法（方法论、工具、流程）②使用数据（类型、来源）③分析结果（图、数、表···）④分析结论（基于分析结果图/数/表的描述性论述·更专业更学术）" | **结论 = 面向结果的描述性论述**（descriptive statement of results·objectivity）·与第一段观点互补：观点答"用户问的"，结论述"结果本身的" |
| **第三段 · 接口参数** | "针对市场/行业'接口'对标对表，形成一键入库的'参数'。暂时基于城市体检/城市更新展示板块，针对'更新需求调研'场景具体指标产出（参考国内指标案例优化细化）" | **出口 = 行业接口契约参数**（structured outlet params·可入库）·与现有 outlet_kb「更新需求调研」场景对接·细化到具体指标 |

### 1.2 工具管线（用户原话 → 结构化）

- "工具的调用、工具之间的协作（线性关系、并行关系等）、工具分析结论与地点信息的联动等管线还需要进一步优化"
- "所有工具的'出口'都要联动空间/地点信息……宏观尺度联动行政区划/片区等面域地点信息，中微观尺度联动用地类型、详细地点信息，以此逻辑类推"
- "至于在三段式的哪个环节或哪几个环节插入地点信息描述，需要 EMC 在成果范式 agent 思考（LLM 介入）"

### 1.3 目标（用户原话）

"让生成内容（即'出口'）既稳定又保持灵活性"——**稳定**（确定性组件·不飘）+ **灵活**（LLM 在观点/结论/地点插入处介入）——正好对齐项目「AI·Copilot 开发内核」：**Smart Agent（两端聪明）+ Dumb Tool（中间稳定）+ 编排器确定性**。

## 三、焦点问题（待 claude组 / Codex / glm组 讨论）

### 焦点 1（最高优先）：新三段式 vs 现有出口机制的映射与落地

新三段式（观点 / 4 要点 / 接口参数）如何落到现有机制上？三个候选：

| 方案 | 落点 | 优点 | 缺点 |
|---|---|---|---|
| **A. 呈现层重组**（不动承重） | finalStep prompt 输出结构化三段（观点+4 要点+接口参数引用），前端新模板渲染；四态出口/outlet_kb 不动 | 不撞红线；改动集中 finalStep+前端 | finalStep 极瘦红线（D019）——观点段需 LLM 介入，与"极瘦"张力 |
| **B. 结果 agent 结构化**（新增段） | 后端新增"结果结构化"纯函数（聚合诊断卡+tool_history+outlet 卡 → 三段 JSON）；finalStep 只渲染 | 确定性组装（对齐出口抽象层"结果范式"）；finalStep 保持极瘦 | 新增后端层；"观点"仍需 LLM（Smart 出口） |
| **C. 出口抽象层第三段扩展** | outlet_kb 增加"更新需求调研"指标细化 + 观点/结论模板；build_outlet_schema 扩字段 | 复用现成出向链路 | outlet_kb 变复杂；观点段可能被纯函数化丢 LLM 价值 |

**初步倾向**：**B（结果结构化）+ C（接口细化）组合**——确定性组件（4 要点 + 接口参数）走后端纯函数，LLM 只在"观点"（第一段）介入；对齐「Smart Agent 两端 + Dumb Tool 中间」。请两组独立评估。

### 焦点 2：「观点 vs 结论」的区分在 LLM/prompt 层的实现

用户强调第一段"观点"与第二段"结论"必须区分（观点=转化回答用户；结论=描述性论述）。落地难点：
- finalStep 极瘦（D019）下，观点段（LLM 介入）与结论段（可确定性生成）如何分工？
- 观点段需要"用户提问"作为强上下文——现状 finalStep 有 `context`（router.py:114 传 req.context）——是否够？
- 会不会出现"观点与结论重复/矛盾"？如何用 prompt 约束 + 前端呈现区分（视觉层级：观点=强调卡 / 结论=学术段落）？

### 焦点 3：第三段「一键入库参数」——更新需求调研场景指标细化

- 现有 outlet_kb「更新需求调研」卡的指标颗粒度（需求类型/强度/位置/归因/对接任务/优先级/数据基础）够不够"入库"？
- 参考国内案例（上海 45,578 份·93.60 分 / 广州 6.5 万份·81 项 / 南京大数据 87.65 分·15 处堵点 / 宁夏片区策划 13 表），细化哪些字段（如需求强度分级标准、优先级排序规则、指标口径对齐）？
- "一键入库"的技术形态：结构化 JSON schema（行业可消费）？CSV 导出？对接哪张行业表？

### 焦点 4：地点信息联动尺度规则 + 三段式插入环节

- **尺度规则**：宏观=行政区/片区面域（如"西陵区/滨江片区"）；中观=街道/社区/用地类型（如"葛洲坝街道/商业用地"）；微观=POI/详细地点（如"滨江公园/xx 路"）——规则是否成立？边界在哪？
- **插入环节**：用户要求"三段式哪几个环节插入地点描述由成果范式 agent（LLM）思考"——落点方案？(a) 观点段带地点（回答带地点才接地气）(b) 结论段带地点（描述性论述锚定位置）(c) 接口参数段带地点（入库参数需地点字段）——组合？
- **与 CB-15 的衔接**：place_name/poi_names/落点模板已落地——本专题是把"地点信息"从"工具出口"提升为"三段式出口"的标准要素。

### 焦点 5：工具管线优化（调用/协作/地点联动）范围与优先级

- 工具协作的"线性 vs 并行"编排规则：哪些工具天然串行（聚合→Gi\*→排序）、哪些可并行（独立分析）、现有 `multi` skill 够不够？
- 与「AI·Copilot 开发内核」（Smart Agent 两端 + Dumb Tool 中间 + 编排器确定性）的对齐；
- 优先级：出口三段式（A）vs 工具管线（B）vs 地点联动（C）——哪个先做、哪个后置？
