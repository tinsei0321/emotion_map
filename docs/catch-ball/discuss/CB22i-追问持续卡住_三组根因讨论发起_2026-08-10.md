## 四、核心矛盾（三组须解释）

**同机同 serve·Playwright 17:50 正常 10s·用户 18:09 挂起**。可能解释：

### 疑点 1：office 网络间歇性（最可能）
- DeepSeek 流式对 office 网络间歇性挂起（curl github 128KB 断流·git fetch reset 历史）
- Playwright 测时网络好·用户测时网络坏 → **环境差异·非代码**
- **但**：若网络挂起·前端 45s abort 应降级（Playwright 挂起桩测 45s 降级通过）→ **为什么用户没看到降级？**

### 疑点 2：前端降级在真实网络挂起场景的 edge case（核心待查）
- Playwright 桩测是「前端 route 拦截·连接挂着」→ 前端 abort → catch 降级 ✓
- 真实场景是「后端 uvicorn 调 DeepSeek 挂起」→ 前端 45s abort → **fetch abort 后 reader.read() 是否真的 reject？** 若后端挂着不发数据·前端 abort 应抛 AbortError→catch。但**若 DeepSeek 间歇发心跳/空 chunk·前端 reader 一直有数据·45s abort 后当前 read 挂**——需要验证
- **关键差异**：Playwright 桩测前端 abort 后**无后端真实连接**；真实场景 abort 后**后端 uvicorn 线程还在等 DeepSeek**（threadpool zombie）→ 前端 abort 后**浏览器可能等后端响应**而非立即 reject？

### 疑点 3：用户浏览器 JS 缓存（需排除）
- `?v=mtime` 自动注入·但用户若没强刷/浏览器缓存 → 旧 JS（无 catch 降级）→ 当然不降级
- **验证**：确认 serve 返回新 JS + 用户强刷

### 疑点 4：追问路径未覆盖（需确认）
- 用户说「追问后卡住」·但 trace 显示首问就挂——**用户首问成功过吗？** 若首问成功·追问卡·那卡点在 generate_point_layer/FC（未修）·若首问就卡·卡点在 finalStep（已修但未兜住）

### 焦点 1：为什么 Playwright 验证通过但用户仍卡（核心）

- 后端 uvicorn 挂起（DeepSeek 心跳）→ 前端 45s abort → `reader.read()` 行为？

### 焦点 3：首问 vs 追问的真实卡点

### 焦点 5：DeepSeek 流式挂起的根治
