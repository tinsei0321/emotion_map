## 一、9 个讨论问题逐条回应

### Q1. 出口差异化闭环（B1）——分歧：需要执行层强制，不能只靠 prompt

**判定：方向 agree（必须做），方法 partial（prompt 不够·需执行层强制）**

**理由**：

报告问"scale→出口强制映射——结论形态怎么区分"。核心问题是：当前架构下 outlet 是 diagnose 卡的一个**文本字段**（`stages.js:373` 硬编码"生成图层"），它被 `formatDiagnoseSummary`（`harness.js:145`）注入 ctx.context——**但没有任何执行层逻辑消费它**。finalStep LLM 看到 outlet=生成图层 vs outlet=报告结论 vs outlet=指标排序，对它的结论写作没有**约束力**——只是 context 里的一行提示文字。

**判据建议**（"不一竿子插到底"的客观判据）：

| 尺度 | outlet | 结论形态判据 | 执行层强制点 |
|------|--------|------------|------------|
| 宏观（分布把控） | 结构性结论·不归因 | 结论**不含**4×5 矩阵引用/单元名排序；**含**空间分布特征（密集区/稀疏区方位） | finalStep prompt 条件化 + R10（归因检测：宏观问 + 结论含"归因/4×5/要素×领域"→ 标注降级） |
| 中微观（归因排查） | 单元归因 + 排序 | 结论**含**具体单元名 + 4×5 落点 + 排序；**不含**全域泛述 | finalStep prompt 条件化 + R11（泛化检测：中微观问 + 结论不含具体单元名 → 标注） |

**为什么 prompt 不够**：即使 FC prompt 教了判尺度（Q2），finalStep prompt 仍需条件化——否则 LLM 拿到"宏观"tag 但仍然按惯性写归因（因为 toolHistory 有 zonal_stats 的 4×5 数据）。**必须执行层强制**——在 finalStep 调用前，据 outlet 注入不同的结论模板段。

**行动建议**：
1. 先修 `_normalizeFcDiagnose` 的 scale/outlet 硬编码（Q2 前置）
2. finalStep prompt 按 outlet 条件化（宏观→禁止归因段 / 中微观→必含单元排序段）
3. 加 R10/R11 防线（确定性检测·补 L1-R9 之后的新维度）

### Q2. scale 判定强化（B2）——共识：必须做·但 FC prompt 改动撞"不动 FC prompt"教训

**判定：agree（必须做），但需与 CB-10 教训对齐**

**理由**：

**与 CB-10 教训对齐**：

KNOWLEDGE §2 记录：「FC prompt 无内容守卫 → 静默删已验证段」（CB-10）。`build_fc_sys_prompt:29` 明确注释"plans/domain_lens 不再内嵌"——这是 0073990 删除后的**有意决定**，不是遗漏。重新加回 scale/outlet 指令 = 撞这条教训。

**但情况不同**（agree 加回）：
- 0073990 删除的是**plans 多步规划指令**（被 `_allToolCalls`/autoExpand 取代·有替代）
- scale/outlet/domain_lens **没有替代品**——硬编码默认值不是"替代"是"放弃"
- 加回的不是"plans 多步规划"（高风险），是"卡字段产出指令"（低风险·只增字段不改控制流）

**行动建议**：
1. `build_fc_sys_prompt` 加 scale 判定段（低风险增量·不碰工具选择规则）：
   ```
   ## 尺度判定（填入 diagnose 卡 scale 字段）
   - 用户问"分布情况/整体趋势/大致哪里"→ macro（宏观分布·粗粒度·不到归因）
   - 用户问"哪里最差/哪个区域/为什么/原因"→ meso（中微观·细粒度·要归因）
   - 用户问"这条街/这个点/这个小区"→ micro（微观落点）
   ```
2. 加内容断言（仿 `test_final_prompt_stays_lean`·防再被删）：`assert '尺度判定' in build_fc_sys_prompt('')`
3. `_normalizeFcDiagnose` 去硬编码 scale → 从 FC content 解析（仿 domain_lens A 部模式）
4. domain_lens A 部同包加回（已有 parse 逻辑 `stages.js:390-393`·只缺 FC prompt 指令）

**去硬编码默认 scale 的风险**：低——当前硬编码 macro 本身就是错的（中微观问被当宏观答）。去掉硬编码后，最坏情况是 FC 不输出 scale → fallback 到 macro（与当前行为一致）→ 无回归。

### Q3. 搜索能力（B3）——分歧：可行但应限制范围·避免成本/延迟爆炸

**判定：partial（可行·但不应全量搜索）**

**理由**：

EMC 当前是**纯本地分析**（GIS 工具 + LLM 推理·无外部数据源）。加搜索是架构级新能力——改变 EMC 的信息边界（从"只有用户上传的数据"到"可联网获取实据"）。

**可行性**：
- 技术栈已有 MCP web-search（`docs/mcp-strategy.md`·智谱 web-search-prime）——但这是 ZCode/Claude Code 的 MCP，**不是 EMC 运行时能力**。EMC 后端（FastAPI）需自行接搜索 API。
- DeepSeek/GLM 有搜索 API（智谱 web-search-prime / DeepSeek 搜索）——可接。

**建议的触发范围**（不是全量搜索·只补两个缺口）：

| 场景 | 触发条件 | 搜索什么 | 流程 |
|------|---------|---------|------|
| 大问题（情绪地图是什么/理念） | intent=general + 含"情绪地图/产品/理念/定位" | 四领域前沿政策 | diagnose→search→finalStep（搜索结果注入 context） |
| 聚焦问题（宜昌某区更新策略） | intent=emotion_analysis + 含策略/作用/应用场景 | 宜昌新闻/公开资料 | diagnose→search→finalStep |

**不搜索的场景**：纯 GIS 操作（依据 1）·单工具情绪分析（依据 3·有数据即可）——搜索会增延迟且无价值。

**成本/延迟控制**：
- 搜索只在 intent=general 时触发（`_quickIntent` 短路路径扩展）
- 搜索结果限制（top 3·截断）·注入 context 不独立渲染
- 搜索失败不阻塞（try/catch·fallback 到无搜索结论）

**行动建议**：排 G6（新能力最末）·但设计先行——搜索触发条件 + 结果注入格式 + 失败兜底先定稿，再接 API。

### Q4. 连问拆解（B4）——分歧：当前不推荐做·投入产出比低

**判定：disagree（当前不推荐做）**

**理由**：

1. **当前 Flash FC 单 tool_call 是常态**（07-30 P02 教训·CB-10 定型 A 主通道的基础前提）。连问拆解需要多意图解析 + 多步执行——在 Flash 单 call 限制下，**拆解本身就要靠正则或 LLM 二次调用**，成本高且不可靠。

2. **业界做法不适用**：plan-then-execute（GPT-4 多 tool_call）/ parallel tool_calls——这些都依赖**强 FC 能力**。Flash 不具备（CB-10 已验证）。盲目上 multi-intent 会让族 A（多步计划-执行断裂）问题在意图层复现。

3. **用户体验替代**：用户"连问"可以通过**追问胶囊**（已有）+ CPD（搁置但接口预留）实现——用户问第一个问题→系统出结论+追问胶囊→用户点胶囊问第二个。这比"一次输入多问→自动拆解"更可控（用户可见每步·不会黑箱）。

4. **投入产出比**：连问拆解是**架构级新能力**（意图队列 + 并行/串行调度 + 结论合并），工作量远超 PRM 修复/出口差异化。在 PRM 52% fail（链路不通）的前提下做连问拆解 = 在没修好地基时盖楼。

**行动建议**：defer 到 G6 之后·PRM 和出口差异化闭环后再评估。如果用户强烈要求，先做**最简版本**：分句（按。！？/逗号+连词拆）→ 每句独立 diagnose → 串行执行 → 结论拼接——不做并行·不做意图队列。

### Q5. 排版机制（B5）——共识：简单且高收益·应尽早做

**判定：agree（做·低成本高收益）**

**理由**：

当前 FINAL_TEMPLATE（`prompts.py` 的 `build_final_prompt`）已有结构化指令（三句骨架 + `{{show:}}` + `{{chart:}}` + 追问胶囊）——但**没有排版强调指令**（加粗/列表/符号）。用户要求"不只一段话"——这是**纯 prompt 改动**，零代码成本。

**具体范式建议**（加到 FINAL_TEMPLATE）：

```
**排版要求**：
- 用 **加粗** 标关键地名/数值/结论
- 用 - 列表 列多个发现（如多个区域排名）
- 用 > 引用块 标局限/数据口径说明
- 标题用 ## （如「## 西陵区消极情绪分布」）
- 禁纯段落堆砌·结构化呈现
```

**风险**：低——prompt 加段不改控制流。加内容断言（`assert '排版' in FINAL_TEMPLATE`·防删）。

**行动建议**：排 G5（体验门槛·横切）·可与其他 prompt 改动同包。
