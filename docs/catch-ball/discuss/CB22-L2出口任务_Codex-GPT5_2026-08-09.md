## 焦点 1 · outlet_kb 接入方式 — agree（diagnose 触发选型 + 确定性组装 + finalStep 注入）

**三段式**（与方案"Dumb Tool + Smart + 编排器"一致）：

1. **选型（diagnose 触发·零改动）**：复用 `resolve_outlet_ids(diagnose, question)`（`build_outlet_schema.py:158`）——在 harness finalStep 前置（或 router final 阶段）调用；**无命中→出向链路保持 0**（零开销·不改变现有行为）。
2. **组装（确定性）**：情绪数据在场 → `build_outlet_schema(diagnose, result, question)`（现成）；知识数据问题（无聚合）→ 新增 `build_knowledge_cards(diagnose, question)`（焦点 2 数据层·同样确定性·不调 LLM）。
3. **注入（finalStep）**：组装结果以结构化"出口卡"附入 finalStep context（含来源引用）→ 回答引用数值 + 前端可渲染卡片。

**接线位置建议**：`frontend/js/ai_qa/harness.js` 已有轻量 intent 预判（`harness.js:57-65` general 短路）——可仿该模式加 **outlet 短路**（高置信出口型问句跳过 agent loop 直出卡，省 LLM 轮次·利好调用效率轴）；后端 `router.py:114` 的 finalStep 是兜底注入点（context/tool_history 已透传）。

**红线核验**：不改 diagnose prompt/schema（outlet 字段已存在·只是补消费点）；四态出口 / @track 不动；新增函数按铁律埋点注册。

## 焦点 2 · 知识库引用边界 — partial（建议新增 L1.5 数据层 + intent-gated 注入）

**关键判断**："宜昌有哪些更新项目"是**结构化数据查询**——现有 `build_outlet_schema` 依赖情绪聚合 result，无聚合时缺数据源。建议补 **L1.5 结构化知识数据层**：

- 新文件 `ai_qa/outlet_kb/urban_renewal_knowledge.py`：从 L0 提炼**事实卡**（PROJECTS/INDICATORS/PANELS/CHECKUP_ISSUES）——每条 ≤80 字 + `source` 指针（`docs/urban-renewal-plan/_INDEX` 编号 + G 盘相对路径），例：
  - `{id:'URP-P12', name:'葛洲坝城市更新片区建设项目', scale:'12 个·11.07 亿', source:'docs/urban-renewal-plan/_INDEX#00-03'}`
  - `{id:'URP-P55', name:'2025-2027 更新典型片区+机制项目', scale:'55 个·51.33 亿', source:'_INDEX#00-03(260713)'}`
  - 体检数值卡（结构隐患 42 栋 → 附件3·来源标注）

**引用注入三层**：

| 层 | 行为 | 体积 |
|---|---|---|
| 默认 | 不注入（出向 0 保持） | 0 |
| 命中知识型意图 | 注入 top-N（≤5 条）事实卡 + 来源 | ~1-2KB |
| 出口卡/回答内嵌 | `[来源：附件5-城市更新项目库#12]` 标注 | 行内 |

**体积守卫**：intent-gated + top-N 上限 + 复用 `test_final_prompt_with_lens_stays_bounded`（现 final_brief 1625B<6000·余量充足）+ 新增"知识注入后 <8000B"专项断言。

**L1 vs L1.5 分工**：L1 放"口径/基数/底线"（已做厚·如 1058 小区/250 危旧房）；L1.5 放"明细数据卡"（项目清单/指标数值/来源）——**不重复搬 L1 已有内容**，L1.5 只做 L0→运行时的事实化映射。

## 焦点 3 · 体检-更新衔接契约 — agree（放 urban_renewal_outlets.py）+ field_mapping 设计

**放置位置**：agree——`stages.js:419` domain_lens 枚举仅 4 域（CB-21 已核实），checkup 契约 `DOMAIN='urban_governance'` 是贴靠；"体检→更新"衔接落 `urban_renewal`（在枚举内·语义更准·可触发）。

**field_mapping 设计建议**（新契约 `renewal_checkup_link`·体检问题→更新需求→项目衔接）：

| 行业槽 | EMC 字段 / 知识引用 |
|---|---|
| 体检问题指标 | `issue_label` + **L0 体检数值引用**（附件3：结构隐患 42 栋·来源标注） |
| 需求类型 | `domain_top/element_top`（4×5·设施/环境/服务/文化） |
| 需求位置 | `place_name` + 片区（葛洲坝/老城中心…） |
| 需求强度 | `polarity_index`（情绪在场）；**无情绪 → 问题规模分级**（42 栋/缺口数·确定性） |
| 更新项目衔接 | 问题 → `renewal_project`/附件5 项目库条目（id 引用） |

**边界诚实（双轨不混）**：情绪=感知维度（"哪里呼声高"）；体检数值=客观（"缺多少·在哪"）——`cannot` 明确"不能替代结构鉴定/资金评估"；`can` 明确"问题清单→更新需求→项目库条目"的确定性衔接。

**同步义务**：新增契约自动注册 `OUTLET_CONTRACTS`（`outlet_kb/__init__.py:21-26`）+ **TRIGGER_WORDS ↔ emc-patterns.js OUTLET_TRIGGER_KW 两侧同步**（`validate_outlet_trigger_sync` CI 守护）+ `test_outlet_kb` schema（can/cannot/boundary）。

## 焦点 4 · L2 确定性出口 vs RAG — agree（L2 确定性先行·RAG 后置·中间补轻量检索）

**边界**：

| 问题类型 | 手段 | 示例 |
|---|---|---|
| 结构已知查询 | 确定性出口（契约路由 + 结构化数据卡） | "宜昌有哪些更新项目"→项目库表；"葛洲坝体检问题"→问题清单表 |

**理由（代码级）**：`resolve_outlet_ids` + 触发词同步骨架已就绪（`build_outlet_schema.py:158` + `emc-patterns.js`）——确定性出口只差接线；结构化查询用向量是过度设计且召回波动；先确定性出口符合**防幻觉 + 演示逻辑链**北极星。RAG 专题（`EMC-RAG建设方案_本周重点_2026-08-09.md`）后置向量化 L0/outlet_kb，两者互补不冲突。
