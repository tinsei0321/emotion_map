## 一、逐焦点评估

### 焦点 1：P3-1 依赖图判定（DAG + 拓扑·纯函数·不交 LLM）

**判定：partial（方向对·判据缺两类 + 保守默认）**

证据与建议：
1. **不交 LLM 判依赖：对**——对齐编排器确定性铁律（CLAUDE.md:105"编排器确定性——协调是机械的，不调 LLM"）；tcs 本身是 LLM 产的 `diagnose._allToolCalls`，依赖判定若再交 LLM 会双重不稳定。
2. **判据 ③"同源数据链"与 ② 重叠**：`A 聚合 → B 在其结果上分析` 实际就是 `B.params 含 A 产物引用`（layerId/$n/rows）的特例——建议合并为两条硬判据 + 一条软判据：
   - **显式引用**：`$n`（tools.js:202-223 ref 解析）/ params 含前序 layerId / params 含 rows 引用；
   - **资源冲突（缺失）**：同 sourceKey 竞争（如两个 density 同一数据源——generateHeatmapForAI 对同源互斥删旧层）、互斥工具类（grid/terrain 独占显示）——**这类必须串行或降级并行**，计划未提；
   - **保守默认（缺失）**：静态无法证明无依赖 → **串行**（安全默认，宁可少并行不可错并行）。
3. **LLM params 不可靠**：tcs 的 params 可能缺显式 $n 却实际依赖（LLM 省略引用）——所以"静态可证无依赖才并行"是唯一安全策略，计划应写明。
4. **eval 落地未明确**：项目**无独立 JS 单测基建**（测试 = tests/browser Playwright `page.evaluate` + test-cases.js LLM 用例）——`dep-graph.js` 纯函数单测需明确载体：建议 Playwright `page.evaluate` 动态 import 直测（确定性断言），或引入极简 JS 单测 runner；test-cases.js 的 LLM 用例不适合测纯函数。

### 焦点 2：P3-2 并行执行（Promise.all 同层）

**判定：partial（值得做·复杂度被低估·2 个阻断级前置）**

证据与建议：
1. **收益真实**：LLM 产的多 tool_calls 多为并列独立操作（多目标裁剪 autoExpand、多极性 density）——现状全串行（runAllToolCalls :1911-1960 for 循环 await），墙钟 3×→1× 对演示节奏可见。glm 上轮"并行收益有限"针对的是**单用户串行可接受**，但 P3 目标明确（独立分析提速），值得做。
2. **🔴 阻断级前置 1：`$n` 索引破坏**——`_stepResults` 按**产出序 push**（tools.js:181"按产出序·单调"、:369-370 addResultLayer push），`ref('$n')` 按下标读（:202-205）。同层两步并发 → 各自 addResultLayer push 顺序竞态 → 后序层 `$2`/`$3` 解析错位（拿到同层另一步的产物）。**必须改为按 step index 赋值**（`_stepResults[i]=fc`，结合 setToolContext 的 round 或显式传 stepIndex）后才能并行。这是 P3-2 的硬前提，计划未提。
3. **🔴 阻断级前置 2：共享全局竞态**——`setToolContext({tool,round})` 写全局 `_curTool/_curRound`（tools.js:197），并行下 A 步执行中 B 步 setToolContext 覆盖 → A 的 addResultLayer 记账错乱；`_lastToolRows`（harness 全局）同理——两个 zonal 并行时"最后完成者"决定结论段 Top 行（非确定性）。需：addResultLayer 按 stepIndex 记账（不依赖全局 _curRound 竞态）；`_lastToolRows` 改为"按原 tcs 顺序最后成功步的 rows"（确定性选取）。
4. **顺序确定性其余点**：toolHistory 同层按原序写入（计划已写 ✓）；newLayerCount/failedSteps 是求和、顺序不敏感 ✓；`tool:executed` 事件 ts 已带（e2e-seam 可接受乱序）✓；formatRegistry 层列表顺序随完成序变化——finalStep context 图层列表顺序不定，但对账用 includes()、顺序不敏感 ✓。
5. **开关设计**：`PARALLEL_ENABLED` 常量方向对，但建议**默认关**（红线区：先 eval 全绿再置开），且开关同时控制 dep-graph 生效（关 = 全串行回退现状）；一键关只是保底，默认关才是保守。

### 焦点 3：P3-3 编排器稳定性（红线区 SOP）

**判定：agree（SOP 基本充分）+ 3 补强**

证据与建议：
1. **SOP 充分性**：先扩 eval（依赖图单测 + 并行 E2E）再动、一次一处、独立 commit、回退开关——结构完整；补三点：
   - **eval 内容清单**：依赖图单测边界（空/单层/多层/含环输入防御→全串行/未知工具名→全串行）+ 并行 E2E（多目标裁剪顺序确定性 + `$n` 链正确 + rows 型工具 + 失败步不阻塞 + 对账 R2 按钮不破坏）；
   - **P3 拆 3 个独立 commit**：①`dep-graph.js` 纯函数 + 单测（无运行时影响）→ ②tools.js `$n` 索引重构（index-based，**先于并行单独合入**，回归全绿）→ ③runAllToolCalls 并行改造 + E2E。每步可独立回退；
   - **现有防线副作用盘点**：applyQualityDefense/R 规则/出口裁定均文本与计数级、顺序不敏感 ✓；敏感点仅 §焦点2 的 `$n`/`_curTool/_curRound`/`_lastToolRows` 三处共享状态——全部在前置重构中解决，解决后并行不破坏防线。
2. **对账风险**：L1 `_verifyClaims`（声称图层 vs formatRegistry）用 includes 匹配，乱序无影响 ✓；唯一注意是"并行中用户点击/中断"的竞态（stop 信号）——并行 Promise.all 需要统一 abort 传递（现 try/catch 单步 catch 已吞异常，并行下用 `Promise.allSettled` 更稳，失败步入 failedSteps 不阻塞——计划已写，确认用 allSettled 而非 all）。

### 焦点 4：P3-4 地点联动（工具出口统一 place_name）

**判定：partial（价值中低·建议降级/解耦·不做强制）**

证据与建议：
1. **现状已覆盖 90%**：place_name 双源在聚合产物（core/spatial_analysis.py:587-603）、P0 结论段 rows 取地点（result-struct.js `_pick(['place_name','name',...])`）、P2 出口卡 scale 标注——工具返回对象（`r.data`）目前**不带统一 place_name**（tools.js 无 place_name 返回，runAllToolCalls 只消费 observation/data.layerId/data.rows）。
2. **值得做的部分**：对点型工具（clip/extract/nearest）返回 place_name 有助于 EMC 消费；实现为 **additive 可选字段**（`r.data.place_name`，无地点语义的工具返 null）——**不动 TOOLS signature/params/既有字段**，向后兼容（runAllToolCalls/outlet 组装只读既有字段，新增无影响）。
3. **不建议**："所有工具出口统一必带 place_name"的强制——merge/overlay/area_stats 无地点语义，强制会污染契约；且与 P3 并行编排**解耦**（独立 commit，可 P4）。

### 焦点 5：改动量/依赖/风险 + 排期

**判定：partial（改动量偏乐观·排期应后置）**

证据与建议：
1. **改动量复核**：计划 ~3 天（依赖图 1 + 并行 1 + eval 1）**偏乐观**——加两处阻断级前置重构（`$n` index-based 改造 + 共享状态隔离）+ 回归，实际 **约 4-5 人天**。

3. **风险标注**：红线区中风险（编排器）——默认关开关 + eval 先绿 + 独立 commit 后可控；若并行 E2E 暴露对账/顺序回归，回退 = 开关置关 + 回滚 ③ 单个 commit。
4. **红线复核**：四态出口（exit 裁定不变，仅执行层并行，newLayerCount/failedSteps 计数顺序不敏感）✓；finalStep D019（不改 prompt）✓；diagnose（不改）✓——P3 不碰三者，但触碰"编排器确定性"执行层，保守默认（不可证明无依赖 → 串行）是底线。

## 三、可否执行结论

**有条件执行（conditional approve）——先解 2 个阻断级前置 + 明确 eval 载体 + 排期后置。**

通过依据：方向正确——依赖图确定性（不交 LLM）、无依赖并行（墙钟收益）、结果顺序确定性（toolHistory 原序）、开关回退（红线区可逆）；不触碰四态出口 / finalStep D019 / diagnose（确认 ✓）；与 AI·Copilot 内核一致（编排器代码判依赖，Smart 两端 + Dumb 中间）。

**执行前置（3 项）**：
1. **B1**：tools.js `_stepResults` 改 index-based 赋值（先于并行单独 commit + 回归全绿）；
2. **B2**：共享状态隔离（addResultLayer 按 stepIndex 记账 / `_lastToolRows` 按原序确定性选取）；
3. **W2/W3**：明确 eval 载体（Playwright evaluate 单测 dep-graph）+ `PARALLEL_ENABLED` 默认关（eval 全绿后开）。

**执行顺序**：dep-graph.js + 单测 → `$n` 索引重构（回归）→ runAllToolCalls 并行改造 + 并行 E2E → 全量 pytest + test-cases.js 回归 → 置开开关（可选）。
