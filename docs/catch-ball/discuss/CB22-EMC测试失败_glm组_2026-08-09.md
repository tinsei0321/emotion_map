## 二、4 根因假设验证（glm 逐条）

### H1 前端旧代码 — **❌ 不成立（trace 证伪）**

**claude 假设**：serve 未加载新 harness.js → rag_query 短路不存在 → 落 diagnose → 情绪分析式。

**glm 证伪**：
- trace 显示 **F_015（rag_search）跑了**（16:45:38 enter·18630.9ms exit）——若前端跑旧代码（无 rag_query 分支）·**F_015 不会触发**。
- F_015 触发 = **rag_query 短路生效**（harness:978-985 `_quickIntent==='rag_query' → fetch /rag_search`）。
- **结论**：前端跑的是**新版**（含 rag_query 短路）·H1 不成立。

**claude 诊断矛盾点澄清**：
- claude :37 "curl serve 返回的 harness.js 含 0 次 rag_query"——可能 curl 未走 `?v=` 注入（serve.py no-cache + ?v auto-inject）·或 curl 了错误 URL。
- **但 trace F_015 触发是铁证**——前端实际加载了 rag_query 逻辑·curl 结果是检测方法问题·非前端跑旧代码。

### H2 注入被覆盖 — **⚠️ 方向对·机制更精确（"从未注入"非"覆盖"）**

**claude 假设**：短路触发 → rag_search → 注入 ctx.context → **被后续覆盖**。

**glm 修正**：**不是"覆盖"是"从未注入"**——

**时序证据**：
```
F_015 enter 16:45:38 → 15s 时（16:45:53）AbortController abort → fetch 抛 AbortError
→ :1003 catch(_e) { /* RAG 失败 → 正常 finalStep（未注入）*/ }
→ _data 未定义（fetch abort 后 _res.json() 未执行）
→ :989 if (_data && _data.ok && ...) 不成立 → 跳过 ctx.context 注入
→ :1004 const draft = await stages.finalStep(ctx, hooks, '')
→ ctx.context 无 RAG 结果 → finalStep 用现有 context（grounding/情绪分析背景）
```

**glm 关键纠正**：
- **不是"RAG 注入了被覆盖"**——是 **RAG fetch 超时 abort·_data=null·注入 if 不成立·从未注入**。
- finalStep 用的是**现有 ctx.context**（可能含 :1109 deriveAvailable grounding 的范围/情绪分析背景）→ 回答情绪分析式。
- 截断（回答很短）——finalStep 流式时 ctx.context 无 RAG 结构化数据·LLM 凭弱 context 生成短答·非 applyQualityDefense 截断（skipL1:true + skipScaleDefense:true·:1005）。

### H3 finalStep 0ms + 截断 — **partial（0ms 是 trace 记录粒度·截断是 LLM 弱 context）**

**claude 假设**：F_003 0ms = 流式中断或 applyQualityDefense 截断。

**glm 判定**：
- **F_003 0ms 是 trace 记录粒度**——finalStep 是流式（SSE）·enter 后立即返（LLM 调用在后续 F_002/F_001）·enter/exit 同时间戳 = 0ms 是**记录方式**·非真 0ms。
- **截断根因**：ctx.context 无 RAG 结果（H2）→ LLM 弱 context → 生成短答（"观点 + 三类诉求区 + 截断"）——非 applyQualityDefense 截断。
- **证据**：applyQualityDefense（:1005）`skipL1: true + skipScaleDefense: true`——跳过 L1 产物验证 + 尺度防线·**R7 截断（长度防线）仍可能触发**·但回答很短（非长被截）→ **不是 R7 截断**。

### H4 问题分类机制缺陷 — **❌ 不成立（分类正确·走 rag_query）**

**claude 假设**：「宜昌有哪些更新项目」含地名 → 走 REGION_KW 分支 → 范围/分析。

**glm 证伪**（规则推断实测）：

## 三、6 诊断焦点回应（glm）

### 焦点 1：H1 vs H2 — **H2 成立（机制精确：从未注入·非覆盖）**

见上文·glm trace 定案：H1 不成立（F_015 触发 = 短路生效）·H2 方向对但机制是"fetch 超时 abort → _data=null → 从未注入"（非"覆盖"）。

**验证方法（glm 建议）**：
- 在 harness:987 `_data = await _res.json().catch(() => null)` 后加 `console.log('[rag_query] _data:', _data)`——实测 _data 是否 null。
- 在 :989 if 前加 `console.log('[rag_query] 注入条件:', _data?.ok, _data?.results?.length)`——确认是否进入注入分支。
- **复现**：serve 重启后首检（冷加载）必现此 bug。

### 焦点 2：MOD_RANGE 为何触发 — **grounding 预处理（非分类走错）**

**glm 判定**：F_013（MOD_RANGE）是 **grounding 预处理**——
- harness 主循环在 _quickIntent 判定前·有 deriveAvailable（tools.js:1109）等 grounding 逻辑（列 catalog/范围）。
- F_013 0.2ms（极快）·不阻塞短路。
- trace 时序：F_013（16:45:27）→ F_015（16:45:38）——F_013 先 11s·可能 serve 启动 grounding 初始化 + 用户问句 grounding。
- **不是分类走错**——分类正确（rag_query）·MOD_RANGE 是伴随的 grounding（无害）。

### 焦点 3：finalStep 0ms + 截断 — **0ms 记录粒度·截断是弱 context**

见 H3——0ms 是 trace 记录粒度（流式 finalStep）·截断是 ctx.context 无 RAG → LLM 弱 context 短答。

### 焦点 4：模型冷加载修复 — **✅ serve 启动预热（glm 历轮提过·未实施）**

**glm 判定**：**模型冷加载 18.6s 是本次失败的直接原因**——

**glm 历轮追踪**：
- glm CB-22c Phase 0 评估：提"模型缓存不入 git + 文档标注首次下载"——但**未提 serve 启动预热**（glm 遗漏）。
- glm CB-22c Phase 1 评估：提"bge instruction + 段落细切 + 召回率"——**未提预热**（glm 遗漏）。
- claude 诊断 :43 称"Codex/glm 提过启动预热可选·未实施"——**glm 实际未提**（claude 归因略偏）。

**glm 诚实承认**：glm 历轮未明确提"serve 启动预热"——这是 glm 评估遗漏（关注质量/颗粒度·忽略冷启动性能）。

**glm 修复建议（3 层）**：

**① serve 启动预热（治本·消除冷加载）**：
```python
# frontend/serve.py 启动时预热 RAG 模型
def _warmup_rag():
    try:
        from tools.rag_index import _get_model
        _get_model()  # 触发加载 + 缓存
        print('[OK] RAG 模型预热完成')
    except: pass
# serve 启动后 _warmup_rag()
```
- 预热后首检 <1s（模型已缓存）·18.6s 冷加载消除。

**② AbortController 15s → 30s（容错·防冷加载超时）**：
- harness:982 `setTimeout(() => _ac.abort(), 15000)` → 30000。
- 即使预热失效（如进程重启）·30s 容冷加载 18.6s。
- **但禁无限延长**——30s 是用户感知极限。

**③ catch 兜底降级（诚实标注·非静默丢）**：
- harness:1003 `catch(_e)` 现状静默（`/* RAG 失败 → 正常 finalStep */`）。
- **改为诚实标注**：
  ```javascript
  catch(_e) {
    ctx.context = '【知识库检索超时·本次回答未引用 RAG·可能不完整】\n\n' + (ctx.context || '');
  }
  ```
- 超时也注入"诚实声明" → 用户知 RAG 没跑·而非看情绪分析式困惑。

### 焦点 5：问题分类应走哪条路径 — **rag_query（分类正确·已验证）**

见 H4——_quickIntent("宜昌有哪些更新项目") = 'rag_query'（规则推断确认）。分类**正确**——应走 rag_query 短路（RAG 检索 + 注入 + finalStep）。

**但 B 路径（CB-22b）实施后**：
- "宜昌有哪些更新项目" → knowledge_query（B·确定性结构化查询·先）。
- RAG 收窄后此句不再走 rag_query（转 B）。
- **B 是确定性 WHERE（无模型加载）→ 无冷加载超时问题**——B 实施后此问句更快更稳。

### 焦点 6：修复方案 — **3 层（预热 + 超时延长 + catch 兜底）+ B 路径治本**

**glm 修复方案（优先级）**：

| 优先级 | 修复 | 治标/治本 | 理由 |
|---|---|---|---|
| **P0** | serve 启动预热 RAG 模型 | **治本** | 消除冷加载 18.6s → 首检 <1s |
| **P0** | catch 兜底诚实标注（超时也注入声明） | **治标+诚实** | 用户知 RAG 没跑·非看情绪式困惑 |
| **P1** | AbortController 15s → 30s | 容错 | 防冷加载超时（预热失效兜底） |
| **P1** | B 路径（CB-22b）实施 | **治本** | "有哪些项目"走 B 确定性（无模型）→ 无超时 |

**glm 建议**：P0 两项（预热 + catch 兜底）立即修·P1（超时延长 + B 路径）跟进。
