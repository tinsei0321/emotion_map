## 三、2 个发现详析

### 发现 1：e2e test_knowledge_qa_routing_assembles 失败

**根因（glm 定性）**：**模型冷加载超时**（与 glm 上轮 R1-R4 修复前同根因）：
- _assembleKnowledgeQA 调 rag_search → 模型冷加载（bge-small 首次加载 ~18s）→ fetch abort（AbortController 30s·但冷加载可能 >30s）→ R3 兜底（`rag-timeout-exit-concept`）。
- 断言期望 `skipped in ('diagnose-knowledge-qa','quick-rag')`（合流路径）·实际 `rag-timeout-exit-concept`（R3 兜底正确触发）。

**性质**：**环境问题（冷加载）·非逻辑回归**。
- 5 passed（endpoint/fallback/quickintent/false/gold_set）核心逻辑通过。
- R3 兜底是**正确行为**（模型不可用时走确定性兜底·glm R3 设计）—— 只是测试断言**不容错冷加载场景**。

**glm 建议**：
- **方案 A**：测试前预热 RAG 模型（`py tools/rag_index.py --warmup` 或 serve 启动预热）→ 消除冷加载。
- **方案 B**：断言容错——`assert r.get('skipped') in ('diagnose-knowledge-qa', 'quick-rag', 'rag-timeout-exit-concept')`（R3 兜底也算正确·只是不同路径）。
- **glm 倾向 B**——测试应容错环境变化（冷加载/预热是运行时状态·非逻辑缺陷）。

### 发现 2：search "宜昌有哪些更新项目" Top-10 全 note

**性质**：**检索语义自然结果·非索引缺陷**。
- 概念卡（concept）和事实卡（fact）都在索引里——单独查命中正常（concept 0.71 / fact 0.67）。
- "宜昌有哪些更新项目"与 note 段落语义更近（codex 笔记含详细项目描述·score 0.77-0.79）·与 concept（产品定义）/fact（结构化条目·短文本）语义稍远。

**影响**：用户查"有哪些更新项目"→ LLM 收到 note 段落（详细但有冗余）·非 fact（结构化精确·如"55 个·51.33 亿"）——**素材精度次优**。

**glm 建议（P1 优化·非阻断）**：
- **query 改写**：_assembleKnowledgeQA 检索前·对"有哪些 X"类 query 补查 fact 表（`query_knowledge_base(city, topic)` 确定性 WHERE）→ fact + note 混合注入。
- **或混合检索**：rag_search 对知识查询类 query·同时跑向量（note）+ 关键词 WHERE（fact）→ 合并 Top-K。
- **这是 P1 优化**（素材精度提升）·非阻断 P0 交付（note 段落也能答·只是不如 fact 精确）。
