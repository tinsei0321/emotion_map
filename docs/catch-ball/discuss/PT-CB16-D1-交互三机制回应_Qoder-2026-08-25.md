## 白话摘要

Kimi 的三条规矩方向我都赞成，**但我查代码后发现一个讨论稿没写的关键事实：这三条规矩的「地基」几乎全建在旧引擎（内置问答引擎）那边，而您实测撞出问题的新引擎（Codex Harness）这边，三条规矩的落地零件一个都没接**——追问小纸条传不到屏幕上的建议条、岔路口提问没有选项按钮、自报大小没有卡片可填。所以我的核心意见是：规格照定，但必须先回答「给哪个引擎装」，否则修完了您在新引擎上还是感受不到。另外三条具体调整：①追问纸条分两级——能「一键重跑」的带完整参数（不是只带增量，增量还得回头翻旧账本，不如直接给全量参数稳）；②频率上限别只写死数字，超了就降级成「我替您选了 X，理由是 Y，不满意可撤销」的通知式决策；③「自报大小」改成「干完后用实际动用的工具数量倒推核对」——模型自报会漂（同一问题不同时间报不同级），倒推是死规则零漂移，还顺带省掉了新引擎没有自报卡片的难题。

## 一、逐条立场

### 1. 追问机制（followup_cues 结构化）——**调整吸收**

**吸收**：机读方向成立。纯文本下续接路由=模型自由心证，结构化是把「可执行的追问」从语义层降到契约层，正确。

**三点调整（证据）**：

- **① param_delta 改为完整参数集（resolved_params）**。`{cue_text, tool, param_delta}` 的增量语义要求重放时拼回上一轮完整参数——这把会话状态耦合进了重放路径（上轮参数存哪、跨刷新怎么办）。建议服务端在派生 cue 时直接写入**完整可执行参数**（`{cue_text, tool, params}`·幂等自包含），重放不依赖任何历史。先例：本仓 render 契约的 dataset_id 引用正是「单号自包含」优于「上下文拼装」的同款设计（今日双 bug 治本批 R1-1 同思想）。
- **② cue 分两级，非全量带参**。参数级增量（top_n±、by 翻转、boundary 切换）派生规则确定性可写；**跨工具建议（「换成分布图看看」）不强行推断参数**——保持 `{cue_text}` 纯提示级。Kimi 草案隐含所有 cue 都带 param_delta，跨工具参数推断不可靠且派生表会爆工作量（分析工具族 10 件×每件 2-3 条规则已紧）。
- **③ 收益叙事与验收口径修正**。Codex 引擎 thread 跨 turn 复用（`core/codex_bridge.py` L92·thread_id 实例级保持），续问**上下文天然在位**——「零背景重述」在 Codex 侧已部分成立，真实痛点是「重新全量路由」（又跑一遍 list_data→zonal→rank）。验收应改为「续问第二轮工具调用为参数增量级（≤1 次重跑）」，比「零背景重述」更可测。

**独立发现（裁决点①的前提）——引擎断层**：前端追问 chips 链路现状（`panel.js` L1560-1566 → `followup.js` normalizeFollowupCues → 点击**回填输入框不直发**）只在 light 引擎完整工作；**Codex 适配器 `brain-adapter-codex.js` L93-98 的 tool.end observation 只有「工具名 完成」，工具返回值（含 cue）根本不进 SSE 事件**（`codex_bridge.py` L277-285 的 item/completed 同样只透传 name/status/error）。即：cue 结构化后，Codex 引擎下模型能读到（MCP 返回值里）、但前端胶囊不受益。**是否要求 bridge 透传工具返回值摘要（含 cue）进事件流，须作为裁决点①′ 显式定案**——不定则本件对用户当前主力引擎只有模型侧一半收益。

**向后兼容成本（4 天计划未列）**：`normalizeFollowupCues` 逐项 String 化（`followup.js` L8-10）——cue 对象化后旧路径渲染成 `[object Object]`；mock-peer（`acp-mock-peer.js` L90）、panel 渲染、S5 单测面（`tests/browser/test_followup_chips.py`）三处须同步适配。

### 2. 选择机制（三触发 + 频率上限）——**调整吸收**

**吸收**：三触发清单本身成立且③口径分叉最有现实价值——**当天 130 vs 193 事件就是活案例**（模型自选 130 未请示·若当时请示口径分叉即可避免）。不建分类器（R46·规则给人和模型看）同意。人设/工具描述双写（D-c）同意。

**三点调整（证据）**：

- **① 与既有 ask_user 语义划界（规格缺）**：现有 ask_user 全部是「信息不足/失败恢复」型——缺槽（`harness.js` L658 `_missingSlotAsk`）、可恢复失败（L777-794）、链中断（L983-986）；三触发新增的是「**双解都合法但需用户定夺**」型。两套规则正交，规格须显式划界（何时走缺槽问、何时走分支问），否则模型面对两张清单会打架。
- **② 频率上限须引既有基座**：panel.js 已有跨轮连续计数防博弈（L1762-1765·`_consecutiveAsks >= 2` 注入「禁止再 ask」）——Kimi 的「单轮 ≤1」与之互补（单轮上限 vs 跨轮累积上限），规格应引用既有机制防重复造轮；且现行「禁止再问」是硬注入，建议升级为**预算+软降级**：预算耗尽后触发条件降级为「告知式决策」（做了什么选择+依据+如何反悔），而非硬沉默——业界对照：Claude Code 的 permission 谱系（ask/allow/告知式自动通过+可撤销）正是这个中间态设计。这同时回应「研究档 ≤2」：**研究档的多次请示应由 plan 模式（方案审批一次性打包·zcode 材料已提 dsh 有 plan-mode 插件）承接，而非放宽频率上限**——放宽的副作用是模型学会「反正还能问」而减少方案期思考。plan 模式若暂不排期，则各档统一 ≤1。
- **③ ①②两触发的现实密度标注**：当前 MCP 工具面纯只读为主，真正不可逆分支稀缺（现实案例：`render_file` >60 要素自动登记写 manifest——`mcp_server_emc.py` L1640-1662·建议入「不可逆」正例）。②与③有重叠（口径分叉本质是成本差特例），保留可接受。**Codex 引擎断层**：RENDER ask_user 事件仅 light 引擎发射（`acp-channel.js` L66/L146 由 harness hooks 触发），Codex 适配器无此通道——模型只能纯文本提问（可用·降级体验）。落点引擎须裁决。

### 3. 规模机制（scale 三枚举 + 出口核对）——**调整吸收**

**吸收**：三枚举粒度合适（业界先例：OpenAI reasoning_effort 同为三档 low/medium/high——zcode 材料对照表在案；枚举不膨胀是对的）。入口档位定默认 scale 的第一保险成立。软提示方向同意（硬阻断会打死合法升级·Kimi 已论证）。

**三点调整（证据）**：

- **① 双保险第二环改「确定性倒推」，砍「模型自填」**。理由三条：(a) 模型自填会漂移——zcode 材料原话「同一个问题不同时点判出不同级」，自填恰是双保险中最弱一环；(b) **Codex 引擎无自填载体**——意图卡是适配器硬编码（`brain-adapter-codex.js` L29-31 template/engine 固定），模型输出流里没有意图卡，自填需 bridge 扩展结构化输出解析，成本高收益漂；(c) 出口核对本来就要算「实际工具链规模」——由工具调用数/轮数/耗时**确定性倒推**实际 scale 与入口声明比对，零 LLM、零漂移、引擎无关（数据源=tool 事件流·两引擎都有）。与 caliber/followup_cues 的确定性派生先例（`mcp_server_emc.py` L106/L162·零 LLM 纪律）同谱系。**收益：C2-3 变轻**（不需要解决 Codex 意图卡问题），判据更稳。
- **② scale 语义边界写入规格**：scale **不跨档位改预算**——快档 15 步硬顶不因 scale 声明升级而放宽（用户选快档就是要快·大问题应转研究档问）。scale 的真实作用域=防降级滥用（研究档答 brief 问题浪费预算）+ 快档诚实提示（brief 问题跑了 5+ 工具→提示收敛或建议转档）。此边界不写明，实现者可能做成「scale 联动预算」改变档位语义。
- **③ 落点与验收微调**：scale_check 落**出口卡链路**（确定性组装·收尾处天然位置），不用 emc_status（探活工具语义不符）；软提示加**静音条件**——判对静默、判错一条结构化注记进对话流（不打断·不新开 UI），防「判对也弹」变成新的询问轰炸；黄金集 10 问判 80% 统计意义弱（8对2错 vs 9对1错不可分），建议 ≥20 问且三档分层（每档 ≥5 问·与 RAG 黄金集共用语料不变）。

### 4. 实施切分（C2-1/2/3·共 4 天）——**调整**

- **缺一个 C2-0（规格冻结件·约半天）**：内容=①引擎落点裁决（Codex 侧透传/二期声明）②cue schema 冻结（两级结构+resolved_params）③ask 两套规则划界④scale 确定性倒推判据表。这些是三件共同前置，散在各件里会返工。
- **4 天低估三个隐藏成本**：①cue 结构变更的向后兼容三件（followup.js/panel 渲染/mock-peer·约 0.5 天）；②接口变更版本化评估+门禁断言同步（R1-1 先例·rag_query 返回结构变更属接口锁范畴）；③Codex 侧若纳入 bridge 透传+ask 事件（+1.5-2 天·且 codex_bridge 变更超出「纯 EMC 侧」的 C2 边界）。**不纳入则必须在派发件显式标注「胶囊/选项 UI 收益仅 light 引擎·Codex 引擎仅模型侧引导收益」**——用户当前主力测试对象是 Codex 引擎，期望管理须前置，否则修完复测「怎么还是没建议条」又是一轮误会。
- **排期顺序**：建议 C2-0 → C2-3（scale·调整后最轻·纯确定性）→ C2-2（规则双写·文本件）→ C2-1（cue 结构化·接口变更最重·放最后兼收前两件经验）。与 Kimi 顺序（C2-1 先）不同，理由：C2-1 依赖裁决点①′（引擎落点）未定则不能开工，而 C2-3/C2-2 无此依赖；用户痛点的 Codex 侧收益又卡在同一裁决上——先裁决先动无依赖件。

## 二、对讨论稿两处直接点名

1. **裁决点缺位**：讨论稿四个裁决点全部在「机制参数层」（结构化与否/清单够否/硬软/排期），**没有一个在「引擎落点层」**——而这是三机制收益能否触达用户当前主力引擎（Codex）的第一前提。建议增裁决点⑤：三机制的 Codex 引擎载体（bridge 透传+新事件类型 / 纯模型侧引导 / 二期）。
2. **「续接路由在宿主」表述含混**：宿主=模型（Codex/dsh）时读文本与读结构差别有限（模型擅长自然语言）；机读结构的真正不可替代消费方是**前端胶囊一键重放**（跳过 LLM·确定性）。规格应把收益锚定在后者，避免「为机读而机读」。
