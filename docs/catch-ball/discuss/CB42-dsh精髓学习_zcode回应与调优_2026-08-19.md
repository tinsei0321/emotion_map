## 一、总评

**方向判定：强同意，零翻案。** 报告核心主张——「不把 dsh 搬进平台，而是把平台能力做成标准插座，让通用助手来消费」——与 08-18 EMC×dsh 可行性深挖轮的用户共识完全同向，是那份共识的第一份系统化工程草图。报告不做推翻性建议，做的是**给现有铁律体系补理论名字、给现有排期补完整路线**。

**事实核查**：报告引用的工程先例全部属实——`.claude/mcp_servers/vision_bridge_server.py`（FastMCP 先例）、`ai_qa/tool_contracts.py`（619 行契约单一源）、`api/geo_routes.py`（706 行）均在位。横向对比表（§2.2）口径与台账修正后事实一致（dsh 周级 breaking、开发者预览），无误传。

**一句话**：这不是一份「要新东西」的报告，八步路径里近半数 EMC 已实现或正在实现；真正的增量是 **MCP 对外工具面**（有前置门槛）、**会话级可重放日志**（真 gap）、**守卫管线设计语言**（立即可吸收）。

## 三、四档裁决（报告 §七 要求）

### 立即吸收（零排期成本，并入在途任务）

- **A1 守卫四态设计语言 → T2**：拒绝报错升级三段式——①这是什么层（id+中文名）②为什么拒（结论层不得作分析原料）③用什么替代（同 group 的 input 层建议）。对应四态中 add-context：拒绝时附上下文，不裸拒。
- **A2 校验入口管线化 → T2**：单一校验函数 + 明确错误码，为后续守卫（脱敏检查、口径标注）留挂点，不做一次性 if。
- **A3 插件需求卡模板 → 派发规范**：现有任务卡四列（任务/执行/白名单/验收）增加「业务背景」「数据源」两栏；失败沉淀已有 debug-memory + buglog 承接。下次 dsh 派发生效。
- **A4 「小工具不大插件」→ 派发判据**：与 Dumb Tool 契约（铁律 11）互认，列为白名单拆分判据之一。

### 并入现有排期（不新开专项）

- **B1 能力目录字段设计 → 并入 B3 口径注册表**（dataset 登记含样例行/安全级别/口径链接）。
- **B2 会话事件流（可重放日志）→ 并入阶段 2 C 线蒸馏素材规范**，与 check_caliber 门禁同批设计。
- **B3 MCP Server v1（7 工具）→ 平台工具面第一批，排 B 线治理 + C 线蒸馏规范之后**，并入平台化批次顺延编号，不开新 CB 专项。前置门三件：B 线治理完、C 线 RAG 蒸馏规范、check_caliber 零命中门禁通电。
- **B4 第一消费者定为自家**：ZCode/Claude Code 会话先消费自家 MCP（开发辅助场景吃狗粮），dsh 接入为第二场景验证。理由：dsh 周级 breaking（六天 10 版的事实已核），宿主无关的 MCP 面不得以 dsh 为首要目标。

### 暂缓（挂看板，给触发条件）

- **C1 render_spec**：触发条件 = 第二渲染消费方真实出现（C 线出口卡片直接渲染，或 dsh web GUI 实测需求）。在此之前 MapLibre 同源样式即事实契约。

### 反对与修正

- **D1 反对「现在开 MCP Server 专项」**——非方向反对，是时序反对。B 线治理未完即开数据面 = 未治理数据外流，违背「工具输出必须脱敏、带口径、可追溯」红线。zonal_stats/buffer/rank 需从分析任务型管道剥离出只读查询能力，有真实工程量，不是 FastMCP 壳一层。
- **D2 修正报告基线**：报告 §三第 1 步「盘点资产建能力目录」读起来像从零开始；实际 manifest 57 层注册已完成（同日 PT-CB2 T1 刚回收）。作者写报告时可能未及见最新进展，特此校准，避免后续组照报告重复建设。
