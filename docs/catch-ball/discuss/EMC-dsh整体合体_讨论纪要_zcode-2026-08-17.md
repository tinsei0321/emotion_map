## 一 R0（08-16 晚）发起：整体寄生的设想

**用户设想**（润色）：将情绪地图**整个项目**（项目+数据+功能模块）作为拓展嵌入 dsh，让 EMC 模块直接融合进 dsh 的对话机制而非作为一个独立模块，直接运用 dsh 的高度开放性、人机交流、工作流与工具调用（通用工具+GIS 工具）的 harness——追求更智能、更灵活。

**zcode 评估**：拆解为两层诉求——方案A（整体寄生·架构迁移·字面）与方案B（能力融合·工具暴露·精神）。**方向性反对 A**（六维：四承重红线失守/地图-终端形态错位/CB-22 系列再硬化成本/preview 供应链风险/零 TS 工具链/收益均有更便宜等价物）；**支持 B**（稳定入口打包为 MCP 工具面，EMC 本体零改动）。关键洞察：用户想从 dsh 获得的东西=通用 harness 的定义，**已拥有三份**（zcode/claude code/codex）；情绪地图独有资产=领域栈；正确寄生方向=**协议级（寄生所有 harness）而非运行时级（寄生进一个）**。

## 三 R2（08-17）方案B 的提升与核心改变

**用户问题**（润色）：如果按方案B，对我目前有哪些提升？核心改变在哪？

**zcode 回答**：三层提升——①工作流调用质量（agent 从「读代码猜参数+bash 裸调+报错重试」到「function calling+schema 校验+dataset_id 枚举」，脱敏/sim 禁入/路径沙箱从纪律条款变内建机制）；②真正的新能力（rag_query 进任意会话/outlet_card 对话级出口/kb_facts 权威源）；③生态战略（四 harness 即插即用·dsh 零代码）。**核心改变一句话：变的不是能力，是能力的可达性与安全性。** 四条诚实边界居首：**EMC 产品本身零提升**——四痛点一个不解决。

## 四 R3（08-17）纠偏：真痛点是 EMC 入口聪明度

**用户澄清**（润色）：前几轮讨论的核心点与真痛点错位。EMC 最大痛点 = **从自然语言输入到分析方法+工具调用+结果产出的路径不够「聪明」**——LLM 接入的效果没有充分发挥，实际靠提示词、字典等关键信息去驱动预制好的分析路径；这个逻辑换来了稳定的产出，但大大弱化了 LLM 的灵活性。核心是**意图判断不够准、不够灵活，导致选不中正确的分析方法+工具组合**；这个困境持续很久无法彻底解决，一直在「拆东墙补西墙」，修复无穷无尽，没有发挥出 agent 的优势。

**zcode 机理分析**：四层叠加——①**开放问题空间 vs 封闭意图分类法**（paradigm 尺度→方法映射+预判词表=有限字典索引无限空间，修补数学上不收敛）；②**单发诊断不可恢复**（一次 FC 定终身，失败全走降级、宁可降级也不澄清）；③**参数闭卷填空**（CB-08 实测：覆盖内选型 12/12 全对、瓶颈在参数填充——LLM 看不见数据资产清单）；④**eval 失真**（CB-01 C6：手工空 context 不反映运行时）。**核心 reframe：痛不在内核错，在内核承诺的「Smart 入口」未兑现足额——灵活性归还的位置在入口端，不在中间开放**（B001/B003 是中间变聪明的病）。四机制：M1 迭代诊断/M2 参数接地/M3 计划生成（G9）/M4 eval 重放（G6），推荐序 M4→M2→M1→M3。

## 五 R4（08-17）天然对照实验：通用 harness 为什么不用调优

**用户之问**（润色）：这几天用 dsh 的过程中产生疑问——用 claude/codex/zcode/dsh，喂点线面数据，让它们按要求做合并、剪裁等操作，**不告诉剪裁逻辑、不做任何 GIS 工具调优**，它们能迅速、准确地完成；而 EMC 是调试了很久才知道怎么做，多次调优仍常出错、不能完美完成任务。EMC 和这些平台的差别在哪？同样是用 GIS 工具，为什么它们能在不调优的情况下完成？

**zcode 分析**：**它们不是没调优——调优发生了三次转移**：①**前移到预训练**（通用 agent 用的是代码底座+geopandas 公共库知识=世界替你调好了；EMC 的 19 契约是私有 API 模型零先验，全靠现场教——「你每调优一次 EMC 学到一条映射；通用 agent 的教材是整个 GitHub，词典竞赛赢不了」）；②**内置到会话循环**（读真实数据→写代码→执行→看结果→修正，内部多次迭代，用户只看到最后一次成功——「不调优就完成」是错觉；EMC 单发闭卷，第一次尝试直接见用户，试错责任外包给用户）；③**外置给用户**（剩余不适配全变成字典/映射/CB 轮）。三个结构差：工具空间（无限=代码生成 vs 有限=契约分类选择）/反馈回路/接地方式。**关键区分：可验证操作（合并剪裁·结果客观可查）vs 叙事分析（结论不可客观验证）——B001/B003 的病在后者，不在前者**；一刀切 dumb 中间把两类一起禁了，是 EMC 在可验证操作类上「不智能」的直接原因。由此新增 **M5 有界代码执行通道**候选。诚实 caveat：测试任务恰是通用范式最强的类型，但 EMC 也必须服务这类任务，故不翻结论。

## 六 R5（08-17）存在之问：做 EMC 的意义是什么

**用户之问**（润色）：既然用 dsh 喂数据做操作能实现、并且比我的 EMC 好——那做 EMC 的意义是什么？只是用来展示在地图上吗？

**zcode 分析**：EMC 四层拆解——**NL 路由壳**（diagnose→19 契约→final）=被通用范式支配；**数据与口径资产**（治理后 12345/体检落位/边界/总账/口径注册）=不可替代；**知识与范式资产**（industry_kb/RAG/出口卡/尺度-方法）=不可替代；**产品形态**（地图+演示逻辑链+视野-数据-结论同步）=不可替代。「dsh 更好」的隐藏前提：它服务**会提问的人**（用户本人·一次性任务·无需口径辩护）；EMC 按立项章程服务**规划师/住建局**（不开终端·要跨会话一致·要口径可辩护——dsh 会话蒸发了，口径注册表和 trace 还在）。**会话智能（每会话·用完蒸发）vs 沉淀资产（累积复利）——「EMC 的意义」之问混淆了两者：路由壳是会话智能（输了）；平台是沉淀资产（正在赢）**。三种终局形态：形态1 自研路由全栈（被支配·不可取）/形态2 壳改造（M 系入口聪明化·渐进正路）/形态3 平台化（EMC 退为领域平台：数据+口径+知识+渲染 API；NL 入口交给通用 harness 经 MCP；前端为共享呈现层·长期归趋）。

## 七 R6（08-17 晚）用户裁定倾向：形态3

**用户论断**（润色）：**形态3 更接近我想要的形态。** ① EMC 到目前为止的地图+情绪分析图例样式+专业知识库+宜昌市基础信息+我开发设计的地图交互方式与逻辑等，是**可以复用、长期迭代积累的财产**；② 深挖 EMC 的意图判断、agent-loop 等「让 EMC 自己更聪明」的路，**是一条死路**——我能在 EMC 的输入、输出口径和范式上做规则，但「如何跑起来的路由」实在不是个人开发者应该做的事情；LLM 也好、harness 也好，都该用通用版本，**在通用的基础上搭架子**才是我应该走的路。

**zcode 意见：同意，理由=比较优势**——路由/意图/loop 是巨头商品化竞赛（个人参战必输·R4 实证）；口径/范式/资产是私有复利；「只能做规则」不是退让，**规则工作（契约/schema/口径/脱敏/审批）就是平台本体**（C1-C7=平台宪法雏形）。五个实施含义：①**产品入口空窗**（现有 QA 冻结为演示级+中期薄入口=通用 FC over MCP+dsh Web 场景 S）；②**渲染 API=最大新工程**（样式/交互资产须接口化——style registry/render contract，否则资产锁死前端=重蹈 19 契约锁死路由的覆辙；一般化教训：**资产没有稳定对外接口就会被锁死在当时的入口形态里**）；③现行 CB 线大部分直接转为平台资产（B3 口径注册/C 线知识/G1 出口表格式·无推翻只重排）；④治理逻辑转变（从「限制入口」到「把正道修得比野路好走」）；⑤沉没清单：M1/M3/M5(体内) 不再投入，M2 变身存活（schema 接地服务 MCP 工具面），G6 降权为平台 eval，G8+G10 从侧门升主路。**闭环：用户最初的「合体」设想在形态3 中以协议级方式实现——dsh 与所有 harness 经 MCP 成为平台一等消费者；当初否决的是运行时级寄生，方向反过来就成立了。**
