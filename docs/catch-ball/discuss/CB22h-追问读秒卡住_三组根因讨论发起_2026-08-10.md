## 二、根因链（待三组验证）

```
用户追问
  → rag_search（15.9s·BGE 冷加载·慢但成功）
  → finalStep LLM 流式（DeepSeek）
  → **office 网络对 api.deepseek.com 间歇性不稳** → 流式挂起/401/net/mid-stream
  → 前端 45s 超时 abort（读秒）

  → 用户看「读秒卡住」+ 资源不释放 + 后续请求排队
```

### 分层根因

- **R1 直接根因（环境）**：office 网络对 api.deepseek.com 间歇性不稳（curl 超时证据 + trace 401/net/mid-stream）→ LLM 流式挂起
- **R2 放大根因（代码）**：后端 uvicorn LLM 调用**无服务端超时/快速失败**（httpx 默认无超时？或超时过长）→ 挂起阻塞单线程事件循环 → 前端 abort 后资源不释放
- **R3 次因（代码）**：rag_search BGE 冷加载 15.9s 挤占时间（且同步阻塞 uvicorn·finalStep 排队）
- **R4 疑点（代码）**：前端 45s abort 后降级链路（`_composeDegradedConclusion`）是否生效？用户没看到降级结论说明可能 abort 后仍挂

## 三、待三组评估焦点

### 焦点 1：DeepSeek 流式挂起机制（三组各自实测）
- 三组**各自** curl 测 `api.deepseek.com` 非流式+流式（`curl -m 30` + 计时）——记录通/断/耗时·判断是**全网段不稳**还是 office 特例
- 关注：连接建立后数据流中断（curl 128KB 断流）vs 连接超时——机制不同修复不同
- 关键：**为什么 trace 里 LLM 挂起 5 分半无 exit**？DeepSeek 流式是连接挂着不返回还是 uvicorn 阻塞？

### 焦点 2：后端 LLM 无服务端超时（代码放大）
- 查 `ai_qa/llm.py` 的 httpx/requests 调用是否设超时（`timeout` 参数）——`LLMClient.chat` 的 stream 调用
- 若 httpx 无 timeout → 网络挂起时 uvicorn 无限等 → 单线程阻塞 → 这就是「读秒卡住」后端侧根因
- **修复**：服务端 LLM 调用加超时（如 60s）→ 超时抛错 → SSE 返回 error 帧 → 前端降级

### 焦点 3：前端 abort 后降级链路（用户没看到降级结论）
- 前端 45s abort（api.js answer phase）→ 是否走 `_composeDegradedConclusion`？查 harness.js:795-802 catch 链路
- 若 abort 后 fetch 流仍挂（服务端没断）→ 前端 await reader.read() 不返回 → 降级不触发 → 一直读秒
- **修复**：前端 abort 需主动断开 fetch + 确保降级触发

### 焦点 4：rag_search 冷加载 15.9s（BGE 模型·同步阻塞）
- BGE 模型加载在 rag_search 端点内同步执行·15.9s·阻塞 uvicorn 事件循环 → finalStep LLM 排队
- 是否该预热（serve 启动时预载 BGE）？还是异步化？与「读秒」的时序关系（15.9s + LLM 挂起 = 用户感知 60s+）

### 焦点 5：修复方案定稿
- **服务端**：LLM 调用超时（httpx timeout·如 connect 15s/read 60s）→ 超时 SSE error 帧 → 前端降级
- **前端**：abort 后强制降级（确保 reader 中断·走 _composeDegradedConclusion）
- **网络**：DeepSeek 重试策略（backoff）·或 office 换网络（用户侧）
- **预热**：BGE 模型 serve 启动预热（消 15.9s 冷加载）
- 三组评估优先级与实现细节

### 焦点 6：验收口径
- 修复后浏览器实测（知识问答→追问）：正常时 <30s 出结论·网络挂起时 **<50s 出降级结论**（不无限读秒）
- 模拟网络挂起（curl 慢 / route 桩挂起）→ 断言降级触发
- trace 断言：LLM 调用有 timeout·挂起后 SSE error·前端降级
