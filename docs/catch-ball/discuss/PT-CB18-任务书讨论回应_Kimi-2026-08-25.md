## 二、文章 → 任务书映射核对

- **总体准确**，三档 8 条无误用。两处确认未被高估：RTK 60-90% 已标注「项目方声称、以实测为准」；文章第 8 条转成红线条款（三要素不得删），方向正确。
- **一处论据被高估**：解读第 2 点「分层是原生机制、能用原生机制就不用自觉性」——原生分层只对 Codex / Claude Code 成立，本仓实际还有 ZCode、WorkBuddy 等只读根手册的 harness。该论据在多 harness 现实下不成立，v1.0 表述应降为「对支持者原生生效，对不支持者靠根手册兜底」，与裁决②白名单约束一致。
- **一处可接受的漏吸收**：文章第 4 条提到 OpenAI Responses API 原生上下文压缩，任务书只取「阶段结束换新会话」习惯。取舍合理（不必研究接口细节），不算遗漏。
- **一处草案未覆盖的成本**：七字段交接段若每批都手写，短批次（一天两批）的写作成本可能抵消收益。建议交接段触发条件与会话切分纪律一致——里程碑级才写交接段，小批只更新机器骨架。

## 三、草案遗漏扫描（三处）

1. **双环境同步新风险（草案未覆盖）**：STATE.md 两机各自跑生成器重建，而两机 push 天然不同步——家机生成的状态文档落后于办公室机若干 commit 时，「单一状态源」反而产出两份互相矛盾的「权威状态」，坑 2 换皮复活。补救成本一行：骨架首行必须含「生成时间 + HEAD 短哈希」，读者一眼判新旧。
2. **验证法可执行性打折**：四项指标中「开工到首次产出耗时」「返工轮次」依赖人工记录口径，「规模相当的中档批」天然难选（批次不均质）。建议主判据改为硬数据两项——文档份数/总行数 + token 计量面板读数；耗时与返工轮次降为参考。否则「≥2 项改善 30%」易沦为各说各话。
3. **手册瘦身与在途批次的冲突窗口**：草案已提（依赖裁决①），无新增；但去重验收「同一要求全仓只出现一次」需加执行细则——删除清单逐条标注「原分布文件 / 删后唯一落点 / 哪些 harness 读该落点」，防止某 harness 恰好只读被删的那份，纪律静默丢失。

## 四、顺序调整（一件）

W3 内部：**W3-2（讨论归档喂 RAG）应排在 W3-5（RTK 评估）之前**。理由：W3-2 复用既有工具链（已有 375 chunk 索引经验），零新依赖、直接攻击开工阅读税；RTK 是新第三方组件，评估与双环境配方成本更高，且其 60-90% 区间针对长重复日志，对本仓门禁类结构化短输出收益存疑。先吃确定收益，再赌不确定的。

另：W3-5 验收须加一条——**「门禁输出经 RTK 代理后判定结果不变」**，防止压缩器误删失败行导致「全绿」信号失真。

## 五、总裁决

**修改后执行**。须入 v1.0 的修改点：

1. 裁决②加「下沉白名单」验收条（全局条款禁下沉）；
2. 裁决⑥每日记忆不冻结、改一行式瘦身；
3. STATE.md 骨架加「生成时间 + HEAD 短哈希」行；
4. 验证法主判据改为文档行数 + token 读数两项硬数据；
5. W3-2 先于 W3-5；
6. W3-5 加「门禁信号不失真」验收条；
7. W2-1 验收改「下一批起严格试用」，本批不计样本。

其余按草案执行。
