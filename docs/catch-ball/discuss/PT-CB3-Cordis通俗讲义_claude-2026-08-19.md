## 第 1 课：什么是"插件"（Plugin）

### 预备词
- 程序：电脑/手机上跑的"东西"，本质是一堆指令。
- 框架：已盖好承重墙和水电线路的毛坯房。
- 插件：往毛坯房里搬的家具——符合房门尺寸（标准接口）就能用，搬走不破坏房子。

### 一句话
> 框架是毛坯房，插件是家具。

### 情绪地图例子
数据导入、情绪分析、地图渲染、出口卡片——若做成"框架+插件"，每件都是独立家具：单独装、单独换、单独卸。

### dsh 例子
模型适配器、工具注册表、会话日志、甚至 AI 主循环本身，都是家具。"一切皆插件"= 没有一件家具焊死在墙上。

### 为什么这样设计
想加就加 / 想换就换 / 想卸就卸 / 别人也能搬（生态）。反例：一体化大房子，改一个全楼动工。

### 小结
> 插件 = 可独立搬进搬出的家具；框架 = 毛坯房。

## 第 2 课：上下文（Context）——所有插件共用的"工作台"

### 预备词
- 服务：工作台上的一件"公共设施"（第 3 课细讲）。

### 白话比喻
Cordis 里所有插件都在同一张工作台上干活，这张台子叫上下文（ctx）。台子上有固定区域：

| 区域 | 用途 | 类比 |
|---|---|---|
| 插座区（服务区） | 公共设施插在这，谁用谁取 | 电源插座墙 |
| 公告板（事件区） | 贴通知、喊话 | 小区公告栏 |
| 工具箱（注册表） | 记录房间里有哪些家具、什么状态 | 物业住户登记簿 |
| 日志本 | 记录发生的事 | 工作日志 |

### 关键点
1. **所有插件共享同一张工作台**——不互相认识，只认识台子。
2. **插件拿到的是"台子 + 服务生（代理）"**：喊名字，服务生去取。换设备不用改指令。
3. 服务生是**笨**的：只按名字机械传递，不推理、不猜测。

### 情绪地图例子
数据插件放数据 → 分析插件喊"数据服务" → 渲染插件喊"分析结果"。三个插件谁都不认识谁。换情绪分析供应商：拔旧插头插新插头，其他插件不动。

### 现状对比
情绪地图问答层现在直接点名找具体文件（写死 import）= 每个插件揣一本"谁住哪"的通讯录，邻居搬家就失效。

### 中间人的坏处（Q2 答案展开）
用户的直觉"传递意图过程中偏离远意图"正确，展开三条：
1. **中间人一旦自作聪明就会传歪**——所以服务生必须"笨"（确定性、不推理）。这正是情绪地图内核铁律"编排器不调 LLM、代码裁定三态出口"的原因。
2. **名字拼错才报错**：按字符串名字找服务，编译期查不出，运行期才知道（类型安全损失）。
3. **多一层跳转**：性能开销极小，但存在；服务生是单点，所以 Cordis 把工作台设计得极轻。

### 小结
> 上下文（ctx）= 所有插件共用的工作台 + 随叫随到的"笨"服务生（= 用户命名的编排器）。
> 插件不认识对方，只认识台子——这才是低耦合的真义。

## 第 3 课：服务（Service）——工作台上的"标准插座"

### 白话比喻
工作台的插座区有很多插座，每个插座都有**名字标签**：写着"情绪分析"的插座、写着"地图渲染"的插座、写着"LLM"的插座。插件要用什么能力，就对服务生喊插座名字，服务生把插头插进去。

一个插座背后有三样东西（这就是"能力接缝"）：

| 角色 | 是什么 | 生活类比 | Cordis 叫法 |
|---|---|---|---|
| 插座规格 | 定义"能提供什么、怎么用" | 国家标准插座孔型 | 接口（Service Definition） |
| 插座背后的电器 | 真正干活的东西 | 发电厂/供电局 | 提供方（Provider） |
| 插头/电器 | 用这个能力的东西 | 你的冰箱 | 消费方（Consumer） |

**核心规则：换电器（提供方）不换插头（消费方）。** 插座孔型不变，插座背后从"供电局A"换成"供电局B"，全屋电器照用。

### 情绪地图例子（现成的！）
- 情绪地图有三个大模型供应商：DeepSeek、火山引擎、讯飞。如果按 Cordis 设计，"LLM 服务"就是一个插座：孔型（接口）= "给我一段文本，返回回复"；背后的电器可以随时在三个供应商之间换；所有用 LLM 的插件只认识插座，不认识供应商。
- 情绪地图已有一份"插座规格书"：`ai_qa/tool_contracts.py`（工具契约单一权威源）。这就是"接口"的雏形——Cordis 里叫"服务名 + 类型声明"，情绪地图里叫"工具契约"，同一个思想。

### 与 EMC 内核呼应（用户自己悟到的）
| 概念 | Cordis | 情绪地图 EMC |
|---|---|---|
| 笨服务生 | ctx 代理按名取服务 | 确定性编排器（harness.orchestrate） |
| 插座（能力） | Service | Dumb Tool（笨工具） |
| 插座规格书 | 类型声明合并 | tool_contracts.py（单一权威源） |
| 聪明两端 | 模型（Agent） | 意图理解 + 结果表达 |

> 两套系统说的是同一件事：**聪明放两端（理解/表达），中间全是"标准插座 + 笨服务生"。**

### 小结
> 服务（Service）= 工作台上带名字的标准插座。接口/提供方/消费方三角色分离，换提供方不换消费方——这就是"能力接缝"。

## 第 4.5 节：插件走了又回，重装一遍不浪费吗？（用户疑问详解）

用户疑问极好，触及 Cordis 设计哲学的核心。三层解答：

**第一层：清扫掉的不是"信息"，是"临时接线"。**
代码和配置（图纸）永远没丢——丢的只是运行时的临时状态（内存里的监听器、注册条目、定时器、缓存）。重装 = 拿着图纸重新组装，毫秒级完成。图纸是资产，组装是消耗品。

**第二层：不清扫的代价，比重装大得多。**
如果不清扫，热重载 10 次就会残留 10 份监听器、10 个定时器——事件触发 10 次、工具执行 10 次（真实 bug 类型）。"排查脏状态 bug 的几小时" vs "重装一次的几毫秒"，后者便宜一万倍。

**第三层：确定性 = 可预测 = 可审计。**
系统状态永远 = 声明 + 当前配置。任何时候问"系统里现在有什么"，答案可精确推导，不存在"不知道哪个旧版本留了什么"。这正是 dsh"模型可见即已记录"（状态可从事件流重建）的根基。

**类比**：酒店退房。每个客人走都彻底打扫（dispose）、新客人入住重新布置（apply）——绝不留上一个客人的私人物品。保留会串味、会出错。餐厅翻台同理。

**边界**：什么被清扫？运行时注册（监听器/服务/子插件/定时器/连接/缓存）。什么不被清扫？插件自己写的持久数据（文件/数据库）——那是插件主动管理的资产，Cordis 不碰。

## 第 5 课：事件（Event）——公告板是"广播"，不是"派发"

### 修正理解（Q2）
用户猜"展示→派发任务到指定房间"——**反了**。事件恰恰是**不指定接收者**的：

- 插件 A 干完大事 → 在公告板贴一张"数据导入完成！" → **谁感兴趣谁自己来看**。
- A 不知道谁在看，也不需要知道，更**没有派任务给任何人**。
- 听的人是自己选择订阅（"我对数据导入完成感兴趣"），不是被 A 点名。

### 为什么"不指定接收者"才是精髓
如果 A 直接调用 B（定向派发），A 就必须知道 B 存在——这叫耦合。公告板让 **A 完全不知道 B，也能通知到 B**。将来加一个新插件 C 也想听，A 一个字不用改；C 自己来公告板登记就行。这就是"可扩展性"：**加听众不打扰发布者。**

### 五种广播方式（打个照面）

| 方式 | 大白话 | 场景 |
|---|---|---|
| emit | 喊一嗓子，不等回应 | "数据导入完成"（通知） |
| waterfall | 传话游戏：每人可改写、可截住 | "这条结论能不能发出去？"（守卫链） |
| serial/bail | 排队问，第一个答对的算数 | "谁负责处理这个？" |
| parallel | 同时通知所有人，一起等 | "各位都去更新自己的缓存" |

### 用情绪地图说
将来 EMC 若事件化：数据插件导入完成 → 贴公告"数据导入完成" → 情绪分析插件（自愿订阅）自动开始分析 → 分析完贴公告"分析完成" → 渲染插件（自愿订阅）自动画图。**整条管道靠公告板自动流转，没有任何一个插件认识另一个**——这正是"低耦合"的最高形态。

### 第 5 课小结
> 事件 = 公告板广播：**发布者不指定接收者，监听者自愿订阅**。A 不认识 B 也能通知 B——解耦与可扩展的根源。
> （对比第 4 课：依赖是"我要用你"的强关系；事件是"我通知、你自愿"的弱关系。强弱搭配，各管一摊。）

## 第 5.5 节：事件的机制深挖——"订阅制查表广播"（用户疑问详解）

用户问"B 怎么接收？是全局广播吗？没有接收者会怎样？"——源码（events.ts）给出的机制：

**第一问：B 怎么"接收"？——B 不是被动接收，是提前订阅。**
B 启动时调用"我要听'数据导入完成'"（代码叫 `ctx.on('数据导入完成', 回调函数)`）。这一刻，Cordis 把 B 的回调**登记进一张表**：事件名 → 监听者名单（源码 `_hooks: { '数据导入完成': [B的回调, ...] }`）。B 的"接收"发生在**订阅的那一刻**，不是事件发生那一刻。

**第二问：是"对全局广播"吗？——是"按名字查表"的广播。**
事件发生时，Cordis 做的事只有两步：①拿事件名字去表里查（源码 `this._hooks[name] || []`）；②逐个调用名单上的回调（`map(cb => cb(...args))`）。**没订阅这个事件的插件完全不被打扰**——不是广场大喇叭人人听见，是"邮件订阅制"：只有订了这份邮件的人才会收到。

**第三问：没有接收者，结果是什么？——静默完成，不报错、不丢失（也无处可丢）。**
查表得到空名单 → 遍历零次 → 事件"喊"完就散。对空房间喊话：没有人听到，但房间不塌、喊话的人不受影响。所以：
- **不报错**：发布者不需要知道有没有人听（这正是解耦）。
- **不丢失**：事件本身不是数据仓库，它只是一次"通知动作"。真正要留痕，靠的是**常驻监听者**——dsh 的会话日志就是一个永远在听的监听者，保证"模型可见即已记录"（任何事件都有记录可回放）。**没有常驻记录者，事件过了就过了——这是设计者要主动补的**（对应 dsh"可重放日志"思想）。

**第四问（Q2 修正）：EMC 问答链哪些该"贴公告"？——事实贴公告，动作走服务。**
用户答"提问→意图、意图→工具都要公告"——方向对一半。修正规则（Cordis 实践规则原文）：
> "拦截和策略优先使用事件；直接能力调用优先使用服务方法。"

拆开说：
- **动作**（"去理解意图""去调用工具"）= 强关系，应该**直接喊插座**（服务调用）：因为动作需要返回值、需要等待、需要确定成功失败——公告板给不了这些。
- **事实**（"意图已生成""工具执行完成""工具失败了"）= 弱关系，适合**贴公告**（事件）：任何插件可以自愿响应——比如"工具失败了"贴公告，日志插件记录、告警插件提醒、降级插件换方案，各干各的，互不认识。
- 所以 EMC 事件化的正确姿势：**"意图已生成"发事件（谁要谁听），"去执行意图"走服务（确定调用）**。

### 第 5.5 节打卡（机制题）
- Q1①："B 和 C 谁先收到？" → 答："都能收到，没有先后" ❌ ——**有先后**：emit 按订阅顺序（注册顺序）同步调用，先订阅的先收到（源码：`_hooks[name]` 数组按 on 的调用顺序 push，emit 时 map 逐个调用）。
- Q1②："B 的回调报错，C 还能收到吗？" → 答："C 能收到" ⚠️ 半对——**要看 B 怎么错**：B 同步抛异常 → map 中断，C 收不到；B 异步失败（返回的 promise reject）→ emit 不等待（fire-and-forget），C 照样收到。**教训：事件回调里尽量别同步抛异常，否则会连坐后面的监听者。**

### 补充讲：同步 vs 异步（用户追问·2026-08-19）
- **同步（synchronous）**：代码一行一行执行，做完一件再做下一件。调用一个函数，必须等它返回才能继续。类比：**排队买票**——前面的人没买完，后面的人等着。
- **异步（asynchronous）**：调用后不等结果，先干别的，结果好了再回来处理。类比：**点外卖**——下单后不用站在店门口等，可以回家，外卖到了再取。
- 代码层面：JS 里"返回 Promise（承诺）的函数"就是异步；`async` 函数自动返回 Promise；Promise 失败叫 reject。
- **为什么 B 同步异常 → C 收不到**：`emit` 的实现是"按名单顺序逐个同步调用"（类似 for 循环）。B 的回调在**被调用的当场**直接抛异常（throw）→ 异常从循环里炸出来 → 循环中断 → C 根本还没轮到。类比：排队买票，第一个人突然晕倒砸在窗口，队伍后面的人今天都买不了票。
- **为什么 B 异步失败 → C 能收到**：B 的回调是 async 函数，`emit` 调用它时只拿到一个 Promise 对象就**丢掉不管**（不等待）。Promise 内部的失败发生在"未来"（事件队列里），等它失败时，`emit` 早就跑完了，C 早就被调用了。类比：骑手送外卖摔了（订单失败），但你下单时根本没等，其他订单照常派送。
- **一句话**：同步异常 = 当场爆炸，连坐全场；异步失败 = 未来爆炸，只炸自己。
- Q2："事件没人听没关系，但漏了什么责任？" → 答："？" ——**答案是"记录"**：必须装常驻日志监听者（订阅所有事件落盘），否则事件过了就过了、不可回放（dsh"模型可见即已记录"的根基）。

## 第 6 课：效应（Effect）——借的东西一定要还（Cordis 的灵魂课）

### 预备词

- **副作用（side effect）**：插件干活时产生的"额外动作"。插件的主业是提供能力（比如"分析情绪"），但干活过程中它会**借一堆东西**：开定时器、连数据库、注册监听器、写缓存……这些借用就是副作用。

### 白话比喻

插件是一个"租客"。干活时它从房东（Cordis）那里借了一堆东西：

| 借的东西 | 生活类比 |
|---|---|
| 定时器（每 5 秒做件事） | 借了个闹钟 |
| 数据库连接 | 借了根水管 |
| 事件监听器（第 5 课的订阅） | 订了份邮件 |
| 子插件 | 请了个帮工 |

**房东的规矩只有一条：走的时候，借了什么还什么。** 而且不用租客自己记着还——房东有一本"借出登记簿"，租客搬走时房东**照着登记簿自动收**。这就是"效应"：**每一次借用都登记在案，每一次离开都自动归还。**

### 机制讲解（源码验证）

代码上只有两个动作：

1. **借**：`ctx.effect(() => { 借东西; return 归还函数 })`——执行体在插件加载时运行，借好东西；**返回的"归还函数"（disposer）就是承诺**。
2. **还**：插件卸载时，Cordis 自动调用所有归还函数（**按登记顺序逆序**）。

关键细节：

- **大部分借用不用你手写"还"**：Cordis 自己管的 API（`ctx.on` 订阅、`ctx.plugin` 挂子插件、注册服务/工具）**自带归还**——订阅自动退订、子插件自动带走、工具自动注销。只有 Cordis 不管的（原生定时器、外部连接、文件 watcher）才需要你亲手包一层 `ctx.effect`。
- **逆序归还**：后借的先还。为什么？见下方检查题 2。
- **异步归还并发跑**：多个归还函数若都要等，Cordis 一起等；但**有顺序要求的步骤要放进同一个归还函数里**（第 2 课 heartbeat 例子：`clearInterval` 必须在 `clearTimeout` 前——同一个函数里依次写）。

### 用情绪地图说（你已经在做这件事了！）

zcode 二轮回应里有一条"副作用必带补偿"纪律，第一个示范就是 T2 的 `clear_layer_usage_cache()`——**手动清缓存 = 手写归还函数**。Cordis 的进步是把它从"纪律"变成"机制"：不用记得清，卸载自动清。

再回忆第 4.5 节你问的"重装浪费吗"——**效应就是"不浪费"的保证**：因为每次卸载都按登记簿还干净，重装才敢放心重来。

### 第 6 课小结

> **效应（Effect）= 房东的借出登记簿。** 借东西登记，离开自动归还（逆序）。Cordis 管的 API 自带归还；Cordis 不管的资源要亲手包 `ctx.effect`。**没有登记簿的借用 = 漏还 = 脏状态**（第 4.5 节的 bug 之源）。

### ✅ 第 6 课理解检查（待答）

1. **判断题**：插件 A 用系统原生方法开了个定时器（每 5 秒打印一次），**没有**用 `ctx.effect` 包裹。A 被卸载后，定时器会怎样？
   A. 定时器继续跑，直到整个程序退出
   B. Cordis 会自动发现并关掉它
   C. 程序报错提醒 A 忘还了
   （提示：Cordis 只能管"登记过的借用"——想想"登记簿"记了什么）

2. **想一想**（逆序归还为什么安全）：帮工 B 干活时，**借用了 A 的工具**（B 依赖 A）。A 和 B 都要走。如果按"先借的先还"：A 先还（把工具收走）→ B 再还（B 还在用工具，工具没了）——出问题。那按"后借的先还"：谁先还？顺序是什么？——用一句话回答"后借的先还 = 先还____，再还____"。

## 第 7 课：生命周期（Fiber）——积木块的"出生到拆除"全程

### 白话比喻

每个插件实例从装进房间到搬走，都有**一张房态卡**（Fiber），记录它现在的状态。酒店房态：

```
预订中(PENDING) → 入住办理中(LOADING) → 已入住(ACTIVE) → 退房办理中(UNLOADING) → 已退房(DISPOSED)
                        ↘ 入住失败(FAILED)
```

### 五种状态逐一解释

| 状态 | 大白话 | 什么时候出现 |
|---|---|---|
| PENDING（等待中） | 客人在前台排队，还没入住 | 插件声明的服务还没就绪（第 4 课：插座没通电就等着） |
| LOADING（加载中） | 正在办理入住 | `apply` 函数正在执行（正在借东西、登记） |
| ACTIVE（运行中） | 已经住下了 | `apply` 跑完，插件正常干活 |
| UNLOADING（卸载中） | 正在退房打扫 | 归还函数们正在跑（第 6 课：按登记簿收东西） |
| DISPOSED（已拆除） | 房间清空，房态注销 | 所有归还完成 |
| FAILED（失败） | 入住手续办砸了 | `apply` 或配置校验抛异常（第 5 课讲过：明确报错不静默） |

### 三个最实用的事实

1. **"为什么我的插件没动静？"——先查 PENDING。** 插件一声不吭不干活，八成是它要的服务没人提供，停在"排队"状态。Cordis 允许枚举所有插件的房态卡来诊断（`ctx.registry` 遍历 fiber 状态）。注意：PENDING 的插件**不会让程序保持运行**——房间里只有"等待的客人"没有"住下的客人"时，酒店前台会下班（进程静默退出）。
2. **拆一个，带走全家。** 调用 `fiber.dispose()` 会**递归卸载所有子插件**——请的帮工（子插件）会跟着主人一起走，等全部归还完成才算拆完（包括异步归还，会等）。
3. **失败不静默。** 插件加载失败会**明确报错**，不会假装没事跳过——这是 Cordis 的诚实度纪律（和情绪地图 CB-39 的诚实度原则同构）。

### 用情绪地图说

将来 EMC 插件化后，你看到一个插件"卡住不动"，第一反应应该是查它的房态卡是不是 PENDING（缺依赖）——而不是满世界找 bug。这就是 Fiber 的价值：**把"插件为什么不干活"从玄学变成可查的状态。**

### 第 7 课小结

> **生命周期（Fiber）= 每件家具的房态卡。** PENDING 等依赖、ACTIVE 干活、UNLOADING 归还、DISPOSED 清空、FAILED 报错。拆一个带走全家（递归卸载子插件）；不干活先查 PENDING。

2. **判断题**：A 插件挂载了子插件 B。A 被卸载时，B 会怎样？（A. B 继续独立运行 B. B 跟着 A 一起被卸载 C. B 报错）

## 第 8 课：串起来——dsh 的一天（全部概念穿成一条线）

### 早上：开工（装配）

dsh 启动 = 毛坯房开门，房东照着**施工图（cordis.yml 配置）**搬家具：

1. 读施工图 → 创建工作台（Context，第 2 课）
2. 逐个安装插件（第 1 课）：模型适配器、工具注册表、会话日志、Agent 主循环……全是家具
3. 每件家具声明"我要什么"（inject，第 4 课）→ 家具们自动排队：插座没通电的保持 PENDING（第 7 课房态卡）

### 上午：通电（服务就绪）

依赖的服务一个个装好 → PENDING 的家具自动醒来（ACTIVE）→ 工作台通电完成。**顺序由依赖决定，不是施工图顺序**（第 4 课）。

### 白天：上班（干活）

模型（Agent）接到用户问题 → 通过工作台服务生（第 2 课）调用工具：

1. 工具执行 = 走**五道闸流水线**（第 5 课事件链：每个闸门是 waterfall 监听器，可拦截/可放行/可替换——"post-execute 四态"就是守卫的决策）
2. 每一步都**贴公告**（事件，第 5 课）：`tool/call`、`tool/result`……会话日志（永远在听的监听者）全部记录——**"模型可见即已记录"**（第 5.5 课：没有常驻记录者，事件过了就过了）

### 傍晚：换家具（热重载/HMR）

开发者改了某个插件的代码 → 热重载：

1. 旧家具**按登记簿归还**（第 6 课效应：监听器退订、定时器关闭、工具注销——全部逆序清扫）
2. 房态卡走到 DISPOSED（第 7 课）
3. 新代码重新装 → apply 重跑 → 家具复活
4. **不留一点旧痕迹**——这就是第 4.5 节"重装不浪费"的现场版

### 深夜：打烊（卸载）

程序退出 = 全部家具按登记簿归还 → 所有房态卡 DISPOSED → 工作台关门。**没有一件家具留下借的东西。**

### 全书一句话

> **Cordis = 毛坯房（框架）+ 家具（插件）+ 工作台（Context）+ 插座（Service）+ 排队（inject）+ 公告板（Event）+ 登记簿（Effect）+ 房态卡（Fiber）。**
> dsh 的一切能力——工具、模型、日志、甚至 Agent 主循环——都是这套机制上的家具。理解这八课，你就读懂了 dsh 的骨架，也读懂了"标准插座"计划（情绪地图平台化）要借鉴的全部机制思想。
