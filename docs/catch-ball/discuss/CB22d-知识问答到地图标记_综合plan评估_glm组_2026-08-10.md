### 焦点 B：方案有效性（P0-2 路由 + P0-4 验收）— **disagree P0-2 触发机制（实质缺陷）**

#### B.1 ★ P0-2 路由使能的 `ctx.resume` 条件永不成立 — **实质缺陷·必须重构**

这是 glm组 本轮**最核心的独立发现**。plan P0-2（综合 plan 第 102-103 行）说：

> `ctx.resume && priorTurn.intent==='knowledge_qa' && /标记|标到地图|在地图上|点位/` → 上下文提示

但 glm组 实测代码路径，**`ctx.resume` 在本场景恒为 false**：

| 条件 | 实测 | 证据 |
|---|---|---|
| `_resumingAsk`（上轮 ask_user 出口） | **false** | 上轮 knowledge_qa 走 `_assembleKnowledgeQA`（[harness.js:1207](frontend/js/ai_qa/harness.js#L1207)）→ return 对象（harness:162/169）**无 `exit` 字段** → `_prevTrace.exit !== 'ask'` → `_resumingAsk=false`（[panel.js:1695](frontend/js/ai_qa/panel.js#L1695)） |
| `_isResumeCue(text)`（续作词正则） | **false** | 用户句「能在地图上标记出这些项目的位置吗」—— `_isResumeCue`（[panel.js:1631](frontend/js/ai_qa/panel.js#L1631)）正则 `/继续\|接着\|续做\|补充\|那个\|上一个\|把刚才/` **零命中** |
| → `ctx.resume` | **false** | `ctx.resume = _resumingAsk || !!(ctx.priorTurn && _isResumeCue(text))`（panel.js:1696）= false \|\| false = **false** |

**结论**：P0-2 的 `ctx.resume && ...` 条件**第一个子句就 false，整个分支进不去**。「上下文提示」永远不会被注入。plan 自己也说（P0-2 第 103 行）「不改 diagnose 文本·不翻转 resume 布尔」——但不翻转 resume，条件就不成立。**这是自相矛盾**。

**进一步推演后果**：`ctx.resume=false` → 走 harness:1203 `else` 分支 → FC diagnose（harness:1124）正常跑。此时能否触发 generate_point_layer **完全取决于 FC LLM 能否从契约 `when` 选到它**（见 B.2）。P0-2 的「上下文提示」机制形同虚设。

**glm组 修正建议**：放弃「resume 条件」机制，改为**在 FC 路径前置注入上下文提示**（不依赖 resume 布尔）：

- 位置：harness orchestrate FC diagnose 之前（harness:1124 `fcDiagnoseStep` 调用前），检测 `ctx.priorTurn && ctx.priorTurn.intent === 'knowledge_qa' && /标记|地图|位置|点位/.test(ctx.question)` → 往 `ctx.context` 注入「用户要把上一轮知识问答的项目标记到地图·请选 generate_point_layer 并从上轮回答提取项目/片区名入 names[]」。
- **不翻转 resume**（仍守 Codex 挑战 A·不污染续作语义）·**不进 1197 续作分支**（走正常 FC）·**仅上下文提示引导 FC 选型**。
- 这样无论 resume 真假，提示都注入——修复 B.1 缺陷。

#### B.2 ★「标记」句落 diagnose 是否可靠 + FC 能否选到新工具 — **取决于契约 when，非 prompts.py 铁律**

plan P0-2 第 104 行说「本句（无续作词）天然落 diagnose 由 LLM 判新技能」。glm组 验证「落 diagnose」部分成立，但**「判新技能」的机制 plan 描述错了**：

- **「标记」句落 diagnose**：✅ 成立。`_quickIntent`（harness:60-82）对「能在地图上标记出这些项目的位置吗」：CONCEPT_KW 无 · GEO_VERB_KW（emc-patterns.js:34，含「地点/在哪/坐标」但**不含「标记」**）无命中 · RAG_QUERY_KW 无 · REGION_KW「宜昌」命中但非 SEARCH_EVIDENCE_RE → `return null` → 落 FC diagnose。**这部分 plan 正确**。

- **★ 但 FC LLM 选工具靠的是契约 `when`，不是 prompts.py:267「选择要点铁律」**：这是 plan **第二个实质缺陷**。glm组 实测路由机制：
  - 前端走 **FC 路径**（[harness.js:1124](frontend/js/ai_qa/harness.js#L1124) `stages.fcDiagnoseStep`），**不走旧 diagnose SSE**（router.py:115）。
  - FC 路径的 system prompt = `build_fc_sys_prompt`（[router.py:25-50](ai_qa/router.py#L25)），**极精简**——只含工具通用规则 + 尺度判定 + 极性纪律 + 数据上下文。**不含「选择要点·铁律」、不含 TEMPLATE_REGISTRY、不含 GEO_TOOL_CATALOG**（那些是旧 diagnose `build_diagnose_prompt` 的附录，prompts.py:264-270）。
  - FC LLM 选工具**主要依据 `contracts_to_tools_schema()` 返回的各工具 description**——即 `TOOL_CONTRACTS` 每条的 `when` 字段（CB-09 承重 learning·KNOWLEDGE §2「契约 when = FC 工具 description」）。
  - → **plan P0-3「prompts.py 选择要点铁律增量追加 generate_point_layer」对 FC 主路径基本无效**（LLM 根本看不到那段）。真正决定 FC 能否选到新工具的，是 **`tool_contracts.py` 的 `when` 字段写得够不够诱导**（要含「标记/地图/项目名→点位」等触发词）。

**glm组 修正建议**：P0-3 把诱导重心**从 prompts.py 铁律移到契约 `when`**：
- `tool_contracts.py` generate_point_layer 的 `when` 字段须显式含触发场景：「把文字答案/项目名/地点名标记到地图·生成点位图层·批量地名→点」（仿现有 extract_feature `when`「从面边界按属性抽单要素」的诱导写法）。
- prompts.py:267 铁律追加**可保留**（旧 diagnose 兜底路径用·零成本），但**不能作为主依赖**。
- `build_fc_sys_prompt`（router.py:25）可考虑加一行工具选型提示「用户要把地名/项目标记到地图 → generate_point_layer」（可选·加强诱导）。

#### B.3 验收标准覆盖度 — **agree 主体 + 补 2 个必测场景**

plan P0-4 验收清单（工具单测/路由负例/B3/黄金集/eval 复采/静态断言）基本完整。glm组 **补充 2 个必测场景**（针对 B.1/B.2 缺陷）：

1. **FC 选型正例**（B3/黄金集）：「知识问答→追问标记」→ 断言 FC 输出 `tool_calls[0].function.name === 'generate_point_layer'`（验证契约 when 诱导有效·**这是修复有效的命门断言**）。

**若不补这 2 个场景，plan 的「修复有效」无法被验收证明**（现行清单只测工具执行，没测 FC 是否真选到它）。

**B 小结**：P0-2 触发机制**失效（resume 恒 false）必须重构**；P0-3 诱导重心**错位（铁律对 FC 无效·须移到契约 when）**；验收须补 FC 选型正例 + 选错兜底 2 场景。

#### F.1 names[] 提取的鲁棒性问题（承接 plan 隐含点）

plan P0-1 说 generate_point_layer 入参 `names[]`，但 **names[] 从哪来 plan 未明确接线**（上轮 glm 建议「LLM diagnose 从 priorTurn.final 提取」被 claude组 采纳但未落 plan 步骤）。glm组 强调：

- **FC 路径下 names[] 提取的可靠性**：FC LLM 在 `fc_diagnose` 阶段输出 `tool_calls[0].function.arguments`——它需要从 `ctx.context`（含 priorTurn 蒸馏·panel.js:1689 `_buildPriorTurn`）提取项目名填入 names[]。**priorTurn.final 是否注入了 FC 可见的 context？** glm组 核验：`_distillTurn`（panel.js:1601）蒸馏的是 `intent/method/done/gap/strategy`——**不含 final 文本原文**。→ FC LLM **看不到上轮回答的项目名列表**，无法填 names[]。
- **修正建议**：P0-2 上下文提示（修正后）须**同时注入上轮 final 文本片段**（或 priorTurn 扩展加 `final_excerpt` 字段），让 FC LLM 能提取项目名。否则即使选到 generate_point_layer，names[] 为空 → 工具无输入。**这是 plan 的第 3 个隐性缺陷**（与 B.1/B.2 并列）。

#### F.2 并发策略的 timeout 预算（强化 Codex 挑战 2）

Codex 提「55 名并发超时策略」已纳入 plan。glm组 补具体预算建议：`/api/v1/place/search` 单次约 200-500ms（本地 4310 POI + 高德兜底），55 名 Promise.all + 限流（如 p-limit 5 并发）→ 约 5-10s。**须在 FC 单轮预算内**（FC + 执行 + answer 总预算约 30s）。建议 timeout 设 15s + 未完成者落第三级文字（部分命中也能出图层·不必全等）。

#### F.3 工具命名一致性（小建议）

plan 用 `generate_point_layer`，但现有 Toolbox 工具命名风格是 `generateHeatmap/generateGrid/generateTerrain3D`（驼峰·ForAI 入口）。前端 TOOLS 对象用小写下划线（density/buffer/lookup_place）。**建议 FC 契约名 = `generate_point_layer`（下划线·与 FC tool name 一致）·前端 TOOLS 方法名同步·内部委托函数若复用 Toolbox 则驼峰**。避免 CB-04 式契约分裂（KNOWLEDGE §2「EMC-Toolbox 参数契约单一源」）。

**F 小结**：3 条增量——F.1 names[] 提取隐性缺陷（priorTurn 不含 final·须注入）/ F.2 并发 timeout 预算 / F.3 命名一致性。

### 判定：**可行·但需修正（P0-2 重构 + P0-3 诱导重心转移 + 补 names[] 注入）**

| 维度 | 判定 | 理由 |
|---|---|---|
| 方案方向 | ✅ 可行 | generate_point_layer + 三级回退 + 归 gis_operation·C2 豁免验证通过·红线零触碰 |

| **P0-3 契约诱导** | ⚠️ **需转移重心** | prompts.py 铁律对 FC 主路径无效·重心须移到契约 `when` + 可选 build_fc_sys_prompt |

## 三、补充建议（优先级排序）

### S1（必须·阻断性）修正 P0-2 触发机制

- 放弃 `ctx.resume &&` 条件（恒 false）。

### S4（必须）补 `_deterministicRecover` 兜底
