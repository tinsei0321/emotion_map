## 〇 一页结论

### 1. EMC × dsh 的定位

EMC × dsh 不是“把情绪地图搬进 dsh”，也不是“给 dsh 写一个大插件”。它的正确定位是：

> **测试阶段：dsh 是外置实验驾驶舱，EMC 是数据、工具、知识和地图资产的权威提供方。**  
> **稳定阶段：EMC 成为一个壳，把测试阶段跑通的能力、流程和体验吸收进自己的产品形态。**

换句话说：

- 现在：在 dsh 窗口里测试“通用助手 + EMC 资产”这套工作方式；
- 以后：把证明有效的部分收回 EMC，形成正式产品壳，而不是永久依赖 dsh 界面。

### 2. 测试阶段主线

```text
用户在 dsh 窗口提问
  → dsh 通过 EMC 标准插座读取数据说明书 / 知识 / 工具
  → 调用注册 Toolbox 能力，或在受控条件下临时编写工具
  → 形成结论、报告或表格
  → 通过渲染契约控制 8080 地图页面
  → 生成对应图层
  → 图层样式复用 Toolbox / 参数面板的样式权威源
```

### 3. 双环境同步的真正问题

office 和 home 之间并不是“有没有 git”的问题。EMC 仓库已经有 git、Gitee、GitHub 备份和移动硬盘同步机制。真正容易断的是四层：

1. **仓库内容层**：未 commit / 未 push 的文档和代码；
2. **dsh 运行环境层**：`~/.dsh` 里的 profile、preset、插件、junction、版本配置；
3. **可重建资产层**：RAG 向量索引、模型缓存、依赖包、端口进程状态；
4. **外部原始资料层**：OneDrive、本地大文件、会话记录、密钥。

目前最大的新断点是：**PT-CB8 T7 双模预设和相关 guard 只在 office 的 `~/.dsh` 里，尚未形成可入库、可重建、可跨机复制的环境配方**。

### 4. 沉淀内容同步原则

情绪地图的沉淀资产必须分成四类：

1. **权威资产**：进 git，双侧同步；
2. **派生资产**：不直接同步，靠源资产 + 版本 + 脚本重建；
3. **秘密资产**：不进 git，只同步变量名与配置方法·值禁入库禁搬运；
4. **外部原始资产**：不盲目搬全文，必须登记来源、版本、路径和入库策略。

核心口号：

> **能进仓库的进仓库；能重建的不要手工搬；不能进仓库的必须登记；没有登记的沉淀不算沉淀。**

# 第一部分：EMC × dsh 工程预期

## 一、测试阶段：dsh 作为外置实验驾驶舱

### 1.1 用户真正要测试什么

当前阶段不是做“dsh 版 EMC”，而是验证：

> 用户用自然语言提出城市情绪分析需求后，一个通用 AI 助手能否在 EMC 的受控资产供给下，完成从理解、查数、分析、出图到报告的全链路。

dsh 的价值在于：

- 它是现成的通用助手运行环境；
- 它已经有对话、工具调用、权限、插件和会话管理；
- 它适合快速测试“外部大脑 + EMC 资产插座”的组合效果；
- 它能让用户先看到未来 EMC 壳的交互形态，而不必一开始就重写 EMC 前端。

但 dsh 不应拥有 EMC 的业务真相。数据、口径、知识、工具语义、样式和渲染规则仍必须归 EMC 管。

### 1.2 要消费的 EMC 资产

#### A. 数据资产

dsh 应通过 EMC 的数据说明书读取：

- 可用点层；
- 可用边界层；
- 字段和类型；
- 坐标系；
- 数据用途：原料层还是结论层；
- 数据性质：真实、模拟、治理产物或临时层；
- 口径与覆盖范围。

关键要求：

1. 先看说明书，再取数；
2. 不允许 dsh 自己猜路径、猜字段、猜口径；
3. 结论层不能被当作空间分析原料；
4. 输出必须带口径、覆盖和来源。

#### B. 工具箱资产

dsh 应优先调用 EMC 已注册的 Toolbox 能力，例如单元聚合、缓冲影响圈、排序评价、热点或密度分析、叠加裁剪等。

原则：

> **dsh 可以调度工具，但不应重写工具。**

如果能力在 EMC Toolbox 中已经存在，dsh 只能通过标准入口调用；不能在 dsh 侧复制一份算法，否则会出现两套结果、两套口径和两套 bug。

[v1.1-G3] 现行注册插座以 `tools/mcp_server_emc.py` 工具面为准（数据清单/知识检索/行业事实卡/出口卡/单元聚合/缓冲/排序/渲染说明/文件直显/服务状态共十件）——本报告不复制清单防漂移，消费方以运行中工具面为唯一事实。

#### C. 临时工具

测试阶段允许 dsh 临时编写小工具，但必须：

1. 标记为“临时实验件”；
2. 只处理当前任务；
3. 不绕过 EMC 数据安全、脱敏、usage 和口径规则；
4. 若有长期价值，走沉淀流程。

沉淀流程：

```text
临时工具
  → 任务验证有效
  → 说明输入输出、口径、限制和依赖
  → 补测试或验收样例
  → 入库或并入 Toolbox
```

临时工具是试验田，不是私人后门。

[v1.1-G1] 模式归属：临时编写工具仅发生在**研究档**（emc-research·全工具白名单）；**快分析档**（emc-analysis·白名单无 write/edit/shell）只消费注册工具与已沉淀工具。研究档临时工具经验证沉淀后，其注册形态进入快分析档消费面。快分析档内尝试写工具被 guard 拒绝是**预期行为**，不是故障。

#### D. 知识与 RAG 资产

dsh 应能查询 EMC 的行业知识、项目知识、口径卡、案例卡和概念卡。

当前 RAG 正在重构，因此必须预留接口：

```text
dsh / EMC 壳
  → 稳定的知识查询接口
  → 适配器
  → 当前 RAG 实现 / 未来重构后的 RAG 实现
```

要求：

1. 对 dsh 暴露的接口不绑定当前索引文件结构；
2. RAG 重构后，dsh 侧调用方式不应大改；
3. 知识结果必须带来源、维度、口径和置信边界；
4. 当前索引可以重建，但知识源内容和知识卡片必须作为权威资产同步；
5. 重构期间，新旧链路要用同一黄金集对照评估，不能凭感觉切换。

[v1.1-G4] 接口锁条款（双写 PT-CB9 收口验收）：`rag_query` 工具名、核心返回字段（results/count/dim_counts/caliber）、`synthesize` 语义零破坏性变更；如需破坏性变更，走版本化新工具名（如 rag_query_v2），旧名保留过渡。

#### E. 渲染与地图资产

dsh 生成结论后，应控制 EMC 的 8080 页面出图，包括：

1. 启动或探测 8080 服务；
2. 判断服务是否就绪；
3. 发送渲染说明；
4. 生成对应图层；
5. 控制图层命名、类型、样式、图例和提示；
6. 避免重复图层、旧图层残留或旧进程重放旧说明。

关键原则：

> **dsh 可以决定“要画什么”，但 EMC 决定“应该怎么画”。**

图层样式必须继续消费 Toolbox / 参数面板的样式权威源，包括色带、极性映射、拉伸方式、图例、透明度、高度或三维参数、点线面默认视觉语言。

dsh 不应自己发明一套彩虹色、灰阶或热点样式。否则测试阶段看到的地图和未来 EMC 产品会分裂。

### 1.3 测试阶段交互形态

#### A. 问答型

例子：

> “12345 热线诉求最密集的 10 个社区是哪些？”

dsh 应：

1. 查数据说明书；
2. 选择正确点层和边界；
3. 调用聚合或排序工具；
4. 给出口径和覆盖说明；
5. 如用户要求，渲染到 8080 地图。

#### B. 任务型

例子：

> “对伍家岗某设施做 500 米影响圈，分析圈内负面情绪，并输出一份可放进报告的结论。”

dsh 应：

1. 读取数据说明书和工具说明；
2. 调用缓冲工具；
3. 对圈内点做聚合；
4. 结合知识库或口径卡解释；
5. 形成报告段；
6. 生成图层；
7. 标注临时工具或注册工具来源。

### 1.4 测试阶段验收标准

一条链路算跑通，至少要同时满足：

1. 数据正确：使用正确的数据层和边界；
2. 口径正确：不把宏观结论说成微观诊断；
3. 工具正确：优先调用 EMC Toolbox，不重复造轮子；
4. 结果可追溯：能说明工具、数据、口径来源；
5. 地图可复现：8080 图层与结论对应；
6. 样式一致：地图样式来自 EMC 权威样式契约；
7. 过程可控：临时工具受控，不污染主工程；
8. 跨机可续：office 跑通的内容，home 能快速复现；
9. RAG 可替换：当前 RAG 重构不破坏外部调用方式；
10. 报告可用：输出能进入规划 / 体检 / 更新工作材料。

## 二、稳定阶段：EMC 壳吸收测试成果

### 2.1 “隐化”的含义

用户对第二阶段的预期是：

> 测试稳定 + RAG 重构框架确定后，将测试阶段的逻辑和内容“隐化”进 EMC，EMC 作为一个壳子把测试阶段内容套住。

这应理解为：

```text
dsh 窗口中的成功体验
  → 抽象成稳定接口和流程
  → 由 EMC 自己的壳承载
  → 用户不再需要理解 dsh / MCP / 外部大脑
```

“隐化”不是把 dsh 简单嵌入 EMC，也不是把所有代码搬进前端，而是把已验证的能力变成 EMC 的产品体验。

[v1.1-Q5] 阶段进入判据（可证伪·防凭感觉切换）：①标准任务（12345 五社区快分析）双机等价通过；②RAG v2 黄金集达标且接口锁验收通过；③快分析档标准任务稳定低于 2 分钟线。三者齐备才启动稳定阶段迁移讨论。

### 2.2 EMC 壳应拥有的东西

稳定阶段 EMC 壳应拥有：

1. 统一入口：用户只看到 EMC；
2. 服务生命周期管理：启动、预热、就绪、异常恢复；
3. 工具调用界面：自然语言、按钮或模板任务；
4. 数据说明书：内部使用，也可按需展示；
5. 知识查询：接重构后的 RAG；
6. 分析执行：调用同一 Toolbox；
7. 结果呈现：报告、表格、地图图层；
8. 过程留痕：trace、口径、来源和版本；
9. 会话承接：用户能继续追问、修正和比较；
10. 跨环境运行：office/home 可复现。

[v1.1-G2] 11. 继承三支柱纪律：知识问答成功路径必须 LLM 综合（检索素材→架构路由→LLM 归纳·不新增事实）；零 LLM 仅限检索失败兜底——测试期与壳继承期同此纪律，任何方案不得砍三支柱之一。

### 2.3 不应吸收的东西

EMC 壳不应吸收：

1. dsh 的开发者界面细节；
2. dsh 的插件管理复杂度；
3. dsh 的 debug 终端体验；
4. 未经验证的临时代码；
5. 绕过 EMC 安全和口径规则的自由工具调用；
6. 只适用于单机、单用户、单会话的硬编码配置。

### 2.4 迁移原则

从测试阶段进入稳定阶段时，应遵循（[v1.1-S3] 以下为**方向性约束**·非已拍板结论——具体实现方式按下阶段讨论·不草率定死）：



1. 先接口，后壳；
2. 先复用，后重写；
3. 先对照，后切换；
4. 先资产，后界面；
5. 先小闭环，后大迁移；
6. 先可测，后上线。

### 2.5 下一阶段必须讨论的问题

1. EMC 壳是轻前端、完整前端，还是服务端编排加现有地图页；
2. 自然语言入口放在 EMC 内部哪一层；
3. 是否保留 dsh 作为开发调试后门；
4. 会话记录和 trace 如何迁移；
5. RAG 新框架的接口边界；
6. 工具注册和临时工具沉淀机制；
7. 渲染契约是否需要升级；
8. 用户身份、权限和数据安全如何进入壳内；
9. office/home 环境配置如何自动生成；
10. 哪些测试期能力暂缓产品化。

# 第二部分：office / home 双环境下 EMC × dsh 如何同步

## 一、现状判断

### 1.1 已有的同步能力

EMC 仓库当前已有：

- `EMC_harness_dsh` 工作分支；
- `origin` 指向 Gitee，office 可直接访问；
- `github` 作为 home 侧备份远端；
- DEV-SYNC-HUB 移动硬盘同步专区；
- HOME / OFFICE 换机卡；
- repo 内 `memories/auto/` 蒸馏记忆镜像；
- `docs/sync-reports/` 中的双环境合流记录；
- 服务新鲜度检查意识（R7：页面新不等于后端新）。

所以，仓库和文档的同步机制已经存在，问题不在“没有通道”。

### 1.2 当前真正的断点

#### 断点 1：`~/.dsh` 不随 EMC 仓库同步

PT-CB8 T7 双模预设目前落在 office 的 `C:/Users/Administrator/.dsh/`，包括：

- `profiles/emc-analysis/`
- `profiles/emc-research/`
- `.agent-presets/emc-analysis/`
- `dsh-emc.ps1`
- `EMC_DUAL_MODE.md`
- `ptcb8-t7-backup-20260821/`

这些内容不在 EMC git 仓库里。home 端拉取 EMC 分支后，不会自动得到这些配置。这是当前最大断点。

#### 断点 2：dsh 版本和安装形态可能不同

office 刚部署 `dsh 0.1.0-rc.8`。dsh 处在快速迭代期，rc.7 / rc.8 的 profile、preset、headless 行为已经出现差异。若不记录版本，双机容易出现“同一配置一边能跑、一边不能跑”。

#### 断点 3：本地路径和用户名不同

office 是 `C:/Users/Administrator/.dsh/`，home 可能是 `C:/Users/Hi/.dsh/`。配置不能硬编码绝对用户路径，应由脚本按当前用户推导。

#### 断点 4：node_modules / junction 不应直接复制

T7 中 MCP client 通过 junction 指向本机已安装 rc.8 包。不同机器安装位置可能不同。应记录包名、版本、来源、期望哈希和创建命令，而不是手工复制 junction。

#### 断点 5：RAG 索引和模型缓存是派生资产

RAG 向量索引、embedding 模型缓存、Python 依赖缓存不应手工复制同步，应由知识源版本、构建脚本版本、模型名、构建参数和源内容哈希重建。

#### 断点 6：密钥不能进 git

模型、地图、dsh 或其他服务凭据不能写入仓库。只同步变量名和安全配置方法；校验时只显示是否存在，不显示值。

#### 断点 7：服务进程和端口状态不随文件同步

常见问题：

- 8000 / 8080 / 3080 被旧进程占用；
- 前端文件是新的，后端进程是旧的；
- dsh 页面是新 build，MCP server 是旧代码；
- render inbox 残留旧说明导致重放。

每次到岗不能只看文件版本，还要跑服务新鲜度和端口检查。

#### 断点 8：未提交内容不会同步

任何未 commit / 未 push 的内容，对另一台机器都不存在。尤其要注意新报告未 add、配置只写本机目录、执行记录未入库、大文件只是本地副本、任务状态只在会话里。

## 二、目标机制：环境即代码 + 到岗自检

### 2.1 核心思想

不要靠“每次手工配置很多内容”，而要逐步做到：

> **仓库里保存环境和能力的配方；每台机器根据配方自动生成自己的本地运行时。**

结构：

```text
EMC git 仓库
  = 业务代码 + 数据资产 + 测试 + 文档 + 环境配方

office / home 本机
  = 由配方生成的运行时 + 本机密钥 + 可重建缓存
```

### 2.2 建议新增环境配方层

建议在仓库中新增类似以下结构：

```text
docs/dsh-environment/
  manifest.yml
  profiles/emc-analysis/
  profiles/emc-research/
  presets/emc-analysis/
  setup-office.ps1
  setup-home.ps1
  check.ps1
```

名称可后续调整，但必须包含版本清单、profile 配方、插件依赖来源、可重建资产清单和到岗检查清单。

#### A. 版本清单

记录：

- dsh 全局版本；
- dsh 源码 checkout commit（如需要）；
- Node 版本；
- Python 版本；
- MCP client 包版本；
- EMC 分支和 commit；
- 关键插件版本；
- RAG 模型名和版本。

#### B. Profile 配方

入库模板而非直接改动后的本机目录。例如：

```text
profile 名：emc-analysis
bundle：dsh-base + dsh-headless
settings：flash / low / default preset
plugins：emc-analysis-guard + mcp-emc
guard：EMC 八件 + read/glob/grep/ask_user_question
step budget：15
```

脚本根据当前用户目录生成真实 `~/.dsh` 配置。

#### C. 插件与依赖来源

记录：

- MCP server 启动命令；
- MCP client 包来源；
- 本地插件路径；
- node_modules 创建方式；
- 是否使用 junction；
- 期望版本和哈希。

#### D. 可重建资产清单

记录：

- RAG 索引构建命令；
- 模型缓存目录；
- 依赖安装命令；
- 哪些目录不同步；
- 什么条件下重建。

#### E. 到岗检查清单

至少检查：

1. git 分支和 commit；
2. dsh 版本；
3. profile 是否存在；
4. guard 是否在配置树；
5. MCP client 是否可解析；
6. EMC MCP server 是否能启动；
7. 8080 是否就绪；
8. RAG 索引是否匹配源版本；
9. 端口是否被旧进程占用；
10. 双模 marker 是否通过；
11. 快分析任务是否低于 2 分钟。

### 2.3 Leave / Arrive 工作流

#### 离开一台机器前

1. 完成执行记录；
2. 更新 HOME / OFFICE 交接卡；
3. 检查 `git status`；
4. 显式 add 本次白名单文件；
5. commit；
6. push `origin EMC_harness_dsh`；
7. home 侧可再 push `github` 备份；
8. 运行 DEV-SYNC-HUB `Leave`；
9. 运行记忆同步；
10. 登记本机环境差异；
11. 停止容易占端口的测试进程；
12. 明确记录哪些内容只是本机临时件、未入库。

#### 到另一台机器后

1. 插入并运行 DEV-SYNC-HUB `Arrive`；
2. `git pull origin EMC_harness_dsh`；
3. 恢复蒸馏记忆；
4. 读取主交接卡和对端 HOME / OFFICE 卡；
5. 读取环境 manifest；
6. 运行环境检查脚本；
7. 缺什么补什么；
8. RAG 源版本变化则重建索引；
9. 启动 EMC 服务并跑 freshness check；
10. 跑双模 marker；
11. 跑标准快分析任务；
12. 确认地图和图层行为；
13. 开始正式工作。

### 2.4 快速衔接目标

建议目标不是“零配置”，而是：

当前 office 实测约 30 秒（**快分析档**标准任务实测 29.730s·[v1.1-F2] 非泛指所有到岗任务；研究档同任务耗时数量级不同·不共用此线）。home 端快分析档若明显变慢，说明环境不等价。

# 第三部分：office / home 下情绪地图沉淀内容如何同步

## 一、什么是沉淀内容

情绪地图的沉淀内容不只是文档，而是六类资产：

1. 数据资产：点层、边界、分析产物、manifest、总账；
2. 知识资产：行业知识卡、项目卡、口径卡、案例卡、RAG 源材料；
3. 方法资产：分析范式、工具契约、参数规则、评估集；
4. 表现资产：地图样式、图例、渲染契约、交互逻辑、报告模板；
5. 工程资产：代码、测试、脚本、追踪 ID、debug memory；
6. 过程资产：CB 讨论、决策记录、执行记录、交接卡、revision log。

## 二、沉淀资产四分法

### A. 权威资产：必须进 git

应同步：

- 源代码；
- 测试；
- 工具契约；
- 数据 manifest；
- 小型治理后数据文件；
- 口径卡和知识卡源文件；
- 图层注册表；
- 渲染样式契约；
- 报告模板；
- 执行记录；
- 决策文档；
- debug memory；
- 环境配方；
- 评估黄金集。

原则：

> **只要它影响未来结论、未来工具行为或未来架构决策，就必须进仓库或进入受控资产库。**

### B. 派生资产：不同步，重建

不应直接同步：

- RAG 向量索引；
- 模型缓存；
- node_modules；
- Python 虚拟环境；
- 前端构建缓存；
- 临时图层；
- render inbox 中已消费的说明；
- 可再生测试截图；
- 本地日志和 trace 临时副本。

同步方式：

```text
源资产 + 脚本版本 + 参数 + 哈希
  → 到岗重建
  → 生成后做一致性检查
```

### C. 秘密资产：不进 git，人工受控迁移

包括 API key、token、credentials、私人账户配置、含敏感信息的会话导出。

要求：只同步变量名和配置方法，不同步值；校验时只报告存在性。

### D. 外部原始资产：登记来源和入库策略

包括 OneDrive 规划资料、PDF、图纸、大型原始 GIS、外部表格、第三方报告。

不能默认“全部塞进 git”。应登记：

```text
资产名
来源路径
来源版本 / 日期
责任线
是否纳入 RAG
是否生成治理产物
治理产物路径
原始文件是否必须保留
同步策略：git / HUB / OneDrive 引用 / 不迁移
```

核心要求：

> **外部资料可以不全文入库，但它的存在、来源和衍生关系必须入库。**

[v1.1-G5] dsh 会话记录（`~/.dsh/sessions`）= 本机临时件：重要结论以执行记录形式沉淀进权威资产，会话本体不同步；dsh 产出的成文报告按沉淀四要素入库（权威路径随 C 线总账登记）。

## 三、沉淀入账四要素

以后每个沉淀内容都应回答：

1. 它在哪里：权威路径；
2. 它从哪来：来源和生成过程；
3. 它可信吗：口径、验证方式和限制；
4. 它能否重建：脚本、参数、依赖和哈希。

如果四问答不清，就只是本地文件，不是工程沉淀。

## 四、分支与合并策略

当前 `main` 冻结，EMC × dsh 工作在 `EMC_harness_dsh`。要求：

1. 双机开工前先 pull；
2. 收工前处理未提交文件；
3. 不允许关键改动长期只在本地；
4. 大批合并前必须审计；
5. 数据、口径、工具契约的沉淀要有测试或校验脚本；
6. 不用 U 盘手工覆盖工作区替代 git 合并；
7. 分叉时先看共同祖先和双方提交，不盲改。

## 五、RAG 重构期的特殊同步要求

RAG 同时涉及知识源、索引构建、embedding 模型、检索策略、黄金评估集、MCP 查询接口和未来重构框架，是最容易分叉的沉淀资产。

规则：

1. 知识源和口径卡必须入库；
2. 向量索引不入库，重建；
3. 索引版本号进入查询结果或调试信息；
4. RAG 接口保持稳定，内部实现可替换；
5. 新旧 RAG 用同一黄金集对比；
6. 重构分支也定期同步 office/home；
7. RAG 源哈希变化时触发重建提示；
8. dsh 侧不得直接读取索引文件绕过接口。

这样 RAG 重构完成后，EMC × dsh 测试链路只需替换适配器，不需要重做入口。

## 六、当前必须补的同步缺口

按优先级排序：

1. **把 T7 双模预设从本机配置升格为环境配方**：当前只在 office `~/.dsh`，应转成仓库内模板和安装脚本；
2. **建立环境 manifest**：记录 dsh rc.8、MCP client、Python、Node、EMC 分支、profile、guard、RAG 模型和索引构建命令；
3. **建立到岗检查脚本**：避免人工记忆 git、dsh、profile、MCP、8080、RAG 和端口检查；
4. **明确未提交并行内容归属**：每条线收工时说明责任、是否可提交、是否阻塞同步、是否本机临时；
5. **给沉淀资产建立入库判断规则**：新增数据、知识、样式、脚本和报告时，判断四类资产归属。

# 第四部分：全局核心思想

## 一、十条工程原则

1. EMC 是资产权威源：数据、口径、知识、工具语义、样式和渲染规则归 EMC；
2. dsh 是测试驾驶舱：验证通用助手消费 EMC 资产的体验，不是最终产品本体；
3. 先插座后壳：测试期先稳定数据、知识、工具和渲染接口；
4. 不复制业务逻辑：dsh 调度能力，不重写 EMC 能力；
5. 结论必须可辩护：每个结果带口径、覆盖、来源和限制；
6. 样式必须同源：图层视觉消费 Toolbox / 参数样式，不在 dsh 另做一套；
7. RAG 必须可替换：外部接口稳定，内部实现演进；
8. 临时工具必须可沉淀：有效后入库，无效后废弃，不长期悬空；
9. 环境必须可重建：跨机同步配方，不手工复制运行时；
10. 沉淀必须入账：没有路径、来源、口径和重建方式的文件不算资产。

## 二、对各组的通知要求

zcode、Codex、claude组、Qoder 等开发组与执行手，在涉及 EMC × dsh 时必须先读本文，并遵守（dsh 为被消费的运行平台·执行副手身份须主手派发+白名单授权·无仓库写权与决策权）：

1. 不把 dsh 当成 EMC 的替代架构；
2. 不在 dsh 侧另建数据、工具和样式权威源；
3. 不绕过 EMC 标准插座直读敏感数据；
4. 不把本机 `~/.dsh` 改动当作已同步；
5. 不把向量索引、模型缓存当成交互资产；
6. 不让 RAG 重构破坏 dsh 消费接口；
7. 不把测试期临时件直接产品化；
8. 不在没有口径和验收的情况下生成正式结论。
