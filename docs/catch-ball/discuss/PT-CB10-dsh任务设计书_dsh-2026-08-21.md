## 〇、一页结论

1. **架构方向不必推倒**：EMC 作为契约集合体、dsh 作为外置实验驾驶舱、两阶段路线（测试期外挂 → 稳定期 EMC 壳吸收）在宿主侧仍然成立；EMC 权威源红线与双环境规则七必须保留。
2. **但 PT-CB3 v2 的「契约载体落位表」必须按宿主现实重写**：office 实装的 dsh 0.1.0-rc.8 MCP client 只真实消费 `tools/list` + `tools/call` 两件事。`prompts`、`resources`、以及工具安全/权限类声明（含 MCP 工具注解与 PT-CB3 v2 所称 security 载体）在当前宿主上**不是真实消费面，是纸面契约**。真实载体只有四个：**MCP tools（描述+inputSchema+输出 JSON）**、**宿主策略插件（persona/policy 系统段）**、**工具返回负载（caliber/followup/错误提示）**、**仓内文件经 read/glob/grep 按需读取**。
3. **思维量管控在宿主侧有硬边界**：`reasoningEffort`、模型档位、工具白名单、步数硬顶、plan-mode 审批门、`ask_user_question` 都是真实的；但「模型在同一会话内自己按问题规模改档」**不是宿主机制，不应立项**。正确形态是：入口/预设定档 + 硬预算 + 关键分支问一次 + 研究走 plan-mode 用户门。
4. **最需要立刻修的三件事**：①MCP stdio 协议纯度（本轮实测严格 MCP client 连接失败，dsh 只是容忍了非法 stdout 行）；②工具面→guard 白名单一致性机制化（白名单漂移不再靠人记）；③进度视图改成「可再生的 git 内看板」，而非又一份手写说明。

## 1.2 「真实世界」会在宿主侧扭曲哪些设计

以下七条都有实测或源码证据，不是观点。

**扭曲 1：宿主不主动拉 prompts / resources，MCP 客户端只消费 tools。**
对 office 实装的 rc.8 mcp-client 构建产物（`C:/Users/Administrator/AppData/Roaming/npm/node_modules/@deepseek-ai/dsh/node_modules/@deepseek-ai/dsh-mcp-client/lib/index.js`）grep：只有 `tools/list`、`tools/call` 两条 MCP 方法，无 `prompts/list`、`resources/list`、`get_prompt`。dsh 源码 checkout（`D:/Github/dsh/packages/mcp/mcp-client/src/tools.ts`）同样只做 tools 桥接。因此 PT-CB3 v2 把方法论/回答范式/意图卡挂在 prompts/resources 上的设计，在 dsh 测试期是**纸面契约**：EMC 写了，宿主也不会读。

**扭曲 2：工具描述才是 planner 唯一必读，系统段是第二杠杆。**
rc.8 每次模型请求由 `systemPrompt` 装配器产出 sections + tools（`D:/Github/dsh/packages/core/system-prompt/src/index.ts`）。模型规划只能看到：系统段（persona/policy 等）+ 每个工具的 name/description/inputSchema（及可选 outputSchema）。EMC 前端的 `ai_qa/prompts.py` 在 dsh-MCP 路线上**根本不可见**。PT-CB6 大脑实测也给出行为证据：模型第一动作命中 `list_data`、按描述走 zonal/rank、按描述自我纠错——说明真正起作用的是 MCP 工具 docstring，而不是项目 prompts 文件。

**扭曲 3：openPath 会被第三方插件 monkey-patch。**
better-sidebar 包装 `workspaces.openPath`，曾导致地图被内置弹出且空白；已用「优先 host 原生 openPath + 回退 workspaces」修复（`22ac60c1`、`vendor/dsh-emc-entry/src/client/index.ts:66-83`）。含义：**依赖宿主“标准服务”的设计必须带绕行与降级链，且要有行为证据（浏览器窗口类型），不能只看服务端 200**（debug-memory M1/R15）。

**扭曲 4：profile/preset 的生效方式与“放个配置文件就行”的直觉不一致。**
T7 三次修正全部是宿主机制天花板：profile 目录里的 settings 不会自动被读，必须显式 `- id: settings config.path`；headless bundle 不挂 agent preset，guard 必须挂 host 层；patch 新增插件必须 `- insert:` 语法。rc.8 还有 stub/inject/build:web 三约束、web profile 包管理是 pnpm、后台起 web 会触发 node-pty 崩溃（R13-R16）。**任何把 dsh 配置当“一份 yml 处处生效”的计划都会撞墙。**

**扭曲 5：工具白名单是名字级手工集合，工具面变更不会自动传导。**
guard 的 `EMC_TOOLS` 是硬编码 8 个字符串；MCP server 加第 9、10 个工具时没有任何机制提醒 guard。这就是 emc_status/render_file 漂移的机制根因，与人的疏忽无关，是设计缺口。

**扭曲 6：磁盘新 ≠ 进程新 ≠ 页面内存新（R7.3）。**
前端 JS、插件 bundle、MCP server 三层各有生命周期。宿主侧测试交付的最低口径是「重启服务 + 硬刷新 + 页面内存里确认 build/stamp」，否则“修了还是没修好”会反复出现（色板透传事件已付过学费）。

**扭曲 7：MCP stdio 协议纯度被 dsh 的“宽容”掩盖了。**
本轮现场复核：用 Python `mcp==1.29.0` 标准 stdio client 连接 `py tools/mcp_server_emc.py`，初始化阶段 `Connection closed` 失败；同命令直跑观察，预热路径的 `[TRACE]` 行仍写入 **stdout**（`core/tracker.py` 的 safe_print 默认 stdout；`tools/mcp_server_emc.py:760-788` 的预热调用触发 `@track`）。dsh rc.8 客户端能继续工作，是因为它对 transport 的 parse error **没有挂 onerror 中断处理**，非法行被丢掉后继续（机制见 `@modelcontextprotocol/sdk` 1.29 client/stdio 的 onerror 语义；dsh `connection.ts` 未注册 onerror）。结论要诚实：**“EMC 标准插座”目前对 dsh 可用，但对严格 MCP 客户端不合格；协议纯度修复应进 P0，而不是等别的宿主来踩。**

## 1.3 零思考壳子架构在宿主视角是否成立

**成立，而且宿主恰好能执行它的操作性定义。** 「思考=不可枚举决策、校验=闭包规则」的边界与 rc.8 的 guard 机制同构：`agent/pre-step` 步数拒绝是闭包；`system-prompt/assemble` 按白名单过滤工具是闭包；服务端 G-2 拒绝结论层、render_spec 词表校验、render_file 路径白名单也都是闭包。壳子不需要“想”。

**但契约四分类的载体落位要重写。** 逐类对账如下：

| 契约类 | PT-CB3 v2 原落位 | dsh rc.8 真实消费 | 判定 |
|---|---|---|---|
| 工具调用类 | tools | 真实：description + inputSchema + 输出 JSON 键 | **成立，但有第二债**：MCP 工具 docstring 与 `ai_qa/tool_contracts.py`/前端 SKILL_DEFS 是两套工具契约，目前靠人同步；MCP 面应自己成为单一权威或至少可机检 |
| 方法论类 | prompts 详版 + 工具描述摘要 | 工具描述真实；prompts 纸面；persona/policy 系统段真实（guard 注入的 `emc-analysis-policy` 与 web profile 的 EMC persona 都进系统段） | 修正：**双写 = 工具描述摘要 + 宿主策略段**；prompts 文件留给 EMC 壳未来 |
| 回答范式类 | prompts 模板 + output.schema | output.schema 的**格式消费**在 rc.8 mcp-client 源码中存在（`supportedOutputSchema()`），但 EMC server 是否已声明可解析的 outputSchema 本轮未复核成功（严格客户端初始化失败阻断 list_tools）——待核实；当前实际靠 outlet_card 确定性组装 + 返回键约定 | 半真实：**outlet_card 是事实上的制式输出器**，应继续加厚；不要指望 prompts 管版面 |
| 意图理解类 | prompts 引导 + resources schema | 纸面 + 纸面 | 测试期不建意图卡。最粗分流由 profile/入口显式承担（`em:mode` 的宿主等价物）；意图卡 `scale` 留给 EMC 壳阶段 |
| 补①数据口径类 | resources | 纸面；实际经 `list_data` 返回负载、`rag_query`/`kb_facts` 结果、每个工具返回的 `caliber` 对象、以及 read/glob/grep 读仓内文件 | 修正：**“资源”在 dsh 上就是一个只读工具 + 返回 JSON**，不是 MCP resources |
| 补②安全权限类 | 工具 security 字段/安全声明 | 安全/权限声明不被 rc.8 client 作为可执行约束消费；真实安全=服务端代码内强制（G-2/path 白名单/字段白名单）+ guard 工具过滤 | 修正：**安全必须落在服务端实现和宿主 guard 两处**，不能只写契约声明 |

一句话：**零思考壳子不需要改，但「契约集合体」在 dsh 测试期的物理形态是：10 个工具的描述与返回 JSON + 1 个 guard/policy 插件 + 1 个 persona 段 + 仓内权威文件。** 任何脱离这四件套的“契约化”，在 dsh 上都不会被执行。

## 2.1 终态蓝图：不推倒，但把“契约”钉到宿主真实载体上

维持两阶段路线与 EMC 权威源，测试期目标架构如下：

```text
用户（dsh 会话）
  → 档位/入口显式选择（emc-analysis headless 快档 | web 全工具档）
  → EMC 标准插座 = 10 个 MCP 工具（描述 = 方法论摘要；返回 = caliber + 数据 + followup）
```

稳定期再把验证过的工具、策略、追问、渲染吸进 EMC 壳；dsh 不吸收任何业务逻辑。

**允许推倒的部分只有一个：契约载体的“理论化”部分。** 宿主侧证据已在 1.2/1.3 给出。代价很小：prompts/resources/安全声明三行退为“未来壳阶段接口”，不新增任何工程。

### 2.2.2 可行设计（与双模结局 A 一致，再补两件）

1. **规模属性 = 三个正交硬参数，不做“模型自判 scale”**：
   - brief 档（emc-analysis，无头/脚本/默认）：flash + low + 10 工具白名单 + 15 步 + 建议补 `maxTokens` 输出上限（具体值待基准任务实测，先不拍）。
   - web 档（日常交互）：pro/max + 全工具 + EMC MCP + persona；用于研究时由**用户**开 plan-mode。
   - 不在 dsh 侧做关键词分类器；C5 按既定方案退役 emc-research，把“研究”路由改为「引导到 web 档 + /plan」。
2. **选择机制 = ask_user_question + 决策点清单，而不是泛化“多问”**：
   - 在 guard POLICY 与 persona 中写死触发条件：分支不可逆/两解成本差大/口径分叉才问；**一次硬选择 + 可并发软确认**；模型可给 options，推荐项放第一。
   - 把「哪些场景该问」下沉为每个工具描述里的一行决策提示（如 zonal_stats：社区口径不明确时先 ask，不要混 174/154/118）。
3. **预算硬顶 = 步数（已有）+ 单调用超时（已有）+ 输出 maxTokens（建议补）+ plan 审批（研究）**。不要追求“思维 token 预算”：DeepSeek 在 dsh 侧只暴露 reasoningEffort 档位，没有可配置的 thinking token 数；把精力花在步数与工具面更划算。

## 2.3 追问机制在同窗口上下文的宿主侧实现路径

1. **上下文天然在位**：dsh 会话历史同窗口保留，追问不需要任何持久化工程。缺的不是上下文，是「下一步可追问什么」的结构化提示。
2. **最低成本正解（软接）**：EMC 的确定性工具在返回 JSON 中增加 `followup_cues`（由服务端从本轮参数/结果推导，LLM 不产）：`[{text, tool, params, level}]`；guard POLICY/persona 要求模型在答案末尾原样或压缩呈现 1-3 条。这是把 EMC 前端已有的 `_followupCue`/追问胶囊思想搬到 dsh-MCP 路线上，不新造机制。
3. **自然语言追问接续（软接）**：POLICY 增加一句“后续追问先读上一轮工具返回中的 followup_cues 与 caliber，优先复用其中 tool+params，不要重新全量判断”。这是把 `harness.js` 的 `_followupCue` 分类器在宿主策略层的等价物；不做 dsh 侧分类器。
4. **可点击追问芯片（硬接，暂缓）**：rc.8 原生 UI 只有输入框内联建议/命令建议（`ui-input-trigger`），未发现「从工具结果渲染点击追问芯片」的现成 API——待核实。**测试期不建议写专用 UI 插件**：收益有限，且又多一个宿主 monkey-patch 风险面。先让文字追问跑顺，观察用户真实频率。
5. **与入口向导衔接**：C1 固定文本应改为「插件已负责启动与打开浏览器；你只需用 emc_status 确认就绪并欢迎」，消除模型重复启动动作；emc_status 的 down 提示同步改口径（插件是启动者，模型是观察者）。这项建议并进 C1b 一次改。

## 2.4 体验蓝图（用户能感知的三条线）

- **快问线**：web 入口点一下 → emc-lab 会话 → 服务已开/已弹地图 → 模型确认就绪；常规问题 list_data→工具→带口径答案，≤2 分钟口径只对标准任务成立，不泛化。
- **研究线**：用户显式 `/plan` → 模型只读勘察并提交计划 → 用户批准 → 执行 → 出图 → 出口卡；期间关键分支 ask 一次。
- **追问线**：每个答案末尾带 1-3 个具体追问项；用户直接打字追问时，模型复用上轮参数而不重开全量判断。

# 四、CB 机制优化方案（最频繁执行方之一的角度）

## 4.1 哪里最卡：四个实测卡点

| # | 卡点 | 实证 | 机制缺口 |
|---|---|---|---|
| K1 | 工具面变更 → guard 白名单不同步 | emc_status/render_file 漂移，跨两个批次才暴露 | 没有“工具面 vs 白名单”差集检查，靠人记得 |

## 4.2 该自动化什么（按收益排序）

1. **K1 → 工具面-白名单差集检查器（B4）**。实现建议：一个只读脚本拉 MCP `tools/list` 得到 `mcp__emc__*` 全名，读 guard 的 `EMC_TOOLS`，差集非空即 `[ERR]`；同时可反查「guard 里有、server 没有」的僵尸名。挂两处：pytest 门禁（用 mock/静态解析保快）+ M3 到岗体检（真连）。**这是白名单漂移的治本，不是再写一条纪律。**
2. **K2 → 执行记录机器可读块 + 备份哈希**。任务书和执行记录都加 YAML frontmatter：`files/backup_paths/commands/acceptance/commit`。回收时一个只读脚本对比 `git diff --name-only` 与 frontmatter `files`，多出的文件必须有人工豁免记录。~/.dsh 文件改动附 SHA256；M1 配方直接用同一清单。
3. **K3 → 证据模板**：每个批次固定五格——`disk`（语法/门禁/哈希）、`process`（重启了哪些服务）、`browser`（DOM/截图）、`protocol`（严格 MCP client 工具数）、`sync`（复刻清单/commit hash）。服务端全绿只算 `disk` 一格。
4. **K4 → 见第五节进度视图**；CB 流程本身（SCAN→Journal→四档→审计→回收）不需要推翻，缺的是“任务态”这一层，而不是再开一轮文档讨论。

## 4.3 不赞成自动化的部分（诚实表态）

- **四档裁决与交叉审计不自动化**：采纳/暂缓/反对需要证据判断，脚本只能给差异，不能替主手拍板。
- **不自动 commit/push**：保留主手唯一提交者，自动化只到「生成证据包 + 待办提示」为止。
- **不建 CB 管理系统/看板 SaaS**：违反规则七，且对当前团队规模是过度工程。git 内 YAML + 生成脚本足够。

# 五、进度可视化机制设计（熟悉 dsh 工程实践的方案）

## 5.1 设计目标

用户要求“多线可并行，但看到一条线性过程”。最便宜的可靠做法是**双层资产**：

```text
docs/catch-ball/_board.yaml      （唯一手写源：任务状态机）
tools/gen_progress.py            （只读生成器：确定性渲染，带 --check）
docs/catch-ball/_progress.md     （生成视图：提交进 git，用户只读这个）
```

三条纪律：
1. **源与视图都进 git**，`_board.yaml` 是手改的权威任务态，`_progress.md` 是可再生的视图快照——没有本地数据库、没有 SaaS、没有只在聊天里存在的进度。
2. **生成器确定性**：排序固定、无时间戳（时间只取 git commit）、无随机数；`--check` 比较磁盘与生成结果，不一致即红。跨机 pull 后直接读 `_progress.md`，或跑 `py tools/gen_progress.py` 重建，两边结果相同。
3. **路径无硬编码**：只用 `{REPO}`/`{DSH_HOME}` 占位符；生成器自身在仓内，天然遵守规则七的差异适配。

## 5.2 用户看到的一页（`_progress.md` 结构）

**顶部：一条线性主干**

```text
EMC×dsh 主线
A 收口批     [#######---] 70%  剩余：C2-7/C5、C1b、stdio 纯度、审计、commit+push
B 数据智能   [----------]  0%  等待用户拍板 Q-A/Q-B
C 环境同步   [----------]  0%  等待 M1-M3 立项
D 稳定壳     [----------]  0%  三判据未齐
下一个里程碑：A 销号（完成定义见收口批任务书）
```

**中部：线性任务表**（按阶段和拓扑序排，而不是按负责人排）

| 顺序 | 任务 | 阶段 | 优先级 | 状态 | 负责人/证据 | 阻塞原因 |
|---|---|---|---|---|---|---|
| 1 | C2-7+C5 | A | P0 | 进行中 | Qoder 交接→Codex 接手 | 换组待续 |
| 2 | C1b+文本修正 | A | P0 | 待派 | — | 依赖 1 |
| ... | ... | ... | ... | ... | ... | ... |

**底部：三问卡**

- 还差什么：按完成定义列，不按百分比列；
- 谁在做：每任务一名主责 + 一名证据方；
- 下一里程碑：只写一个，避免“多线并行”在用户心智里变成“多头并进”。

## 5.3 状态机（比百分比更可靠）

每个任务只允许七态：

```text
draft → dispatched → executing → evidence_ready → recovered → audited → closed
                        └──→ blocked（必须写阻塞原因与解锁条件）
```

- 完成百分比 = 各阶段内 closed 任务数按 P0:P1:P2:P3=4:2:1:0.5 加权计算，只作辅助；**里程碑以 closed+commit hash 为准**。
- `_board.yaml` 每行带 `commit` 字段；生成器对 closed 任务校验 commit 非空、对进行中任务校验 owner 非空，避免“文档上销号、git 里没有”的假进度。
- 与规则七绑定：closed 的必要条件 = `commit` 存在且已 push（主手确认）；仓外任务 closed 的必要条件 = 复刻清单路径存在。

## 5.4 为什么不做交互式看板

dsh web 有 task-board 插件，但它面向“单个会话/工作区任务”，不是项目级多组进度；用它承载 CB 进度会产生第三个状态源，并且跨机同步还要额外配方。**测试期先把 git 内看板跑顺；将来若用户确实需要图形化，再让生成器输出同一 YAML 的 HTML/图片，逻辑不变。**
