## 一、三数字复核

### 1.1 计数头部一致（预期：五龙 112、润城 110、深圳路 107…）

- 数据：`DATA/analysis/77项量化/checkup_qty_合并_全覆盖.geojson`（2296 点，无 `score`、无 `polarity`）。
- 边界：`DATA/boundaries/presets/checkup_配置_社区174.geojson`（174 社区）。
- 后端：`aggregate_by_polygons(pts, bnd, agg_cols=[], polygon_name_col='name')`。
- 源码确认：`agg_cols=[]` 时 `_num=[]`，不生成 `score_mean`；`resolve_field_alias('polarity', ...)` 找不到极性列，`polarity_index` 整段跳过（`core/spatial_analysis.py:312-341`）。因此输出只有 `point_count`、4×5 归因、POI 等，**没有极性列**。
- 排序：`zonal_stats` 在无 `polarity_index`、无 `agg_cols` 时回退 `point_count` 降序（`api/geo_routes.py:369-384`），头部应为：五龙 112、润城 110、深圳路 107、西峡 91、金安岭 84、镇境山 82、峡江 66、幸福路 65、新隆康路 62。
- 零点：`aggregate_by_polygons` 对无点面域以 `how='left'` 合并并 `fillna(0).astype(int)`，所以 174 个面中应有 30 个 `point_count=0`。

**复核结论：头部一致、零点 30/174 可信。**

### 1.2 tip 错配 34/174（预期：22 错名 + 12 无归属）

- 脚本算法：对每个聚合社区面取 **bbox 中心**，再用该中心对社区库做**文件序首命中** point-in-polygon。
- 文件核验：`checkup_配置_社区.geojson` 与 `checkup_配置_社区174.geojson` 在本仓库中同为 174 个要素，几何/字段基本同源。

**复核结论：34/174（22 错名 + 12 无归属）可信。**

## 二、根因验证与挑战

### 2.1 B013 根因链：基本成立，补充两个细节

zcode 的链：

```
无极性/无score → 后端不产 polarity_index
→ preprocessGrid 用 _grid_h = heightOf(point_count, max)
→ gridStyle(level!=L2) 用 grid-warm + _grid_h
→ grid-warm 0=暗红、1=金黄
→ 点数越多 _grid_h 越大 → 颜色越浅；零点 _grid_h=0 → 暗红
```

验证：

- `grid-tool.js:162-209` 确实在无 `polarity_index` 时仍计算 `_grid_h`，且 `gridStyle` 对非 L2 固定使用 `_grid_h`（`grid-tool.js:79-95`）。
- `state.js` 的 `grid-warm` stops 为 `0→透明`、`0.10→#8B0000`、`1.00→#FFDF00`。`normStops` 去掉透明首段后，`0` 值会落到 `#8B0000`，`1` 值落到 `#FFDF00`，所以“高值浅金、低值深红”成立。
- `map.js:719-724` 的 `_gridColorExpr` 确实用 `interpolate(linear, get(gridField), ...gridStops)`，没有额外方向修正。

**挑战/补充**：

1. **不是“后端计数错”，而是“前端着色轨选错”**：计数本身正确，罪在把“点数”塞进了情绪热度色带，且方向与用户语义相反。
2. **“零点=最深红”是双重反语义**：`_grid_h=0` 被 MapLibre clamp 到色带低端 `#8B0000`。这在社区聚合里尤其致命，因为 30 个无点社区会被误读为“最严重”。
3. 链中没提 **用户手动 reverse 可临时缓解**，但默认仍 false，所以复现是默认态；不能把“用户可点反向”当作修复。

### 2.2 B012 根因链：基本成立，补充一个残留 bug

zcode 的链：

```
grid/terrain 绑定 tip-popup
→ fillContent(feat)
→ 社区行 = fillCommunity(centroidOf(feat))
→ 无 _center 时 = bbox 中心
→ fillCommunity 拿中心点对社区库首命中即返
→ 与 Table 直读 feature.properties 不一致
```

验证：

- `map.js:592-596` 只给 `tool==='grid' || tool==='terrain'` 绑 tip-popup，社区面聚合层走此路径。
- `tip-popup.js:402-435` 确实在非 point 分支用 `centroidOf(feat)` 作为社区归属点。
- `panel.js` Table 直接读图层 feature 属性，天然正确。

**挑战/补充**：

1. **根因准确，但修复不能只改“用鼠标位置”**：对“指定单元（社区面）聚合层”，要素本身就是社区，直接读 `feature.properties.name` 是零查找、零错配；对“标准网格/terrain”，才需要用鼠标 lngLat 做空间归属。
2. **还有一个残留问题**：`fillContent` 的 point 分支（`tip-popup.js:426-431`）提前 `return`，**没有清空上一轮 polygon 留下的 `#tp-community`**。用户从社区面悬停切到点层悬停时，tip 可能残留上一个社区名。这虽然不是 B012 主因，但属于同一交互区域的连带 bug，应一并修。

### 2.3 第三条踩坑路径：不是新根因，而是同一根因的传播面

任务书要求验证：`generateZonalForAI` / `generateGridForAI`、rank-tool、area-stats、3D 模式、time-source。

| 路径 | 是否踩坑 | 说明 |
|---|---|---|
| `generateGridForAI`（square/zonal） | **是** | 与 UI 的 `generateGrid` 共用 `preprocessGrid` + `gridStyle`。L0 无极性时 square 同样高值浅金；zonal 同样零点深红。 |
| `generateZonalForAI` | **是** | 走 `toolbox/zonal-tool.js _execute` → `buildZonalFc`。无极性时 `_grid_norm=0.5`，`defaultPaint('zonal')` 用 `polarityStops('overall')`，174 个社区全部同色（中性色），属于 zcode 已列的第二形态，AI 入口同样中招。 |
| `rank-tool` | **不是同一错误** | 后端 `/geo/rank` 对无 `polarity_index` 的 L0 聚合会直接 `raise ValueError('rank 需 layer 含 polarity_index...')`。这是**诚实报错**，不是错误着色；但说明 rank 目前不支持 L0 计数排序，是能力缺口。 |
| `area-stats` | 否 | 面积统计不走 grid-warm/terrain-9，且不表达点数，不受本双 bug 影响。 |
| 3D 模式 | **是** | `addPolygonPaint` 的 3D fill-extrusion 与 2D 共用 `gridField/gridStops`，因此 3D 柱体颜色同样反语义；悬停高亮 `showCellHover` 也复用同一 stops。 |
| time-source / timeline | **是（传播）** | `timeline.js _buildVirtualFc` 对无极性片仍写 `_grid_norm=piToNorm(null)=0.5`，但图层 paint 若仍是 `grid-warm + _grid_h`，则时间片切换后颜色方向不变，依然反语义。 |

**结论**：真正的“第三条路径”不是新代码缺陷，而是**入口/维度扩散**：AI 编程式入口、3D、时间轴都复用了同一套情绪轨着色。理想上应统一收口到“按数据轨选色带/字段”。

**但按 §六约束，本轮修复范围要收窄**：
- 分叉先落在 **dialog/UI 路径**，用户能看见并选择“点数 / 极性”；
- **不新增 ForAI 契约**，`generateGridForAI` / `generateZonalForAI` 契约本轮不动，默认行为不跟随；
- 3D、time-source 属于前端展示层，可随 UI 分叉一起修；但如果它们与 AI 入口共用同一函数，必须用**显式参数隔离**，避免改 UI 时把 AI 旧行为也悄悄改掉。

## 三、8 题逐答

### 第 1 题：验证三数字

见上文“三数字复核”。结论：头部一致、零点 30、错配 34/174 均可复现。

### 第 2 题：挑战根因链 + 第三条路径

- B013 链成立；补充“零点=最深红”是双重反语义。

### 第 3 题：计数填色归一化策略（在“点数模式”内讨论）

按 §六，无极性时 UI 进入显式的「点数」模式，所以这里讨论的是**点数模式内部用什么归一**。

**建议：采用“低位数可区分 + 长尾压缩”的连续归一化，并单独处理 0。**

理由：

- 数据 `max=112`、中位约 6、零点 30，典型长尾。若用 **max 线性**，绝大多数 1~10 点的社区会被压到很浅，几乎无法区分；112 一个点把色阶拉满。
- 若用 **分位数**，会把“1 点和 6 点”强行拉开，虽然视觉对比强，但会误导用户以为是绝对数量差异，且阈值随数据变化不稳定。
- **log1p 或现有 `_grid_h` 的 offset+sqrt 都合适**。`_grid_h` 已经在 3D 高度上验证过：1→2 可区分，3 起跳，高位压缩。可以直接复用它作为颜色归一，或新增 `_count_norm = log1p(point_count) / log1p(max)`。
- 对用户最可读的呈现：连续渐变 + 临时色阶/悬停显示真实点数（如 0、1、2、5、10、20、50、100），而不是只标“低/中/高”。

**我的推荐**：最小改动是**复用 `_grid_h` 作为计数色字段，但把色带方向反转为“低浅高深”**；若想更标准，可新增 `_count_norm=log1p(count)/log1p(max)`，与高度字段解耦，避免改 3D 高度。

**与 §六的衔接**：点数模式是临时分析出图，不套用情绪轨标准图例；但 UI 上仍应让用户看到“当前是点数模式”，并可通过 tip/简易色阶知道数值。

### 第 4 题：零点社区渲染语义（点数模式）

- 零点社区**不能落入“最严重”深色端**。
- 建议：零点用**浅灰/无填充（仅描边）**，并在 UI 上以“0 点 / 无数据”的临时标注说明。
- 若产品上希望“无数据”和“有数据但很少”区分，可用：
  - 0 点：`#F0F0F0` 或透明；
  - 1~2 点：最浅的计数色；
  - 3 点以上：进入连续计数色阶。
- 按 §六，**不建设情绪轨标准图例**；但临时点数说明仍应写“点数：0 / 1-2 / 3-9 / 10-29 / 30+”，不要写“负面/中性/正面”。

### 第 5 题：分叉控件怎么设计（§六重述后的 Q5）

§六已把问题从“reverse 翻不翻默认”改为“**分叉控件怎么设计**”。我的建议：

1. **UI 上显式提供“着色语义”选择**，例如：
   - 下拉/按钮：`点数（临时）` / `极性`；
   - 或两个卡片：`按点数看分布` / `按情绪看正负`。
   - 不能静默自动切换；用户必须能看见当前选的是哪一种。

2. **默认选中规则按数据轨**：
   - L0 / 无极性层：默认选「点数」；
   - L1：若仍是无极性/热度语义，也默认「点数」或「热度」，由 plan 明确；
   - L2 / 有极性层：默认选「极性」；
   - 用户手动选择后，以用户选择为准，不要每次覆盖。

3. **两模式各自的色带方向**：
   - 点数模式：低值浅、高值深（例如浅黄→深红/深棕），零点灰/透明；
   - 极性模式：保持现有发散语义（如 `terrain-9` 红=消极、绿=积极），不要全局 reverse。

4. **图例/文案**：
   - 点数模式不套情绪轨“负面/中性/正面”标准图例；
   - 用临时点数说明或 tip 显示真实点数；
   - 极性模式继续使用现有情绪图例。

5. **reverse 降级为模式内的辅助开关**：
   - 点数模式可允许用户手动反向（虽然默认已是高值深色）；
   - 极性模式一般不建议反向，避免破坏正负语义。

通俗解释：不是“把所有图反转”，而是先让用户选“这张图看点数还是看情绪”，选点数时默认点数多=颜色深，选情绪时仍然红绿代表正负。

### 第 6 题：tip 修复取向

**建议采用“组合方案”，不是单选 A 或 B。**

1. **指定单元（社区面）聚合层**：直接读 `feat.properties.name`。这是最优解：零查找、零错配、天然与 Table 一致。
2. **标准网格 / terrain**：用鼠标真实 `lngLat` 做社区归属，配合：
   - 预建社区 bbox 网格索引或 R-tree，减少每帧 174 面全遍历；
   - mousemove 节流（如 50ms）或坐标变化阈值；
   - 现有 `_commCache` 继续按 lngLat key 缓存。
3. **point 分支残留**：在 `fillContent` point 分支 return 前，隐藏并清空 `#tp-community`，防止上一轮社区名残留。

### 第 7 题：测试建议

见下文“测试草案”。按 §六，测试要锁两件事：
- **分叉后两模式各自语义正确**：点数模式低浅高深、零点不深红；极性模式发散语义不变。
- **ForAI 契约不动**：`generateGridForAI` / `generateZonalForAI` 不新增契约、默认行为不因 UI 分叉被无意改变。

### 第 8 题：修复影响面

见下文“修复影响面”。其中必须包含两条边界：

   - UI dialog 路径传递 `level`/`track`，并显示“点数/极性”分叉；

### 5.2 回归风险点

- **勿伤 L2 极性 choropleth**：`terrain-9` 的红绿发散语义不能全局 reverse。
- **勿改 `_grid_h` 高度语义**：`_grid_h` 同时是 3D 柱高字段。若为颜色改用 log1p，建议新增 `_count_norm`，不要把 `_grid_h` 的数值含义改掉。
- **`buildZonalFc` 被 zonal/rank 共用**：改动无极性分支时，要确保 L2 极性分支仍走 `piToNorm` + `polarityStops`。
- **tip 修复不能对 square/terrain 直接读 `properties.name`**：标准网格和等值环没有社区名，必须保留空间归属逻辑。
- **AI 入口与 UI 入口共用**：改 `grid-tool.js` / `toolbox/shared.js` 内部函数时，要用显式参数隔离；`generateGridForAI` / `generateZonalForAI` 的 **ForAI 契约本轮不动**，默认行为不能被 UI 分叉无意改变。
- **时间轴**：如果新增字段，`timeline.js` 的 `_buildVirtualFc` 必须同步，否则播放/切片时颜色字段缺失或回退。

## 七、结论

zcode 的两条根因链方向正确，主要漏洞是“修复范围不够”：B013 需要按数据轨建立独立计数着色，而不是简单翻转默认值；B012 需要区分“社区面聚合层”和“标准网格/terrain”两种 tip 场景。

按 §六约束，本轮修复应：
- 在 **UI/dialog 路径**显式分叉“点数 / 极性”，无极性默认点数、有极性默认极性；
- 点数模式按临时分析出图处理，不套情绪标准图例、不接 EMC 出口；
- **不新增/不修改 ForAI 契约**，`generateGridForAI` / `generateZonalForAI` 默认不动；
- 3D、time-source 等前端展示层可随 UI 分叉修复，但需用显式参数隔离，避免影响 AI 入口。
