## 〇、一页结论

1. **双模确实建好且当时验收通过**（T7 执行记录：快分析 29.730 秒·双档 marker 均过）；但它们是**无头 CLI profile**，不出现在 3080 网页里——用户日常交互面实际是 web profile。
2. **「emc_status 缺席」是白名单漂移实锤**：快分析档 guard 白名单（T7 建）写死 8 件工具；第 10 件工具服务状态探测 `emc_status`（F_032）在 T9 才上线（`d2acc8e6`·10:17），白名单未跟随——这是《EMC×dsh 核心思想报告》预警的「`~/.dsh` 配置漂移」第一次真实发作。
3. **「按意图控制思维量」方向正确，但 dsh rc.8 有机制天花板**：思维强度（reasoningEffort）是 profile/会话级设置，不支持逐消息动态调节——双 profile 是 dsh 当前唯一能承载「意图→思维量」映射的形态。
4. **提议收敛**（三选一·推荐 A）：日常交互全走 3080 网页档；无头侧只留快分析档作脚本化通道；**退役研究档**。无论选哪个，先修 emc_status 白名单（一行）。

## 一、事实核查（全部本机取证·office 机 2026-08-21）

### 1.1 双模 profile 现状：建好了，但是无头形态

| 项 | 快分析档（emc-analysis） | 研究档（emc-research） |
|---|---|---|
| 目录 | `~/.dsh/profiles/emc-analysis/`（在盘✓） | `~/.dsh/profiles/emc-research/`（在盘✓·cordis.yml/cordis.patch.yml/package.json/settings.yaml 四件） |
| 思维强度 | flash / low | flash / max |
| 工具面 | guard 白名单过滤：EMC 8 件 + read/glob/grep/ask_user_question；**无** shell/write/edit/web/workflow/subagent | rc.8 standard 全工具 + EMC MCP |
| 步数预算 | 15 步硬预算（第 16 步 reject） | 无本地步数上限 |
| 验收记录 | T7 实测 29.730 秒（2 分钟线内）·marker PRESET_POLICY_PRESENT | T7 marker RESEARCH_MODE_READY（16.792s） |

**用户"只看到 analysis"的机理**（三层叠加）：
1. 双模入口只在命令行：`dsh --profile emc-research "<任务>"` 或机械启动器 `dsh-emc.ps1`——**3080 网页没有 profile 切换器**；
2. 启动器**默认走 analysis**，仅当提示词含「研究/调研/探索/对比方案/系统评估/为什么」才切 research，或显式 `-Research`；
3. 用户日常面对的 3080 网页跑的是 **web profile**（实测：PID 21688·`dsh web` 无 `--profile`·今日 11:57 启动），该档经 cordis.patch.yml 挂了 EMC MCP + 人设 + 左下角入口插件——它既不是 analysis 也不是 research。

### 1.2 emc_status 缺席：白名单漂移时间线（实锤）

| 时点 | 事件 | 证据 |
|---|---|---|
| 08-21 上午 | T7 建快分析档 guard：`ALLOWED_TOOLS` = EMC **8 件** + 4 件只读 | `~/.dsh/profiles/emc-analysis/node_modules/emc-analysis-guard/index.mjs` 实测在盘·T7 执行记录§一 |
| 08-21 10:17 | T9 给 MCP 服务新增第 10 件工具 `emc_status`（F_032·8080 就绪探测 down/starting/ready） | commit `d2acc8e6`；`tools/mcp_server_emc.py:39/717/721` |
| 之后 | 白名单**未跟随**——快分析档模型看到的 EMC 工具仍为 8 件 | guard 源码实测无 `mcp__emc__emc_status` |
| 用户实测 | 模型提示「本会话的工具集中没有 emc_status 工具（只有数据/渲染类 EMC 工具），无法轮询 8080 服务状态」并出三选项问用户 | 用户转述（与白名单状态完全吻合） |

**对照组**：3080 网页（web profile）的 MCP 连接**有** emc_status——其进程 11:57 启动，晚于工具上线 10:17。即问题只在无头快分析档。

**结构性教训**（比这一行修复更值钱）：guard 源码只存在于 `~/.dsh`、仓库无副本——这正是核心思想报告断点1（`~/.dsh` 不随仓库同步）+ G1/M1（T7 配方入库）要治的病。**本次漂移应作为 M1 配方入库批的第一需求证据**。

### 1.3 机制天花板：思维强度为什么只能靠 profile 切

- dsh rc.8 的思维强度配置是 `settings.yaml` 的 `agent-default-model.reasoningEffort`——**profile 级**（全局配置现为 max；快分析档覆盖为 low；研究档覆盖为 max）；
- PT-CB7 批 Qoder 复核已实测记录：rc.8 该设置为 4 档、**无 medium**（台账 R44 批 F1）；
- 未找到逐消息/逐轮动态调节思维强度的原生机制——**「按意图分配思维量」在 dsh 当前形态下，唯一承载体就是多 profile**。

### 1.4 项目既有裁决（必须对齐的历史）

- **台账 R46（2026-08-21）**已就「意图判断控制思维量」裁决过一次：**模式即预设（按钮/档位）·禁建意图分类器**——EMC 内部意图分类的历史是「拆东墙补西墙」打地鼠（R3 机理分析），不重走；升级三信号=显式词/阻塞停下问/模板化后直跑。本轮用户之问与该裁决同题——**本报告不推翻该裁决**，而是在 dsh 侧给出落地形态的收敛建议；
- **台账 R45**：effort=max 每步固定税 2~34 秒——思维强度直接换算为时间与成本，「快问题用低档」有真实收益（T7 实测：低档 29.7s vs 修正前高档 122.8s）；
- **核心思想报告（Codex·08-21）**：`~/.dsh` 配置漂移列为最大断点；环境配方化三步走（M1 模板入库/M2 manifest/M3 体检脚本）待拍板。

## 二、双模价值重估（成本收益·诚实版）

### 2.1 双模解决了什么（真实收益）

1. **快问题不被慢思维拖死**：低档+15 步预算+工具子集=29.7 秒出结果（实测）；max 档同类问题每步 2~34 秒税；
2. **风险面收窄**：快分析档无 shell/write/web，纪律由 guard 机械保证，不靠模型自觉；
3. **批量/脚本化通道**：无头形态可被脚本、定时任务、其他 harness 编排调用。

### 2.2 双模的代价（本次实测暴露）

1. **体验断裂**：用户看不到档位的存在，切换靠记命令行参数/关键词黑话；研究档事实上不可发现；
2. **双份配置双倍漂移**：白名单 vs MCP 工具面、cordis.patch 两份、settings 两份——emc_status 事件是首张账单，后续每次工具面变更（PT-CB9 后大概率还有）都要记得同步 guard；
3. **与真实交互面错位**：用户日常在 3080 网页（web profile·max 思维·全工具），双模服务的无头场景使用频次低——**为低频场景维护两套配置**；
4. **升级路径断裂**：guard 策略写了 MODE_ESCALATION（遇研究深度问题停下声明），但声明之后用户要自己重敲命令换档——半截自动化。

### 2.3 判断

双模是「机制天花板内的正确解」，但**其收益集中在无头批量场景，而用户的真实重心在网页交互面**。当收益场景低频、漂移成本常态发生时，收敛是合理选择——这与用户直觉一致，且不与 R46 裁决冲突（R46 禁的是意图分类器，不是档位合并）。

## 三、三个收敛选项（供 dsh/zcode 讨论·推荐 A）

| 选项 | 内容 | 收益 | 代价/风险 | 推荐 |
|---|---|---|---|:-:|
| **A 收敛为主** | ①修 emc_status 白名单（公共件）；②**退役研究档**（归档不删除）；③日常交互全走 3080 网页档（本就 max+全工具+emc_status）；④无头侧只留快分析档作脚本/批量通道；⑤研究类需求=网页档天然满足 | 维护面减半；体验断裂消失；网页档本就是研究档的超集（有 GUI、有 emc_status、无步数限制） | 损失研究档的「无头+全工具」组合（如有脚本化深度研究需求需另议）；EMC_DUAL_MODE.md 改写 | **推荐** |
| **B 保留双模修摩擦** | ①修白名单；②升级路径一键化（MODE_ESCALATION 声明时附可直接复制的 research 命令，或启动器加 `--escalate`）；③双档配置纳入 M1 配方入库，建立「工具面变更→白名单同步」检查项 | 保留无头研究能力；漂移有机制兜底 | 双份维护继续；研究档使用率存疑（投入可能持续空转） | 备选 |
| **C 最小修** | 只修 emc_status 白名单一行，其余不动 | 成本最低 | 体验与漂移问题原样保留；下次工具面变更再炸一次 | 不推荐（治标） |

**A 的两条护栏**（防过度收敛）：
- 研究档**归档不删除**（`~/.dsh/profiles/emc-research` 改名 `_retired` 或入备份目录），配方文件随 M1 入库——未来需要可随时复活；
- 若后续出现真实的「无头深度研究」需求（脚本化跑长任务），按 B 的升级路径复活研究档，届时它已在仓库配方里。
