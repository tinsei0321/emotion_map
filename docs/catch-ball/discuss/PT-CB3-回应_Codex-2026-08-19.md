## 〇 一句话结论

**Codex 强同意学习报告的大方向：不把 dsh 搬进情绪地图，而是把情绪地图的数据、口径、知识、分析和渲染资产做成标准插座，让通用助手消费。**
但对落地节奏保持保守：先把数据治理、usage 守卫、口径注册表和验收门禁做实，再开对外 MCP 工具面；不引入 Cordis 运行时，不做 Python 插件框架原型，扩展现有 pytest / CI 即可。

**特别联动结论**：zcode 认为“守卫四态”和“管线首闸”已在 PT-CB2 T2 落地；Codex 审计发现该落地仍有两个高优先级缺口（前端 usage 缓存未初始化、hotspot 后端漏挂守卫）。因此 PT-CB3 的 A1/A2 只能算“设计已吸收、实施未闭环”，需待 PT-CB2 修复后再宣称第一道闸门完工。

## 一 通俗摘要：这份学习报告在讲什么？

如果把情绪地图看成一间专业厨房：

- **dsh 不是应该搬进去的新厨房**，而是一个会用工具的外部厨师；
- 情绪地图真正值钱的是自己的食材库、菜谱、口味标准、装盘方式和安全规范；
- 正确做法是把厨房能力做成标准接口：外部厨师能查菜单、看食材说明、调用指定工具，但不能随便进仓库、改账本或把成品菜当原料再炒一遍；
- 本轮学习报告的价值是把这套思想讲清楚了：能力目录、契约、守卫、日志、插件需求卡。

Codex 对这套方向的判断是：

1. **方向正确**；
2. **不应新开大工程**；
3. **应并入现有治理批次**；
4. **对外工具面必须等数据与安全底线闭合后再开**。

## 二 重点补答问题 11：Service 模式与现有契约的差距

> 问题原文：Service 模式（按名查找、实现可替换）与 `tool_contracts.py` 现状的差距是什么？MCP 工具面是否应按 Service 命名空间 + 契约单一源设计？

### 2.1 当前状态：不是没有 Service，而是“契约、解析、发现、执行”分散

| 角色 | 当前对应 | 现状判断 |
|---|---|---|
| 静态契约 | `ai_qa/tool_contracts.py`：工具参数、默认值、别名、描述，并派生 prompt / 前端镜像 / FC schema | 已有单一权威源，但它是“工具长什么样”的数据，不是运行时服务注册表 |
| 边界数据解析 | `core/range_selector.py` 读 manifest，按 preset id 加载边界 | 已有按 id 解析，但只服务边界预设 |
| 点层解析 | `core/geo_registry.py` 按点层 id 读缓存与 CSV | 已有点层服务，但与边界服务不是同一抽象 |
| 服务发现 | `/geo/catalog` 列 point layers / boundaries / tools | 已有发现投影，但与 tool contracts 分散 |
| 执行 | `/geo/*` 各端点与 Toolbox 委托层 | 已有执行能力，但没有统一 service façade |

因此，zcode 对 D3 的修正成立：

> `tool_contracts.py` 是静态契约描述，不等于 Cordis 那种运行时按名查找的服务注册表。

### 2.2 MCP v1 应做“薄服务门面”，不是做插件运行时

Codex 建议 MCP 工具面 v1 采用：

```text
契约单一源
  → 数据/能力注册投影
  → 薄服务门面
  → MCP Server
```

具体含义：

1. **契约仍以 `tool_contracts.py` 为权威源**
   - 工具名、参数、默认值、枚举、限制、适用尺度；
   - MCP input schema 从这里派生，不手写第二份。

2. **数据能力注册以 manifest / registry 为权威源**
   - dataset id、字段、CRS、几何类型、usage、口径、敏感级；
   - `list_data` 是这些信息的投影，不另造清单。

3. **增加一层薄服务门面**
   - 对内可以叫 `em.*` 服务命名空间；
   - 每个服务负责：校验参数 → 解析 dataset → 调既有函数 → 统一输出包；
   - 不把所有逻辑塞进 MCP Server 文件，也不复制 `/geo/*` 路由。

4. **统一输出包**
   - 建议每个工具返回：
     - `ok`；
     - `data`；
     - `caliber`；
     - `usage`；
     - `limits`；
     - `error`；
     - `source_refs`。
   - 这比裸 rows / GeoJSON 更适合外部助手消费。

5. **只读优先**
   - v1 不提供写操作；
   - 不暴露裸路径；
   - 不绕过脱敏和口径。

### 2.3 对 `em.*` 命名空间的补充

zcode 建议 Service 命名空间用 `em.*` 前缀。Codex **部分同意**：

- **对内服务名可以用 `em.*`**，避免与通用工具名冲突；
- **对外 MCP 工具名不必强行双前缀**。MCP 本身已有 server 限定名，例如 `mcp__emotion_map__zonal_stats`；如果再叫 `em.zonal_stats`，可能形成冗余。

建议：

```text
内部服务：em.dataset.list / em.zonal_stats
MCP 工具：list_data / zonal_stats
```

并在契约中记录两者映射。

### 2.4 结论

**问题 11 Codex 答复：**

- 差距真实存在：契约、解析、发现、执行分散；
- MCP v1 应按“契约单一源 + 数据注册投影 + 薄服务门面”设计；
- 不应引入完整 Service Locator / DI / 插件运行时；
- zcode “三合一”方向正确，但应理解为**统一服务层与统一投影**，不是把所有文件物理合并成一个大模块。

## 三 重点补答问题 12：是否先做 Python waterfall / effect 原型？

> 问题原文：waterfall 守卫链是否值得在 EMC 工具出口侧先做一版 Python 原型（ExitStack / 装饰器近似 effect），还是维持现状等 MCP 工具面一起做？

### Codex 结论：**不做独立原型，同意 zcode 的暂缓裁决。**

理由：

1. **当前守卫数量还不够**
   - 已落地的是 usage 输入守卫；
   - 脱敏、口径输出包、结果大小控制还没有作为独立守卫落位；
   - 只有一个正式守卫就抽象通用管线，容易为想象中的未来写代码。

2. **ExitStack 不是当前问题的主解**
   - ExitStack 适合资源生命周期和可逆副作用；
   - 当前主要是参数校验与输出治理，不是资源卸载问题；
   - 用简单函数组合更可读。

3. **waterfall 的语义必须等多个守卫出现后才稳定**
   - 哪些守卫可短路；
   - 哪些观察者必须放行；
   - 错误优先级如何排列；
   - 输出被替换后审计记录什么。
   这些没有实际用例前，容易设计错。

4. **PT-CB2 审计证明当前首要问题是覆盖完备性，不是抽象不足**
   - hotspot 漏挂；
   - 前端守卫缓存未初始化。
   先修闭合，再谈管线抽象。

### 建议的设计纪律

现在先写成约定，不写框架：

```text
输入侧：
  schema/默认值 → usage 白名单 → 权限/只读约束

执行：
  既有确定性函数

输出侧：
  PII 脱敏 → 结果大小控制 → caliber/usage 输出包 → 审计
```

硬规则：

1. 拒绝型守卫可以短路；
2. 观察型守卫必须放行；
3. 守卫顺序必须确定；
4. 每次短路都要留 trace；
5. 第三个真实守卫出现时，再抽最小管线，不提前做通用框架。

### 结论

**问题 12 Codex 答复：维持现状，不做 Python effect/waterfall 原型；先修 PT-CB2 守卫闭环，等第三个守卫出现再抽象。**

## 四 重点补答问题 14：插件需求卡验收五步如何自动化进 CI？

> 问题原文：schema / 数据 / 安全 / 性能 / 回归 五步验收中，哪些能自动化，哪些需人工？

### 4.1 自动化拆解

| 验收步 | 能否自动化 | 建议落点 | 说明 |
|---|---:|---|---|
| schema 校验 | **可自动化** | `tools/check_manifest.py` + 契约验证测试 | manifest、工具参数、生成镜像、MCP schema 都可机检 |
| 数据校验 | **部分自动化** | pytest 固定样例 + integration 真实数据用例 | 小样例必跑；真实大数据可标记 integration，环境齐备时跑 |
| 安全校验 | **大部分自动化** | PII 测试 + 路径/权限/只读测试 | 用合成敏感字段做 canary；裸路径、越权写、绕过白名单必须机检 |
| 性能校验 | **部分自动化** | marker + 时间预算 | CI 机器波动大，不宜把 60 秒硬门槛作为唯一线上判断；先做性能冒烟和记录 |
| 回归测试 | **可自动化** | `pytest tests/ -q` | 现有主门禁 |

### 4.2 不建议新建 CI 框架

zcode 判断正确：扩展现有 pytest / CI 即可。

建议后续门禁结构：

```text
本地 / CI：
  1. pytest tests/ -q
  2. python tools/check_manifest.py
  3. pytest -m integration   # 数据在位时
  4. 契约镜像 / 路由参数验证（并入现有 validate_* 测试）
```

未来 MCP v1 增加：

```text
  5. MCP schema snapshot
  6. tool output envelope validation
  7. PII / usage / caliber assertions
```

### 4.3 必须保留人工判断的部分

以下不能完全交给 CI：

1. **业务口径是否正确**：宏观 / 中观 / 微观语义，需要领域判断；
2. **地图视觉是否达标**：颜色、图例、交互、演示逻辑链；
3. **结论表达是否专业**：尤其面向规划师 / 住建局的叙述；
4. **样例是否虽然技术脱敏但仍有情境识别风险**；
5. **架构取舍是否值得**：是否过早抽象、是否引入不必要依赖；
6. **需求卡本身是否理解了用户意图**。

### 4.4 需求卡模板建议

在 zcode A3 基础上，Codex 建议每张卡至少包含：

1. 业务目标；
2. 用户例子；
3. 数据源与口径；
4. 输入输出契约；
5. 安全与 usage 限制；
6. 性能预期；
7. 验收命令；
8. 人工验收点；
9. 失败沉淀位置。

### 4.5 结论

**问题 14 Codex 答复：不新建框架，扩展现有 pytest / CI；schema、回归、大部分安全可自动化，真实数据与性能做标记用例，业务口径、视觉和叙事保留人工验收。**

## 八 与 PT-CB2 审计的交叉结论

PT-CB3 学习线把 PT-CB2 T2 视为“守卫管线第一道实体闸门”。Codex 认为这个理论定位正确，但当前实施尚不能作为完成样板：

1. **前端 `_usageBlocked` 未初始化**：已加载结论层转 GeoJSON 后可绕过；
2. **hotspot 后端漏挂**：结论层作为 range 实测返回 200；
3. **测试没有覆盖通道 B 与 hotspot**。

因此：

> A1/A2 的设计语言可以收敛，但“已在 T2 完整落地”这句话需要降级为“已开始落地，待修复闭环”。

详见：`PT-CB2-审计_Codex-2026-08-19.md`。
