## 二、PRM-05 深挖 — **真因 ≠ _validAfter**

### 现状确认

B3 Run 2 PRM-05（"西陵区范围内按面聚合情绪统计"）fail：`tpl=zonal tools=[] L=0 boundary[ERR]`。Run 1/3 PASS。

### _validAfter 正则模拟（全 pass）

glm组 用 Python 复现 `_validAfter` 逻辑·对 13 组测试**全 pass**：

```
val='西陵区' q='西陵区范围内按面聚合情绪统计及4×5归因' → True ✅

```

**_validAfter 不是 PRM-05 的根因**——正则对 PRM-05 问句**始终匹配**。

### 真因推演：deriveAvailable 返回 null 的 3 种可能

deriveAvailable 在 PRM-05 问句上**应返回非 null**（"西陵区" 匹配 + _validAfter 通过 + 白名单通过）。如果偶发返回 null·可能原因：

| 可能 | 分析 | 概率 |
|------|------|:---:|
| **① admin_district 层未加载/加载延迟** | B3 飞轮 `loadRange('行政区')` 在 case 开始时注入·但异步加载可能未完成时 deriveAvailable 读 `getLayers()` | **高** |
| ② FIXED_ADMIN_DISTRICTS 白名单偶发不匹配 | 白名单 = `['西陵区','伍家岗区','猇亭区','点军区']`·"西陵区"精确匹配·不会偶发失败 | 低 |
| ③ _boundaryNames 返回空 values | `_boundaryNames(l)` 读 layer.fc.features.properties·如果层刚加载但 fc 未填充 | 中 |

**最可能**：**① 层加载竞态**。B3 飞轮的 `loadRange` 是异步的（`await t.loadRange(RANGE)`）·但 `deriveAvailable` 在 `deriveMissingParams` 内**同步**调 `getLayers()`——如果 FC diagnose 返回时 admin_district 层的 fc.features 尚未完全填充到 getLayers()·deriveAvailable 遍历 layers 时找不到匹配要素 → 返回 null。

### 修复方案

**方案 A（推荐·防御性·deriveAvailable 兜底）**：zonal 强制路由（`:1508`）的 deriveAvailable 返回 null 时·fallback 到 preset 行政区搜索（仿 chain pre-check `:1131-1141` 的 preset fallback 逻辑）：

```javascript
// :1508 当前
const _zonalD = deriveAvailable(q, layers);
if (_zonalD) { ... }

// 建议（加 fallback）
let _zonalD = deriveAvailable(q, layers);
if (!_zonalD && /(.+?)(?:区|市|县)/.test(q)) {
    // deriveAvailable 失败但问句含区名 → fallback 行政区 preset
    const _presetLayer = getLayers().find(x => x.name === '行政区' || /行政区/.test(x.name || ''));
    if (_presetLayer && _presetLayer.fc) {
        const _dm = q.match(/(.+?)(?:区|市|县)/);
        const _pname = _dm ? _dm[1] : '';
        const _pf = _presetLayer.fc.features.find(f => {
            const v = f.properties && (f.properties.name || f.properties.MC || f.properties.NAME);
            return v != null && String(v).includes(_pname);
        });
        if (_pf) _zonalD = { name: _pname + '区', layer: _presetLayer.name, field: 'MC' };
    }
}
```

**与 chain pre-check `:1131-1141` 一致**——同一 fallback 模式·只是位置不同（zonal 强制路由 vs chain pre-check）。治层加载竞态导致的 deriveAvailable 偶发 null。

**方案 B（不推荐·正则放宽）**：_validAfter 已经对 PRM-05 问句匹配·放宽无意义。

**方案 C（不推荐·FC few-shot）**：撞 diagnose prompt 红线。

### 风险

方案 A 风险**低**——fallback 逻辑与 chain pre-check 一致·已在 RST-L06 验证。只在 deriveAvailable 失败 + 问句含区名时触发·不影响正常路径。

## 三、PRM-07 方案收敛 — **方案 A（后端 resolve_boundary dict 校验）**

### 现状确认

LLM 直传 GeoJSON boundary 绕过 FIXED_ADMIN_DISTRICTS 白名单的完整链路：

```
FC LLM → params.boundary = { type: 'FeatureCollection', features: [{ properties: { MC: '小溪塔' }, geometry: ... }] }
  ↓
harness.js deriveMissingParams :1508-1524
  → zonal 强制路由：deriveAvailable 返回 _zonalD（preset 行政区 + 白名单过滤 → 小溪塔不在白名单 → null）
  → 但 FC 已直供 boundary（params.boundary = GeoJSON dict）→ _zonalD = null → zonal 路由不触发
  → BUT :1540 _boundarySuspect 检查 params.boundary：
      _boundarySuspect = (!p.boundary && !p.boundaries) || _boundarySuspect(p.boundary)
      _boundarySuspect(boundary): typeof boundary !== 'string' && features.length === 1 → false（GeoJSON FC 1 feature → 不 suspect）
  → 不重新 derive → p.boundary 保持 FC 直供的「小溪塔」GeoJSON
  ↓
harness.js :1126 runAllToolCalls 或 :1098 runTemplatePath
  → TOOLS.zonal_stats({ boundary: 小溪塔 GeoJSON })
  ↓
frontend zonal-tool.js _execute → resolveBoundaryGeo(boundary)
  → shared.js:84 typeof input === 'object' → return input（GeoJSON dict 直通·不校验白名单）
  ↓
POST /geo/zonal_stats body.boundary = 小溪塔 GeoJSON
  ↓
后端 geo_routes.py resolve_boundary(dict) → GeoDataFrame.from_features → 不校验名称
  → 执行 zonal_stats（成功产出层）
```

**根因**：`resolveBoundaryGeo`（shared.js:84）对 GeoJSON dict **直通无校验**。FIXED_ADMIN_DISTRICTS 白名单只在 `deriveAvailable`（tools.js:621-622）·deriveAvailable 只在 deriveMissingParams 的 derive 路径中调用·FC 直供 boundary **绕过了 derive 路径**。

### 方案评估

| 方案 | 改动 | 符合 CB-14 | 不破上传层 | 改动面 | 风险 |
|------|------|:---:|:---:|:---:|:---:|
| **A 后端 resolve_boundary dict 校验** | `core/geo_registry.py:169-181` dict 路径加：检查 features[0].properties 是否含 FIXED_ADMIN_DISTRICTS 之外的名字 → 如果是法定功能区 → raise ValueError | ✅ EMC 不硬猜 | ✅ 用户上传层无 source 标记 → 不校验 | 小（后端 1 函数） | 低 |
| B 前端来源标记 _source | FC 输出的 boundary 加 `_source: 'fc'` 标记 → zonal-tool.js 检查 source | ⚠️ FC 不自带 source | ✅ | 中（改 FC 解析 + zonal-tool） | 中 |
| C 不动 | 维持现状 | ❌ 法定功能区直通 | ✅ | 0 | 高（PRM-07 fail 持续） |

**glm组 推荐：方案 A（后端 resolve_boundary dict 校验）**

理由：
1. **CB-14 对齐**：后端 `resolve_boundary` 是 boundary 的最终关口——在关口校验"这个 GeoJSON 的要素名是否可信"最直接
2. **不破上传层**：用户上传层的 GeoJSON 没有标记区分——但方案 A 可以用 **启发式**（要素名 ∈ 行政区 preset manifest 的 MC 字段列表 → 校验；不在 → 放行用户上传）
3. **最小改动面**：`resolve_boundary` dict 路径（`:169-181`）加 5-10 行校验

**方案 A 具体实现建议**：

```python
# core/geo_registry.py resolve_boundary dict 路径（:169-181 之后）
if isinstance(boundary, dict):
    # ... 现有 from_features + name_field 逻辑 ...
    # CB-19 PRM-07：dict 直供 boundary 校验——要素名是否在法定功能区黑名单
    _ADMIN_BLOCKLIST = {'小溪塔', '龙泉', '白洋', '龙泉绿心', '生物产业园', '东部产业新区'}
    _name_col = 'name' if 'name' in polys.columns else (nf or 'MC')
    if _name_col in polys.columns:
        for _nm in polys[_name_col].astype(str):
            if _nm in _ADMIN_BLOCKLIST:
                raise ValueError(f'边界要素「{_nm}」为法定功能区·非真实行政区划·不硬猜（CB-14）')
    return polys
```

**注意**：用黑名单（`_ADMIN_BLOCKLIST`）而非白名单——因为用户上传层可能含任意合法地名·白名单会误拦。黑名单只拦已知的法定功能区（CB-16 preset 清理时删掉的 5 个）。

### 风险

方案 A 风险**低**——黑名单精确（5 个已知法定功能区名）·不会误伤用户上传层（用户上传的"深圳南山区"不在黑名单）。
