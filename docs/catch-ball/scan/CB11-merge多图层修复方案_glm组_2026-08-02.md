## 第二部分：扫描结果 / 评价

### 一、根因独立核实（agree 问题报告）

**1. merge 后端确无多图层能力**（`api/geo_routes.py:239-262`）：

```python
class MergeRequest(BaseModel):
    boundary: Optional[Any] = None   # 单值，非数组
    by: Optional[str] = None

polys = resolve_boundary(req.boundary)   # resolve_boundary 只接受 str|dict
# 无 layers 参数 → 无法接收多个图层
```

`resolve_boundary`（`core/geo_registry.py:146`）签名只接受 `str`（preset_id）或 `dict`（单个 GeoJSON）——**类型层面就不接受多图层**。核实无误。

**2. `unary_union` 丢属性**（`api/geo_routes.py:256-258`）：

```python
merged = gpd.GeoDataFrame(
    {'name': ['合并区']}, geometry=[polys.geometry.unary_union], crs=polys.crs
)
```

即使绕过限制把 3 个图层塞进单个 boundary GeoJSON，`unary_union` 会把所有要素合并成**一个几何**，丢掉 DLMC 分类等全部属性。核实无误。

**3. LLM 的 `layer_list` 猜测被拒**：

前端 `TOOLS.merge`（`tools.js:1130`）：`if (!params.boundary) return [ERR]`——只认 `boundary`，不认 `layer_list`/`layers`。LLM 猜的参数名连第一道 guard 都过不了。核实无误。

### 二、A vs B 字段冲突——geopandas 独立实测（核心证据）

**我独立编写 geopandas 脚本实测了字段冲突行为**（Codex 的报告基于代码推理，我基于运行时实测，证据链互补）：

#### 实测场景

3 个独立裁剪图层，模拟真实情况（商业/居住/公园，各有不同字段子集）：

```python
a = GeoDataFrame({'name':['商业'],'landuse':['commercial'],'area_km2':[2.5],'source':['clip']},
                 geometry=[box(0,0,1,1)])
b = GeoDataFrame({'name':['居住'],'landuse':['residential'],'floor_area':[1500],'area_km2':[3.2]},
                 geometry=[box(1,0,2,1)])
c = GeoDataFrame({'name':['公园'],'landuse':['park'],'green_ratio':[0.8],'area_km2':[1.1]},
                 geometry=[box(2,0,3,1)])
```

#### 实测结果

| 指标 | 方案 B（overlay union 链） | 方案 A（concat） |
|------|--------------------------|-----------------|
| **第 1 次 overlay(a,b,union)** | `name`→`name_1`,`name_2`；`landuse`→`landuse_1`,`landuse_2`；`area_km2`→`area_km2_1`,`area_km2_2`。**9 列** | — |
| **第 2 次 overlay(res1,c,union)** | `name_1`→`name_1_1`...**13 列**（字段爆炸） | — |
| **concat([a,b,c])** | — | `name`/`landuse`/`area_km2` 保持不变（7 列·NaN 填充缺失） |
| 下游 LLM 读 `name` | ❌ `name` 只剩第 3 层值 | ✅ 3 行各有 `name` |
| 几何保留（不相邻区域） | ✅ | ✅ |

#### 字段冲突严重度判定

| 冲突类型 | overlay union | concat |
|---------|:---:|:---:|
| 同名字段（name/landuse/DLMC） | 🔴 后缀爆炸（`_1`/`_2`/`_1_1`） | ✅ 直接对齐 |
| 异名字段（floor_area/green_ratio） | 🟡 散落在不同后缀列 | ✅ 并集列·NaN 填充 |
| N 层链式叠加 | 🔴 列数指数增长（3→9→13） | ✅ 线性（列数 = 并集） |
| `_to_geojson` 序列化 | ⚠️ NaN 值多但可序列化 | ✅ 干净 |

**独立结论**：方案 B（overlay union 链）的字段冲突不是理论推测——**geopandas 运行时实测确认**，3 个图层 2 次 union 后属性列从 3 个爆炸到 13 个，且 `name` 字段无法统一读取。这对下游 finalStep LLM（需要读 `name` 描述产物）、地图图例（需要 `name` 标注）都是致命的。

### 三、方案 A（concat）的独立评估

**语义正确性**（agree Codex 讨论点 1）：
- "合并 3 个独立图层"= 要素拼接（concat），不是空间求并
- overlay union 的语义是"求两块面的并集几何"——对不相邻的裁剪产物会产生碎片 + 属性污染
- `pd.concat([gdf1, gdf2, gdf3])` 是 GIS 标准的多图层拼接操作

**字段处理**（独立验证）：
- `pd.concat` 取字段并集，同名字段直接对齐（无后缀）
- 不同字段 NaN 填充——可接受（3 个裁剪产物字段结构通常一致）
- 加 `_source_layer` 标记列可追溯每行来源（我建议的改进点）

**唯一风险**：
- CRS 不一致 → concat 前必须 `to_crs` 统一（裁剪产物同源通常一致，但防御性处理成本极低）
- 不同来源的同名列如果语义不同（如 A 的 `area` 是 m²、B 的 `area` 是 km²）会静默混合 → 但 merge 端点会重新算 `area_km2`，不受影响

### 四、四个讨论点的独立意见

#### 讨论点 1：concat（A）vs 空间并集（B）

**agree Codex·agree 问题报告**：concat 是唯一正确语义。

补充独立判断：overlay union 在"相邻面合成连续片区"场景（如西陵区+伍家岗区→大片区）是有用的——但这正是 merge 单层 `unary_union` 或 `dissolve` 已覆盖的。两个操作不应混用。

#### 讨论点 2：merge 语义边界——并入 merge 还是新建工具

**agree Codex·agree 问题报告**：并入 merge，不建新工具。

独立理由：本次失败正是 LLM 在 merge/overlay 之间纠结所致（问题报告 §二.3）。新建工具（如 `combine_layers`）会增加选型歧义，让 LLM 更纠结。并入 merge 让"合并"的直觉命中即成功。

#### 讨论点 3：字段冲突处理

**agree Codex**：concat 无冲突；overlay 重复列是独立改进。

独立补充（geopandas 实测依据）：
- `pd.concat` 对同名字段（DLMC/MC/name）直接对齐——**实测确认无后缀**
- overlay 的 `_1/_2` 后缀是 `gpd.overlay` 内部 `pandas.merge` 的默认行为——在"两图层属性并集"场景是合理的（intersection 结果需要同时保留两图层的属性），**不应"修复"** overlay 的这个行为，它是正确的空间分析语义

#### 讨论点 4：LLM 提示

**agree Codex**：契约 `when`/`params_str` 显式两模式 + `layers` alias 收 `layer_list`。

独立补充：LLM 已经猜了 `layer_list`（问题报告 §一），说明它的直觉是对的——只需在契约中正式承认这个参数（alias `layer_list`→`layers`），LLM 的猜测就能命中。

## 第四部分：讨论点

### 讨论点 1：overlay union 链是否应整体退役？

**glm组意见**：merge 语义下的 union 链应退役（改调 `merge(layers=[...])`），但 **overlay 工具本身的 union 能力保留**——overlay union 在"空间并集"场景（相邻面求并）是正确语义。

`buildLanduseCompletion` 当前把 union 链用于"合并多类用地"是**语义误用**——应改为 `merge(layers=[...])`。这同时消除了 G1/G2 的无限循环风险（循环代码被替换掉）。

### 讨论点 2：`_source_layer` 标记列的必要性

concat 后各要素来自不同图层，如果下游需要按来源筛选（如"只看商业用地"），需要追溯。建议 merge 端点 concat 时自动加 `_source_layer`（值为原始图层名或序号）。成本低、收益明确。
