## 第二部分：扫描结果 / 评价

### 2.0 总评

> **EMC v1.0 的工具选型能力优秀（100%），但接地上下文的信息完整性不足，导致 LLM 在简单查询上也频繁出错。两个系统性缺陷贯穿所有失败案例：① 接地上下文缺关键语义标注（数据来源、可用引用） ② LLM 在面对信息缺口时进入推理螺旋而非快速承认。**

### 2.1 发现 1（🔴 CRITICAL）：接地上下文缺语义标注 — 两类信息缺失

**缺失 A：层的数据来源（用户上传 vs 系统预设）**

`buildContext()` 将所有层以相同格式列出，不区分来源。导致 C2 中 LLM 声称用户"没有上传任何数据"。

**证据**：`tools.js:buildContext()` line 576 — 仅输出 `l.name(cnt,kind,fields)`，无来源标注。

**缺失 B：层的可用引用（预设 ID vs 展示名）**

接地上下文展示的是展示名（如"宜昌 L2 · T3（中心城区情绪·末）"），但 `layer` 参数需要预设 ID（如 `yichang_l2_t3`）或精确层名。LLM 不知道用哪个，于是拼凑出 `T3·综合·yichang_L2_T3_L2_result_geojson.geojson`（C4 根因）。

**证据**：`tools.js:buildContext()` — 无"引用"字段；`tools.js:ref()` — 无错误反馈。

### 2.2 发现 2（🔴 CRITICAL）：LLM 推理螺旋 — 面对信息缺口时的行为模式

在 C1 和 C2 中，LLM 展示了相同的失败模式：

```
判断 → 推翻 → 重新判断 → 再推翻 → 再判断 → ...（token 耗尽）→ 放弃
```

| case | 转向次数 | 最终行为 |
|------|:---:|------|
| C1（裁剪西陵+伍家岗） | 12 次 | 放弃 → request_upload |
| C2（上传了哪些数据） | 7 次 | 错误结论（"没有上传任何数据"） |

**根因分析**：
- C1：FC 架构单工具限制 + system prompt 缺"多要素提取"指引 → LLM 找不到方案 → 反复尝试 → 耗尽
- C2：接地上下文中无"来源"信息 → LLM 无法判断 → 反复推演 → 猜错

**这不是模型能力问题，是信息供给不足触发的行为退化。** 当 LLM 缺关键信息时，它会用推理来"猜测"缺失信息，而非直接说"我不知道"。

### 2.3 发现 3（🟠 HIGH）：finalStep 无执行结果感知

finalStep 的 `ctx.context` 只有"计划"没有"结果"。C3 中工具执行失败但 finalStep LLM 写出了完整的假结论。

**证据**：`harness.js:523` — `【单技能路径·已执行 extract_feature】` 不区分成功/失败。

### 2.4 发现 4（🟠 HIGH）：per-call 超时 25s 过紧

C5 中 finalStep 需要 25-35s（大接地上下文 + 1738 网格单元），触发 25s 超时 → 降级结论。

**证据**：`api.js:32` — `_timeout = 25000`。WS1 从 45s 降至此值，覆盖了 80% 场景但边界 case 不够。

### 2.5 发现 5（🟡 MEDIUM）：字段名规范化断裂（MC→name）

`resolve_boundary` 将 MC 重命名为 name，但 `_apply_attr_filter` 仍引用原始字段名 MC。

**证据**：`geo_registry.py:174-177` vs `geo_routes.py:77-80`。详见 `rootcause/2026-07-28-MC-field-rename.md`。

## 第四部分：讨论点

### D1：FC 架构的单工具假设是否应该打破？

当前 FC 只能返回 1 个 tool_call。提取多个要素（C1）、多步链（extract+merge）等常见需求被这个限制卡住。两个方向：

- **保持单工具**：强化 plans[] 机制，让 LLM 知道 rank=2+ 会被系统自动执行
- **支持多工具**：FC 返回 tool_calls 数组，orchestrator 顺序执行

建议先走方向 A（零架构改动），观察 plans[] 使用率后再决定是否走方向 B。

### D2：LLM 推理螺旋是模型特性还是系统设计问题？

C1 和 C2 的推理螺旋都发生在 LLM 缺关键信息时。这不是 DeepSeek V4 特有的——所有 LLM 在信息不足时都会"猜测"而非"承认不知道"。

**系统设计可以改变这个行为**：
- 提供完整信息（P0-1/2）→ LLM 不需要猜 → 螺旋不发生
- System prompt 加"信息不足时直接说明，不要反复推理"→ 螺旋提前终止

### D3：为什么"简单"查询比"复杂"查询更容易失败？

C2（"我上传了哪些数据"）比 C5（"500m 方格网聚合"）简单得多，但 C2 失败了而 C5 成功了（图层层面）。

**原因**：复杂查询有明确的工具路径（问聚合 → density），LLM 只需选工具+填参。简单查询没有工具对应（"列出数据"不是工具能力），LLM 必须从接地上下文中提取信息来组织回答——但接地上下文缺少它需要的信息（来源标注），于是螺旋。

**启示**：EMC 的工具覆盖了"做分析"但没覆盖"回答问题"。需要给 LLM 一个 `query_layers` 式的"只读信息查询"出口。
