## 二、多步问热力图问题评估

### 2a. 根因确认——**agree claude组："FC 计划不完整"·非早停**

**claude组 推理正确**。代码证据链：

1. **FC prompt 指令"先做第一步"**（`router.py:35`）：
   ```
   '多步骤请求（如裁剪多类用地）→ 先做第一步，系统自动补全后续'
   ```
   FC 看到"先裁剪...再生成热力图"→ 按"先做第一步"指令 → 只出 `clip` tool_call → `method=[clip()]`

2. **系统补全不覆盖 clip→density**：
   - `buildLanduseCompletion`（`:1334`）只覆盖用地 overlay/merge 模式
   - `_autoExpandOverlays`（`:1422`）同上
   - `CHAIN_REGISTRY`（`stages.js:78`）**有 `clip_density` 链**——但触发器 `/范围.{0,4}密度/` 和 `/区.{0,4}(热力|密度分布|分布)/` 不匹配"先裁剪西陵区情绪点，再生成热力图"（"区"与"热力"间距 > 4 字）
   - `deriveMissingParams` 无"先...再"顺序检测

3. **早停不是根因**（agree claude组）：
   - 早停前：method=[clip()]·plan=1（clip 在 GEO_TOOLS）·clip 执行 exec=1·1≤1 → 早停
   - 早停后（3abb503）：同上——plan 仍=1（density 不在 GEO_TOOLS·不计入 plan）·1≤1 → 早停
   - **行为一致**——density 从未被纳入计划 → 不论早停与否·density 都不执行

**根因 = FC 只出第一步 + 系统补全不覆盖 clip→density 顺序模式 + CHAIN_REGISTRY `clip_density` 触发器不匹配此问句变体。**

### 2b. 严重度——**中（真实用户场景·B3 无断言）**

| 维度 | 评估 |
|------|------|
| 用户影响 | **中**——"先做A再做B"是自然的多步表达·用户实际会说"先裁剪再出热力图"/"先筛选再排序"等 |
| B3 覆盖 | **无**——PRM 全单工具·RST-L* 无多步·T9 复合多步测的是 Pro chain（非 while-loop 单工具补全）|
| 体验影响 | **"只做一半"变体**——用户看到"接下来基于这批点生成密度热力图" = 计划描述·非已完成·需要用户追问第 2 步 |
| 频率 | **中低**——多数用户单步问（"生成热力图"直走 density·不经 clip）·多步"先...再"是进阶用法 |

### 2c. 修复方向

#### 方案 A：CHAIN_REGISTRY 触发器放宽 — **P1·推荐（最小改动·确定性）**

当前 `clip_density` 触发器（`stages.js:79`）：
```javascript
triggers: [/范围.{0,4}密度/, /区.{0,4}(热力|密度分布|分布)/],
```

放宽到覆盖"先裁剪...再热力图"模式：
```javascript
triggers: [
  /范围.{0,4}密度/,                           // 原：范围内密度
  /区.{0,4}(热力|密度分布|分布)/,               // 原：区内热力
  /(?:裁|剪裁|裁剪).{0,20}(热力|密度|分布)/,    // 新：裁剪...热力图（间距放宽到 20）
  /(?:先|然后|再|接着).{0,15}(热力|密度)/,      // 新：顺序词 + 热力
],
```

**效果**：FC 出 clip（第一步）→ `_deriveChainId` 匹配 `clip_density` → `runChainPath` 执行 clip + density → 完整多步。

**风险**：低——CHAIN_REGISTRY 是确定性链（不调 LLM）·触发器放宽只影响匹配面。

#### 方案 B：deriveMissingParams 顺序检测 — **P2·补充**

在 `deriveMissingParams` 加"先...再"顺序检测——如果问句含 `(?:先|然后|再|接着).{0,15}(热力|密度)` 且 FC 只出了 clip → 构造 `_allToolCalls = [{clip}, {density}]`（仿 `buildLanduseCompletion` 模式）。

**比方案 A 更灵活**（不依赖 CHAIN_REGISTRY 固定参数模板）·但改动更大。

#### 方案 C：FC prompt 改"输出多 tool_calls" — **P3·不推荐（撞红线）**

改 FC prompt 教"先...再 → 输出两个 tool_calls"——撞 CB-10 教训（FC prompt 改动风险高·Flash 单 call 是模型现实）。glm组 CB-11 主通道讨论已 disagree B 方案（促多 call）·此处同理。

#### 方案 D：B3 加多步问断言 — **P1·防复发**

B3 加一个多步问用例（T9 类）：
```javascript
{ id: 'T9-L02', name: '多步 clip+density', run: async (t) => llmRun(t, 
  '先裁剪西陵区情绪点，再生成热力图', 
  (b, _tt, sig) => ({
    pass: sig.tools.includes('clip') && sig.tools.includes('density'),
    obs: `tools=${sig.tools.join(',')}`, review: '两步都执行了？'
  }), { range: '行政区', csv: 'L2-T1' }) },
```

**防复发**——即使方案 A/B 修了·断言确保不退化。

### 2d. 与 density 不在 `_GEO_TOOLS` 的关系

上轮 glm组 发现 density 不在 `_GEO_TOOLS`——这不影响 CHAIN_REGISTRY 方案（`runChainPath` 不查 `_GEO_TOOLS`）。但如果方案 B（`_plannedGeoSteps`/`_executedGeoSteps`）要正确处理 clip+density 计划完成度·density 需在 `_GEO_TOOLS` 中。

**建议**：方案 A（CHAIN_REGISTRY 放宽）+ `_GEO_TOOLS` 补 density——两条互补。
