## 审查结论：claude组 判断方向正确但机制推断有偏差

**claude组 说"zonal 强制路由误触发 → validateParams fail → while-loop 退化"——glm组 判定：disagree 机制·agree 方向。**

zonal 强制路由不会**直接**导致 while-loop（validateParams fail → ask_user·不是 while-loop）。但它可能通过**间接路径**（template 被改 + boundary derive 失败 + ask_user 触发后用户未答 → 某些 B3 用例的 waitAnswer 超时 → ERR）导致大面失败。claude组 的"msgs=12 = while-loop"推断**需要 b3_final8.log 原始证据验证**——msgs=12 也可能是 FC 诊断本身变慢（思考链长）或 search_chat 遗留影响，不一定是 while-loop。

**最大嫌疑变更**：不是 zonal 强制路由（它是 `deriveMissingParams` 内·不直接控制 orchestrate 路由），而是 **deriveAvailable 双字段扫描的性能/行为变化**——新增 `for (const f of features.slice(0,30))` 遍历 + `new Set` 构建·如果 `features` 数量大或 properties 结构异常·可能引入延迟或匹配行为变化（原始值精确优先 → 某些之前 stripped 匹配的区名现在不匹配 → boundary 填不上）。

## 二、a04a714 四处改动逐处分析

### 改动 1：zonal 强制路由（harness.js:1368-1382）—— **partial 嫌疑（间接非直接）**

```javascript
} else if (/(聚合|归因|统计).{0,4}(情绪|极性)|按面聚合/.test(q) && tool !== 'zonal_stats') {
    diagnose.template = 'zonal'; diagnose.method = ['zonal_stats()'];

```

**Node.js 触发分析**（14 例复现）：

| 问句 | FC 选了 | 路由触发？ | boundary derive？ | 后果 |
|------|---------|:---:|:---:|------|
| "西陵区按面聚合情绪统计及归因" FC→extract | extract | ✅ → zonal | 取决于 deriveAvailable | 如果 derive 成功→OK / 失败→ask_user |

**claude组 说"强制 zonal + boundary 未填 → validateParams fail → while-loop"——机制错误**：
- validateParams fail → `runTemplatePath:508-513` 返回 `exit: 'ask'`（ask_user）·**不是 while-loop**
- ask_user 是合法出口（四态出口之一）·不会落 while-loop

**但间接风险存在**：
- 如果 zonal 强制路由把 FC 成功选的工具（如 extract_feature）改成 zonal·然后 boundary derive 失败 → ask_user
- B3 `llmRun` 的 `waitAnswer(90000)` 会等 90s（ask_user 渲染后无用户答）→ 判 ERR
- 这解释了 **PRM-05/06/07 类 zonal 问句的 ERR**——但不解释 UI-L01/RST-L01 等**非 PRM 问句**的 ERR

**影响面评估**：zonal 强制路由只影响含 `(聚合|归因|统计).{0,4}(情绪|极性)|按面聚合` 的问句。B3 25 例中 PRM-05/06/07 + RST-L01 + UI-L01 + SMT-L04 = 约 6 例含此模式。其余 19 例不应受影响。**OK 1/ERR 23 远超此范围**——说明有**其他系统性根因**。

### 改动 2：多 call 重写 `_allToolCalls=[{name:'clip'}]`（harness.js:1352-1354）—— **低嫌疑**

只在裁剪点问句 + FC 多 call 时触发。B3 中仅 PRM-10 匹配。不影响其他 24 例。

### 改动 3：deriveAvailable 双字段（tools.js:590-609）—— **🔴 最大嫌疑（行为变化 + 性能）**

```javascript
// 新增：遍历 features 提取 name/NAME/名称 字段
const _nameVals = [];
for (const f of (l.fc && l.fc.features || []).slice(0, 30)) {
  const p = f.properties || {};
  for (const k of ['name', 'NAME', '名称']) {
    if (p[k] != null) _nameVals.push(String(p[k]));
  }
}
const _allVals = [...new Set([...(b.values || []), ..._nameVals])];
// 原始值精确优先（第一轮）→ stripped 兜底（第二轮·≥3字）
```

**行为变化风险**：

| 变化 | 影响 |
|------|------|
| **原始值精确优先**（第一轮 `q.includes(nm)`）| 之前 stripped 双向包含先匹配·现在精确优先。如果 admin_district 的 name 字段 = "西陵区"（含后缀）·问句"西陵区范围内..."精确匹配 ✅。但如果 name = "西陵"（无后缀）·问句"西陵区范围内..."精确不匹配 → 退到 stripped → `_nmStrip="西陵".length>=3` ✅。**行为正确·但改变了匹配顺序** |
| **stripped 阈值 2→3** | `_nmStrip.length >= 3`——"西陵"(2字) 不再 stripped 匹配！"伍家"(2字) 同理。**这是行为退化**：2 字区名被 stripped 阈值挡住·只有 3+ 字才 stripped 匹配 |
| **new Set 去重** | 如果 `b.values` 含大量值 + `_nameVals` 含 30×3=90 个值 → Set 构建 + 两次遍历·性能可能变慢（但 <1ms 级·不应导致 1-3min） |

**🔴 关键发现：stripped 阈值 2→3 是行为退化**：

```
改前（cde3cf4）：_nmStrip.length >= 2 → "西陵"(2字) stripped 匹配成功
改后（a04a714）：_nmStrip.length >= 3 → "西陵"(2字) stripped 不匹配！
```

如果 admin_district preset 的 nameField 值是"西陵区"（3 字·stripped="西陵"2 字）：
- 原始值精确：`q.includes("西陵区")` → 问句"西陵区范围内..." ✅ 匹配
- 但如果问句是"西陵范围内..."（不带"区"）→ 原始不匹配 → stripped `_nmStrip="西陵".length=2 < 3` → **不匹配！**
- 改前：`_nmStrip.length >= 2` → 匹配 ✅

**这意味着某些区名查找在 a04a714 后失效**——boundary 填不上 → validateParams fail → ask_user → B3 ERR。

**但这仍只影响需要 boundary derive 的 zonal/compare/rank 问句**——不解释全部 23 ERR。

### 改动 4：ask 断言收窄（test-cases.js:325 `d.expectRadius != null`）—— **仅影响 PRM-03/04**

`d.expectRadius != null` 限制 ask_user PASS 只给 center 类（PRM-03/04）。PRM-09 不再 PASS。但这是断言改动·不影响 EMC 运行时·只影响 B3 判定。**不影响其他 23 例**。

## 三、claude组 漏掉的根因（新发现）

### 根因 5（🔴 最大嫌疑）：deriveAvailable 行为变化 → 连锁 boundary derive 失败 → 多例 ERR

上节分析：stripped 阈值 2→3 导致 2 字区名（西陵/伍家/点军/猇亭）stripped 匹配失效。虽然原始值精确匹配仍工作（如果问句含完整"西陵区"）·但**任何不带"区"后缀的问句**（如问句变体"西陵范围内"）会导致 boundary 不填。

**连锁效应**：
1. boundary 不填 → zonal/compare 的 validateParams fail → ask_user
2. ask_user 在 B3 `waitAnswer(90000)` 内等待 → 90s 后判 ERR
3. 每例 1-3min（ask_user 渲染 + waitAnswer 超时）

**但这仍不解释 UI-L02/RST-L05 等概念问的 ERR**——它们不涉及 boundary。

### 根因 6（中嫌疑）：zonal 强制路由 + `deriveMissingParams` 异常 → diagnose 状态不一致

如果 `deriveMissingParams` 内部抛异常（如 `deriveAvailable` 双字段代码在新数据结构上出错）·`diagnose` 可能处于 `template='zonal'` 但 `params` 不完整的中间状态。`orchestrate` 继续 → `runTemplatePath` → validateParams fail → ask_user。

**验证方法**：在 `deriveMissingParams` 入口/出口加 try/catch + console.error·确认是否有静默异常。

### 根因 7（低嫌疑但需排查）：FC 行为概率性变化

06/07 到 final8 之间如果 DeepSeek API 端有模型更新/限速变化 → FC 输出格式变化 → diagnose.degraded → while-loop。**这与 a04a714 无关·但时间巧合**。

**验证方法**：用 06/07 完全相同的代码（git stash a04a714）重跑 B3·如果恢复 76-80% → 确认是 a04a714 引入。如果仍 ERR 23 → 是 API 端变化。
