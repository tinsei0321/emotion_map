**验证缺口**：glm组 无法独立确认 `yichang_L1_T1_result_csv.csv` 文件真实存在（应在 frontend/ 静态目录）。建议 claude组 确认文件存在 + B3-verify-06 看 CPD-L01/L02 是否真转 PASS。

### 1.2 CPD-L03 恒真 → 硬断言

## 第二部分：改动 2·PRM-08 compare 兜底（✅ 正确·治根因）

### 2.1 改动内容

`harness.js:1471-1477` compare 分支补 `_allToolCalls` 重写：
```js
if (_bs.length >= 2) {
  p.boundaries = _bs;
  // CB-14（PRM-08）：FC 多 call 会走 :1077 runAllToolCalls 批量执行·绕过强制 compare
  if (Array.isArray(diagnose._allToolCalls) && diagnose._allToolCalls.length > 1) {
    diagnose._allToolCalls = [{ name: 'compare_regions', params: { boundaries: _bs } }];
  }
}
```

### 2.2 根因匹配验证（治 CB-13 定案的根因）

CB-13 glm组 定案：PRM-08 根因 = **FC 选 extract_feature×2（多 call）走 `:1077 runAllToolCalls` 批量执行，绕过单工具路径的强制 compare 改写**。

本改动**精准对治**：在 compare 分支（:1471）把多 call 重写为 compare_regions 单 call → `:1077 length > 1` 不成立 → 不走批量 → 落单工具路径执行 compare_regions。**治根因，非治表**。

### 2.3 执行顺序验证（决定性证据）

| 行号 | 操作 | 时机 |
|---|---|---|
| :1033 | `deriveMissingParams(diagnose, ...)` ← **含 compare 重写 :1475** | **先** |
| :1077 | `if (_allToolCalls.length > 1) runAllToolCalls(...)` ← 批量执行 | **后** |

`deriveMissingParams`（:1033）**先于**批量执行（:1077）。重写在批量之前完成 → 批量条件 `length > 1` 被破坏 → **正确拦截**。**顺序无瑕疵**。

### 2.4 边界安全分析（claude组 注意点逐条回应）

**注意点 A：「FC 多 call 但区名 <2 会怎样？」**

推演链：
1. :1456 从问句提取区名 `_n` → :1457 `if (_n.length >= 2)` 守门
2. 区名 <2 → **跳过整个补填块** → `_bs` 不构造 → :1471 `if (_bs.length >= 2)` 不进
3. → `_allToolCalls` **不重写** → 仍走 :1077 批量执行原 FC 多 call

**判定：合理保守行为，无副作用**。区名不足时无法构造 compare 的 boundaries（compare 需 ≥2 区要素），强行重写反而错。此时保留 FC 原选（批量执行）是正确兜底。

**注意点 B：「其他多 call 场景（extract+merge）会被误改吗？」**

三分支互斥性验证（deriveMissingParams :1402-1480 是连续 `if/else if` 链）：
- `:1402` density（方格/网格）→ `:1405` else if clip（裁剪点）→ `:1424` else if extract（筛选）→ `:1427` else if zonal（聚合/归因）→ `:1451` else if **compare（对比/比较）**

**互斥**——问句只能命中其一。「对比 A 与 B」必走 compare 分支，不会误入 clip/zonal 的 `_allToolCalls` 重写。反之「裁剪点」走 clip 分支（:1409 重写为 clip 单 call），不会进 compare。**三分支各自守自己的语义域，无交叉误伤**。

**注意点 C：「重写是否对齐 clip/zonal 模式？」**

对齐性确认：
- clip（:1409）：`_allToolCalls = [{name:'clip', params:{as:...}}]`
- zonal（:1441）：`_allToolCalls = [{name:'zonal_stats', params:{boundary:p.boundary}}]`
- **compare（:1476 新）**：`_allToolCalls = [{name:'compare_regions', params:{boundaries:_bs}}]`

**模式完全一致**（重写为该分支对应工具的单 call + 正确参数槽）。对齐 zonal 的 `:1441-1443` 模式（claude组 提到的对齐目标）。

### 2.5 判定

**✅ 正确·治根因·边界安全·无副作用**。这是 CB-13 PRM-08 根因（FC 多 call 绕过强制 compare）的精准修复。

## 第三部分：改动 3·A4 选择性注入（⚠️ 方向对·2 个改进点）

### 3.1 改动内容

1. `industry_kb/__init__.py` 新增 `industry_kb_final_brief(domain_lens)`——按命中领域渲染精简归因速查（每域 ~0.6KB：政策方向前 2 + 术语前 4 + 底线指标前 2 + 项目类型前 5 + 情绪归因焦点 + 4×5 主归属）。
2. `prompts.py:169-176` `build_final_prompt` 条件注入：`if domain_lens: prompt += industry_kb_final_brief(domain_lens)`。
3. `test_industry_kb.py` A4 守卫：命中注入 / 未命中（None/general/[]）不注 / 不注全量权威语境（'聚焦领域权威语境' 不在）。

### 3.2 方向验证（治 A4 真痛点）

CB-14 RAG 报告 glm组 已定案：A4 = finalStep 被 D019 主动裁掉行业知识（`prompts.py:166` 注释「17KB→0.9KB」）。本改动用「条件选择性注入精简版」治——**正是 glm组 RAG 报告 §3.1 P0 推荐的方案**（仿 `_PEOPLE_CITY_LINE` 模式）。**方向完全正确**。

守卫测试三层覆盖到位：
- ✅ 命中注入（`['urban_renewal']` → 含「归因速查」+「城市更新」）
- ✅ 未命中不注（None/`['general']`/[] → 不含「归因速查」）
- ✅ 不注全量（不含「聚焦领域权威语境」·D019 极瘦仍在）

### 3.3 体积回弹风险（claude组 注意点·实测）

**实测 A4 注入体积**（build_final_prompt 各场景）：

| domain_lens | 体积 | 注入 | vs 极瘦基线 |
|---|---|---|---|
| None（无） | 1.3 KB | ❌ | 基线 |
| `['general']` | 1.3 KB | ❌ | +0（general 不命中领域） |
| `['urban_planning']`（单域） | 2.0 KB | ✅ | +0.7 KB |
| `['urban_renewal']`（单域） | 1.9 KB | ✅ | +0.6 KB |
| 双域 | 2.6 KB | ✅ | +1.3 KB |
| 四域全注（理论上限） | 3.9 KB | ✅ | +2.6 KB |

**体积判定**：单域 +0.6KB / 双域 +1.3KB 在可控范围。四域全注 3.9KB 是理论上限——但 diagnose 实际输出通常 1-2 个 domain_lens（不会四域同时命中），所以**运行时典型回弹 +0.6~1.3KB，可接受**。

### 3.4 改进点 ①：注入条件过宽（⚠️ 应限归因类问句）

**问题**：当前条件 `if domain_lens:` —— 只要 domain_lens 非空（即非 general 问句）就注入。但 finalStep 处理所有类型结论，包括：
- **纯 GIS 操作出口**（clip/extract/buffer 产图层）—— 这类结论是「我裁出了西陵区的点」，**不需要行业归因速查**。
- **通用问答**（general）—— domain_lens=['general'] 不注入（已正确）。
- **归因类**（zonal/compare/rank 出情绪归因）—— **这才是 A4 要治的场景**。

**回弹风险量化**：若用户问「裁剪西陵区的点」（gis_operation·domain_lens 可能含 urban_planning），finalStep 会 +0.6KB 注入一个**用不上的**归因速查。这是**无谓回弹**。

**建议**：仿 `_PEOPLE_CITY_LINE`（`_is_concept_question`）模式，加 `_is_attribution_question(context/question)` 条件——只在问句含归因信号（"为什么/归因/原因/差在哪/极性/情绪"+ 非纯操作）时注入。或更简单：只在 `intent === 'emotion_analysis'` 时注入（diagnose 卡的 intent 字段）。

> 注：`build_final_prompt` 签名目前只收 `domain_lens`，不收 intent。若要限归因类，需 claude组 评估是否传 intent 或用 context 文本启发式判断。

### 3.5 改进点 ②：静态门禁盲区（⚠️ 测试覆盖缺口）

**发现**：`test_final_prompt_stays_lean`（`test_emc_template.py:80-84`）的门禁方式：
```python
n = len(build_final_prompt('', '').encode())   # 传 '' 和 ''（domain_lens 默认 None）
assert n < 3000
```

它调用 `build_final_prompt('', '')` —— **domain_lens 走默认 None → 不触发 A4 注入**。所以这个门禁**只守裸模板（1.3KB），不守条件注入后体积**。

**后果**：A4 注入的回弹（单域+0.6KB / 四域+2.6KB）**完全绕过这个静态门禁**。未来若有人把 `industry_kb_final_brief` 加厚（每域从 0.6KB → 2KB），四域全注会到 9KB+，但这个门禁仍绿——**D019 精神在条件注入路径上无守卫**。

**建议**：补一个条件注入后的体积守卫，例如：
```python
def test_final_prompt_with_lens_stays_bounded():
    """A4 条件注入后体积仍可控（四域全注·防 final_brief 加厚回弹）"""
    from ai_qa.prompts import build_final_prompt
    p = build_final_prompt('x', domain_lens=['urban_planning','urban_renewal','urban_operation','urban_governance'])
    assert len(p.encode()) < 5000, f'A4 注入后 final 膨胀到 {len(p.encode())}B（四域全注应 <5KB）'
```

### 3.6 渲染质量评估

`industry_kb_final_brief` 每域抽：政策方向前 2 + 术语前 4 + 底线指标前 2 + 项目类型前 5 + 情绪归因焦点 + 4×5 主归属。

**判定：信息密度合理**。相比 `industry_kb_brief_text`（全 4 域速查·注入 diagnose），final_brief 是**命中域的精简版**——这正是 A4 要的（finalStep 不需要全 4 域，只需要当前问的领域归因框架）。**不该用 brief_text 替代**（那会注全 4 域 + 回弹更大）。

唯一疑虑：「政策方向前 2 / 术语前 4」是硬截断——若某域的关键政策恰在第 3 条，会被截掉。但这是体积与信息量的必然取舍，0.6KB/域 的预算下合理。建议 claude组 在实际跑归因类问句后，人工抽检 finalStep 结论是否真用上了这些速查（验证信息够不够）。

### 3.7 判定

**⚠️ 方向对·治真痛点·有 2 个非 blocker 改进点**：
- ① 注入条件过宽（应限归因类）—— 优化项
- ② 静态门禁盲区（应补条件注入体积守卫）—— 测试覆盖项
