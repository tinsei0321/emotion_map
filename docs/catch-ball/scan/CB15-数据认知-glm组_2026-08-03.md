### 0.2 关键架构发现（glm组 独立·比报告更深一层）

**`place_name` 的致命依赖**（`spatial_analysis.py:585-597`）：

```python
# place_name：格内代表地名（点侧 spatial_hotspot 多数；空则 area_seed 多数兜底）。
def _place_mode(g):
    for fld in ('spatial_hotspot', 'area_seed'):  # ← 从点的标注字段取众数
        vals = g[fld][g[fld].astype(str) != '']
        ...
stats['place_name'] = grouped.apply(_place_mode)
```

**这个实现的根本问题**：`place_name` 完全依赖**点数据自带的** `spatial_hotspot`/`area_seed` 标注字段（sim 期写入）。**真实采集数据若没有这两个字段，`place_name` 恒为空** → 下钻链第一步就断。

**这是归因↔地点联动的根本断点**——不是"接入问答管线"的问题，是**网格聚合本身就产不出地点信息**（除非点带标注）。报告把这点列在 4.2 "格↔POI 空间查询缺失"，但低估了它的严重性：**即使接了问答管线，没有格↔POI 空间查询，格子照样没有地点清单**。

### 0.3 配额基建的关键细节（glm组 独立）

`reverse_geocode`（`geocode.py:263-302`）的调用链：
- 本地 `place_layer.reverse` 为主（瞬时·给 zone + 最近 POI + 近邻 top5）
- amap regeo 为辅（补街道地址·`extensions=all`）
- `_amap_fetch`（:120）`@lru_cache(maxsize=256)` + 指数退避重试

**但 lru_cache 的 key 是 `params_key = json(sort_keys)`**——即**坐标级别的去重**。同一坐标重复查命中缓存；**不同坐标（不同格子质心）全部 miss** → 每个格子一次高德调用。**批量逆地理时 lru_cache 几乎无效**。这是配额分析的硬约束。

## 第一部分：6 个问题独立判断

### ① 架构分层：后端空间查询 + 前端联动工具（✅ 分层）

**判断：分层方案正确。勿混。**

**通俗解释**：
- **后端**擅长"算"——空间查询（格×POI 的 sjoin）、批量逆地理、坐标→地点，这些是 **CPU/IO 密集**的确定性计算，放后端（`core/spatial_analysis` + `core/geocode`）。
- **前端**擅长"显"——格子选中后的联动呈现（POI 清单浮层、归因→地点高亮）、悬停试探，这些是**交互密集**的 UI，放前端（`frontend/js/ai_qa/tools`）。

**理由**：
1. **承重组件归属**：`place_layer`/`geocode` 已是后端承重组件（搜索栏/弹窗依赖），后端扩展它们的风险 < 前端重写一套。
2. **AI 工具调用边界**：EMC 的 AI 工具（FC 选型）是**后端执行**的（`runToolCall` 调后端 API）。若格↔POI 查询放前端，AI 无法调用（agent loop 在后端）。
3. **数据一致性**：格↔POI 空间查询的结果要进 `tool_history`（供 finalStep 归因），必须在后端产出。

**反方案（全前端）的问题**：前端无空间索引能力（sjoin 需 geopandas），强行做只能调后端 API——那还是分层，只是把编排挪前端，增加耦合。

### ② 触发范式：默认轻量 + 按需重查（✅ 混合）

**判断：不要二选一·用混合分层触发。**

**通俗解释**：
- **默认轻量**（已有）：网格聚合时**自带** `place_name`（代表地名·0 额外成本·现在就有）。
- **按需重查**（新建）：用户**选中/点击格子** → 触发该格的 POI 清单查询（sjoin + 逆地理·按需·省配额）。

**理由**：
1. **配额约束倒逼**：若所有格子默认带 POI 清单（默认重查），100 个格子 = 100 次 sjoin + 100 次逆地理·高德配额秒爆。**必须按需**。
2. **EMC 交互范式对齐**：报告 §5.2 提到 EMC 是"悬停试探/点击锁定"——**点击 = 按需触发**的自然锚点。
3. **已有 `place_name` 不浪费**：默认输出保留（轻量·已有），给用户"这格大概在哪"的提示；点击后给详细 POI 清单（重·按需）。

**具体方案**：
- 网格聚合产物（`zonal_stats`/`density` 输出）**保留** `place_name`（代表地名）。
- 新增前端交互：格子 `click` 事件 → 调后端 `/api/v1/grid/pois?cell_id=xxx`（新建端点·sjoin 格×POI）→ 返回该格 POI 清单 → 浮层呈现。
- AI 路径（agent 主动查）：新增 `grid_pois` 工具（FC 可选）·供 LLM 在归因时主动拉格子 POI 清单。

### ③ 数据接入：分情况（⚠️ 逐项判断）

**3a. `yichang_pois.geojson`（3220 条孤岛）接入运行时？**
**判断：✅ 接入，但作为 place_layer 的补充层，非替代。**

- 现有 place_layer 已有 1270 高德 POI + 158 种子。3220 条 yichang_pois 是**更全的宜昌 POI 集**（含 address/district）。
- 接入方式：place_layer 初始化时 load yichang_pois.geojson，合并进 POI 索引（去重 by name+coord）。
- **风险**：3220 条 load 进内存 + 建 R-tree/kd-tree 索引，启动延迟 +N ms。需实测。

**3b. `amap_poi_centralcity_wgs84.json` 缺失怎么补？**
**判断：用 regeo 兜底，不重建该文件。**

- 缺失影响：中心城区外围 POI 空（报告 4.3）。
- 补法：不主动爬 POI 填文件（成本高·配额贵）·而是在**运行时**用 `reverse_geocode`（本地 place_layer 优先 + amap regeo）兜底——格子在中心城区外围时，逆地理自然补出地点。
- 即：**文件缺失不是阻塞**，regeo 是运行时能力，能覆盖。

**3c. 评论↔POI 关联：最近 POI 反查 vs text 地点抽取？**
**判断：✅ 最近 POI 反查（复用现有 reverse）。不用 text 抽取。**

**理由**：
1. **复用现有能力**：`place_layer.reverse(lng, lat)` 已能返回最近 POI——评论点有坐标 → 反查即得关联 POI。零新基建。
2. **text 抽取的坑**：评论文本提地名需 NER/LLM 抽取，**概率性**且 EMC 评论区可能口语化（"那边""这地方"）抽取准确率低。与 EMC「确定性优先」哲学冲突。
3. **已有标注复用**：L1/L2 点已带 `area_seed`/`spatial_hotspot`（sim 期写入）——这些**就是**评论↔地点的关联（sim 期用 place_layer 打的标）。真实数据用 `reverse` 重新打标即可。

### ④ 配额/性能：🔴 关键风险·必须节流

**判断：这是整个重构的最大工程风险。不解决则方案不可行。**

**风险量化**（glm组 推演）：
- 高德个人 key：免费配额约 **3000 次/日**（regeo·个人开发者常规额度）·QPS 限制约 **3-10 次/秒**。
- 一个 zonal_stats 产出 50-100 格子 → 若每格逆地理 = 50-100 次高德调用 → **单次分析打掉日配额 2-3%**。
- 一天跑 30-50 次分析 → **配额爆**。

**节流策略（必须三层）**：

| 层 | 策略 | 已有？ |
|---|---|---|
| 1 | **本地 place_layer.reverse 优先**（瞬时·零高德调用）·amap 仅补街道地址 | ✅ `geocode.py:271-272` 已如此 |
| 2 | **批量上限**：单次格子逆地理上限 20 格（超出的格用 place_name 代表·不逆地理）| ❌ 需新建 |
| 3 | **持久化缓存**：regeo 结果落盘（SQLite/JSON·key=坐标·跨会话复用）| ❌ 需新建（现有 lru_cache 仅内存·重启失效） |

**关键洞察**：现有 `lru_cache(256)` 是**内存级·同坐标去重**——会话内同格复用有效，但**跨会话/不同格无效**。格子质心每次分析可能不同（用户改范围）→ 缓存命中率低。**必须持久化缓存**（坐标离散化到 ~10m 精度做 key，避免微差 miss）。

### ⑤ 承重红线：✅ 不触碰（方案对的话）

**判断：方案若按 glm组 建议（新增工具走 tool_contracts 单一源 + 新增端点），不触碰承重。**

**逐项核实**：
| 承重项 | 是否触碰 | 条件 |
|---|---|---|
| `diagnose prompt` | ❌ 不触碰 | 地点查询是 agent_step 工具·非 diagnose 路由变化 |
| `harness orchestrate` | ❌ 不触碰 | 新工具走现有 `_allToolCalls`/单工具路径·不改主循环 |
| `ChatRequest schema` | ❌ 不触碰 | 地点查询结果进 `tool_history`（已有字段）·非 schema 变更 |
| `place_layer`/`geocode` | ⚠️ **轻改** | 接入 yichang_pois 是**数据扩展**非接口变更·逆地理批量是**新增包装函数**非改签名 |

**守红线要求**（对齐 KNOWLEDGE §1）：
- `place_layer`/`geocode` 是承重组件 → **改前先扩 eval**（如 `test_place_layer.py` 加 yichang_pois load 测试 + 逆地理批量测试）。
- 新增 AI 工具（`grid_pois`/`lookup_place`）走 `tool_contracts.py` 单一源 → 勿在 prompts/SKILL_DEFS 各搞一份（守铁律 11·CB-04 教训）。

### ⑥ 拓扑关系扩展：⚠️ 分阶段（包含已有·相邻延后）

**判断：**
- **"包含"（格含哪些 POI / 区含哪些 POI）**：✅ **已有 + 补全**。现状 `sjoin within`（`spatial_analysis.py` 用）能做"点在面内"。缺的是**格↔POI 的 sjoin 产物输出**（现在只聚情绪点不 join POI）。补这个 = P0。
- **"相邻/邻接"（伍家岗与谁相邻）**：⏸️ **延后**。需求弱（用户场景是"归因→地点"·非"区→邻区"）+ 成本高（面相邻需共享边判定·geopandas `touches`/`adjacency`·要建拓扑）。

**理由**：
1. 用户场景（§3.3 下钻链）是"格子→涉及地点"——这是**包含**关系（格含 POI），不是相邻。
2. "相邻"是城区规划视角（伍家岗接西陵）·EMC 当前是情绪分析（格子归因）·**相邻不是当前出口**。
3. 若将来真需求（如"对比相邻区的情绪差异"），再补 geopandas touches——但现在不做。
