## 审查结论：disagree 定案——trace.log 证据推翻"非 while-loop"

**claude组 定案说"F_001 每例 1 次·没有 while-loop"——glm组 从 `.trace/trace.log` 独立发现：**

1. **`MOD_AIQA.F_002`（build_agent_prompt·ReAct 每轮 prompt）在 B3 窗口出现 ≥7 次**（21:54:03/09·21:55:00/04/12·22:04:06/16）——**证明 while-loop 确实被触发**。`F_002 = build_agent_prompt`（`prompts.py:604` 注册·ReAct agent loop 每轮 prompt）·只有 while-loop 路径会调用它。

2. **同一 case 内多次 F_002 连续出现**（21:54:03 + 21:54:09 = 2 轮 ReAct·间隔 6s）——这是 **while-loop 多轮**的铁证·不是单次 finalStep。

3. **claude组 漏看了 F_002**——他们只数 `MOD_LLM.F_001`（LLM chat 调用）·发现 msgs=12 恒定·推断"finalStep 单次慢"。但 `F_001` 是 provider-agnostic 的 `LLMClient.chat()`（`llm.py:93`）——**agentStep 和 finalStep 都走 F_001**。区分两者的不是 F_001 的 msgs 数·而是 **F_002（agent prompt）vs F_003（final prompt）** 的出现。

**定案不成立。真实根因仍有 while-loop 退化成分。**

## 一、独立证据（`.trace/trace.log` 直接读取）

### 证据 1：F_002（build_agent_prompt）= while-loop 铁证

```
[TRACE] 21:54:03 | MOD_AIQA.F_002 | [enter]     ← agentStep 第 1 轮
[TRACE] 21:54:03 | MOD_LLM.F_001  | msgs=12     ← agentStep LLM 调用
[TRACE] 21:54:09 | MOD_AIQA.F_002 | [enter]     ← agentStep 第 2 轮（6s 后）
[TRACE] 21:54:09 | MOD_LLM.F_001  | msgs=12     ← agentStep LLM 调用
[TRACE] 21:54:17 | MOD_AIQA.F_003 | [enter]     ← finalStep（退出 loop）
[TRACE] 21:54:17 | MOD_LLM.F_001  | msgs=12     ← finalStep LLM 调用
```

**解读**：同一个 B3 case 内·21:54:03 到 21:54:17 之间有 **2 轮 agentStep（F_002）+ 1 次 finalStep（F_003）** = 3 次 LLM 调用。这是 **while-loop 2 轮 ReAct**·不是"finalStep 单次慢"。

### 证据 2：F_002 在 B3 窗口统计

| 时间 | F_002（agentStep）次数 | 含义 |
|------|:---:|------|
| 21:54:03-09 | 2 | 1 个 case · 2 轮 ReAct |
| 21:55:00-12 | 3 | 1 个 case · 3 轮 ReAct（或 2 个 case） |
| 22:04:06-16 | 2 | 1 个 case · 2 轮 ReAct |
| **B3 窗口总计** | **≥7** | **至少 3 个 case 走了 while-loop** |

### 证据 3：F_001 msgs=12 恒定的误导

claude组 用"F_001 msgs=12 恒定·非递增"推断"不是 while-loop"。**错误**：

- `F_001` 是 `LLMClient.chat()`（`llm.py:93`）——**所有 LLM 调用共用**（agentStep / finalStep / deliberateStep）
- agentStep 的 msgs 数 = system prompt + conversation history。`build_agent_prompt` 的模板结构固定（round + tool_history + context）·渲染后 msgs 恒为 12（不因轮次递增——history 是文本拼接进 context·不是 messages 数组追加）
- **msgs 恒定 ≠ 非 while-loop**。区分 agentStep vs finalStep 的正确判据 = **F_002（agent）vs F_003（final）的出现**

### 证据 4：F_001/F_005 ratio = 1.00（25:25）的误导

claude组 可能据此说"每例 1 次 chat"。**ratio 1.00 是巧合**——F_001(msgs=12) 只统计了 stream=True 的调用·while-loop 的 agentStep 也是 stream=True msgs=12。25 个 F_001(msgs=12) 中·部分是 agentStep（F_002 触发）·部分是 finalStep（F_003 触发）。ratio 1.00 不证明"每例 1 次"。

## 二、修正后的根因定位

**claude组 定案"API 慢时段·与 a04a714 无关"——glm组 判定：partial**

### agree 部分
- API 确实可能慢（部分 case 间隔 100-239s）——DeepSeek Flash 在高峰时段响应变慢是合理的
- 超时=0 排除了 API 完全超时

### disagree 部分
- **while-loop 退化确实发生**（F_002 铁证）——至少 3 个 case 走了 while-loop
- while-loop 退化 + API 慢 = **双重打击**：while-loop 每轮一次 LLM 调用·API 慢时每轮 30-60s·2-3 轮 = 60-180s·叠加 finalStep 30-60s = 90-240s → B3 `waitAnswer(90s)` 超时 → ERR
- **与 a04a714 的关系仍需验证**——glm组 上轮指出的 deriveAvailable stripped 阈值 2→3 + zonal 强制路由可能是 while-loop 退化的触发因素（zonal 强制改 template → validateParams fail → 但 ask_user 而非 while-loop）。如果不是 a04a714 直接触发 while-loop·则是 a04a714 的路由变更 + API 慢的**叠加效应**

### 修正后的根因链

```
a04a714 路由变更（zonal 强制 / deriveAvailable 阈值变化）
    ↓
部分 case 的 template 被改为 zonal·但 boundary 未填
    ↓
validateParams fail → ask_user（非 while-loop）
    ↓ 但...
某些 case 的 _tplHitRateReady() gate 因 template 变更导致命中率统计变化 → gate fail
    ↓
落 while-loop（单技能路径被 gate 挡住）
    ↓
while-loop 每轮 agentStep（F_002）·API 慢时段每轮 30-60s
    ↓
2-3 轮 = 60-180s + finalStep 30-60s = 90-240s
    ↓
B3 waitAnswer(90s) 超时 → ERR
```

**注意**：以上是修正后的推断链·仍需 claude组 用 `git stash a04a714` 重跑确认（glm组 上轮建议的验证方法）。
