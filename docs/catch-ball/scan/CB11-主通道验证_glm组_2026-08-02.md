## 〇、一句话结论

**主通道 A（确定性补全）的方向正确且 Codex 决策评审合理**，但 `buildLanduseCompletion` 的 union 链存在一个**确定的高危 bug（无限循环→OOM 崩溃）**——当用户问"合并商业+居住+公园用地"且三类用地图层都已存在时，浏览器 tab 会被 JS heap OOM 杀死。**这个 bug 三处都有**（`buildLanduseCompletion:1351` / `_deterministicRecover` 模式 A `:1235` / 模式 C `:1300`）。此外，inline 路径的 N/M 完成度判定存在**时序缺陷**（LLM 写结论时看不到部分失败信息）。这两个问题必须在主通道宣布"闭环"前修复。

## 一、五个分歧点的独立判定

### 分歧 1：主通道 A（确定性补全）是否真能根治「只说不做/只做一半」？

**判定：partial — 时序问题已根治，但覆盖面和正确性仍有缺口**

**A. 已根治的部分（agree）**：
- **半成品 answer 时序**（B002 核心）：`a5eb3e1` 在 `runTemplatePath:527-558` 实现了"第 1 步成功→finalStep **前**内联扩展→统一出单次 finalStep"，不再先渲染半成品再后台补。`orchestrate:945` 用 `_inlineExpanded` 标志跳过二次 `_autoExpandOverlays` 防双执行。**这是实质进步，时序问题确实解决了。**
- 45s 总预算兜底（`:538`）：`_inlineDeadline = Date.now() + 45000`，防 4+ 步拖死。Codex 的风险提示（43s 高于 15-20s 预算）被有效缓解。

**B. 未根治的部分（disagree 根治声明）**：

**B.1 🔴 union 链无限循环 bug（新发现·高危·已 Node.js 复现）**

`buildLanduseCompletion`（`harness.js:1351-1357`）：
```javascript
// union 模式：链式两两合并
if (_wantUnion && _tcs.length >= 2) {
  let _chainAs = _tcs[0].params.as;
  for (let i = 1; i < _tcs.length; i++) {   // ← 迭代 _tcs
    _tcs.push({ ... });                       // ← 同时 push 到 _tcs → i 永远追不上 length
    _chainAs = _tcs[_tcs.length - 1].params.as;
  }
}
```

**Node.js 复现结果**（3 个用地图层 → "合并商业+居住+公园用地"）：
```
初始 _tcs: ['商业用地_西陵区', '居住用地_西陵区', '公园用地_西陵区']
→ FATAL ERROR: Ineffective mark-compacts near heap limit
  JavaScript heap out of memory
```

**同样的 bug 还存在于两处**：
- `_deterministicRecover` 模式 A（`:1235-1240`）：`for (let i = 1; i < _tcs.length; i++)` + `_tcs.push()`
- `_deterministicRecover` 模式 C（`:1300-1308`）：`for (let i = 2; i < _mergeMatches.length; i++)` + `_tcs.push()` — 这个**碰巧不无限循环**（因为迭代的是 `_mergeMatches` 不是 `_tcs`），但 push 的 `layer_a` 引用的是 `_tcs[_tcs.length-1].params.as`，在 push 后立刻读取，逻辑正确但极易在后续修改中引入同样的 bug。

**触发条件**：问句含"合并" + 已加载 ≥2 个含 `LANDUSE_KW` 的面层。这是真实用户场景——用户上传了商业/居住/公园三类用地后说"合并这些用地"，直接崩溃。

**修复**（1 行）：
```javascript
// 修复：先算出需要追加的 union 步骤数，用独立循环
if (_wantUnion && _tcs.length >= 2) {
  const _n = _tcs.length;
  let _chainAs = _tcs[0].params.as;
  for (let i = 1; i < _n; i++) {   // ← 固定上界，不跟随 _tcs.length
    _tcs.push({ name: 'overlay', params: { layer_a: _chainAs, layer_b: _tcs[i].params.as, how: 'union', as: 'merged_final_' + i } });
    _chainAs = _tcs[_tcs.length - 1].params.as;
  }
}
```

**B.2 覆盖面窄（agree Codex 分歧 3）**：
inline 扩展只触发 `extract_feature` 首步 + 区/用地模式（`:530` 的正则 `(?:区|市|县|街道|镇).*(?:用地|地块)|.*(?:用地|地块).*(?:区|市|县|街道|镇)`）。以下多步形态在成功路径仍无补全：
- `merge→clip`（合并后再裁剪）
- `filter→density`（先筛选点层再做密度）
- `buffer→zonal`（先缓冲再归因）
- 多区单用地（`extract_feature` where in 双区 → overlay）只在 `_deterministicRecover` 模式 D（失败路径）存在，成功路径 inline 不触发

**B.3 boundaryName 硬编码"西陵"（`:1339`）**：
```javascript
const _boundaryName = _firstLayerName || (_polyLayers.find(
  (l) => l.name.includes('范围') || l.name.includes('边界') || l.name.includes('西陵')  // ← 硬编码地名
) || {}).name;
```
非西陵区场景（如伍家岗区、点军区）若 `firstLayerName` 为空且无"范围/边界"命名的图层，`_boundaryName` 为 undefined → `buildLanduseCompletion` 返回 null → 扩展不触发。这是**地名硬编码泄漏**到通用逻辑的典型问题。

### 分歧 2：`buildLanduseCompletion` 共享函数是否合理收敛？

**判定：partial — 方向正确（消重复），但收敛不彻底且引入了新 bug**

**A. 合理的部分（agree）**：
- 三处（inline `:532` / autoExpand `:1364` / recover 模式 A/C/D）现在共用同一个匹配+构造函数，消除了 Codex 指出的"3 份近似重复"。这是正确的工程收敛。
- 词表 `LANDUSE_KW` 集中到 `emc-patterns.js`，新问法改注册表不改内联正则。

**B. 收敛不彻底（disagree 完全收敛）**：

**B.1 触发入口仍分散**：
- inline 路径（`:530`）：用正则 `(?:区).*(?:用地)` 判断是否进入扩展
- autoExpand 路径（`:1362-1364`）：无条件调 `buildLanduseCompletion`，由其内部返回 null 决定
- recover 路径（`:1216-1217`）：用自己的 `_mentionedLU.length >= 2 && _region` 判断

三处的**触发条件不一致**。同一个问句"西陵区的商业用地"，inline 路径的正则可能不匹配（因为"的"不在正则里），但 recover 路径的 `_mentionedLU.length === 1` 会走模式 D。这意味着同一个问句在 FC 成功 vs FC 失败时走不同的多步逻辑——成功路径不扩展，失败路径扩展。**这不是"同一函数三处共用"，是"同一函数被三套不同触发条件各自调用"**。

**B.2 共享函数引入了 union bug**（见分歧 1.B.1）：原本 `_deterministicRecover` 模式 C 的 union 链是正确的（迭代 `_mergeMatches`），但 `buildLanduseCompletion` 重写时把循环改为迭代 `_tcs` 并 push，引入了无限循环。**收敛反而引入了回归**。

**C. 更优的单一入口建议**：
把触发判断也收入 `buildLanduseCompletion`——由它统一决定"这个问句+这批图层是否需要多步补全"，返回 `{tcs, mode, mentioned}` 或 null。调用方不再各自写正则：
```javascript
// 统一入口（建议）
function tryMultiStepCompletion(ctx, diagnose, firstResult) {
  const _c = buildLanduseCompletion(ctx.question, firstResult?.layerName, { mode: 'auto' });
  if (!_c) return null;
  return _c.tcs;   // 调用方只管执行 tcs，不管触发条件
}
```

### 分歧 3：N/M 完成度判定是否足够？部分失败时 finalStep 是否还可能写出完整结论？

**判定：disagree — 当前实现有确定性的时序缺陷，LLM 仍可能掩盖部分失败**

**A. `runAllToolCalls` 路径（基本足够）**：
- `:1401-1402`：`_failNote`（失败步骤列表）注入 `ctx.context`，finalStep **能看到** → LLM 写结论时有失败信息 ✅
- `:1409-1412`：确定性追加 `> ⚠️ 仅完成 X/Y 步` 在 finalStep 之后 → 即使 LLM 措辞乐观，用户也能看到追加声明 ✅

**B. inline 路径（时序缺陷·disagree）**：

`runTemplatePath` inline 扩展（`:527-558`）：
- `:555-556`：`_inlinePartialNote` 在扩展后赋值
- `:564-568`：`ctx.context` 注入 `_execSummary`——但 `_execSummary` 只描述**主工具**（`def.tool`）的执行结果，**没有**包含 inline 扩展的失败信息
- `:572`：finalStep 调用——LLM 此时**看不到**"2/3 扩展步骤失败"的信息
- `:582`：`_inlinePartialNote` 在 finalStep **之后**追加

**后果**：假设主工具 `extract_feature` 成功（newLayerCount=1），inline 扩展 3 个 overlay 中 2 个失败。finalStep LLM 看到的 context 是"工具 extract_feature 执行成功，产出了 1 个新图层"——它可能写出"已成功裁取并叠置了所有用地"的乐观结论。然后 `:582` 追加"⚠️ 仅完成 1/3 个扩展步骤"。用户看到的是**矛盾文本**：结论说成功了，追加说大部分失败。

**对比 `runAllToolCalls`**：它的 `_failNote`（`:1401`）在 finalStep 前注入 context，LLM 能据此调整措辞。inline 路径**缺这一步**。

**修复**（3 行）：
```javascript
// runTemplatePath :568 之前，注入 inline 扩展失败信息到 context
if (_inlinePartialNote) {
  ctx.context = `【扩展部分失败】${_inlinePartialNote}——结论必须如实说明哪些未生成。\n\n` + (ctx.context || '');
}
```

**C. R4 防线的盲区**：
`applyQualityDefense` 的 R4（`:280-281`）检测 `obsOk && /请求失败|未成功生成/`。但 inline 扩展失败的 observation 是 push 到 toolHistory 的文本（`扩展-X: overlay 异常`），不在 R4 的检测模式里。R4 拦不住"LLM 措辞乐观 + inline 部分失败"的矛盾。

### 分歧 4：命中遥测驱动退役是否可行？

**判定：agree — 机制设计合理，但当前遥测有缺陷**

**A. 设计合理（agree）**：
- `_hitInline` / `_hitAutoExpand` / `_hitRecover`（`:15-17`）三个计数器 + console.log（`:535,1367,861`）——命中可查 ✅
- 退役条件"命中趋零 + LLM 多 call 覆盖"逻辑正确：如果某模式长期 0 命中，说明 LLM 已能处理该场景，规则可删 ✅

**B. 缺陷**：
- **遥测只在 console**：不进 episode、不进持久化存储。用户关掉 tab 后数据丢失，无法做跨会话趋势分析。Codex 提到"进 episode 或 console 可查"——但 console 不够，应至少写入 `localStorage`（仿 `_TPL_STATS_KEY` 模式）。
- **无分模式遥测**：`_deterministicRecover` 有 A/B/C/D 四模式，但 `_hitRecover` 只是一个总数。无法判断"模式 C（union 链）长期 0 命中"——需要分模式计数。
- **无"应该命中但没命中"的漏判遥测**：当前只统计"命中了"，不统计"本该扩展但没扩展"（如分歧 1.B.2 的 merge→clip 不触发）。退役决策需要双向数据：命中数 + 漏判数。

**C. 一个隐患**：
退役机制依赖"LLM 多 call 覆盖该场景"作为前提。但 LLM 多 call 通道（`runAllToolCalls`）目前**几乎不被触发**——Flash 单 call 是常态（07-30 P02 教训），`diagnose._allToolCalls.length > 1`（`:936`）极少成立。如果 LLM 多 call 通道长期不活，退役条件"LLM 多 call 已覆盖"永远不满足，规则永远不会被退役——遥测机制沦为摆设。

### 分歧 5：独立理解和建议——多步执行在 Flash 单 call 限制下如何最稳？

**判定：有未考虑的路径——"后端补全"和"结构化 grounding"值得探索**

**A. 对项目方 A 定型的独立判断**：
A（确定性补全）作为主通道是**当前 Flash 能力下的务实选择**。但它的本质是用**正则规则替代 LLM 的规划能力**——长期来看，正则覆盖面永远追不上自然语言的变体。项目方和 Codex 都认同"B 留待模型换代"，我同意，但补充：**即使模型换代，A 也不应完全退役**——确定性补全作为"快速路径"（0 LLM 轮）有价值，与 LLM 多 call 不冲突。

**B. 未被考虑的路径**：

**B.1 后端补全（推荐探索）**：
当前多步补全在前端 `harness.js` 用正则 + `getLayers()` 实现。但后端已经有完整的 `tool_contracts.py`（含 `exclusive_with` / `composes_with` / `recipes` 字段设计）和 `candidate_selector.py`（0LLM 规则选择器）。**多步规划更适合放在后端**：
- 后端有完整的 contracts 元数据（工具依赖关系、互斥关系）
- 后端 `fcDiagnoseStep` 已经调用 LLM，可以在同一调用中让 LLM 产出多步 plan（`_allToolCalls`）
- 后端不受前端 `getLayers()` 异步状态影响（后端有完整的 layer catalog）

具体路径：FC prompt 增加"若需多步，输出 `tool_calls` 数组（≥2 个）"指令 + 后端校验 tool_calls 合法性（按 `composes_with`）→ 前端 `runAllToolCalls` 执行。这比前端正则更稳健，且是 B 方案的低风险版本（不改 FC 单/多 call 行为，只在 FC 成功时鼓励多 call）。

**B.2 结构化 grounding（Codex 也提到了·族 B 同源）**：
当前 grounding 是文本摘要（`buildContext()` 输出自然语言）。如果改为结构化（每个图层带 `{name, kind, fields:[{name,role}], geometry:'point'|'polygon'}`），FC LLM 能更准确地判断"这个问句需要 clip（有 point）还是 extract_feature（有 polygon）"——从源头减少误选。这与族 B/C 同源（KNOWLEDGE §2 已记录），但对族 A 也有价值：LLM 选对工具 → 第 1 步成功 → inline 扩展才有机会触发。

**B.3 前端多轮 while-loop 兜底（不推荐作主通道）**：
while-loop 的 ReAct 模式理论上能处理多步（每轮 LLM 决定下一步），但：① 耗时高（每轮一次 LLM call·2-4 轮 = 10-20s+）② Flash 概率性失败（每轮 p 概率出错·p^N 放大）③ 用户已反馈"慢"。作为兜底保留合理，作主通道不合适。

**C. 我的综合建议**：
主通道分层（与 Codex 三层定位一致，但补充演进路径）：
```
当下（Flash 单 call 现实）：
  确定性补全（inline/autoExpand）= 主通道 [修 union bug + 补 merge→clip 等]
  LLM 多 call = 机会通道 [几乎不触发]
  _deterministicRecover = 失败兜底 [修 union bug]

中期（后端补全探索）：
  后端 FC 产 _allToolCalls = 主通道 [更稳健·有 contracts 元数据]
  前端确定性补全 = 快速路径 [0 LLM 轮·简单场景]
  _deterministicRecover = 失败兜底

长期（模型换代后）：
  LLM 多 call = 主通道
  确定性补全 = 退役候选 [遥测驱动]
```
