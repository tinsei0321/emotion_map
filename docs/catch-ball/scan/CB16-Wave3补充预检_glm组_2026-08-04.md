## 一、2b 可感知计算器 B 类条件等式

### 1.1 B 类 7 项确认（完整）

glm组 独立分类验证：METRIC_MAPPINGS 18 项中 B 类（`element_top=X` 条件 + 无 polarity_index + 可感知）恰好 **7 项**：

| 指标 | 条件 | 值字段 | 关键词 |

| 15分钟生活圈覆盖满意度 | element_top=设施 | topic_top | 生活圈/买菜/便民 |
| 小区环境品质感知 | element_top=环境 | issue_label | 绿化/卫生/秩序 |
| 物业管理评价 | element_top=服务 | issue_label | 物业 |

**覆盖确认**：claude组 说"6-7 项"——实际 7 项。glm组 验证完整。

### 1.2 `_parse_emc_expr` 拆分方案——**OK（需处理多值条件）**

草案方案：按 `+` 拆 → 识别条件部分（`element_top=X/Y`）与值部分（`field（kw1/kw2）`）。

glm组 验证：B 类 7 项的 `emc_field` 结构一致——`element_top=<值>[/<值>] + <值字段>（<关键词>）`。`_parse_emc_expr` 需处理：

| 结构 | 例子 | 条件值 | 解析 |
|------|------|--------|------|
| 单条件单值 | `element_top=环境 + topic_top（公园/绿地/散步）` | ['环境'] | condition_field=element_top, condition_values=['环境'], value_field=topic_top, keywords=['公园','绿地','散步'] |
| 多条件单值 | `element_top=设施/环境 + issue_label（老旧/破旧）` | ['设施','环境'] | condition_values=['设施','环境']（`/` 拆多值） |
| 多条件多值 | `element_top=服务/文化 + topic_top（商圈/人气/烟火气）` | ['服务','文化'] | 同上 |

**关键**：`element_top=设施/环境` 的 `/` 是"或"语义（element_top 匹配设施**或**环境）——与 `_build_card` 的 `/` "取前者"语义**不同**。`_parse_emc_expr` 必须把 `/` 拆成多值条件列表（不是取第一个）。

**判定**：`_parse_emc_expr` 方案对路·但需明确处理 `element_top=A/B` 的多值 `/`（拆成列表·非取首）。

### 1.3 计算语义——**OK**

| 情况 | 处理 | 判定 |
|------|------|:---:|
| element_top 缺失 | `'暂无数据'` + source `'缺失·不编造'` | ✅ 与 2a 一致 |
| element_top 不匹配条件 | **跳过**（该指标不适用当前要素）| ✅ 正确——不在卡面占位 |
| element_top 匹配 → 值字段缺失 | `'暂无数据'` | ✅ |
| element_top 匹配 → 值字段命中 | 值 + 关键词命中标注 | ✅ |

**"不匹配→跳过"语义正确**——B 类指标是**条件型**（"公园绿地可达性感知"只在 element_top=环境 时有意义）。如果当前分析要素是"设施"·该指标不适用·不应占卡面。这与 2a（极性类·无条件·总是适用）不同——2a 总出值（或暂无数据）·2b 条件不匹配时不出。

### 1.4 source 标注统一建议

**建议**：2b source 标注格式与 2a 一致：
```python
# 2a 当前
'source': 'polarity_index（确定性）·命中：停车难'

# 2b 建议
'source': f'{value_field}（确定性）·条件：element_top={matched_value}' + (f'·命中：{kw}' if kw_hit else '')
```

统一格式 = `值字段（确定性）·条件/关键词标注`——便于前端渲染一致。

| 不满意项定位 | `'issue_label + place_name'` | 不动 | ✅ 已是真实字段 |

### 2.2 `/` 语义需明确——**保持 Wave 1 一致**

`'domain_top/element_top + polarity_index'` 的 `/` 在 `_build_card:194` 被 `split('/')` 解析为**取前者**（domain_top only·element_top 丢弃）。

glm组 运行时验证：
```
Expression: domain_top/element_top + polarity_index
Parsed field_parts: ['domain_top', 'polarity_index']  ← element_top 丢失
```

**判定**：这不是 bug——是 Wave 1 `checkup_dimension` 已建立的行为（`'小区维度': 'domain_top/element_top + polarity_index [scale=meso]'` 同模式）。`/` 在 `_build_card` 中是"优先取前者"（domain_top 更宏观·element_top 更细·优先取宏观）。P2 应**保持一致**——不改 `_build_card` 的 `/` 语义。

**但需在 P2 注释中标注**：`/` = 优先取前者（非两者都取）·与 `_parse_emc_expr` 的多值 `/` 语义不同。

### 2.3 与 checkup_dimension 重复？——**不重复**

| 卡 | 触发 | 卡面 |
|---|------|------|
| checkup_satisfaction | 问句含"满意度" + outlet=报告结论 | 满意度 4 尺度（polarity_index）+ 8 领域（domain_top+polarity_index）+ 不满意定位（issue_label+place_name） |
| checkup_dimension | 问句含"体检" + outlet=生成图层 | 住房/小区/街区/城区四维度（scale 限定·[scale=micro/meso/macro]） |

**不重复**：satisfaction 聚焦"满意度值"（polarity_index 代理满意率）·dimension 聚焦"四维度诊断"（scale 限定）。卡面字段不同·触发的 outlet 提示不同（报告结论 vs 生成图层）。

### 2.4 CI 兼容——**OK**

glm组 运行时验证：P2 改后 `_extract_contract_fields` 提取消费字段 = `{domain_top, element_top, issue_label, place_name, polarity_index}`——全部 ∈ `_EMC_FIELDS` 白名单。`validate_outlet_fields` 不会红。
