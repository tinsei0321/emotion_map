## 第一节：A 出口抽象层六焦点独立判断

### A1 架构位置：分层对·但"新增 prompt 阶段"方向错（⚠️ 核心分歧）

**报告倾向**（出口报告第八节焦点1）：方案 C 分层——"后端 outlet_adapter 产 schema + prompt 层 build_outlet_prompt 渲染自然语言"。

**我的判断：分层正确，但"build_outlet_prompt"这一步应该砍掉。**

**理由（代码证据）**：

1. **定量要素是确定性数据，禁让 LLM 生成**。出口卡片的"定量指标"要素（polarity_index/n_negative/占比/排名）来自 `aggregate_by_polygons` 的聚合产出（`spatial_analysis.py:244-283`，已是确定性数值）。这些数**必须后端纯函数算出**，不能让 LLM 组织语言时编造——这呼应 EMC 已有的诚实约束（`prompts.py:132` 禁编造数字）。让 LLM "渲染"定量 = 引入编造风险。

2. **撞 D019 final 极瘦红线**。CB-09 D019 把 finalStep prompt 砍到极瘦（~0.9KB），`industry_kb_final_brief` 刚补了精简版（限前2域·<5KB 守卫）。若再新增 `build_outlet_prompt` 做"行业对接卡渲染"，等于在 final **之后**再加一个 LLM 阶段——要么撞极瘦红线（outlet 也要精简），要么变成"两层 final"（final 给情绪结论 + outlet 给行业卡 = 答案两层皮）。

3. **正确的架构：outlet 是 final 的结构化伴随产物，非独立 LLM 阶段**。

```
现有 final 链路（不变）：
  tool_history + 聚合图层 → build_final_prompt → LLM → 流式 markdown 结论

新增 outlet 伴随链路（无新 LLM 调用）：
  tool_history + 聚合图层 → 后端纯函数 build_outlet_schema() → outlet JSON
                                ↓
  前端渲染：final markdown（结论）+ outlet 卡片（结构化对接卡）并排呈现
```

**具体实现**：
- 后端 `core/outlet_adapter.py`（新增·纯函数·@track）：消费 `tool_history`（已执行工具的聚合图层字段）+ diagnose card（scale/domain_lens/outlet）→ 产出 `outlet_schema`（JSON：接口标识/定量/地理定位/对接建议/局限标注）。
- 前端 `harness.js`：final answer 流式完成后，用 outlet_schema 渲染"行业对接卡"（类似现有 `{{show}}/{{inspect}}` 内联模板的扩展，或独立卡片组件）。
- **LLM 不参与 outlet 数据生成**，只在 final answer 的自然语言里**引用** outlet 已算好的数（grounding）。

**与报告方案 C 的差异**：报告说"prompt 层渲染自然语言"——我把这步交给前端模板渲染（确定性），不交给 LLM（概率性）。语言组织的"灵活度"损失，换来"定量不可编造 + 不撞红线"的确定性。**对立项演示（要给规划院看硬数）而言，确定性优先于灵活度。**

**反方风险**：若 outlet 的"对接建议/观点"要素需要自然语言组织（如"建议电梯加装>停车位增设"），纯前端模板可能僵硬。**缓解**：这部分可由 final answer 的 LLM 结论承载（final 本就用自然语言给建议），outlet 卡片只放**结构化字段**（任务编号/优先级/数据基础），语言留给 final。即：**outlet 卡 = 结构化数据卡，final 文 = 自然语言结论，两者互补不重叠**。

**报告倾向**：补全 outlet 的接口标识/schema/尺度/所需字段。

**我的判断：同意升级，但禁硬编码为静态 dict。**

**理由**：

### A3 尺度耦合校验层：不需要（❌ 拒新层）

**报告倾向**：问是否需额外尺度校验层（防 macro 卡混 micro 落点）。

**我的判断：不需要。**

**理由**：
1. **已有两层硬约束足够**。`SCALE_PARADIGM`（`paradigm.py:16-50`）注入 diagnose prompt + 前端 `_outletLine`（harness.js）按 scale 强制"宏观禁归因/中微观必落单元/微观必落点"。再加校验层 = 重复维护。
2. **真正的尺度风险不在"校验"，在"模板分派"**。macro 卡片不该有单点 POI——这靠**outlet 模板按 scale 选字段**保证（macro 模板不读 poi_names），而非运行时校验。
3. **schema 自带 scale 标签**即可：`outlet_schema.scale = 'macro'`，前端按 scale 选渲染模板。这是"分派"非"校验"，零运行时开销。

**唯一例外**：若后端 `build_outlet_schema` 算错 scale（如 meso 问句却读了 micro 的 poi_names 清单），需在 schema 产出时 assert。这是一行断言，非"校验层"。

### A5 MVP 范围：报告 S2+S6+S3 偏大·建议先 S2 单场景打穿

**报告倾向**：MVP = S2（更新需求分析）+ S6（体检指标对接）+ S3（时序排序）。

**我的判断：MVP 应更狠——先 S2 单场景打穿。**

**理由**：

### C3 S2 更新需求分析（核心演示）前置能力拆解（🔴 含两报告忽略点）

逐要素拆解 S2 卡片所需数据/能力/依赖：

| S2 卡片要素 | 所需数据 | 现状 | CB-15 依赖 | 出口层自身 |
|---|---|---|---|---|
| 接口标识 | 静态（片区策划·需求分析） | ❌ 出口层缺失 | 无 | 需补 |
| 数据基础 | N/时间窗/L2 聚合 | ✅ point_count + 时间 | 无 | — |
| 定量指标 | polarity_index/n_negative/占比/排名 | ✅ 聚合产出 | 无 | — |
| 地理定位（meso） | 单元名+代表地名+top5 POI | ⚠️ name 有/**place_name 恒空**/poi_names 无 | **CB-15 P0** | — |

| 局限标注 | 数据口径 | ❌ 出口层缺失 | 无 | 需补 |

**🔴 两报告都忽略的硬约束——S2"观点（归因）"要素质量**：

现状 `lookup_attribution`（`spatial_analysis.py:551-558`）是 **DEMO 规则查表**，注释明示"L3/L4 LLM 归因上线后替换"。`_ATTRIBUTION_RULES`（:490-543）是手工写的 `(domain, element, sign) → (label, attr, sug)` 三元组规则，覆盖有限（约 20 条规则 + 1 兜底）。

**对 S2 立项演示的影响**：
- S2 卡片若展示"主要归因：电梯老旧+停车难"，这目前是**规则匹配**（urban_renewal×facility×neg → 某固定 label），**不是**从评论语义深度抽取的归因。
- 风险：若向规划院演示时把 DEMO 规则归因当作"海量真实评估的深度洞察"展示，**过度承诺**——一旦规划院追问"这个归因怎么来的"，规则查表的局限暴露。
- **诚实度要求**：S2 卡片的"观点"要素必须标注归因来源（`attribution_source: demo_rule / l4_llm`）。MVP 阶段（DEMO 规则）标"基于规则归因·L4 深度归因待接入"；L4 deep_attribution 常态化后升级标注。

**S2 完整的前置能力清单（定案）**：
1. **CB-15 P0**（硬依赖）：place_name 双源融合 + 格↔POI sjoin + /grid/pois 端点 → 治"地理定位"要素空
2. **出口层自身**（不依赖 CB-15）：outlet_schema 定义 + OUTLET_CONTRACTS（renewal_demand 契约）+ 前端卡片渲染 + 4×5→更新任务映射 + 局限标注
3. **归因质量**（影响演示诚实度）：现状 DEMO 规则可用但须标注；L4 常态化是质量升级项，非 MVP 阻塞
