## 结论先行（TL;DR）

| 问题 | glm组 判断 | 一句话 |
|---|---|---|
| **①必要性** | ❌ **不必要（现阶段）** | 痛点不是"知识超限"，是"finalStep 被 D019 主动裁"。RAG 解决的不是真问题。 |

**总判定：现阶段不建议建 RAG。** A4 痛点（finalStep 缺行业知识）有**轻 10 倍**的解法——条件选择性注入（见 §3 MVP-Lite）。

### 1.2 注入机制（核心发现·推翻"静态全注入"假设）

**关键**：知识**不是全量静态注入每个 prompt**，而是**分阶段差异化注入**。实测三阶段 prompt 体积：

| 阶段 | 函数 | 实测体积 | 注入的知识 |
|---|---|---|---|
| **diagnose**（FC） | `build_diagnose_prompt` | **23.3 KB** | MANIFESTO 全文 + 尺度矩阵 + 出口范式 + **industry_kb brief** + 工具目录 + B 赛道树 |
| **agent_step**（ReAct） | `build_agent_prompt` | **18.3 KB** | MANIFESTO 全文 + **industry_kb lens_appendix（命中领域）** + 工具目录 + 代码目录 |
| **final/answer** | `build_final_prompt` | **1.4 KB** ⚠️ | **极瘦·仅裸模板** |

**A4 痛点的真正根源（代码定案）**——`prompts.py:166`：
```python
# CB-09 D019 极瘦：去 MANIFESTO 前置（省 11.2KB）+ industry_kb_lens_appendix（省 0-20KB）·17KB→~0.9KB
prompt = _today_line() + FINAL_TEMPLATE.format(tool_history=hist, context=ctx)
```

> **A4 不是"知识超 context window 装不下"，是"D019 瘦身工程主动裁掉的"**。裁它的动机是防 prompt 膨胀（FC + agent 已各占 18-23KB，final 再塞就三段都胖）。这是**工程取舍**，不是容量约束。

### 1.3 基建现状（实测）

| 项 | 实测 | 对 RAG 的影响 |
|---|---|---|
| Python | 3.14.5 | chromadb/faiss wheel 兼容性存疑（Py3.14 太新·2025 末发布） |
| 向量库依赖 | requirements.txt **零**向量/embedding 库 | 全新引入 |
| .env keys | 仅 `AMAP_KEY` + `DEEPSEEK_API_KEY` | 无 embedding 相关键 |
| LLM provider | DeepSeek V4（OpenAI 兼容·`api.deepseek.com/v1`） | flash + pro 双模型 |
| **DeepSeek embedding API** | 🔴 **proposal 阶段（未实现）** | **硬阻塞**（见下） |

**DeepSeek embedding 现状（搜索取证 2026-08-03）**：
- 官方 GitHub Issue #802（2026-02-22）仍是 **proposal**——embedding-aware API **未实现**。
- 第三方（milvus 等）提及 DeepSeek embeddings API，但官方文档未正式列出 embedding endpoint。
- **结论**：EMC 现有 provider（DeepSeek）**无可用 embedding 能力**。要做 RAG 必须换/加 provider（如智谱 embedding-3 / OpenAI / 本地 BGE），意味着新的 API key + 新的依赖链 + 新的故障面。

## 第二部分：四个问题独立评估

### ① 必要性：RAG 解决的是真问题吗？

**判断：否。** 痛点定性错误。

**通俗解释**：RAG 是为"知识太多，context window 装不下"设计的。但 EMC 的情况是——
- 知识总量 150KB，DeepSeek V4 pro 的 context window = **1M**（`llm.py:23` 实测）。150KB 占 15%，**远未超限**。
- 真正的痛点 A4（finalStep 缺行业知识）是**主动裁剪**的结果（D019），不是"装不下"。
- 即使把 industry_kb 全部（42KB）塞进 finalStep，prompt 也才 ~43KB，离 1M 上限差 23 倍。

**所以 RAG 要解决的"知识超限"问题在 EMC 根本不存在**。A4 的本质是"想省 token / 防 prompt 膨胀"与"finalStep 需要领域知识"的矛盾——这是**注入策略问题，用 RAG 是杀鸡用牛刀**。

**A4 的轻解法（选择性条件注入）**：EMC 已有现成模式——`prompts.py:32-34` 的 `_PEOPLE_CITY_LINE` 就是"仅概念问注入"的条件注入。照此模式，给 finalStep 加一个 `_industry_lens_for_final(domain_lens)`：只在 `domain_lens` 命中某领域时，注入该领域的**精简归因框架**（每个领域 1-2KB·非全量 10KB）。这比 RAG **轻 10 倍**，且零新依赖、零检索不确定性。

### ② 价值：RAG 对"体验收敛"是正收益还是负担？

**判断：现阶段负担 > 正收益。**

**负担面**：
1. **检索不确定性**：RAG 的检索是概率性的（top-k 召回可能不准）。EMC 当前是**确定性 GIS + 静态注入 + 代码查表**——三个确定性支柱。引入 RAG = 在确定性体系里塞一个概率性组件，故障面从"工具选错"扩到"检索不准 + 工具选错"。
2. **新故障面**：embedding API 失败 / 向量库损坏 / 索引过期 / 检索质量退化——每个都是新 debug 维度。EMC 刚花两轮（CB-12/13）把 while-loop + pro 收敛，正是**减故障面**的方向，RAG 是反向加法。
3. **延迟**：每次 finalStep 多一次 embedding 调用 + 向量检索（~200-500ms）。EMC p95 50s 里，agent loop 是大头，但 finalStep 加检索会延长感知延迟。

**正收益面（承认存在的）**：
- 若未来 industry_kb 长到 500KB+，全静态注入会真的撑爆中段 prompt——那时 RAG 的"按需检索"才有价值。
- 开放性归因（"这个区为什么消极"）若能检索到该区历史案例/政策语境，结论会更厚。**但这要求知识库先做厚**（当前 4 领域 42KB 太薄，检索出来的也有限）。

**核心矛盾**：RAG 的价值随知识库规模增长而显现，但**当前知识库规模（150KB）远未到 RAG 的收益拐点**。在"体验收敛"的关键期引入一个"现在没用、未来才有用"的重型基建，是**时机错配**。

### ③ 可行性：硬阻塞 + MVP

**硬阻塞**：DeepSeek embedding API 未实现（proposal）。EMC 要做 RAG 必须：
- **方案 A**：加智谱 embedding-3（`embedding-3`·智谱优先铁律契合）→ 新 API key + 新 client。
- **方案 B**：本地 BGE-M3（中文强·开源）→ 无 API 依赖但需模型下载（~2GB）+ CPU/GPU 推理。
- **方案 C**：等 DeepSeek embedding 上线 → 时间不可控。

**Py3.14 向量库风险**：chromadb/faiss 的 wheel 对 Py3.14（2025-11 发布）兼容性存疑。需实测 `pip install`；若失败须降级 Python 或源码编译（高成本）。

**若做的 MVP（最低可行）**——但 **glm组 不推荐现在做**：
1. 向量库：**SQLite + numpy 余弦**（零依赖·200KB 知识量无需 chromadb/faiss 这种重型）。150KB / chunk 化约 50-100 条向量，numpy 暴力余弦 <10ms。
2. Embedding：智谱 `embedding-3`（API·符合智谱优先）。
3. 检索时机：仅 finalStep，按 `domain_lens` 预筛领域 → 该领域内 chunk 检索 top-3。
4. 知识源：仅 industry_kb（paradigm/tool_contracts 是结构化契约·不宜向量化，应继续静态）。

> 但这个 MVP 的复杂度，仍**高于**"条件选择性注入"（§① 轻解法），而收益在当前知识量下不显著。**ROI 不成立**。

### ④ 时机：现在 vs 以后

**判断：现在不做。触发再评估的信号**：

| 信号 | 阈值 | 说明 |
|---|---|---|
| 知识库规模 | > **500 KB** | 静态注入开始挤压 context（尤其中段 agent/diagnose） |
| 痛点转向 | 从"finalStep 缺知识"转为"**选不准**该注入哪块" | 这才是 RAG 的真问题（检索 = 选准） |
| embedding 基建 | DeepSeek embedding 上线 **或** 智谱 embedding 已接 | 消除硬阻塞 |
| industry_kb 结构 | 从"4 领域概览"长到"**多案例/多政策/多时点**"结构化条目 | 向量化才有意义（概览性文本向量化收益低） |

**当前四个信号均未触发**。建议：先把 industry_kb 做厚（CB-15+ 内容工程），届时痛点会自然从"缺知识"演变为"选不准"——那才是 RAG 的入场时机。

## 第三部分：建议方案

### 3.1 推荐路径（按优先级）

**P0·立即（治 A4 真痛点·轻方案）**：条件选择性注入 finalStep
- 仿 `_PEOPLE_CITY_LINE` 模式，加 `_industry_lens_for_final(domain_lens, question)`
- 仅当 `domain_lens` 命中某领域 **且** 问句含归因信号（"为什么/归因/原因/差在哪"）时，注入该领域精简归因框架（每领域 1-2KB·从 industry_kb 提炼，非全量）
- 预期：finalStep 1.4KB → 2.5-3.5KB（仍远低于 D019 的瘦身目标·不回弹）
- 成本：1 个函数 + 提炼 4 段精简框架·**零新依赖**

**P1·近期（知识库做厚·为未来 RAG 铺路）**：industry_kb 内容工程
- 4 领域各补：典型案例 / 政策语境 / 时点对照 / 归因模式
- 这是无论将来是否上 RAG 都该做的（知识是 EMC 的护城河）

**P2·观望（RAG 触发条件监控）**：
- 监控 §④ 四信号
- 信号齐备时再启动 RAG MVP（SQLite+numpy + 智谱 embedding）

**P3·不做**：
- chromadb/faiss（150KB 用不上重型向量库）
- 对 paradigm/tool_contracts 向量化（结构化契约·静态更可靠）

### 3.2 与"体验收敛"的关系

用户原话："今日聚焦 EMC 整体使用体验收敛，收敛前先研究这个环节。"

**glm组 理解**：用户把 RAG 当作"可能影响体验收敛的因素"来排查——这个排查方向**对**（该问），但结论是"RAG 不是收敛的阻碍，A4 才是"。**收敛期应聚焦 P0（治 A4）+ 守住已收敛的 while-loop/pro/多步问**，而非引入新基建。RAG 是收敛**之后**、知识库成长**之后**的事。

## 第四部分：讨论点（架构级）

1. **"确定性 vs 概率性"哲学边界**：EMC 的核心竞争力是"确定性 GIS + 静态权威知识"。RAG 在哪一层引入概率性是可以接受的？（glm组 倾向：仅 finalStep 的"润色性"知识可概率检索；工具选型/参数/数据流必须保持确定性。）
2. **知识库的结构化 vs 向量化**：industry_kb 当前是"概览文本"。若做成"结构化条目（领域×案例×政策×时点）"，代码查表（确定性）可能比向量检索（概率性）更合适——至少在条目数 <1000 时。**结构化优先于向量化**，直到结构化查表的分支逻辑复杂到不可维护。
3. **Embedding provider 统一**：若未来上 RAG，embedding provider 选型应纳入 MCP 策略（智谱优先）。当前硬阻塞（DeepSeek 无 embedding）也是重新审视 provider 矩阵的契机。
