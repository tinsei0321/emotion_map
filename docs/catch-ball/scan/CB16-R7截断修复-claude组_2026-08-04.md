## 第一节：4 环节逐项核验

### ① R7 阈值 1500：✅ 合理

**实测验证**（场景 1·复刻用户多要素结论）：
- 构造 4 要素结论（问题类型/需求强度/需求位置/对接建议·每要素 8 句）= **436 字** → 不触发 R7 ✅
- 交接卡称"实测 p95≈1000"——1500 阈值给 p95 留 50% 余量，合理。

**阈值是否该动态调（多要素 vs 单句）？**
- **不建议动态**。理由：① 结论类型判定本身不可靠（LLM 产出形态多变）·动态阈值引入新风险 ② 1500 固定阈值 + 结构回切已能兼容多要素（4 要素 ~1000 字正常通过）③ 真正的失控长文（>1500）无论单句还是多要素都该截。**固定阈值 = 确定性优先**（EMC 哲学）。

**拦得住失控吗？** 能。场景 2（1600 字）+ 场景 3（1560 字）均触发 R7。1500 对"真失控"（LLM 啰嗦/重复）有效。

### ② 切点结构回切：⚠️ 治住 3/4·漏 markdown 列表标题

**实测 4 场景切点行为**（Python 复刻·与 JS 字符串操作语义等价）：

| 场景 | 输入 | cut 点 | 切点位置 | 判定 |
|---|---|---|---|---|
| 2 | 1600 字·含 `**4.` 标题在 ~410 字（非边界） | 1491 | 切在 `。`（正文句末） | ✅ 正确 |
| 3 | 1560 字·无任何句号 | -1（下限兜底） | slice(0,1500) | ✅ 兜底正确 |
| 4 | 1551 字·`**4.` 标题在 1495（1500 边界） | **1498** | **切在 `**4.` 的 `.` 上** | 🔴 **残留 bug** |
| 5 | 1600 字·中段有 {{show:}} | 1494 | 切在 `。` | ✅ 正确 |

**场景 4 的 bug 复现（精确根因）**：
```
原文: ...xxxxx**4. 对接建议**\n这是第四点的内容。...
                 ^1495  ^1498(切点·落在 4. 的句点)
slice(0, 1498+1) = ...xxxxx**4.
                                    ↑ 结尾是空标题！后面接 _note
最终: ...**4.\n\n…（结论已截断·详见上方图层与数据）
```

**根因**：`final.lastIndexOf('.', 1500)` 把 markdown 有序列表标题 `**4.` 里的英文句点 `.` 当成了句末切点。`Math.max(。,；,\n,.)` 取最大值时，`.` 的位置（1498）> `。`（1399），于是 cut 落在 1498——**正好切在 `4.` 之后，标题保留但内容丢失，复现原 bug**。

**为什么这是真实风险而非理论构造**：
- FINAL_TEMPLATE（`prompts.py`）指导 LLM 用编号结论——`1.`/`2.`/`3.`/`4.` 在结论中**极其普遍**（prompts.py:94-97/301-304 实测多处编号）。
- 多要素结论（4+ 点）接近 1500 字时，第 4 点标题落在 1500 边界是**高概率事件**（非边缘）。
- 用户实测的原 bug 就是「4.\n…（结论已截断）」——场景 4 精确复现了这个症状，说明**原 bug 的根因之一就是这个 `.` 误切**，而修复版**没堵住**。

**下限 750 合理吗？** 合理。场景 3（无句号）cut=-1 < 750 → 走 slice(0,1500) 兜底，正确。750 是"切点不能太靠前"的保护（防切掉大半内容），合理。

**切句符够吗？遗漏什么？**
- `。`（中文句号）✅ 主切点
- `；`（中文分号）✅ 补充
- `\n`（换行）✅ 重要·列表项间分隔
- `.`（英文句点）⚠️ **多余且有害**——中文结论里英文句点本就罕见（除非英文术语），但它会误判 `1.`~`9.` 列表标题。**建议去掉**。
- 遗漏：`！` `？`（中文叹号问号）——可选补充，但结论里少见，非必须。

## 第三节：残留 bug 根因 + 修复建议

### 根因（场景 4·精确定位）

```python
s4 = '前文内容。'*280 + 'xxxxx' + '**4. 对接建议**\n这是第四点的内容。补充内容。'
#     ^1400字              ^1495  ^1498 是 **4. 里的英文句点

final.lastIndexOf('.', 1500) == 1498  # ← 把列表标题的句点当句末！
Math.max(。(1399), ；(-1), \n(-1), .(1498)) == 1498  # ← . 胜出
slice(0, 1498+1) == '...xxxxx**4.'  # ← 空标题残留
```

`lastIndexOf('.')` 设计本意是切英文句末，但 markdown 有序列表标题（`1.`~`9.`）的句点被误判。中文结论里英文句点本就罕见（除非英文术语/小数），**`.` 作为切句符弊大于利**。

### 修复建议（3 选 1·按推荐度排序）

**方案 A（推荐·最简）**：去掉 `lastIndexOf('.', 1500)`
```js
const _cut = Math.max(final.lastIndexOf('。', 1500), final.lastIndexOf('；', 1500),
                      final.lastIndexOf('\n', 1500));
// 去掉 final.lastIndexOf('.', 1500)
```
- 理由：中文结论句末用 `。`·英文句点在中文语境罕见且高误判（列表标题/小数/URL）·去掉净收益。
- 影响：英文长结论可能切不到句末（走 \n 或 750 兜底）·但 EMC 结论以中文为主·可接受。

**方案 B（保守·正则排除数字后句点）**：改用正则找"非数字后的句点"
```js
// 找 1500 内最后一个"非数字+句点"的位置（排除 1. 2. 等列表标题）
const _dotMatches = [...final.slice(0,1500).matchAll(/(?<!\d)\./g)];
const _lastDot = _dotMatches.length ? _dotMatches[_dotMatches.length-1].index : -1;
const _cut = Math.max(final.lastIndexOf('。', 1500), final.lastIndexOf('；', 1500),
                      final.lastIndexOf('\n', 1500), _lastDot);
```
- 理由：保留英文句点切句能力·排除 `数字.` 的列表标题。
- 缺点：lookbehind `(?<!\d)` 在旧浏览器不支持（Safari <16.4）·EMC 前端兼容性需确认。

**方案 C（最稳·只信 `。\n`）**：只保留中文句号 + 换行
```js
const _cut = Math.max(final.lastIndexOf('。', 1500), final.lastIndexOf('\n', 1500));
```
- 理由：最保守·中文结论主切点 = 句号 + 换行·分号/英文点都去掉。
- 缺点：无分号场景可能切点偏前（但 750 下限保护）。

**claude组 倾向**：**方案 A**（去掉 `.`）—— 最小改动 + 净收益 + 无兼容性风险。方案 B 过度工程（正则 lookbehind 兼容性 + 复杂度）。方案 C 略激进（分号也是合法切点）。

### 修复验证（方案 A·复跑场景 4）

```python
# 去掉 . 后重跑场景 4
_cut = max(s4.rfind('。',0,1500), s4.rfind('；',0,1500), s4.rfind('\n',0,1500))
# = max(1399, -1, -1) = 1399
# slice(0, 1399+1) = 切在前一个句号·不落在 **4. → 空标题消失 ✅
```
方案 A 在场景 4 下 cut=1399（切在前一个正文句号），空标题消失，且内容损失可接受（多切 ~100 字）。
