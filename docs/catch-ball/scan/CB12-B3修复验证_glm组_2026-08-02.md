## 三、新发现（非回归·设计 limitation）

### 设计 limitation 1（中）：REGION_KW 拦截宜昌实据问搜索

**现象**：Node.js 复现发现 3 例"实据问应搜索但没搜"：

```
✗ 宜昌市城市更新政策           → null（非 general）·不搜
✗ 宜昌市城市更新的最新策略      → null（非 general）·不搜
✗ 城市更新有哪些典型案例       → null（非 general）·不搜
```

**根因**：`_quickIntent:69` `REGION_KW.some(p => s.includes(p.toLowerCase()))` — `'宜昌'` 在 REGION_KW（`emc-patterns.js:44`）。任何含"宜昌"的问题先被 REGION_KW 拦截 → `_quickIntent` 返回 `null`（落 diagnose）→ 永远到不了搜索分支。

**影响**：用户最可能搜索的正是"宜昌市的 XX 政策/策略/案例"——但这些问题因含"宜昌"被路由到 GIS diagnose（FC 选工具），不触发搜索。搜索的实际触发面被大幅收窄（只覆盖不含宜昌地名的大问题/聚焦问题）。

**严重度**：中——不影响 B3 回归（B3 无"宜昌实据搜索"测试例）。但影响 G6b 搜索能力的实际可用性。

**非本次引入**：REGION_KW 在 G6b 加入搜索前就已存在。是 `_quickIntent` 的优先级设计与搜索触发位置的架构冲突——搜索在 general 短路内·但宜昌问题在 REGION_KW 被拦出 general。

**建议（P2·不阻塞 B3 重跑）**：
- 方案 A：搜索触发位置从 `_quickIntent === 'general'` 内·前移到 `_quickIntent` 之前（先查 SEARCH_KW·再查 REGION_KW）
- 方案 B：REGION_KW 增加条件——含宜昌地名 + 含 SEARCH_KW 实据词 → 不落 diagnose·走搜索
- 方案 C：搜索分支也在 diagnose 失败/fallback 后触发（第二轮机会）

推荐 **方案 B**（最小改动·不改 `_quickIntent` 优先级）：
```javascript
// _quickIntent:69 改为
if (REGION_KW.some(p => s.includes(p.toLowerCase())) && 
    !SEARCH_KW.some(w => s.includes(w))) return null;  // 地名+搜索词 → 不拦·让搜索分支判
```
