### 2. 可感知 10 项计算器：⚠️ 草案低估复杂度（核心子项）

**草案**：解析 emc_field 表达式 → 从 result 取字段 → 计算指标值（极性/主题命中）。

**glm组 关键发现：emc_field 不是简单字段名，是条件表达式·需专门解析器。**

**METRIC_MAPPINGS emc_field 实测分类**（10 项可感知）：

| 类型 | emc_field 示例 | 语义 | 解析难度 |
|---|---|---|---|
| **A. 极性直取**（2 项） | `'polarity_index + domain_top 综合'`（宜居宜业） | 直接取 polarity_index + domain_top | 🟢 易·+ 合成已支持 |
| **B. 条件等式 + 关键词**（6 项） | `'element_top=环境 + topic_top（公园/绿地/散步）'` | element_top**必须=环境** + topic_top/issue_label **命中关键词** | 🔴 难·需表达式解析 |
| **C. 纯关键词 + 极性**（2 项） | `'topic_top（积水/内涝/淹）+ polarity_index'` | topic_top 命中关键词 + 取 polarity_index | 🟡 中·关键词匹配 |

**B 类表达式拆解**（以"公园绿地步行可达性感知"为例）：
```
emc_field = 'element_top=环境 + topic_top（公园/绿地/散步）'

计算逻辑：
  1. 条件判断：result.element_top == '环境'？
     - 是 → 该单元可能涉及绿地·继续步骤 2
     - 否 → 该指标 N/A（非绿地类评论）
  2. 关键词命中：result.topic_top 或 issue_label 是否含 {公园,绿地,散步} 任一？
     - 是 → 命中·指标值 = polarity_index（该单元绿地情绪）
     - 否 → 未命中·指标值 = 空（有环境归因但无绿地关键词）
```

**这远超 build_outlet_schema 的 + 号合成**（:149-160 只做字段取值 + join·不做条件判断/关键词匹配）。需要**新的表达式解析器**：
```python
def _eval_metric_expr(expr, result_row):
    """解析 emc_field 表达式 → 指标值。
    支持：element_top=X（条件等式）+ topic_top（关键词列表）+ polarity_index（直取）
    """
    # 解析条件等式：element_top=环境 → 条件
    # 解析关键词：（公园/绿地/散步）→ 集合
    # 评估：条件满足 + 关键词命中 → 取 polarity_index
    ...
```

**glm组 建议（子项 2 分两步）**：
| 步骤 | 内容 | 理由 |
|---|---|---|
| **2a 首轮（P1）** | 只算 A 类（极性直取）+ C 类（关键词命中·简单）= 4 项 | 解析简单·立即可做·覆盖 40% 可感知指标 |
| **2b 后续（P2）** | B 类条件等式（6 项）·需完整表达式解析器 | 复杂度高·单独迭代·不影响 2a |

**落点 card.perceptible_metrics 合理性**：✅ 合理——出口卡 fields 是行业表单项·perceptible_metrics 是**细粒度体检指标**（可感知 10 项）·两者层次不同·并存合理。

**计算语义建议**：
- 指标值 = **polarity_index**（该单元该主题的情绪值·-1~1）·非"满意度%"（polarity→满意度%需换算·首轮不做）
- 主题命中 = **布尔 + 命中关键词**（如 `命中：绿地`）·让用户看匹配依据
- 缺失（条件不满足/无数据）= `'N/A（非绿地类评论）'`·诚实标注

### 3. validate_outlet_fields CI：✅ 对路·模式现成

**草案**：AST 解析提取 field_mapping + METRIC_MAPPINGS emc_field → 消费字段集合 → 对比产物实际字段。

**glm组 判断：对路·复用 validate_outlet_trigger_sync 的 AST 模式·放 tests/ CI 守卫。**

**模式参考核验**（validate_outlet_trigger_sync.py:22-40）：
- `_parse_py_words`：ast.parse + ast.walk 找 Assign → 提取 tuple/list 常量 ✅
- 同模式可提取 CONTRACTS field_mapping 的字段名 + METRIC_MAPPINGS emc_field 的字段名

**死字段/缺消费判定**：
| 判定 | 含义 | 严重性 |
|---|---|---|
| **死字段** | field_mapping 引用了产物不存在的字段 | 🔴 高（出卡必"暂无数据"） |
| **缺消费** | 产物有字段但 field_mapping 没用 | 🟡 中（字段浪费·非 bug） |

**glm组 建议**：
- 死字段 → **CI fail**（硬错·防回归）
- 缺消费 → **warning**（软提醒·不 fail）
- 放 `tests/validate_outlet_fields.py`（与 validate_outlet_trigger_sync 同级·CI 跑）

**AST 解析的挑战（子项 2 关联）**：
若子项 2 的 emc_field 是条件表达式（`element_top=环境 + topic_top（公园/绿地）`）·AST 提取字段名需**解析表达式语法**（区分字段名 element_top vs 值"环境"vs 关键词"公园/绿地"）。**这和子项 2 的表达式解析器是同一个问题**——建议子项 3 的 AST 提取**复用子项 2 的表达式解析器**（DRY·一份解析器两处用）。
