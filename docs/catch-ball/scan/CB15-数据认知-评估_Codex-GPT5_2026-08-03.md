## 结论摘要（先行）

1. **架构分层：后端空间计算 + 前端联动编排（分层）**。地点认知与格×POI 空间查询天然在后端（geopandas/shapely/4546 都在后端）；前端 ai_qa 只做"工具封装 + 渲染下钻"，不新造空间能力。与现有 `/geo/*` 端点 + tools.js + 契约三处同步的模式完全同构。
2. **触发范式：标准产物轻量预置 + 选中格子按需深查（双层）**。不搞"格子自带全量地点清单"（token/延迟爆炸·违背交互范式）；聚合响应加 `top_places`（前 3-5 POI·聚合期顺带 sjoin 一次算），点/悬停格子再按需查完整清单。对齐 EMC"悬停试探/点击锁定"。
3. **数据接入：3220 孤岛接入运行时（P0）**；`amap_poi_centralcity` 本地重生成（AMAP_KEY 已在 .env）+ 3220 兜底；评论↔POI 用**最近 POI 反查为主 + text 抽取为辅**（复用模拟期 area_seed/spatial_hotspot 标注 schema，不推倒重来）。
4. **配额：网格→地点基本不需要高德**（sjoin + 本地 reverse 即可）；regeo 仅作街道地址增强，走"本地优先 + 批量上限 + lru_cache 放大 + 降级兜底"。
5. **承重：不触碰 diagnose/harness 主循环/ChatRequest**；place_layer/geocode 只读复用、只增不改；新工具/端点走既有注册机制 + 契约三处同步（CB-04 铁律 11）+ 新 F_* ID 连续注册。
6. **拓扑：补"包含/相邻/覆盖"轻量端点**（shapely 现成·行政区邻接表预计算）——包含（POI in boundary）是下钻链核心，P1；相邻 P2。

**总判定：方向正确、基础能力八成已有，缺的是"中间层打通"——建议 P0（下钻链最小闭环）先行，增量落地，与 B3 收敛并行不冲突。**

## 二、六问深入评估

### 1. 架构分层：后端空间查询 + 前端联动工具（分层方案）

**结论：后端管"地点认知与空间计算"，前端管"联动编排与下钻渲染"。**

理由：
- **空间计算全在后端**：shapely/geopandas/pyproj（4546 米制）在 place_layer/spatial_analysis/geocode；浏览器没有等价物。格×POI sjoin、范围×POI 包含、邻接枚举都是后端能力。
- **联动是"分析结论→地点"的空间动作**：格子集合在后端聚合时已产生（grid aggregation），顺带 sjoin POI 是同一坐标系下的免费计算；前端拿到的应是"格子 → 地点清单"结果而非原始空间运算。
- **前端角色 = 编排与呈现**：ai_qa tools.js 加「查地点」「格内地点」工具（薄封装调后端端点）→ LLM 可回答"万达在哪/这格有什么"；UI 面板做"选中格子 → 地点卡片 → 点地点反查评论"的下钻。前端不新造空间逻辑。
- **同构证据**：zonal/compare 已是"后端 `/geo/*` + tools.js 封装 + 契约三处同步"模式，本次只是同类扩展。

落地形态（新增端点，全部落 core + api/routes，守 EMC 委托红线）：
- `GET/POST /geo/places_in_grid`（格 id/geometry → 格内 POI 清单）
- `POST /geo/pois_in_boundary`（范围 → 含 POI + 类别覆盖）
- `POST /geo/topology/adjacent`（边界 → 相邻边界）
- 复用既有 `/place/search`、`/reverse-geocode`（ai_qa 工具直接调）。

### 2. 触发范式：轻量预置 + 按需深查（双层）

**结论：标准产物默认带"轻量地点 hint"，深钻走"选中格子→按需查询"。** 不做"格子自带全量清单"。

理由：
- **全量默认输出不可行**：400m 网格一城数百格 × 每格 POI 清单 → 聚合响应与 LLM context 体积失控（与 CB-09 D019 极瘦方向相悖）；用户只看典型格，全量输出 99% 是噪音。
- **对齐交互范式**：EMC 是"悬停试探/点击锁定"（Overview 指挥台）。下钻链的正确挂点是**格子选中事件**：点格 → 面板显示该格涉及 POI 清单（名称/类别/距离）→ 点 POI → 反查相关评论 → 结论性归因。这既是确定性 UI 路径，也可作为 ai_qa 工具（"这个格子有什么地点/为什么消极"）。
- **轻量预置 = 聚合响应加 `top_places`**：格聚合已算 place_name（单一代表名），增强为 top 3-5 POI 清单（聚合期顺带一次 sjoin，无额外查询成本）→ "分析即得地点 hint，深钻再按需"。与现状 place_name 无缝升级。
- **不引入"每格自动逆地理"**：地点清单靠 sjoin（POI 有坐标，不需要 regeo）——见配额节。

### 3. 数据接入：3220 接入 + centralcity 重生成 + 最近 POI 反查为主

**3220 孤岛 → P0 接入**：`yichang_pois_wgs84.geojson`（已 WGS84、含 address/district/category/keyword）是运行时池（~1434）的天然扩充。接入方式：place_layer 增加该文件为 amap 池补充层（保手标种子与 zone 权威信号优先），forward/reverse 命中面扩大——直接缓解"奥体中心"类中文 POI 解析问题。**承重注意**：place_layer 是搜索栏/弹窗依赖，数据源扩充后 forward 排序可能变化 → 必须跑 `test_link_checkup.py`（20 例四件套）回归 + 用户肉眼。

**centralcity 缺失 → 本地重生成**：`SCRIPT/poi_data/pull_amap_poi.py` + AMAP_KEY（.env 已有）重新拉取中心城区外围 POI；生成前 3220 全量文件可作兜底（覆盖外围）。

**评论↔POI：最近 POI 反查为主 + text 抽取为辅**：
- 主路径：坐标最近 POI 反查（`place_layer.reverse` 已实现 nearest_poi + 500m 近邻计数）——确定性、零 LLM 成本、快。
- 辅助：text 地点抽取（评论文本提地名）用于无坐标/坐标偏离场景——但需地名表匹配（place_layer 词表）+ 防同名多义，只作二级增强。
- **复用模拟期标注**：L1/L2 已带 area_seed/spatial_hotspot/location_mentioned——运行时 ingest 对齐同一 schema 即可，不是推倒重来（报告"模拟期写入"表述正确，缺的是运行时同款写入）。

### 4. 配额/性能：本地优先，regeo 仅增强

**关键洞察：格子→地点清单根本不需要高德 regeo。** POI 有坐标 → 格×POI sjoin（后端 4546 米制，3220 POI × 数百格 = 秒级）+ 本地 `place_layer.reverse`（最近 POI + zone + 近邻计数，0 API 成本）即可覆盖下钻链 95% 需求。regeo 只在"要街道地址/行政补全"时才值得调用。

策略（若批量 regeo 确需）：
1. **本地优先**：批量场景默认只走本地 reverse + sjoin，`source='local'`；
2. **批量上限**：单请求 ≤30 格 regeo、总上限可配（如 200/次分析）；lru_cache 256 → 512 放大（格 id keyed）+ 前端缓存；
3. **降级**：429/超限 → 本地结果兜底（source 标记），提示"街道地址未补全"；现有 `_amap_fetch` 的 429 重试退避已具备，缺的是**显式 QPS 节流器**（批量循环 `time.sleep(0.35)` 级，对齐个人版 QPS~3）；
4. **监控**：加高德调用计数（trace 已有 MOD_GEOCODE.F_004 日志可聚合），超标告警。

### 5. 承重红线：零触碰核心，只增不改

- **不触碰**：diagnose prompt / harness orchestrate 主循环 / ChatRequest schema——新工具走既有注册机制（`SKILL_DEFS` + `TOOL_CONTRACTS` + prompts 工具描述，**契约三处同步**，CB-04 铁律 11），不改诊断/编排核心。
- **place_layer/geocode 只读复用 + 只增不改**：不改现有 forward/reverse 语义；新增数据源为追加层；`@track()` 签名 / `_TRACKING_REGISTRY` 格式不动，新工具/端点注册新 F_* ID（编号连续）。
- **EMC 委托红线**：新端点落 core + api/routes 复用 generate*ForAI 契约模式，不自造样式/绕 dialog；ForAI 入口 = dialog 入口镜像（复用既有样式与参数映射）。
- **改前先扩 eval**：place_layer 改动 → `test_link_checkup.py` 回归；新端点 → pytest + 浏览器验证（含承重路径：搜索栏/弹窗不受影响）。

### 6. 拓扑关系扩展：补轻量枚举（包含 P1 / 相邻 P2）

用户强调"包含/覆盖/相邻必须明确"。现状 sjoin within 可答"包含"（封装端点即可）；缺的是**相邻/覆盖枚举**：
- `pois_in_boundary`（包含）：sjoin within，已有能力封装——下钻链核心，P1；
- `adjacent_boundaries`（相邻）：`行政区.geojson` 9 要素 shapely `touches`（4546 米制 + buffer epsilon）**预计算邻接表**（启动一次，O(1) 查询）→ 答"伍家岗与谁相邻"；
- `coverage`（覆盖）：范围 × POI 类别聚合（"西陵区含哪些公园/商圈"），依赖 3220 池接入，随 P0 可用。

优先级：包含 > 相邻 > 覆盖枚举。不做"范围自由识别"（已定性不关键），拓扑只服务"明确来源"的范围。

## 三、方案初稿与优先级

| 优先级 | 项 | 内容 | 验证 |
|---:|---|---|---|
| **P0** | 下钻链最小闭环 | ① grid×POI sjoin → 聚合响应加 `top_places`（轻量预置）② 选中格子 → 地点清单面板（确定性 UI）+ ai_qa「查地点/格内地点」工具 ③ 3220 POI 并入 place_layer 运行时池 | pytest + test_link_checkup 回归 + 浏览器：生成网格→点格→地点清单→归因结论 |
| **P1** | 评论↔POI 关联 + 归因落点 | 最近 POI 反查（复用 reverse + 模拟标注 schema）；归因→地点结论模板（"该格 issue_label → 涉及 POI → 结论性归因"）；centralcity 本地重生成 | 单例问"滨江公园为什么消极"→ 地点化归因 |
| **P1** | 拓扑包含 | `/geo/pois_in_boundary`（sjoin 封装） | "西陵区含哪些 POI" 问答 |
| **P2** | 拓扑相邻/覆盖 + 批量 regeo 节流 | 邻接表预计算 + coverage 端点；QPS 节流器（如确需街道地址） | "伍家岗与谁相邻" 问答 + 批量性能 |

**明确不做**：POI 归因分析（POI 不是分析主体，只是落点）；范围自由识别（不关键·request_upload）；格子全量地点清单默认输出。

## 五、判定

- **可行且有价值**：两个定性与"让宏观结论落到具体地点"的价值主张一致；基础能力八成已具备，缺的是"中间层打通"——不是从零建，是接线。
- **优先级**：P0 下钻链最小闭环（sjoin top_places + 选中深查 + 3220 接入）先行，P1 评论关联/归因落点/拓扑包含，P2 相邻/覆盖/节流。
- **承重**：零触碰 diagnose/harness/ChatRequest；place_layer/geocode 只增不改；新能力走契约三处同步 + 连续追踪 ID + eval 先行。
- **与体验收敛**：增量落地（P0 独立可测），不与 B3 收敛冲突；反而补上"中微观标准出口"这一产品价值核心。
