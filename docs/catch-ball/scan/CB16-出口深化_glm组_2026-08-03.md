## 二、6 焦点逐条回应

### A. 结果范式 agent 架构

#### A1. 后端确定性组装 vs prompt 层 vs 分层

**判定：agree 方案 C（分层）·但简化执行路径**

报告倾向方案 C（后端 `build_outlet_schema` + prompt 层 `build_outlet_prompt`）。glm组 **agree 方案 C 的分层原则**·但建议简化：

```
推荐执行路径（最小可行）：
  后端 build_outlet_schema(diagnose, analysis_result) 
    → 查 outlet_kb 契约 → 填 field_mapping → 产出结构化 outlet_card JSON
  前端 panel.js 渲染 outlet_card（markdown 卡片·不调 LLM）
  
  不新增 build_outlet_prompt（不撞 D019 finalStep 红线）
  不新增 LLM 阶段（outlet_card 是确定性组装·LLM 只在 finalStep 已经出了图/数/观点）
```

**理由**：
- outlet_kb 已有完整的 field_mapping（行业表单项→EMC 字段）——确定性组装就够了
- finalStep 的 LLM 结论（三句骨架+归因）已经包含了"观点"——outlet_card 只是把结论**重新格式化**为行业卡片（加接口标识/数据基础/局限标注/对接建议）
- 新增 LLM 阶段 = 撞 D019 + 增延迟 + 增不确定性——outlet_card 的价值在于**确定性**（每次问相同问题出相同卡片）

**风险**：不新增 LLM 则"对接建议"（如"建议优先级：电梯 > 停车 > 绿化"）只能从 field_mapping 确定性排序（polarity_index 降序）·不能自然语言组织。**但这正好是"诚实"的——确定性排序比 LLM 编造的"建议"更可信**。

#### A2. outlet_id 映射

**判定：agree 诊断卡 outlet 7 值→OUTLET_CONTRACTS 映射·但需扩展 outlet 枚举**

当前诊断卡 `outlet` 字段 7 值（生成图层/地图定位/指标排序/报告结论/建议清单/预警/执行操作）是**前端交互类型**·不是**行业接口标识**。OUTLET_CONTRACTS 的 key（如 `renewal_demand`/`checkup_satisfaction`）是行业接口标识。

**映射方案**：
```python
# 诊断卡 outlet（前端交互类型）→ outlet_id（行业接口）映射
OUTLET_MAPPING = {
    '指标排序': 'renewal_sequence',           # 排序 → 更新时序
    '报告结论': 'checkup_satisfaction',       # 报告 → 满意度调查
    '建议清单': 'renewal_demand',             # 建议 → 需求摸排
    '生成图层': 'renewal_object_identify',    # 图层 → 更新对象识别
    # '地图定位'/'预警'/'执行操作' → 暂无行业接口映射（前端交互专用）
}
```

**加上 domain_lens + scale 联动**：
- domain_lens=urban_renewal + scale=meso + outlet=建议清单 → `renewal_demand`（需求摸排）
- domain_lens=urban_checkup + scale=macro + outlet=报告结论 → `checkup_satisfaction`（满意度调查）

#### A3. 尺度校验

**判定：agree 模板分派（不需额外校验层）**

OUTLET_CONTRACTS 已含 `scales` 字段（如 `renewal_demand: ['meso', 'micro']`）。`build_outlet_schema` 组装时检查 `diagnose.scale ∈ contract.scales`——不匹配则不组装（或降级为通用卡片）。这是**模板分派**（contract 自带尺度约束）·不需要额外校验层。

现有 R10/R11（applyQualityDefense 尺度防线）守的是 finalStep 结论·outlet_card 是 finalStep 之后的确定性组装——**R10/R11 先过滤·outlet_card 再分派**。两层不冲突。

### B. outlet_kb 接入

#### B1. 出口卡片字段→官方三类指标对应

**已验证**：outlet_kb 的 21 个 METRIC_MAPPINGS 已经做了对应——10 可感知 + 3 可评价 + 5 可量化 + 3 特色。每个映射含 `industry`（官方指标名）+ `emc_field`（EMC 字段）+ `can`/`cannot` 双栏。

**glm组 建议**：加一个**组装示例**（从 zonal_stats 产出的 FeatureCollection → 提取 properties → 填入 outlet_card）——让开发者知道"数据怎么流"：

```python
# build_outlet_schema 组装示例
def build_outlet_schema(diagnose, analysis_result):
    contract = get_outlet_contract('renewal_demand')
    card = {'interface': contract['industry_interface'], 'scale': diagnose.scale}
    for industry_field, emc_field in contract['field_mapping'].items():
        card[industry_field] = extract_emc_value(analysis_result, emc_field)
    card['局限标注'] = contract['boundary']
    card['对接任务'] = contract['task_link']
    return card
```

#### B2. 可感知 10 项全量罗列

**已确认完整**：urban_checkup_outlets.py 的 METRIC_MAPPINGS 含全部 10 项可感知指标（公园绿地可达/养老托育/内涝/生活圈/小区环境/停车/物业/老旧街区/商圈活力/宜居感知）。每项有 `can`/`cannot`。

**glm组 建议**：10 项可感知指标目前是**映射**（定义对应关系）·但**没有自动组装**——即 `build_outlet_schema` 不会自动把评论按 10 项分类。需要一个**可感知指标计算器**：

```python
def compute_perceptible_metrics(analysis_result):
    """从聚合产物计算 10 项可感知指标值。"""
    metrics = {}
    for metric_id, mapping in METRIC_MAPPINGS.items():
        if '可感知' in mapping.get('industry', ''):
            metrics[metric_id] = extract_by_topic(analysis_result, mapping['emc_field'])
    return metrics
```

这是 P1 工作（需要 topic 分类引擎支撑·已有 `topic_top` 字段）。

#### B3. 案例库支撑

**已确认**：case_library.py 含 5 案例 × 三段式（survey/emc_angle/benchmark）+ indicator_link + summary。用于出口卡片组装时引用佐证 + 演示依据。

**glm组 建议**：案例目前是**静态引用**（组装卡片时 `get_case('yichang_wangzhou')` 取数据贴入）。未来可加**动态匹配**（据 domain_lens + scale 自动选最相关案例）——但 v1 静态引用足够。

### D. MVP 范围

#### D1. 先 S2 打穿 vs 多场景

**disagree 报告建议的三场景并行（S2+S6+S3）·建议只打穿 S2**

报告建议 MVP = S2（需求分析）+ S6（体检对接）+ S3（时序排序）。glm组 **建议 MVP = 只 S2（更新需求分析）一个场景打穿**——理由：

1. **打穿 = 全链路验证**：S2 从意图判断（meso/micro）→ 工具执行（zonal_stats + 网格聚合）→ outlet_kb 组装（renewal_demand 契约）→ 前端渲染（需求分析卡）——一条链跑通·证明"出口抽象层"可行
2. **三场景并行 = 分散资源**：S6（体检对接）需要四尺度全覆盖（macro+meso+micro）·S3（时序排序）需要多单元对比——都是 S2 之上的扩展。先打穿 S2·再扩展 S6/S3 是更稳的路径
3. **立项演示**：一个**完整的 S2 需求分析卡**（图+数+表+观点+接口标识+局限标注）比三个半成品场景更有说服力——"看·情绪地图的分析结果直接填进了片区策划的需求分析表"

**但**：S2 的 meso 路径（社区单元 zonal）已有成熟工具支撑（zonal_stats L=1 稳定）·可以立即做。S2 的 micro 路径（网格落点）需 CB-15——先做 meso。

#### D2. 最小闭环

**agree 报告的图/数/表/观点四要素**·补充具体字段：

| 要素 | 来源 | S2 具体字段 |
|------|------|-----------|
| **图** | 结果 agent 产出 | 极性面图层（社区单元着色）+ {{show:图层名}} |
| **数** | 聚合产物 properties | polarity_index + n_negative 占比 + 需求类型分布 |
| **表** | outlet_card（确定性组装） | 需求分析卡（接口标识/数据基础/定量/归因/定位/建议/局限） |
| **观点** | finalStep LLM 结论 | 归因（domain_top/element_top/issue_label）+ 对接建议 |

### E. 承重与风险

#### E1. 不触碰 diagnose/harness/ChatRequest

**agree**——outlet_kb 是**纯新增**（`ai_qa/outlet_kb/` 新目录）·不改 diagnose prompt / harness orchestrate / ChatRequest schema。`build_outlet_schema` 是新函数（在 finalStep 之后调用）·不碰承重路径。

**但**：outlet_card 的渲染入口需要在 harness orchestrate 的 finalStep 之后加一个调用点——这是**控制流新增**（不是修改现有控制流）。需确认这不撞"harness orchestrate 主循环"红线。

**建议**：outlet_card 组装放在 `applyQualityDefense` 之后（finalStep + 防线完成 → outlet_card 组装 → onFinalDone 渲染卡片）。这是**出口段·非承重段**——在现有四态出口之后追加·不改四态裁定。

#### E2. D019 finalStep 红线

**agree 不新增 LLM 阶段**——outlet_card 是确定性组装（build_outlet_schema 查 outlet_kb）·不需要 LLM。finalStep 的极瘦 prompt（~1KB）不动。outlet_card 在 finalStep 之后组装·是**后处理**·不是 finalStep 的一部分。

**S2 归因 DEMO 规则诚实标注**：agree——outlet_card 的"局限标注"要素（contract.boundary）是确定性的（来自 outlet_kb 契约·不是 LLM 编造）。这是诚实标注的制度化。

### F. 出口驱动开发（核心逻辑链）

#### F1. 逻辑链评估——**agree 方向·但需"出口验证闭环"**

报告提出的"出口驱动开发"逻辑链（出口→分析方法→计划→执行工具→图例样式→出图范式）是**正确的开发方法论**——每个 EMC 开发决策都应先问"这服务哪个出口的哪张表"。

**glm组 补充**：逻辑链需要**一个验证闭环**来落地——不能只是理念·要变成可执行的流程：

```
出口驱动开发验证闭环（建议）：
  1. 定义出口卡片（outlet_kb 契约·已有 7 契约）
  2. 反推所需字段（field_mapping·已有）
  3. 验证字段可产出（analysis_result.properties 是否含所需字段·测试断言）
  4. 验证卡片可组装（build_outlet_schema 产 outlet_card JSON·测试断言）
  5. 验证卡片可渲染（前端 panel.js 渲染 markdown 卡片·浏览器验证）
  6. 验证卡片对接行业（出口卡片字段与行业表单一一对应·人工审核）
  
  → 闭环完成 = 出口驱动开发落地·后续每个新出口都走这 6 步
```

#### F2. 每个开发决策先问"服务哪个出口"

**agree·但需避免过度约束**——不是所有开发决策都需要出口驱动。基础设施类工作（CB-15 数据认知/性能优化/bug 修复）不应被"出口驱动"阻塞。出口驱动适用于**新增功能**（新工具/新图例/新文本范式）·不适用于**基础设施维护**。

**建议**：出口驱动作为**新功能评审检查清单**（非全量开发门禁）：
- 新增工具？→ 先问"服务哪个出口的哪张表"
- 新增图例？→ 先问"这图例服务哪个出口的'图'要素"
- 新增文本范式？→ 先问"这文本服务哪个出口的'表/观点'要素"
