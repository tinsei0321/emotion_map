## 一、claude组 三假设验证

### 假设 1：搜索分支绕过 EMC 管线 —— **成立（代码级确认）**

- `harness.js:882-900`：general 短路命中 `SEARCH_KW` → `fetch('/api/v1/aiqa/search')` → `_draft = _data.answer`（搜索模型综合回答）→ **直接 `hooks.onFinalDone(_draft)`**；
- **未调 finalStep**（无排版/三句骨架/人民城市背景/4×5 结构）**未调 applyQualityDefense**（R1-R11 全部跳过）——`return {defense:{degraded:false, skipped:'quick-search'}}`；
- 影响：B3 的 UI-L02/RST-L05（概念问含"情绪地图"）输出裸搜索文本——破坏排版/生动专业（依据 2）、R9 防线失效；与假设描述一致（精确说：`search_chat` 返回的是搜索模型的**综合回答 output_text**，非"原文"，但确实是未加工裸文本）。

### 假设 2：SEARCH_KW 过宽 —— **成立**

- `emc-patterns.js:37`：`SEARCH_KW` 含 `'情绪地图'`，而 `CONCEPT_KW`（什么是/含义/解释/定义）**未被排除**——`harness.js:884` 只排除了 `INVENTORY_KW`；
- "什么是情绪地图的 4×5 归因矩阵？"（UI-L02/RST-L05）→ `_quickIntent` 判 general（'什么是'）→ SEARCH_KW 命中 → 触发联网搜索——**项目内部概念问（4×5 是私有矩阵）用 web 搜索答，语义上必然错误**（搜索无此私有概念）；
- 用户需求（依据 2）是"大问题要结合前沿政策需搜索"——应只服务**实据型**问题（政策/趋势/新闻/案例/宜昌实际），非概念问。

### 假设 3：后端旧代码 / episode 404 —— **部分成立，且比 claude组 判断更严重**

- **episode 404 不是"serve 早于修复"，是已提交回归**：`1362167` 把 `@aiqa_router.post('/aiqa/episode')` 装饰器**删除**（diff 确认：SearchIn 类替换了装饰器行，`def post_episode` 变成无路由函数）；当前工作树的装饰器恢复是**未提交改动**（`git status`: `M api/aiqa_routes.py`；`git diff` 显示 `+@aiqa_router.post('/aiqa/episode')`）；
- 含义：**任何从 git 提交状态启动的 serve 都没有 episode 路由** → 404×34 是代码缺陷不是运维问题；修复必须提交，否则换机/拉取即复现；
- 对"旧后端"推断的连带影响：若 B3 serve 运行的是 1362167 **之前**的代码 → `/aiqa/search` 也 404 → 前端 fallback finalStep（快）；若运行 1362167 **之后**的代码 → 搜索生效（可慢到 90s）。**两种后端状态下"每例 60s+"的来源不同**——需确认 B3 run 时 serve 的代码版本（见待补信息）。

## 二、claude组 未列出的根因（补充）

### 根因 4：前端 search fetch 无超时（`harness.js:884`）

- 裸 `fetch('/api/v1/aiqa/search')` 无 `AbortController`；后端 `search_chat` 超时 90s + `MAX_RETRIES` 指数退避（`llm.py:424-477`）——命中搜索的用例最坏可等 90-180s；
- 与"每例 60s+"直接相关：**即使只 2 个 B3 用例命中搜索，也会显著拖长 run 总时长**。

### 根因 5：概念问语义错配（本地知识 vs 联网搜索）

- "什么是情绪地图的 4×5 归因矩阵"必须用**项目本地知识**答（私有概念、四领域归因矩阵），web 搜索给的是通用"归因矩阵"——即使不慢，答案也错；
- 修复方向：搜索只触发**实据型问句**（含政策/新闻/趋势/案例/宜昌地名等），`CONCEPT_KW` 命中一律本地 finalStep。

### 根因 6：B3 环境敏感性 + 回归门错位

- `aaa8319` commit message 已自注"API-slow env unreliable, checkup suite as regression gate 20/20 PASS"——**团队已知 B3 受 API 延迟支配**；
- B3 = 25 例 llm × 90s waitAnswer 串行 ≈ 30-40 分钟/run；API 慢时普遍 60s+ 是环境特性，不是单次代码回归；搜索叠加后更不可用；
- **回归门错位**：B3 不应作每 commit 回归门；确定性 checkup 套件 + B0 no-llm 才是回归门。

### 根因 7：信号级断言空窗（既有，但被 B3 大失败放大）

- `report-2026-08-02-01-llm.md`：RST-L02（compare 用例）与 RST-L03（clip 用例）**tpl=zonal、tools=zonal_stats**——路由错（答非所问）却判 OK（断言只看 badge/层数，`test-cases.js:339-340`）；UI-L03 断言恒 `pass:true`（只 review）；
- 含义：**B3 的"13/25 通过"里已有 3-4 个假阳性**——信号级断言无法区分"工具对了"与"工具错但出了层"。这是既有断言质量问题，B3 大失败是暴露面不是起因。

### 根因 8：claude组 的 19/25 与磁盘报告不一致

- 磁盘最新 B3 报告为 `report-2026-08-02-01-llm.md`（00:47）：**n=25 pass=13（52%）**，fail 12 = CPD-L01/L02（2）+ PRM-01~10（10）——与 08-01 的失败模式相同（PRM 未因 CB-12 derive 改善，且该 run 在 aaa8319 01:24 之前）；
- claude组 声称的 19/25（OK 1/ERR 18）**未落盘**——无法从磁盘核验其逐例构成；需 claude组 提供该 run 的报告或逐例清单（见待补信息）。
