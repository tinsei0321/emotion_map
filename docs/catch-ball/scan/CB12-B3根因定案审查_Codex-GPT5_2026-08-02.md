## 一、定案证据链验证

### 验证 1：F_001 每例 1 次 → 无 while-loop —— **agree（逻辑成立）**

- `MOD_LLM.F_001` = `LLMClient.chat`（非 FC，`llm.py:93`）——diagnose/agent_step/answer 等 SSE 阶段共用；`MOD_LLM.F_005` = `chat_with_tools_stream`（FC，`llm.py:208`）；
- 每例 F_001=1 → 只有 finalStep 一次 chat（agent_step 会加 F_001）→ **确证无 while-loop** ✓；
- 附带：F_001=1 同时排除 gate 假说（gate 关闭会 while-loop → F_001>1）✓。

### 验证 2：F_001 间隔 105-125s 的精确性 —— **partial（需用 [exit] 时长列）**

- `trace_log` 有 `[enter]/[exit] | Xms` 时长列（tracker 日志格式）——**单次调用时长应读 F_001 的 [exit] 时长，而非 enter→enter 间隔**；
- enter 间隔 = 本次 finalStep 时长 + 下一例 FC(F_005) + 工具时长——在 API 慢窗口，下一例 FC 也可能被拖慢（只要 <12s 不 abort）；
- **建议**：若 log 中 F_001 [exit] 显示 100s+ → 定案直接成立；若只有 enter 间隔 → 需减掉下一例 FC/工具时长。这是定案唯一需要再精确的点。

### 验证 3（关键修正）：timeout=0 与 105-125s 的自洽机制 —— **claude组 链写错，实际是 45s 客户端超时 + 降级结论**

- 前端 answer phase 超时 = **45s**（`api.js:34` `opts.phase === 'answer' ? 45000`），**不是 90s**；
- 正确链：后端 F_001 调用 105-125s（服务端跑完·烧 token）→ **客户端 45s abort** → `finalStep` 抛错 → `_composeDegradedConclusion` 降级结论（`harness.js`）→ 答案仍"到达" → `waitAnswer` 返回 done → **timeout=0** ✓ 自洽；
- claude组 写的"waitAnswer(90s) 超时前未完成 → ERR"**与 timeout=0 矛盾**——90s 超时下 105s 的调用必然计 timeout；实际机制是 45s 客户端放弃 + 降级结论（所以 ERR 是"降级/内容错"而非"超时"）；
- **根因方向不变**（API 慢 → finalStep 后端慢），但"为什么 timeout=0"的解释要改为 45s 超时链。
