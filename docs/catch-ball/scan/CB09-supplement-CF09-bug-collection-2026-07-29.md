## 第二部分：根因分类与分析

### 2.1 复现确认（4 个·与 CB-09 v1.0 根因一致）

#### B002 / B004：finalStep 假结论（同 C3 根因）

**表现**：结论文本详细描述了工具执行结果（图层名、数据量），但实际图层未生成。

**根因确认**：`harness.js:523` 的 finalStep context 仅注入计划描述（「单技能路径·已执行 extract_feature」），不区分执行成功/失败。LLM 基于"计划已执行"的前提，将推理出的信息当作事实写入结论。

**新洞察**：B004 的结论文本中出现了精确数字"1,247 条"——这个数字来自 grounding context 中积极情绪点层的统计信息。这揭示了假结论的**生成机制**：LLM 从接地上下文中提取事实数据（如"积极情绪点 9,922 条"），结合空间范围（"西陵区约占 12.6%"），推算出"1,247 条"并写入结论——整个过程看起来非常"真实"但完全是推理产物。

**严重度升级理由**：CB-09 v1.0 中 C3 为单案例，本次 3 个独立场景均触发同一根因（B002/B004/B005），证明这是**系统性问题**而非偶发。且 LLM 的"合理推算"能力使假结论更加难以识别——数字看起来精确可信。

#### B003：LLM 推理螺旋（同 C2 根因）

**表现**：简单数据查询问句（"我上传了哪些数据？"），LLM 经历 7 轮判断→推翻→重新判断的推理螺旋。CB-09 v1.0 C2 中答错了（声称"没有上传任何数据"），本次答对了但耗时异常。

**根因确认**：接地上下文缺数据来源标注（user-uploaded vs system-preset），LLM 无法直接判断哪些是用户上传的数据，只能用推理猜测。

**新洞察**：两次测试（C2 + B003）呈现了同一根因的两种结果——C2 答错（推理螺旋后猜错），B003 答对但慢（推理螺旋后猜对）。这说明**结果正确不能掩盖根因**：只要接地上下文信息缺失，LLM 就必定进入推理螺旋，只是碰巧猜对还是猜错的区别。

#### B005：多步链执行断裂（C1 推理螺旋 + C3 假结论 叠加）

**表现**：Step 1（extract 西陵伍家岗范围）成功执行，Step 2（clip 商业用地）未被触发，finalStep 写出完整假结论。

**根因一（复用 C1）**：FC 单工具限制 + plans[] 多步执行机制不保证所有步骤完成。Step 1 返回后，系统可能认为"已完成"而未继续执行 rank=2+ 的步骤。

**根因二（复用 C3）**：finalStep 无执行结果感知——即使 Step 2 未执行，finalStep 仍基于 plans[] 写出完整结论。

**复合性**：这是一个典型的"两段式失败"——先有编排层断裂（plans 执行不完整），再有表达层遮掩（finalStep 假结论掩盖了断裂）。两者各自都是已知问题，但叠加后更难发现——用户看到完整结论，不会怀疑中间步骤缺失。

#### B007：图层类型混淆（C4 层引用幻觉的变体）

**表现**：结论文本称产出"面层"，实际产出为"点层"。

**与 C4 的异同**：
- C4：LLM 编造了不存在的图层名（名称幻觉）
- B007：LLM 引用了存在但类型错误的图层（类型混淆）

**根因**：接地上下文中图层信息缺少**几何类型标注**（point/polygon/heatmap）。当多个图层名称相似时（如"用地_商业"和"商业情绪点"），LLM 在填 `layer` 参数时可能选错层。此外，工具层缺少「图层类型一致性校验」——clip 面层应产出面层，clip 点层应产出点层，类型不匹配时应有明确报错而非静默接受错误类型。

### 2.2 新发现（3 个维度·CB-09 v1.0 未覆盖）

#### B006-A：意图缩窄（Scope Misinterpretation）

**表现**：用户问"筛选出西陵区的情绪点"（无极性限定），LLM 自行决定只裁剪积极情绪点（"数据最多，给用户直观感受"）。

**根因**：LLM 的"过度帮助"偏误——面对模糊需求时，倾向选择"最安全/数据最多"的选项而非"最完整"的。FC system prompt 缺少"未限定极性时默认全极性"的指引。

**与已知问题的区别**：这不是 CB-09 中"NL vs 胶囊路径差异"（追问路径选择问题），而是**初始意图理解阶段的自主缩窄**。

#### B006-B：图层样式不匹配（Symbology Propagation 缺失）★ 新维度

**表现**：用户明确指出"筛选出的情绪点并未按照标准图例进行样式匹配。这是个大问题，所有生成的图层都要严格匹配我制作的图例和成图样式。"

**根因**：当前 `clip` / `extract_feature` 等工具生成图层时使用默认样式，未继承源图层的图例配置。缺少"样式传播"（symbology propagation）机制——新图层应保持与源图层相同的视觉语言（颜色映射、符号大小、透明度等）。

**影响面**：这不是 B006 独有的问题——所有工具生成的图层都可能存在样式不匹配。这是一个**跨工具的架构性缺陷**。

#### B008：网格聚合 2D/3D 视角未解耦 ★ 新维度

**表现**：用户标记为"老 bug，一直没修好"。无论当前地图是 2D 还是 3D 视角，网格聚合始终生成 3D 柱状图。

**根因推断**：
1. 图层生成时未读取 MapLibre 当前视角状态（`map.getPitch()` / `is3D`）
2. 前端渲染层与工具层未共享视角上下文
3. 样式配置中 2D（`fill`）和 3D（`fill-extrusion`）未分离，硬编码为 3D 渲染

**解耦方向**：
- 工具触发网格聚合时，传入当前 `viewMode: '2d' | '3d'`
- 图层生成器根据 `viewMode` 选择 MapLibre layer type（`fill` vs `fill-extrusion`）
- 图例系统定义 2D 和 3D 两套独立样式配置

## 第六部分：讨论点

### D1：finalStep 假结论为何成为"万恶之源"？

本次 7 个 bug 中有 3 个（B002/B004/B005）直接指向 finalStep 假结论，加上 CB-09 v1.0 的 C3，共 4 个案例。这不是偶然——finalStep 假结论具有**放大效应**：

```
工具执行失败 → finalStep 无感知 → 编造结论 → 用户看到"成功" → 不报 bug → 问题隐藏
```

而其他 bug（如工具选错、参数填错）会直接暴露（报错/空白图层），用户会立即反馈。finalStep 假结论则**系统性掩盖了所有上游失败**，使 bug 发现链断裂。

**建议**：P0-4（finalStep 注入执行结果）应作为最高优先级，先修这个，才能看到其他 bug 的真实全貌。

### D2：样式匹配是"最后一个短板"

B006-B 暴露的样式不匹配和 B008 的 2D/3D 未解耦，都属于"功能已实现但呈现不达标"的层次。它们不影响分析正确性，但**严重影响用户信任**——当用户看到生成的图层"长得不一样"时，会对整个系统的可靠性产生怀疑。

**建议**：N1（样式继承）和 N3（2D/3D 解耦）虽排 P1/P2，但应在 finalStep 修复后尽快处理——一个"诚实但样式不对"的系统比一个"撒谎但样式对"的系统好，但目标是两者都达标。

### D3：Bug 采集飞轮的价值验证

本次 CF-09 采集验证了飞轮模式的有效性：

1. **标准化**：7 个口语化描述 → 7 个结构化测试用例（TC-21~TC-27）
2. **关联分析**：自动识别出 4 个复现 + 3 个新发现
3. **优先级重排**：基于复现频率将 P1-1 升至 P0-4

如果继续用手工方式跟踪，B002/B004/B005 可能被当作 3 个独立 bug 分别处理，而不会发现它们指向同一个根因（finalStep）。
