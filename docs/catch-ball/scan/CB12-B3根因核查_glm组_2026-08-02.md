> **方法**：逐函数读码（harness 搜索分支 → emc-patterns SEARCH_KW → llm.py search_chat → test-cases.js B3 断言）+ 信号链路分析

## 〇、一句话结论

**claude组 的三根因诊断基本正确**——搜索分支绕过 finalStep+防线 是 B3 断言失败的**直接原因**，SEARCH_KW 过宽 是**触发面过广**的原因，后端 episode 404 是**独立次要项**。但有一个 claude组 **未提到的第四根因**：搜索分支返回的 `diagnose: { degraded: true, search: true }` 不携带 `exit` 字段，导致 `llmRun` 的 `t.badge()` 检测（`test-cases.js:33`）拿到 `null` → 所有 B3 llm 例被判 "无 exit-badge" → fail。这解释了为什么 19/25 而非仅仅是搜索命中的几例全挂——**搜索的旁路效应污染了整个 B3 批次的断言基础设施**。

## 一、claude组 三根因逐条核查

### 根因 1：搜索分支绕过 finalStep + applyQualityDefense — **agree（确证·直接原因）**

**代码证据**：

`harness.js:881-896`：
```javascript
if (_searchHit) {
  try {
    // ...
    const _data = await _res.json().catch(() => null);
    if (_data && _data.answer && _data.answer.trim()) {
      let _draft = _data.answer.trim();   // ← 搜索原文直接当 final
      // ... 拼接 sources ...
      if (hooks.onFinalDone) hooks.onFinalDone(_draft);   // ← 直接输出
      return { ok: true, rounds: 0, final: _draft, 
               defense: { degraded: false, skipped: 'quick-search' },  // ← 假 defense·无 fixes
               diagnose: { degraded: true, intent: 'general', quick: true, search: true } };
      //                                                    ↑ 无 exit 字段！
    }
  } catch (_e) { /* fallback */ }
}
```

**确认绕过**：
- ❌ 不调 `stages.finalStep`（无三句骨架 / 无排版 / 无 `{{show:}}` / 无 `{{chart:}}`）
- ❌ 不调 `applyQualityDefense`（无 R1-R11 / 无 L1 对账 / 无降级）
- ❌ `defense.skipped = 'quick-search'` 是假标志——没跑任何防线就标 skipped

**对 B3 断言的影响**：
- **UI-L03（markdown 排版）**：搜索原文无 `#/✳/-` markdown → `md=false` → review 标"排版不美观"
- **RST-L05（答案长度 >10 字符）**：搜索如果返回非空文本 → 可能过，但"搜索未返回文本"时 `_data.answer` 为兜底串 → 可能 fail
- **RST-L01-L04（zonal/density/buffer 产图层）**：这些不是搜索路径——**但如果搜索被错误触发（见根因 2），这些用例不走工具 → newLayers=0 → fail**

### 根因 2：SEARCH_KW 过宽 — **agree（确证·但影响面比 claude组 描述的更精确）**

**SEARCH_KW 内容**（`emc-patterns.js:37`）：
```javascript
export const SEARCH_KW = ['情绪地图', '理念', '定位', '产品', '意义', '价值', 
  '政策', '策略', '作用', '应用', '案例', '新闻', '现状', '方案', '做法', '趋势', '对比', '介绍'];
```

**触发链路分析**（`harness.js:877-880`）：
```javascript
if (!ctx.resume && _quickIntent(ctx.question) === 'general') {  // ← 先过 _quickIntent
  const _searchHit = SEARCH_KW.some((w) => ctx.question.includes(w))  // ← 再查 SEARCH_KW
    && !INVENTORY_KW.some((w) => ctx.question.includes(w));
```

**关键发现：搜索只在 `_quickIntent === 'general'` 时触发**。`_quickIntent`（`:59-73`）的优先级：
1. CONCEPT_KW（什么是/含义/区别…）→ 'general'
2. INVENTORY_KW（数据清单）→ 'general'
3. GEO_VERB_KW（核密度/裁剪…）→ null（不触发搜索）
4. REGION_KW（西陵/伍家岗…）→ null（不触发搜索）

所以搜索只影响 **CONCEPT_KW 触发的 general 问**。但 SEARCH_KW 中 `'情绪地图'` 这个词——**几乎所有 B3 概念问都含它**：

| B3 用例 | 问句 | CONCEPT_KW 命中？ | SEARCH_KW 命中？ | 走搜索？ |
|---------|------|:---:|:---:|:---:|
| FC-07 | 什么是情绪地图？ | ✅ 什么是 | ✅ 情绪地图 | **是** |
| UI-L02 | 什么是情绪地图的 4×5 归因矩阵？ | ✅ 什么是 | ✅ 情绪地图 | **是** |
| RST-L05 | （同上） | ✅ | ✅ | **是** |
| SMT-L04 第一轮 | 什么是情绪地图？ | ✅ | ✅ | **是** |
| B1 意图 10 例 | 含「什么是情绪地图」「情绪地图的数据来源是什么」「情绪地图如何保护隐私」等 | ✅ | ✅ 情绪地图 | **是（大量）** |

**`'情绪地图'` 作为 SEARCH_KW 是过宽的元凶**——它是项目名称，几乎所有概念问都含它。概念定义问（"什么是情绪地图"）应该**本地直答**（FINAL_TEMPLATE + 情绪地图背景段已有 `harness.js:900` 的完整背景注入），而非搜索。

**其他过宽词**：
- `'作用'` / `'应用'` / `'现状'` / `'意义'` / `'价值'` / `'对比'`——这些是高频泛词，可能在非搜索意图的 general 问中误触发
- 但由于 `_quickIntent` 先过滤了 GEO_VERB / REGION（含这些词的 geo 问不会到 general），实际误触发面比字面看窄

### 根因 3：后端旧代码（episode 404）— **agree（确证·但与 B3 fail 无关）**

**代码证据**：`/aiqa/episode` 端点在 `aiqa_routes.py` 中定义（`:41-48` EpisodeIn + episode POST）。如果 serve 启动早于装饰器修复 → 路由未注册 → 404。

## 二、claude组 未提到的第四根因（新发现）

### 根因 4：搜索分支返回无 exit 字段 → llmRun badge 检测 null → 批量 fail 🔴

**代码证据**：

`harness.js:896` 搜索成功返回：
```javascript
return { ok: true, rounds: 0, final: _draft, defense: {...}, degraded: false, 
         diagnose: { degraded: true, intent: 'general', quick: true, search: true } };
//                                                    ↑ 无 exit 字段
```

对比正常 general 短路（`:904`）：
```javascript
return { ok: true, rounds: 0, final: draft, defense: {...}, degraded: false, 
         diagnose: { degraded: true, intent: 'general', quick: true } };
//                                                    ↑ 也无 exit——但正常路径也不影响（见下）
```

**关键在 `llmRun` 的 badge 检测**（`test-cases.js:32-33`）：
```javascript
const b = t.badge();
if (!b) return { pass: false, stage: 's4', obs: '无 exit-badge' };
```

`t.badge()` 读取的是**前端 UI 的 exit-badge DOM 元素**（panel.js 渲染），不是 harness 返回的 exit 字段。所以问题不在 diagnose.exit，而在：**搜索分支绕过了 panel.js 的正常渲染流程**。

搜索分支调 `hooks.onFinalDone(_draft)`（`:894`）——panel.js 的 `onFinalDone` 渲染答案文本。但搜索分支**不调** `hooks.onDefense`（`:895` 调了，但传的是假 defense）——panel.js 的 exit-badge 渲染依赖 `defense.skipped` 值。正常路径 `skipped:'quick-general'` → panel 渲染 general badge；搜索路径 `skipped:'quick-search'` → **panel 可能没有对应的 badge 渲染逻辑**（quick-search 是新值）。

**这解释了 19/25 的规模**——不只搜索命中的几例 fail，而是：
- 搜索命中的例（FC-07/UI-L02/RST-L05/SMT-L04/B1 意图组约 10+ 例）→ badge null → fail
- 搜索失败 fallback 的例（catch `_e` → 走原 finalStep）→ 但 90s 超时（搜索耗时 30-90s + fallback 再走 finalStep 10-20s = 40-110s）→ `waitAnswer(90000)` 超时 → fail
- 非搜索的例（FC 工具调用类）→ 如果 API key 在搜索批次耗尽配额/限速 → 后续 LLM 调用失败 → fail

**信号**：OK 仅 1 / ERR 18——ERR 18 很可能是超时（搜索 30-90s）或 API 限速（DeepSeek Responses API 搜索消耗大），不是断言逻辑失败。

## 三、三个核心问题的独立判断

### 问题 1：搜索分支该不该绕过 finalStep + 防线？

**判定：disagree 当前实现·搜索应作"素材注入"**

**理由**：

用户需求（依据 2 纯问答）："结合前沿政策分析作答" + "不要假大空" + "排版突出关键·不只一段话"。搜索原文直接输出**全部违反**：
- 搜索原文无排版（违反"排版突出关键"）
- 搜索原文是 DeepSeek 综合回答·可能"假大空"（违反"不要假大空"——需要 EMC 的情绪地图背景语境来约束）
- 搜索原文无 `{{show:}}` / `{{chart:}}` 内联模板（违反"不只一段话"）

**正确架构（素材注入·非旁路）**：

```
当前（旁路）：                    建议（素材注入）：
search → onFinalDone(原文)        search → ctx.context += 搜索素材
        → return（绕过一切）              → finalStep（LLM 基于 EMC 背景 + 搜索素材 出结论）
                                        → applyQualityDefense（R1-R11 正常跑）
                                        → onFinalDone（格式化结论）
```

**具体改法**（`harness.js:881-898` 重构）：
```javascript
if (_searchHit) {
  try {
    const _res = await fetch('/api/v1/aiqa/search', { ... });
    const _data = await _res.json().catch(() => null);
    if (_data && _data.answer && _data.answer.trim()) {
      // 素材注入·非旁路：搜索结果进 context·走 finalStep
      ctx.context = `【联网搜索素材（供参考·须结合下方情绪地图背景改写·勿照抄）】\n${_data.answer}\n\n来源：${(_data.sources || []).join(' · ')}\n\n` + (ctx.context || '');
      // 不 return·fall through 到下方正常 finalStep 路径
    }
  } catch (_e) { /* fallback 正常 finalStep */ }
}
// 正常 general 路径（搜索素材已注入 context 或未触发搜索）
ctx.context = '【intent=通用问答...】...' + (ctx.context || '');
const draft = await stages.finalStep(ctx, hooks, '');   // ← LLM 基于 EMC 背景 + 搜索素材 出结论
const _qd = applyQualityDefense(draft, { obsOk: false, toolHistoryText: '', skipL1: true });
// ...
```

**优点**：
- finalStep LLM 能结合 EMC 背景（`harness.js:900` 情绪地图背景段）+ 搜索素材 → 出"不假大空"的结论
- applyQualityDefense 正常跑 → R1（非空）/ R7（排版截断）/ 防线全生效
- panel.js 正常渲染 exit-badge + 格式化结论 → B3 断言全恢复

### 问题 2：SEARCH_KW 该不该收紧？概念问该走本地还是搜索？

**判定：agree 收紧·概念问走本地**

**理由**：

用户需求拆解（依据 2 纯问答）：
- "通用问题（星期几）"：快速·本地 ✅
- "情绪地图大问题（概念/定位/理念）"：结合背景 + 前沿政策 → **需搜索** 
- "略微聚焦的问题（策略/作用/应用场景）"：结合宜昌实际 → **需搜索**
- "表达要求高"：排版 + 生动专业

但 `SEARCH_KW` 含 `'情绪地图'` 导致**概念定义问**（"什么是情绪地图"）也触发搜索——这应该本地直答（`harness.js:900` 已有完整情绪地图背景段注入）。

**收紧建议**：

| 词 | 当前 | 建议 | 理由 |
|----|:---:|:---:|------|
| `'情绪地图'` | 在 | **删** | 项目名·概念定义问含它但应本地答（FINAL_TEMPLATE + 背景段已覆盖） |
| `'理念'/'定位'/'产品'/'意义'/'价值'` | 在 | **保留** | 大问题/聚焦问题触发·需搜索前沿政策 |
| `'策略'/'作用'/'应用'/'案例'/'方案'/'做法'/'趋势'` | 在 | **保留** | 聚焦问题触发·需搜索宜昌实据 |
| `'政策'/'新闻'/'现状'` | 在 | **保留** | 明确需实时信息 |
| `'对比'/'介绍'` | 在 | **删** | 过泛·"对比两区情绪"含"对比"但应走 zonal（已被 REGION_KW 拦·但仍可能误触发纯文字对比问） |
| **新增**：`'政策依据'/'宜昌'+'更新/规划/运营/治理'` | — | **加** | 精准匹配"需宜昌实据"的聚焦问 |

**概念问的判定边界**：
- "什么是情绪地图" / "情绪地图是什么" → CONCEPT_KW 命中 → general → **本地直答**（FINAL_TEMPLATE + 背景段）
- "情绪地图在城市更新中的作用" → 含 `'作用'` → general → **搜索**（聚焦问题·需宜昌实据）
- "情绪地图的理念" → 含 `'理念'` → general → **搜索**（大问题·需前沿政策）

**判据**：CONCEPT_KW（什么是/含义/定义）+ 不含 SEARCH_KW（删"情绪地图"后）→ 本地直答；CONCEPT_KW + 含 SEARCH_KW → 搜索素材注入 + finalStep。

### 问题 3：有无其他根因（claude组 漏掉的）？

**有——根因 4（上文已详述）+ 根因 5（性能）**

### 根因 5：搜索 API 90s timeout + 无并发控制 → 批次串行拖死

**代码证据**：`llm.py:424` `search_chat(question, max_tokens=4000, timeout=90.0)`——单次搜索 90s 超时。B3 批次 25 例·如果 10+ 例触发搜索·串行执行 = 10 × (30-90s) = 300-900s = 5-15 分钟。

**对 B3 的影响**：
- 搜索命中的例：30-90s/例 → 接近或超 `llmRun` 的 `waitAnswer(90000)` 超时
- 搜索失败的例：90s timeout + retry（`llm.py:444` MAX_RETRIES）+ fallback finalStep 10-20s = 100-280s → 远超 90s → fail
- 后续非搜索例：如果 DeepSeek API 限速（搜索消耗大量 token）→ LLM 调用慢/失败 → 连锁 fail

**这就是 OK 仅 1 的原因**——不是断言逻辑全坏，是**性能拖死 + 连锁限速**。

| **R1** | 搜索分支绕过 finalStep + 防线 | 🔴 致命 | `harness.js:889-896` | 改"素材注入"——搜索结果进 ctx.context·fall through 到 finalStep + applyQualityDefense |
| **R2** | SEARCH_KW 含 `'情绪地图'` → 概念定义问误触发 | 🔴 高 | `emc-patterns.js:37` | 删 `'情绪地图'` + 删 `'对比'/'介绍'`·保留大问题/聚焦问题词 |

| **R4** | 搜索分支返回无 exit / 假 defense → badge 渲染异常 | 🔴 高 | `harness.js:894-896` | 由 R1 修复自动消除（走正常 finalStep → 正常 defense → 正常 badge） |
| **R5** | 搜索 90s timeout + 无并发 → 批次串行拖死 | 🔴 高 | `llm.py:424` | timeout 90→30s·MAX_RETRIES 搜索设 1（不 retry）·B3 批次搜索例加 `--no-search` flag 或 SKIP |

### 修复优先级

| 优先级 | 修复 | 理由 |
|:---:|------|------|
| **P0** | R1（素材注入重构） | 根治——搜索走 finalStep + 防线·B3 断言全恢复 |
| **P0** | R2（SEARCH_KW 收紧） | 配合 R1——概念定义问回本地·减少不必要的搜索调用 |
| **P1** | R5（timeout + 并发控制） | 性能——搜索 30s timeout + 不 retry·B3 批次可控 |
| **P2** | R3（serve 重启） | 工程卫生——episode 埋点恢复 |

### 与 B3 回归门的关系

**B3 回归门当前不可信**——19/25 fail 不是因为 G0-G5 改动引入了回归，而是 G6b 搜索能力的**架构错误接入**（旁路 vs 素材注入）+ **性能拖死**。

**修复 R1+R2+R5 后**：
- 搜索命中的例：走 finalStep + 防线 → 正常断言
- 搜索未命中的例：不受影响（原路径）
- 搜索性能：30s timeout + 不 retry → 不拖死批次

**建议**：修 R1+R2+R5 后重跑 B3——如果 OK 率恢复到 G6b 前水平（约 13/25 pass），则确认 B3 fail 纯由搜索接入错误导致·非其他 G0-G5 回归。

## 五、一句话总结

**B3 大失败的直接原因是 G6b 搜索分支的架构错误——搜索原文旁路了 finalStep + applyQualityDefense（根因 1）+ SEARCH_KW 含"情绪地图"导致概念定义问误触发（根因 2）+ 搜索 90s timeout 拖死批次（根因 5）+ 搜索返回无 exit 导致 badge 渲染异常（根因 4·claude组 未提）。修复 = 搜索改"素材注入"（搜索结果进 ctx.context → 走 finalStep + 防线）+ SEARCH_KW 删"情绪地图" + timeout 90→30s。修后重跑 B3 确认非其他回归。**
