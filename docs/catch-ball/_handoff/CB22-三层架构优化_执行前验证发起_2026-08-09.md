## 二、待两组验证焦点（详细讨论报告·agree/disagree + 证据·可交叉挑战）

1. **P0-2 diagnose 加 knowledge_qa 的判据设计**：判定段（数据/事实/清单类问·含地名+领域词·非分析非概念）+ 概念/知识边界（general=定义解释·knowledge_qa=数据清单）——判据够清晰吗？Flash 能稳定判吗？（先扩 eval 能兜住吗）
2. **P0-4 _quickIntent 降级加速器**：明显命中直通（CONCEPT/INVENTORY/GREETING + RAG 精确）·漏网落 diagnose——「明显」边界怎么定？哪些词该保留直通（防明显概念问也走 FC 延迟）？
3. **P0-5 合流路由 + data_plan 覆盖判定**：短路（加速器）与 diagnose knowledge_qa 合流统一范式·素材够不够→request_upload/降级——合流设计对吗？覆盖判定方案？
4. **P0-7 分通道增强**：问答/概念通道自由综合（理解归 LLM + 检索补强 + 提示词增强）·分析类确定性红线不动——增强边界怎么划（哪些约束对问答放开·哪些保留）？防幻觉/防越维/引用来源底线怎么守？
5. **P1 概念库**：3 类（产品定位/方法论/边界·≤200 字·摘抄+引用·type='concept'）+ 两级链路（明显 general 直通·复杂 knowledge_qa）——范围/粒度/链路对吗？
6. **P2 防回归**：触发正负例语义更新（负例「项目有哪些」→ 期望落 diagnose）+ 枚举断言 + 知识问答 e2e——测试设计对吗？
7. **P3 数字出处**：URP-P01 做厚 + 指令出处锚定 + 素材语义断言——治本吗？
8. **整体执行序**：P0 先行 → P1/P2/P3 → P4/P5——顺序对吗？有无依赖风险？（如 P0-2 判据不稳影响 P0-5 合流）
