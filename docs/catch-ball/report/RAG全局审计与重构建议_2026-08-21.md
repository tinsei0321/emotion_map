## 第一部分 · 一页结论（先看这里）

### 1.1 总体判断（一句话）

**你现在的知识库是一个「工程素质优秀、检索能力偏基础、内容厚度不足」的早期生产级 RAG——骨架方向正确，不需要推倒重来；重构的重点是「检索链路补课（混合检索+重排序）」和「内容资产搬家（从代码里搬到可治理的文档里）」两件事，而不是换框架。**

### 1.2 八维评分卡

| 维度 | 得分 | 一句话评价 |
|---|:-:|---|
| 工程可靠性（原子写/一致性校验/预热/离线纪律） | **8.5/10** | 明显优于业界多数玩具级 RAG，是本项目的真亮点 |

**综合：5.9/10 —— 「地基打得正，楼层刚起一层」。**

### 1.3 三条核心建议（摘要）

1. **检索链路补课**（最高性价比）：加「关键词检索（BM25）+ 排名融合（RRF）+ 重排序模型」三件套。这是 2026 年生产级 RAG 的事实标准，实测业界普遍带来召回率 +15~25%、答案质量 +20~40%，且全部有纯本地 CPU 开源方案，与你「离线、免费、不依赖外部配额」的既定路线完全兼容。
2. **内容资产搬家**：把写死在 Python 代码里的知识（事实卡、概念卡、案例库约 80+ 条）迁移为带元数据头（frontmatter）的 Markdown/YAML 文件，让「知识」与「代码」分离。这样内容可以被非程序员维护、可以被门禁检查、可以增量更新——这正是你们「契约卡=资产」主线在知识库上的落地。
3. **评估先行**：动手改任何东西之前，先把黄金集从 14 条扩到 60~100 条并记录基线分数。没有基线，所有优化都说不清有没有效果（这也是业界调优方法论第一步）。

## 第二部分 · 现状盘点（审计事实·全部可复核）

### 2.1 先用大白话讲清楚：你现在的知识库是怎么工作的

打个比方：你的知识库像一家**小型专业图书馆**——

| 图书馆类比 | 你的实现 | 文件位置 |
|---|---|---|
| 藏书（语料） | 364 条知识条目 = 282 条规划笔记段落 + 68 条事实卡 + 9 条概念卡 + 5 条案例卡 | `docs/urban-renewal-plan/`（笔记）+ `ai_qa/outlet_kb/*.py`（卡片，**写在代码里**） |
| 图书编目（索引构建） | 每条知识用「BGE 中文小模型」转成一个 512 维的语义坐标（向量），连同原文、来源、维度标签存进两个本地文件 | `tools/rag_index.py --build` → `DATA/rag_index/vectors.npy + meta.jsonl` |
| 找书方式（检索） | 用户提问也转成坐标，和全部 364 个坐标逐一算「方向接近程度」（余弦相似度），取最接近的前 5 条；事实卡额外 ×1.2 加分 | `tools/rag_index.py search()` |
| 三个借阅窗口（消费面） | ①情绪地图前端问答（冻结演示壳）②MCP 标准插座 `rag_query`（给 dsh 等通用助手用）③命令行试运行 | `api/aiqa_routes.py` / `tools/mcp_server_emc.py` / CLI |
| 图书管理员考核（评估） | 14 道固定考题（黄金集）：10 道考「找得到」，2 道考「不越维」（数据只到某粒度时不许硬答更细），2 道考「不张冠李戴」（不许把南京数据当宜昌答案） | `tools/rag_gold_set.py` + `tools/rag_eval.py` |

**几个值得表扬的工程细节**（审计实测确认，2026-08-20 构建）：
- **原子写**：索引先写临时文件再整体替换，中途崩溃不会留下半个坏索引——很多商业系统都不做这个；
- **一致性校验**：向量数与元数据行数不匹配时明确报错要求重建，而不是带病运行;
- **内容指纹**（content_hash）：每条存 SHA-256 哈希——这是增量更新的地基，已经铺好了；
- **离线纪律**：模型加载强制 `local_files_only=True`，杜绝启动时联网卡死（这是你们踩过 25 分钟卡死坑后沉淀的规则）；
- **启动预热**：服务启动时后台加载模型，消除用户首问 18 秒的冷加载等待；
- **片段全文入库**：检索结果带原文（早期版本只存文件名，大模型无料可综合——已修正）。

### 2.3 与「EMC × dsh 平台化」方向的关系（为什么 RAG 此刻重要）

研读讨论台账 R0-R49 后确认三条已拍板的事实，它们直接决定知识库的命运：

1. **平台化转型（形态3）**：情绪地图的终局是「领域平台」——数据+口径+知识+渲染 API 是资产，自然语言入口交给通用助手（dsh 等）经 MCP 插座消费。在这个终局里，**知识库是平台四大资产之一（「知识与范式层=不可替代的私有认知」，台账 R5 原话）**。通用助手再聪明也不懂宜昌的口径与范式——它们必须经 `rag_query` 插座向你的知识库「借阅」。知识库薄，平台的认知就薄。
2. **架子先行、充实后移**（用户裁定二，R26）：插座架子（七件 MCP 工具）已落成并考试通过，**「再丰富 RAG」正是当前挂账的 C 线批次**（图层说明书卡/事实卡/门禁执行/索引重建）。本报告就是为这个批次提供施工图纸。
3. **契约卡=资产**（用户纪律，R22）：数据内容是一次性耗材，从数据工作中沉淀的格式/口径/规则卡片才是资产。知识库重构必须贯彻这条线——**口径卡要成为知识库的一等公民**，问答结论的「口径引用义务」才有权威源可引。

**结论：知识库不是边缘子系统，而是平台化转型中「私域认知」的承重墙。它的重构值得做，且时机就是现在。**

## 第三部分 · 逐模块专业评估（现状 → 业界做法 → 差距 → 风险）

### 3.1 内容层：知识住在哪里

| | 现状 | 业界主流 | 差距与风险 |
|---|---|---|---|
| 存储形态 | 笔记=Markdown（好）；卡片=Python 硬编码（问题） | 内容与代码分离：Markdown/YAML + 元数据头（frontmatter），知识可被 lint、可被 diff、可被非程序员维护 | **卡片改一条要动代码+重建**；`industry_kb` 与 RAG 双轨并行有口径分叉风险；内容无法被现有门禁（check_caliber 一类工具）机械检查 |
| 元数据 | 事实卡有结构化字段（region/topic/year/keywords·已透传），笔记只有启发式维度标签 | 每条知识声明式元数据：域（体检/更新/方法论）/城市/维度/年份/来源/置信度/时效状态 | 笔记的维度标签靠关键词计数推断（`_infer_dim`），默认兜底「社区」——**标签是猜的不是声明的**，越维降级纪律建立在不可靠地基上 |
| 生命周期 | 有作废卡纪律（X-01）但未机制化进检索 | 知识条目有状态（现行/作废/过期），检索层可过滤 | 作废口径目前靠外部工具扫描，检索本身不感知时效 |

### 3.2 切块层：知识怎么切

| | 现状 | 业界主流 | 差距与风险 |
|---|---|---|---|
| 笔记切块 | 按 `##` 标题一刀切，≥20 字保留，>2000 字截断，**无重叠** | 结构化切分 + 10~20% 重叠防语义断裂；大块配「父块」回传上下文（小块检索、大块给模型读） | 跨小节的问题（如一段话被标题切开）会丢上下文；截断无「还有后续」标记 |
| 卡片切块 | 一卡一向量（正确——原子事实就该原子检索） | 同 | 无问题，这是你们做对的地方 |
| 表格/数值 | 蒸馏笔记中的表格被拍平成文字 | 表格单独结构化入库或转「一句话一行」 | 数值型问答（如「140 个停车泊位缺口」）依赖文字撞运气 |

### 3.3 向量化层：用什么模型把文字变坐标

| | 现状 | 业界主流 | 差距与风险 |
|---|---|---|---|
| 模型 | BAAI/bge-small-zh-v1.5（512 维·92MB·国产开源·中文优秀） | 同族更大型号（bge-large/bge-m3），或按 MTEB 榜单+自有语料实测选型 | **选型本身没错**——小模型对 364 条语料够用、CPU 秒级、离线友好。但注意两点：①未加「查询指令前缀」（bge-v1.5 对 query 侧加 instruction 可提分，代码注释写了支持但实际未用）；②换模型=全索引重建（破坏性变更），未来升级须纳入版本管理——这点业界有共识，你们的 embed_hash 字段已为此预留 |

### 3.4 索引与检索层：怎么找（**差距最大的模块**）

| | 现状 | 2026 业界生产标准 | 差距与风险 |
|---|---|---|---|
| 检索路数 | **单路纯向量** | **混合检索**：向量（语义相似）+ BM25 关键词（精确命中专有名词/编号/地名），两路召回后 RRF 排名融合 | 「葛洲坝」「建科〔2021〕63号」「87.9%」这类精确词，纯向量容易输给语义相近但不含该词的段落——你们的黄金集里已有一例实证（「葛洲坝片区停车泊位缺口」曾 TOP-1 错召南京） |
| 精排 | 无重排序 | **两阶段管线**：粗召回 Top-20 → 交叉编码重排模型（如 bge-reranker-v2-m3）精排取 Top-5 | 向量 Top-5 里通常只有 2~3 条真相关；重排序被公认为「基础 RAG 之后 ROI 最高的单项升级」 |
| 加权 | fact ×1.2 硬编码魔法数 | 类型权重作**可观测参数**随黄金集回归调整 | 代码注释里已写「不拍死·系数作观测起步」——意识是对的，缺的是把观测机制（每次评估记录分项命中率）固化下来 |
| 元数据过滤 | 无（维度标签只随结果返回，不参与过滤） | 检索前先按域/维度/城市过滤候选集（pre-filter） | 问「宜昌停车」时杭州案例仍参与竞争，只能靠事后纪律提醒，不能在召回阶段排除 |
| 索引规模 | numpy 暴力全量点积 | <1 万条时暴力检索完全够（毫秒级）；更大才上向量库（sqlite-vec/LanceDB/Qdrant） | **现状规模无需向量库——这是对的，别被推销**。5 千条以内 numpy 就是最优解 |

### 3.5 查询理解层：用户的话怎么预处理

| | 现状 | 业界主流 | 差距与风险 |
|---|---|---|---|
| 查询改写 | 无（原始问句直接向量化） | 轻量：同义词/别名词典扩展；重量：LLM 改写或 HyDE（先让模型写个假想答案再去检索） | 「危旧房改造」vs「危房改造」、「12345 热线」vs「市民诉求」——领域同义词靠模型泛化不稳。轻量词典扩展零成本可做；LLM 改写与你们「检索层不调 LLM」的纪律冲突，**建议不做**（宿主助手的循环天然会重试改写，外置大脑形态下这一层有人免费干） |

### 3.6 评估层：怎么知道好不好

| | 现状 | 业界主流 | 差距与风险 |
|---|---|---|---|
| 黄金集 | 14 条（10 召回+2 越维+2 案例），三类判据设计**非常专业**（「越维降级」「案例不引数据」是绝大多数商业 RAG 都没有的红线类考题） | 60~100 条真实业务问句 + Recall@K/MRR 量化指标 + 每次改动跑回归 | 样本太少，单条波动 ±7%，优化效果测不出来；且只测「找得到」，不测「答得对」（端到端） |
| 指标 | 通过率（二元） | Recall@5、MRR（平均倒数排名）、维度错配率、引用准确率 | 无法区分「从第 1 名掉到第 4 名」这种实质性退化 |
| 回归 | 未接 CI | 黄金集进 CI，检索改动即跑 | 你们的 pytest 门禁文化（435+2）是全仓骄傲，黄金集却没搭上这班车 |

### 3.7 消费面层：三个入口的体验

| 入口 | 现状 | 评价 |
|---|---|---|
| EMC 前端问答（冻结壳） | 词表短路触发 → 检索 → 大模型综合，带维度分布声明 | 设计完整；但按拍板「演示壳冻结」，不再投入 |
| MCP 插座 `rag_query` | 返回 Top-K+维度分布+口径卡引用，`synthesize=True` 时诚实降级为「请宿主自行综合」 | **这是平台化后知识库的主入口**。描述差异化已在 D 批修复；`deferred_v2` 的诚实降级设计是业界少见的成熟做法 |
| 命令行 | `--query/--stats` | 够用 |

### 3.8 小结：什么必须保留，什么必须改

**必须保留（你们的护城河）**：
- 「聪明两端、笨中间」内核下的纯函数检索层（确定性、可测、零 LLM 依赖）；
- 三类刚性评估判据（尤其越维降级、案例不引数据两条红线）；
- 工程可靠性全家桶（原子写/指纹/一致性校验/离线纪律/预热）；
- 本地离线路线（BGE 系国产开源模型 + CPU + 无外部 API 配额依赖）。

**必须改（按性价比排序）**：
1. 混合检索 + 重排序（检索质量主矛盾）；
2. 黄金集扩容 + 进 CI（让优化可测量）;
3. 内容搬家 + 声明式元数据（让维度标签从「猜」变「声明」，让口径卡入库）；
4. 切块加「重叠+标题上下文」；
5. 查询侧轻量同义词典（可选）。

## 第四部分 · 对照设计目标与交互体验的差距研判

### 4.1 你的设计目标（从产品文档与台账提炼）

1. 面向**规划师**（非程序员）的可信问答：结论必须**带来源、带口径、带数据粒度声明**；
2. **诚实优先**：数据不够就降级声明（三态出口：做成/缺数据/纯问答），绝不编造；
3. **平台化双消费面**：既服务前端演示壳，更服务外置大脑（dsh 等通用助手经 MCP）；
4. 知识是**累积资产**：每轮数据工作沉淀的口径/规则要能回流知识库。

### 4.2 差距与体验痛点（按用户可感知度排序）

| # | 痛点 | 根因 | 对体验的影响 |
|---|---|---|---|
| E1 | 精确名词有时答不准（地名/文号/数值） | 单路向量检索 | 规划师问「建科 63 号文怎么说」可能拿到泛泛的政策段 |
| E2 | 知识「答得出但引不到权威源」 | 口径卡未入库 | 结论的口径引用义务落空——引用的是笔记段落而非 K 卡 |
| E3 | 知识库厚度不足，开放问题常「库里没有」 | 93 素材未入、体检域仅 15 条 | 外置大脑问体检类问题命中率低，被迫退回文件直读（台账 R43 已实测观察到宿主绕开 rag_query 直读文件——**这是知识库薄的最直接证据**） |
| E4 | 检索结果的可信度呈现弱 | 无时效/置信度标签透传 | 用户无法一眼分辨「2025 体检结论」与「旧口径作废数字」 |
| E5 | 首问等待（已大幅缓解） | 模型冷加载 | 预热已修，剩余为索引重建时的构建耗时，属运维侧 |

> **E3 是战略级信号**：台账 R43 记录外置大脑实测时「fs 宿主直读文件绕 rag_query」——当消费者宁可自己翻文件也不走你的插座时，说明插座里的货不够。这验证了「架子先行」之后，**充实内容就是下一程的主矛盾**，与本报告 5.4 内容层改造呼应。

## 第五部分 · 重构方案（顶层设计 → 模块 → 内容）

### 5.1 目标架构 v2：五层流水线

```
┌─────────────────────────────────────────────────────────────┐
│ ① 内容层（单一权威源·全部 Markdown/YAML·git 管理）          │
│    知识域三分：体检域 / 更新域 / 方法论域                   │
│    每条带 frontmatter：域/城市/维度/年份/来源/状态/置信度   │
│    （口径卡 K 系 · 图层说明书卡 · 事实卡 · 蒸馏笔记 · 案例）│
├─────────────────────────────────────────────────────────────┤
│ ② 摄入层（构建时·不调 LLM）                                 │
│    解析 frontmatter → 结构化切块(重叠+标题链) → 校验门禁    │
│    （作废卡禁入/PII 红线/geojson禁入——沿用既有纪律）        │
├─────────────────────────────────────────────────────────────┤
│ ③ 索引层（本地文件·原子写·沿用现有格式扩展）                │
│    稠密向量 bge-small-zh（沿用）+ BM25 倒排(jieba 分词)     │
│    content_hash 增量：未变条目跳过重算                      │
├─────────────────────────────────────────────────────────────┤
│ ④ 检索层（纯函数·确定性·三入口共用同一 search）             │
│    元数据预过滤(域/维度/城市) → 双路召回(向量+BM25)         │
│    → RRF 融合 → 重排序(bge-reranker·Top-20→Top-5)           │
│    → 返回片段+来源+维度+口径卡引用                          │
├─────────────────────────────────────────────────────────────┤
│ ⑤ 服务层（现状不动·只换新引擎）                             │
│    EMC 前端 /aiqa/rag_search ‖ MCP 插座 rag_query ‖ CLI    │
└─────────────────────────────────────────────────────────────┘
```

**设计要点**：
- 服务层（⑤）零改动——三个入口继续调同一个 `search()`，符合「入口统一」铁律；
- 检索层（④）仍不调 LLM——重排序用的是本地小模型不是大模型，**不违反「笨中间」纪律**；
- 索引文件格式（vectors.npy + meta.jsonl）保留扩展，不引入数据库服务。

### 5.2 六条设计原则（业界实践 × 本项目铁律的交集）

| 原则 | 业界依据 | 本项目适配 |
|---|---|---|
| P1 内容与代码分离 | 知识需可维护/可审查/可增量 | 呼应「契约卡=资产」纪律；卡片 Python → Markdown |
| P2 混合检索是标配 | 2026 生产标准=稠密+稀疏双路 | BM25 纯 Python 实现（rank_bm25+jieba），零服务依赖 |
| P3 两阶段排序 | 粗召回+精排是 ROI 最高单项升级 | bge-reranker-v2-m3 支持 CPU，20 对精排约 1~2 秒 |
| P4 元数据先声明后推断 | 过滤与降维依赖可靠标签 | 把 `_infer_dim` 关键词猜测降级为兜底，frontmatter 声明为主 |
| P5 评估驱动一切改动 | 无基线不优化 | 黄金集扩容先行，进 CI 门禁 |
| P6 增量构建 | 内容增长后全量重建不可持续 | content_hash 地基已有，补「按哈希跳过」逻辑即可 |

### 5.3 技术选型对照表（含开源资源与「不选」理由）

#### 5.3.1 向量存储

| 选项 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **numpy 暴力检索（现状）** | 零依赖、毫秒级（万条内）、原子写已实现 | 条数上万后变慢 | ✅ **保留**（你们 5 年内语料大概率 <1 万条） |
| sqlite-vec | 单文件、SQL 生态 | 引入新依赖，当前规模收益≈0 | 观察位：语料 >5 千条再评估 |
| Chroma/LanceDB | 嵌入式、功能全 | 依赖重、Py3.14 兼容风险（你们锁版本纪律严） | ❌ 不选 |
| Qdrant/Milvus（服务式） | 大规模生产级 | 起服务=违背本地离线路线 | ❌ 不选 |

#### 5.3.2 关键词检索

| 选项 | 结论 |
|---|---|
| **rank_bm25（纯 Python）+ jieba 中文分词** | ✅ 推荐：零服务、可离线、中文分词成熟；索引构建时生成倒排表一并原子写 |
| Elasticsearch/OpenSearch | ❌ 服务式，规模不配 |

#### 5.3.3 重排序模型

| 选项 | 体积 | CPU 速度 | 结论 |
|---|---|---|---|
| **bge-reranker-v2-m3** | ~2GB | 20 对≈1~2s | ✅ 首选（与 BGE 同族，中英多语，效果最佳） |
| bge-reranker-base | ~1.1GB | 更快 | 备选（磁盘/内存紧张时） |
| 不加（维持现状） | — | — | 仅当延迟预算 <500ms 且接受质量损失 |

#### 5.3.4 Embedding 模型

| 选项 | 结论 |
|---|---|
| **bge-small-zh-v1.5（现状）** | ✅ 保留：对 <1 万条中文语料够用，换模型=全量重建+重跑黄金集，无充分理由不动 |
| bge-m3（稠密+稀疏一体） | 观察位：它一个模型出两种向量，可替代 BM25；但 2GB+CPU 慢，**先用 rank_bm25 走通再评估** |
| 查询侧加 instruction 前缀 | ✅ 顺手做：bge-v1.5 官方建议 query 加「为这个句子生成表示以用于检索相关文章：」前缀，一行代码的免费提分 |

#### 5.3.5 整体框架（**重要：建议都不选**）

| 框架 | 是什么 | 不选理由 |
|---|---|---|
| LangChain / LlamaIndex | 全家桶框架 | 抽象层厚重、版本漂移快，与你们「纯函数+笨工具」内核正面冲突；你们的检索层只有 ~300 行，框架是杀鸡用牛刀且把鸡刀没收了 |
| RAGFlow / Dify / FastGPT | 带界面的一体化 RAG 平台 | 自带服务与存储，平台化方向下你的知识库要当「被别人调用的资产」而不是「自成一体应用」 |
| GraphRAG / LightRAG | 知识图谱增强检索 | 364 条语料撑不起图谱收益；口径卡之间的关系用「引用字段」表达即可（见 5.6 观察位） |

> **判断依据**：业界经验共识是「RAG 效果 80% 取决于检索卫生（内容/切块/混合/重排），而不是框架」。你们已有干净的 300 行核心，**在其上做增量升级 = 成本最低、主权最完整**的路线。

### 5.4 内容层改造方案（本报告的重心）

#### 5.4.1 知识域三分（对齐既有裁定「体检与更新分开」）

```
knowledge/                      ← 新建·知识库单一权威源目录

├── checkup/                    体检域（找问题·需求侧）
│   ├── facts/                  事实卡 md（从 urban_renewal_knowledge.py 迁出）
│   └── notes/                  体检蒸馏笔记（03-05~03-10 等）
├── renewal/                    更新域（规建营项目·供给侧）
│   ├── facts/  ├── policies/   政策卡（部委/省/市·带文号）
│   └── notes/
├── methodology/                方法论域
│   ├── concepts/               概念卡
│   ├── cases/                  案例卡（只方法论不引数据·红线保留）
```

#### 5.4.2 元数据规范（frontmatter 示例）

```yaml
---
id: CHK-F-012              # 稳定编号（溯源用）
domain: checkup            # checkup | renewal | methodology | caliber | layer
city: 宜昌                  # 本地事实=宜昌；案例=他城（自动触发「方法论参考」标签）
data_dim: 小区              # 住房|小区|社区|街区|城区|片区|城中村|方法论（声明式·替代推断）
year: "2025"
source: 03-05_停车设施专项体检  # 值锚点指向成文 md（沿用口径卡纪律）
status: active             # active | retired | superseded_by:XXX
confidence: high           # high(成文报告) | medium(蒸馏) | low(会议记录)
---
中心城区停车泊位缺口 140 个小区存在缺口……
```

**收益**：维度标签从「关键词猜」（现状 `_infer_dim` 会把含「街道」二字的任何文本判成街区）变为「作者声明」；越维降级、城市隔离、时效过滤全部获得可靠地基。

#### 5.4.3 迁移策略（不动服务、双轨过渡）

1. **导出器先行**：写一次性脚本把 `all_facts()/all_concepts()/CASES` 导出为 md（保留原 Python 为只读镜像）；
2. **索引构建器改读 `knowledge/`**：旧 Python 源在过渡期作为 fallback（与 G8b「双源兜底」同款思路）；
3. **黄金集全绿后**，Python 知识源降级为生成物（类似 `contract_mirror.generated.js` 模式——单一源→派生镜像，禁手改）；
4. **industry_kb 双轨收编**：`kb_facts` 插座与 RAG 共享同一内容源，消灭口径分叉。

### 5.5 检索层改造细节

在 `tools/rag_index.py` 内增量演进（保持纯函数与 ASCII 标记纪律）：

1. **BM25 路**：构建时对全部 text 用 jieba 切词建倒排（存 `bm25.pkl`，与向量同批原子写）；检索时 `rank_bm25.BM25Okapi` 取 Top-20；
2. **RRF 融合**：`score(d) = Σ 1/(60 + rank_i(d))`（k=60 为业界经验值，免分数归一化）；类型权重（fact 1.2）保留为**配置常量+评估日志记录**，每次跑黄金集输出分类型命中率，用数据决定权重去留；
3. **元数据预过滤**：`search(query, k, domain=None, data_dim=None, city=None)`——宿主传了就过滤，不传就全库（向后兼容，三入口零改动）；
4. **重排序**：粗召回 Top-20 → `FlagReranker('BAAI/bge-reranker-v2-m3')` 精排 → Top-K；reranker 模型同样 `local_files_only` + 启动预热（复用现有 warmup 机制）；MCP 插座增加可选参数 `rerank: bool = True`，宿主嫌慢可关；
5. **查询侧**：仅加 ①bge 官方 query instruction 前缀 ②一份 ~50 条的领域同义词表（危旧房↔危房、12345↔市民诉求、葛洲坝片区↔葛洲坝……）做查询扩展——**不做 LLM 改写**（宿主循环免费代劳）。

## 第七部分 · 风险清单与「明确不做」清单

### 7.1 风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 重排序 CPU 延迟 | reranker 精排 20 对约 1~2s，叠加粗召回或超宿主耐心 | MCP 参数可关；宿主超时纪律已有 60s 预算；必要时降 base 型号 |
| 模型下载/离线 | reranker 新模型首次下载依赖 HF 镜像（你们踩过 25 分钟卡死坑） | 构建机下载一次进本地缓存；运行时一律 `local_files_only`；下载步骤写入 `requirements-rag.txt` 注释 |
| jieba 新依赖 | 需登记依赖清单（你们有 Ops 纪律） | 入 `requirements-rag.txt`（按需安装·与现有策略一致）；jieba 首次加载建词典约 1s，随预热消化 |
| 换 embedding 的破坏性 | 未来升级模型=全索引失效 | 维持现状模型；若升级，按「DB schema 变更」对待：新版本号+全量重建+黄金集回归 |
| 内容迁移期双源不一致 | Python 源与 md 源漂移 | 过渡期 Python 只读化；完成后转「单一源→生成镜像」模式（有 G8a 先例） |
| 知识库膨胀引入噪声 | 93 素材入库若不过门禁会污染召回 | 沿用既有红线：geojson/csv 禁入、PII 红线、sim 数据标签禁入真实域；入库前跑门禁脚本 |

### 7.2 明确不做（诚实的边界）

1. **不引入 LangChain/LlamaIndex/RAGFlow 等重框架**——违背「笨工具」内核，且你们的 300 行核心没有它们解决不了的问题；
2. **不建向量数据库服务**——万条内 numpy 最优，服务化违背本地离线路线；
3. **不上 GraphRAG**——当前语料规模收益为负；
4. **不做 LLM 查询改写/LLM 综合**——检索层保持零 LLM；这两件事由宿主助手的循环天然承担（形态3 的红利，别替宿主干活）；
5. **不重构三个消费入口**——它们已统一在同一 `search()` 上，动入口=违反入口统一铁律；
6. **不动冻结的演示壳问答链路**——按既有拍板只修致命问题。

### 附录 B · 给初学者的术语小抄

| 术语 | 大白话 |
|---|---|
| RAG（检索增强生成） | 回答问题前先去图书馆查资料，照着资料答，不凭空编 |
| Embedding（向量/嵌入） | 把一段文字变成一串数字坐标，意思相近的文字坐标也相近 |
| BM25 | 老派但可靠的关键词计数匹配——谁含这个词多且词稀罕谁排前面 |
| 混合检索 | 语义找（向量）和字面找（BM25）两条腿走路，结果合并 |
| RRF（倒数排名融合） | 不看分数只看名次来合并两个榜单的公平算法 |
| Reranker（重排序） | 初筛后的复核员：把问题和每篇候选拼一起逐对精读打分，比初筛准但慢 |
| Chunk（切块） | 把长文切成适合检索的小段——切得好才找得准 |
| frontmatter（元数据头） | 文件开头的一段登记信息（域/城市/年份/状态），像图书编目卡 |
| Recall@5 / MRR | 考题通过率 / 正确答案平均排第几名——衡量「找得准不准」的尺子 |
| HyDE | 先让模型猜写一个假想答案，再拿假想答案去检索（本方案未采用） |

### 附录 C · 参考的业界实践与开源资源

- 混合检索+RRF+两阶段重排序为 2026 生产标准（多篇实战复盘一致：召回 70%→92%、答案质量 +20~40%）；
- BGE 家族（北京智源开源）：`bge-small-zh-v1.5`（现状）/ `bge-m3` / `bge-reranker-v2-m3`——中英多语、CPU 可跑、HF 镜像可下；
- `rank_bm25`（BM25 纯 Python 实现）+ `jieba`（中文分词）；
- 评估方法论：先基线后优化、黄金集进 CI、切换模型视同破坏性变更；
- 框架层 LangChain/LlamaIndex/RAGFlow 经对照后**明确不采用**（理由见 5.3.5）。
